## Registered error contracts

The core layer defines seven stable categories—`ERROR`, `REFUSED`, `AUTH`, `INTEGRITY`, `FAIL`, `INTERNAL`, and `LOCKED`—and a frozen, strict `ErrorCode` record for code, category, message key, retryability, optional public-message selection, and runbook metadata. A similarly strict `ErrorEnvelope` carries the user-facing message, optional precondition action, retry instruction, context, and trace ID. This makes the exception taxonomy a machine-facing contract, not just a collection of Python class names. The declared registry maps exception qualified names to those stable records. It is loaded on first use, rejects duplicate code IDs and duplicate class ownership, and binds subclasses created before the catalogue load through a deferred set. After loading, a `CadrumoError` subclass without a declaration raises an internal invariant error rather than silently receiving an unstable fallback. `RecordedRegisteredError` validates a recorded code through the same catalogue, allowing persisted error references to be rendered without recreating the original exception. ## Rendering and exception flow

`CadrumoError` is the registered root. Subclass creation binds each leaf to a declared code, while a descriptor resolves codes lazily. The hierarchy provides cross-layer catch surfaces such as `CoreError`, `AuthError`, and `CoreNotFoundError`; the latter lets callers handle resource misses consistently across layers. `SiteHealthError` transports a typed structural status/evidence payload across the adapter/workflow boundary without importing an adapter type into core. A narrow `pydantic_validation_boundary` converts registered domain errors into the builtin `ValueError` required by Pydantic and preserves the typed failure as `__cause__`. The output APIs construct human text or deterministic one-line JSON. JSON nests the typed error under the shared success-envelope spine (`schema_version`, command, active-profile label, status, notices); text output adds localized category prefixes and context labels. Both use the same category, code, retryability, and redacted context, while the CLI boundary supplies command/profile facts and core does not scan profile manifests. `build_error_envelope` also accepts a precondition action and trace ID. Context handling merges string-keyed `error.context`, eligible public instance attributes, and caller-supplied context, with explicit caller context taking precedence. It drops private attributes and selected implementation fields, removes keys classified as internal, replaces values under sensitive-looking keys with a fixed redaction marker, then applies `redact_for_log` to other values. Before redaction, stringification permits primitives, dates/times, enums, paths, decimals, and flat collections; arbitrary objects become a stable type placeholder rather than a repr dump. Both text and JSON renderers pass context through this path. `internal_record_fault_context` adds an operator-safe summary for Pydantic record failures. It reports the model name, total count, up to five field-path/rule pairs, and the count withheld or omitted. It never copies Pydantic's `input`; unrecognized path components are replaced by `<key>` unless the supplied model declares the field name. For validator-authored `value_error` and `assertion_error` prose, it reports the error type and raising exception class instead of the message, because that prose commonly embeds the rejected taxpayer value. This gives an operator a compact contract-level clue without exposing the value through the public error context. The helper's usefulness depends on call sites passing the relevant record class; without it, string path parts are conservatively replaced. The source says the full Pydantic error payload remains in the error log, so log access and retention remain a separate privacy boundary. ## Security and implementation assessment

The strongest local controls are strict/frozen error DTOs, duplicate registry checks, deterministic category and retry metadata, and a shared context-redaction funnel. The record-fault projector is especially conservative: it drops raw input and validator-authored prose rather than attempting to scrub arbitrary diagnostic sentences. `CadrumoError` also keeps original exception data out of normal context merging through its private-field and explicit exclusion rules. These controls govern error reporting only; they do not establish authorization, network restrictions, or the correctness of the underlying application operations.

There is a conditional message-disclosure risk: context values are scrubbed for the envelope's `context` field, but `resolve_error_message` interpolates values from the original `error.context` before rendering and can fall back to raw `error.args[0]`. The `public_message_from_registry` flag and canonical-key convention suppress that fallback for selected codes, but ordinary registered codes can still use translated text or exception text. If a template interpolates a sensitive context key, or an exception constructor puts a secret/PII value in its positional message, the message can expose it even when the separate context entry is redacted. I found no assigned locale templates or exhaustive raising call sites in this chunk to establish an actual exposed value; audit those templates and constructors, and test rendered text and JSON with secret-bearing contexts. Message resolution and raw fallback (`src/cadrumo/core/errors/error_codes.py`) Interpolation inputs (`src/cadrumo/core/errors/error_codes.py`) Separate context scrub (`src/cadrumo/core/errors/error_codes.py`)

The main quality strength is that classification and retry semantics are explicit and centrally checked. The registry is nevertheless split across numerous generated-size shards, so change review must include the correct shard and the owning exception declaration. This chunk includes no tests; static inspection cannot establish catalog completeness in a live import, exact translation coverage, error-code stability across releases, or consumer compliance with retry and exit metadata. Useful follow-up is to test first-use registry loading and duplicate refusal, round-trip the text/JSON envelopes, and trace Pydantic boundaries to confirm sensitive record faults consistently pass through `internal_record_fault_context`.
