## Scope and capabilities

This chunk contains the async-first LLM client, semantic tabular-column mapping, the off-host evidence consent mechanism, and the two-stage invoice reading pipeline. Text extraction and vision transcription both produce best-effort drafts that are grounded against deterministic tax-ID, date, currency, and amount rules. Shared prompt contracts keep the requested field forms aligned with the response parser and grounder.

## Dispatch and flow

`LLMClient.complete` resolves provider/model, applies the evidence-consent gate before cache access or adapter construction, reads a cached response if available, checks image support and unsupported parameters, then dispatches through local resource admission and bounded retries. Successful completions carry estimated cost, are written to the cache and usage recorder, and produce run telemetry; failures are logged and recorded before re-raising. Retryability comes from the registered error taxonomy, with exponential jitter and a process-wide per-provider pacing window for rate limits. On-host inference has a process-wide, thread-safe occupancy limit and checks measured memory headroom before loading. Semantic column mapping sends only the observed header names, not cell contents, and asks for a choice from the closed `FieldRole` enum. Parsing records unmapped columns, unknown column indices, invalid role tokens, and duplicate claims; first valid claim wins, leaving affected columns `UNMAPPED` rather than rejecting unrelated columns. A role-resolved model defaults to the local provider, while an explicitly supplied provider/model can route the schema-only request elsewhere. Invoice reading separates pixel transcription from semantic extraction. The vision stage asks for faithful reading-order text with `[?]` for illegible content, then the text stage asks for invoice fields, printed anchors, and separate role evidence assigning tax identifiers to issuer or customer. Both default to local inference and mark requests as evidence-derived unless a public synthetic corpus is explicitly named. Off-host evidence consent is modeled as default-off and requires deployment permission, an eligible active profile, and acknowledgement for that invocation; the client appends the consent ledger record before cache access or network dispatch. The extraction prompt takes already-resolved authority values as input and records a fingerprint of the fully rendered prompt. Its rates, legal regime phrases, and no-tax categories are data rather than local literals. A shared `InvoiceFieldContract` declaration drives field instructions and grounding dispatch. The grounder validates Spanish identifiers by checksum, foreign EU VAT IDs against country-specific formats, dates using supported formats, amounts with finite European-decimal rules, and currency codes through a canonical parser. Ambiguous dot-only amount formats are dropped rather than risking a factor-of-1,000 error; percent and currency units are removed only in their corresponding field forms. ## Security and quality observations

There is a caller invariant at the generic LLM dispatch boundary: for an evidence-derived off-host request, `LLMClient` checks the gestor-mode bar and token presence, then records the token's address and surface; it does not compare that address with the prompt or image content. `EvidenceConsentToken` is constructible as an ordinary Pydantic model, so its type alone does not prove that the policy-checked mint function ran, and a low-level reader instance can retain a token across calls. These observations do not establish a reachable authorization bypass. The canonical ledger extraction path requires a stored evidence reference and explicit per-invocation acknowledgement for an off-host provider, resolves the source hash under the active bucket, mints through a composition port that checks the active bucket, consent outcome, profile eligibility, and settings policy, then checks that the returned token carries that source hash. The extraction use case subsequently reads the secure attachment bytes into an `EvidenceInput` whose SHA-256 is checked against its bytes, and compares the token address with that resolved address before reader routing. Its composition creates a text reader for the invocation, while dispatch again enforces the gestor bar and writes the audit entry. Provider pacing is bounded, but the bound can cause a dispatch before the rate-limit interval expires. `_await_shared_pacing` sleeps for `min(remaining, policy.budget_s)` and then returns normally. If a provider's remaining window exceeds the retry budget, the next request is sent after only the budget-sized wait while the shared pause is still armed. Likewise, the retry loop arms a rate-limit delay capped to that budget. This avoids unbounded sleeping but does not fail or otherwise defer dispatch when the remaining interval is longer; a batch can issue another call into a window it has not fully waited out. Pacing wait (`src/cadrumo/adapters/outbound/llm/client.py`) Rate-limit arming and retry budget (`src/cadrumo/adapters/outbound/llm/client.py`)

Invoice validation is deliberately stronger than trusting the model, but it has an explicit boundary: `ground_extracted_fields` stores model-reported anchors and role evidence with `UNANCHORED` provenance. This function does not have the source text needed to verify excerpt occurrence; the separate anchor-check stage must run before treating those claims as corroborated. Invalid or unsupported field values become `None`, and rejected tax IDs produce discrepancy findings rather than disappearing without explanation. That is a useful fail-safe, but the product flow still needs to enforce the later check and operator review before using the draft. Unanchored provenance record (`src/cadrumo/adapters/outbound/llm/invoice_field_grounding.py`) Grounding and discrepancy behavior (`src/cadrumo/adapters/outbound/llm/invoice_field_grounding.py`)

The convenience image-transcription wrapper accepts a provider override but exposes no consent-token or public-corpus argument, while the underlying transcriber does accept a token. Consequently an off-host call through the wrapper cannot supply the required consent proof and will be refused at dispatch; callers needing an allowed hosted read must use the lower-level class or the wrapper signature must be expanded. Transcriber constructor (`src/cadrumo/adapters/outbound/llm/evidence_draft_vision.py`) Convenience wrapper (`src/cadrumo/adapters/outbound/llm/evidence_draft_vision.py`)

Local resource controls, typed provider failures, image-support refusal, prompt fingerprints, and deterministic grounding are strong quality choices. Remaining consent review should trace every caller that can build an evidence-derived off-host `LLMRequest`: it must preserve the canonical operation's fresh acknowledgement, policy/profile eligibility, active-bucket identity, and address-to-bytes check, or be treated as a trusted internal API. The low-level client does not enforce all those invariants itself, and the token has no expiry field. Other limitations include reliance on generic request callers to mark evidence correctly, `asyncio.run` in synchronous reader entry points (which will not compose directly inside an already-running event loop), and no runtime exercise of model/provider behavior in this static pass. Direct construction or reuse is possible in process memory, but the reviewed canonical application path mints and binds its token before dispatch.

## Assessment and limits

This chunk offers a broad but structured LLM boundary: request-level routing, retry and rate pacing, local memory admission, per-call audit hooks, and separate model-assisted reading stages followed by deterministic checks. The dispatch layer relies on callers to bind consent to the evidence; the canonical invoice-extraction path visibly supplies that binding and fresh policy-gated token, so direct token construction is a low-level hardening concern unless an untrusted request can reach another caller path. The pacing budget can release dispatch early relative to the provider's remaining window. The grounding stage labels anchors as unverified, so downstream corroboration remains necessary. Static source review only; no provider, model, local inference runtime, consent UI, or real invoice was exercised.
