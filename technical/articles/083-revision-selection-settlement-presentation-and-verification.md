## Capabilities and mechanisms

Revision selection gives an operator or downstream operation a deterministic way to address a Modelo work revision without exposing calculation values in the selection receipt. Selectors cover current, latest draft, latest verified, filed, and explicit revision IDs; candidates must match the work unit's model/year/period coordinates, and explicit stale references are rejected. Latest selection orders by creation time and ID. Export selection first honors a current filed revision in `PRESENTADO` state, then a current verified revision; an existing current draft prevents silently substituting an older result, while fallback is allowed only when exactly one verified revision is eligible. Selection rules (`src/cadrumo/application/modelo/selectors.py`), export choice and ambiguity handling (`src/cadrumo/application/modelo/selectors.py`), selection operation projection (`src/cadrumo/application/modelo/revision_selection_operation.py`)

The selection operation also reports whether the chosen revision has exactly one granting verification report. It recognizes a narrow exception for externally filed AEAT imports that have no standalone verification report: the filing record must match the exact work coordinates, revision, time and actor, carry confirmed AEAT origin/status, and include external evidence. Other missing or duplicate granting reports remain visible as inconsistency rather than being inferred from revision state. External-filing exception (`src/cadrumo/application/modelo/revision_selection_operation.py`), selection capture and report check (`src/cadrumo/application/modelo/revision_selection_operation.py`)

A separate snapshot operation reads an exact-profile revision snapshot after matching the requested work unit, revision, registry model/year/period and workflow profile. It provides calculation detail independently from the metadata-only selector, and includes the Modelo 202 modality only when the selected model is 202. These routes therefore serve different needs: locating a safe candidate and inspecting that candidate's stored work. Snapshot request and projection (`src/cadrumo/application/modelo/revision_snapshot_operation.py`), exact-profile snapshot execution (`src/cadrumo/application/modelo/revision_snapshot_operation.py`)

Taxation comparison is a local advisory calculation for one M100 household case. It runs the same calculation engine twice with the same resolved profile inputs and source bindings, changing only the declaration-type binding from individual to joint. It compares semantic roles for the relevant settlement and taxable-base casillas, returns individual-minus-joint difference, and applies a one-euro materiality threshold. The work-unit entry point requires M100, resolves exact-profile inputs and current registry coordinates, and refuses when required bindings are incomplete or a relation prefill would need ledger, manual or prior-filing evidence the comparison cannot safely reconstruct. The result is ephemeral: the operation is registered as a read with no state effect. It is not a pair of independent spouse returns and the output carries that scope limitation. Pure two-mode comparison (`src/cadrumo/application/modelo/taxation_comparison.py`), profile/work-unit preconditions (`src/cadrumo/application/modelo/taxation_comparison.py`), read-only operation contract (`src/cadrumo/application/modelo/taxation_comparison_operation.py`)

Semantic-role lookup centralizes registry-driven discovery of casillas. It returns an ID only for a unique match, returns no value for an absent role, and raises a structured ambiguity error for duplicates; an explicitly advisory helper can turn ambiguity into absence where the caller must not guess. Settlement lookup prefers declared result-disposition casillas and otherwise relies on unique semantic roles. The currently grounded terminal IRPF roles are M100 casillas 0595 and 0670, with 0670 identified as declaration result; models without a rule return no guessed result. Unique role resolution (`src/cadrumo/application/modelo/semantic_role_resolution.py`), settlement casilla choice (`src/cadrumo/application/modelo/settlement_casilla.py`)

`source_policy` gives every known binding source a family, surface and override policy using the source-mesh precedence ladder. Manual entry, fixed design constants and profile editing receive explicit policies; governance sources absent from the ladder resolve to `UNDECIDED`, preserving uncertainty instead of inventing an override rule. The mapping is total for the declared source-kind enum and rejects an unknown kind. The row-input gate separately prevents verification or amendment from accepting scalar stored values for casillas declared as per-row template fields. Source classification (`src/cadrumo/application/modelo/source_policy.py`), total source policy (`src/cadrumo/application/modelo/source_policy.py`), row-field input refusal (`src/cadrumo/application/modelo/stored_row_field_input_gate.py`)

Value presentation converts typed casilla values for ES, CA, EN and HU output. It applies locale-specific separators and dates, preserves decimal precision while enforcing two minimum places for money, scales percentages only when the unit is known, localizes booleans and absence, masks IBANs to the first and last four characters, and leaves codes and ordinary text unchanged. Missing translations and unknown data types fail explicitly; absent values are not rendered as zero. Presentation types and locale catalogue (`src/cadrumo/application/modelo/value_presentation.py`), casilla formatter (`src/cadrumo/application/modelo/value_presentation.py`), localized absence (`src/cadrumo/application/modelo/value_presentation.py`)

Verification is the main lifecycle boundary in this chunk. It first checks that the revision is current for its work coordinates, its parent remains active, required authorities are available, its content and row inputs are admissible, and calculation/profile readiness preconditions hold. Re-verifying a locked revision with an existing granting report is idempotent. It resolves the filing-grade registry snapshot before per-casilla checks; if that snapshot is unavailable or its declared authority grade is insufficient, it returns an explicit blocking finding instead of continuing with invented registry facts. Verification entry and lifecycle gates (`src/cadrumo/application/modelo/verification_actions.py`), snapshot failure findings (`src/cadrumo/application/modelo/verification_actions.py`)

With a snapshot, verification checks required manual casillas, registry-authored predicates, unresolved M210 outcomes, IVA selected-scope and annual compensation evidence, OSS evidence for M369, withholding detail, model-specific checks and advisory findings. Perceptores may be scoped by registry clave. Row templates are satisfied from row data rather than scalar input; M349 operator rows must exist, while an empty rectification section is accepted only when both declared total casillas explicitly equal zero. Missing IVA purchase-side document evidence can block; output-side evidence gaps can be warnings because the CLI cannot complete them. Unsupported required deduction documents are surfaced individually with transaction ID, date, amount, currency and required authority. Finding collection (`src/cadrumo/application/modelo/verification_actions.py`), model-specific evidence checks (`src/cadrumo/application/modelo/verification_actions.py`), required casillas and row templates (`src/cadrumo/application/modelo/verification_actions.py`), severity and outcome classification (`src/cadrumo/application/modelo/verification_actions.py`)

The workflow gate runs only when findings grant verification. A report is saved for both granted and refused attempts so failures remain auditable. On a grant, the revision is stamped verified with a filing-ledger snapshot and evidence; transaction participation-index writes are co-emitted atomically with that revision update. The current-revision pointer is repaired only when absent, with a guarded mutation to avoid overwriting a concurrent operator's change. A bucket event records pass/refusal and bounded counts. Report construction and persistence path (`src/cadrumo/application/modelo/verification_actions.py`), verified evidence and participation writes (`src/cadrumo/application/modelo/verification_actions.py`), bucket event (`src/cadrumo/application/modelo/verification_actions.py`)

## Knowledge, safety, and implementation assessment

The decisions here are grounded in pinned registry revisions, stored calculation inputs and results, profile state, ledger/catalogue evidence, and typed provenance. Legal and source references are attached to findings from registry declarations; this chunk does not independently validate the underlying law. No LLM or external network behavior appears in these files. The strongest controls are exact coordinate/profile matching, unique-role ambiguity refusal, explicit zero versus absent handling, row-source completeness, lifecycle-clock ordering, guarded catalogue mutation, and atomic revision/participation-index writes. IBAN masking is present in value formatting, while verification findings intentionally carry identified transaction facts for operator remediation; check how callers authorize and protect those detailed reports in their composition.

One cross-store recovery question remains: the grant path saves the verification report before persisting the verified revision and its ledger evidence, then emits the bucket event. The revision and participation-index write is atomic internally, but these separate repository actions are not shown here as one transaction. A failure between them could leave a granting report before the state transition, or a completed transition without its final event; wider composition may provide recovery. This is a follow-up to verify, not a confirmed defect. Similarly, snapshot and comparison projections contain sensitive financial work data, so transport-level authorization and redaction should be checked at their callers. No assigned test files were present; runtime behavior, adapter durability, authorization composition and legal accuracy remain unverified.

## Dependencies and follow-up

The operations depend on exact-profile repository bundles and the pinned registry authority. Verification composes domain predicates, M303 wallet reconciliation, IVA and OSS source evidence, withholding detail, profile applicability, workflow gating, ledger snapshots, transaction participation indexes and bucket history. Synthesis should connect these checks to the registry definitions, operation authorization, repository adapters and export/filing paths to determine end-to-end recovery and privacy boundaries. Also verify that the M100 comparison's single-household assumption is clearly shown in the operator surface.
