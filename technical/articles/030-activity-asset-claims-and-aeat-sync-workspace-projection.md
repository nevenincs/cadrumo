## Activity-asset lifecycle

The asset application keeps immutable revision and amortization-claim histories behind a bucket-bound repository. History validation enforces unique revision/claim IDs, a consecutively numbered per-asset chain whose supersession points to the prior revision, and claims that reference the matching asset revision and kind. A new claim must use the current asset revision, preserve the elected method/fingerprint continuity, include opening accumulated history, and remain within the amortizable basis. The repository contract calls for compare-and-swap mutation; revision appends validate their successor against the value read in that mutation, and claim persistence can require the exact expected history. History invariants and append (`src/cadrumo/application/actividad_asset/history.py`) Claim constraints (`src/cadrumo/application/actividad_asset/history.py`) Repository contract (`src/cadrumo/application/actividad_asset/ports.py`)

Forecasting is non-consuming. It resolves the taxpayer's direct-estimation modality from governed profile tokens, checks the asset election against that profile fact, and invokes an injected registry-backed calculation using the pinned model-100 revision, authority generation, workforce reader, legal reference, covered dates, and current claim history. Recording accepts caller-held forecast data only after checking the current asset revision and recomputing it against current history, authority, and profile; an exact claim replay is returned idempotently. The application passes the current history to repository claim storage as its CAS expectation, so simultaneous forecasts cannot both consume the same remaining basis when the repository honors its contract. Filing handoff only projects effective claims to material/intangible M100 and M130 destinations. These mechanisms establish provenance and persistence checks, not the legal correctness of the formulas. The registered surface separates create, inspect, correct, forecast, claim, and filing-handoff request/result types. Wire DTOs explicitly marshal monetary and fractional fields such as basis, coefficients, claim amounts, and schedule outputs through `PublicDecimal`, then rehydrate the canonical domain model for validation. Forecasts carry authority generation and schedule fingerprint; claim results carry deterministic claim identity. Revision and forecast snapshots also retain acquisition lineage, basis/allocation, opening accumulated amortization, elected method and evidence, service dates, coverage, days, source reference/fingerprint, and authority identity. Optional approved plans and small-enterprise, low-value, or free-depreciation evidence references carry their limits and caps into the request model. This makes calculation inputs auditable across the application boundary, although a reference and fingerprint alone do not prove source authenticity or legal sufficiency. ## AEAT Sync workspace

The workspace represents six separate zones and seven independent local/AEAT source authorities. Each source carries availability, optional observation time/count, and a refusal when it is not available. Rows keep source state distinct from discrepancy/reconciliation state, so `NOT_OBSERVED` differs from `ABSENT`, and a blank censo value differs from a value nobody has checked. The pre-pull reader shows local profile/censo and latest local filing records, reports AEAT sources as `NEVER_CAPTURED`, and marks unavailable local readers or uncomposed notification custody separately. It derives pull/list actions only from the public TUI operation contracts actually composed for that session. Zone counts are emitted only when their required source observations are present, while source-level availability and refusal remain available for diagnosis. No network acquisition happens in this local projection; the pull operation is merely declared when composed. Source and zone models (`src/cadrumo/application/aeat_sync/workspace.py`) Local-only read projection (`src/cadrumo/application/aeat_sync/workspace_reader.py`)

The projection boundary validates six ordered zone observations, exact source membership/order, bucket and subject scope for every fact, duplicate natural addresses, canonical action declarations, TUI-permitted operation IDs, and permitted action/operation pairs. Row validators check timestamps against observed states and require both values for claimed conflicts. Notification facts carry a private identity only inside the admission wrapper; the projector replaces it with a keyed HMAC selection key, reconstructs a public metadata row, and sorts by date plus opaque key. The returned workspace contains neither bucket nor subject scope nor raw notification identity. Scope, capability, and row projection checks (`src/cadrumo/application/aeat_sync/_workspace_projection.py`) Private notification key projection (`src/cadrumo/application/aeat_sync/workspace.py`)

One state-classification path deserves follow-up. For comparison zones, `_zone_seen` returns true only when every source is observable. With local filings `AVAILABLE` and AEAT filings `NEVER_CAPTURED`, it therefore returns false; `_zone_availability` then falls through to `UNAVAILABLE` because not all sources are never captured. The branch that returns `NEVER_CAPTURED` for an observed side plus a never-captured side is reachable for list zones, but not for comparison zones. This conflicts with the nearby comment that a comparison with one never-pulled side remains `NEVER_CAPTURED`; source-level detail remains intact, but the zone-level label may mislead consumers. Zone availability rules (`src/cadrumo/application/aeat_sync/_workspace_projection.py`)
