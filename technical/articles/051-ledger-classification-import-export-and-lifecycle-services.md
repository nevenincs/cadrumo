## Operator capabilities and behavior

Classification has two related workflows. CSV bulk classification validates the header set and row shape, reports malformed rows, accepts only the manual business-classification values, and applies the supplied fields while preserving omitted values. It skips finalized calculation references, avoids rewriting identical values, and saves changed catalogue entries with their events under a revision-aware writer. This is an operator edit path rather than a way to set automated pipeline states. Import accepts CSV, OFX/QFX, XLS/XLSX, and provider IDs including automatic selection and named bank/PDF variants, through injected provider ports. It first checks the source path and provider validation, parses rows, optionally hashes a caller-specified original source for verification, and can stage parsed rows in an immutable in-memory value before persistence. That staging boundary means the commit phase does not reopen the source path: later source-file edits do not replace the already parsed facts. Dry-run evaluates the same row classification/deduplication logic but does not save. The row evaluator uses a direction- and currency-qualified import fingerprint to skip rows already in the stored catalogue, while preserving distinct same-signature movements within one statement when the provider supplied distinct transaction IDs. Lifecycle actions archive, stash, restore, mark reviewed-excluded, remove one transaction, or reset a bucket catalogue. ## State, trust, and controls

The action-port object groups the exact registered ledger operation with bucket-scoped repositories for transactions, invoices, events, work units, calculation revisions, attachments, and related evidence. Its validator compares the operation identity and repository bucket IDs, preventing a service call from silently combining a capability from one bucket with repositories from another. Shared helpers require bucket-bound repositories, normalize actors/source-command strings, verify attachment and purchase-invoice references, check usage-ratio references, and block mutations whose source IDs are in finalized calculation revisions. Draft references instead produce stale-draft advisories. The implementation keeps several important refusal cases explicit: unknown providers and unreadable sources fail before import; rows with confident existing fingerprints skip; unsupported conversions do not substitute face value for euros; finalized filing references prevent fact/lifecycle changes; and attachment/evidence references are checked against bucket ownership and manifest/blob state. ## Assessment and follow-up

The strongest design feature is consistency across operator-facing outcomes and stored state: import preview and persistence share the row evaluator; classification edits use common revision/finalization guards; lifecycle transitions append lineage and events; and catalogue mutations use guarded co-commit helpers. Bucket identity is an explicit port invariant rather than an assumption hidden in the caller. The export projection is clear and broad, but callers should treat its returned payload and destination as sensitive because it includes descriptions, notes, counterparty identifiers, and evidence IDs.

Two conditional edges merit cross-module verification. First, import verification hashes the resolved original-source path separately from provider validation and ingestion; those operations reopen the file. If the file can change during preparation, the recorded SHA-256 may not identify the bytes represented by the staged rows. The staged rows do remain fixed between prepare and commit, so the question is about provenance binding, not later commit-time substitution. Preparation order (`src/cadrumo/application/ledger/actions_import.py`) Separate original-file hash (`src/cadrumo/application/ledger/actions_import.py`)

Second, an import’s transaction/event co-commit completes before optional diagnostic events are separately appended. If that later append fails, imported rows can persist while the enclosing call fails or omits diagnostic receipt details; callers should provide recovery/reporting for that partial outcome. Directory import similarly needs caller-level review because this module plans and folds file results but does not implement the outer loop. Primary import commit (`src/cadrumo/application/ledger/actions_import.py`) Follow-on diagnostics (`src/cadrumo/application/ledger/actions_import.py`) Directory file plan (`src/cadrumo/application/ledger/actions_import.py`)

Removal and reset are destructive service actions, although dry-run and finalized-reference checks make their consequences reviewable. Attachment IDs are removed from transaction records and removal events are emitted here; actual blob deletion or retention is not performed by this lifecycle module and should be traced to the event consumer/attachment service. Reset's receipt-size cap is optional and only applies when a caller supplies `max_receipt_items`, so the registration layer should be checked for the intended bound. No tests were inspected or run. Static review cannot prove runtime atomicity of adapter implementations, caller authorization, provider correctness, or that downstream event consumers complete cascades.
