## Capabilities and mechanisms

Profile-access contracts model authority as exact, owner-issued facts rather than client assertions. A session is bound to a profile custody generation, DEK epoch, runtime boot, connection, authenticated client, origin kind, optional parent/grant/key lineage, explicit scope, and time limits. Delegated sessions are short leases; human session expiry remains owned by the login lifecycle. Operation requests carry exact period coordinates or explicitly period-independent work, and current policy separately supplies allowed actions, disclosures, periods, backend, published authority, and provider readiness. Scope intersection narrows operations, actions, disclosures, calendar periods, period-independent work, and delegation across profile, session ancestors, and grant. Status projections report credential authentication, profile binding, storage, custody, authority and provider readiness independently; effective scope is empty when session authority refuses. Authority and operation contracts (`src/cadrumo/application/user_profile/access_contracts.py`), scope algebra (`src/cadrumo/application/user_profile/access_policy.py`), allowlisted status projection (`src/cadrumo/application/user_profile/access_projections.py`)

Administration has a separate policy floor: own-session authority can lock only that session, human profile authority handles ordinary administration, selected lifecycle actions require fresh password proof, and runtime management is reserved to the local OS owner. Fresh proof is bound to the complete typed request and digest, profile binding and lock generation, runtime boot, connection, client, originating native login, and both UTC and monotonic expiry. Current owner facts are rechecked before policy evaluation; proof does not upgrade an API-key session or create a reusable login. Administration floors and proof model (`src/cadrumo/application/user_profile/access_administration.py`), request-bound administration evaluation (`src/cadrumo/application/user_profile/access_administration.py`), safe access refusal (`src/cadrumo/application/user_profile/access_errors.py`)

Automation enrollment supports request, approve, decline, inventory, rotate, renew, and scope-change flows. A proposal has target consistency rules and explicit operation/disclosure/period allow sets; scope must remain within current profile authority and disclosures must target the requesting destination. Its review digest canonicalizes the allow sets and binds purpose, request, profile custody binding, requester, proposal, creation/expiry times, and grant. Reusing a request ID with different proposal or requester facts conflicts. Only durable `COMPLETE` grants confer usable authority. Enrollment state and reviewed proposal (`src/cadrumo/application/user_profile/automation_enrollment.py`), consent digest and lifecycle validation (`src/cadrumo/application/user_profile/automation_administration.py`), canonical request service (`src/cadrumo/application/user_profile/automation_administration_service.py`)

Approval deliberately separates proof, local publication, and client possession. Fresh password proof is obtained before `COMMIT`; the service rechecks the request digest, owner context, profile state, and current scope. Recipient inspection and protected delivery occur outside the publication guard. If needed, the service creates a pending candidate key and credential reference, publishes that inactive candidate under a fresh custody guard, sends the secret to the exact runtime/client-bound recipient, and requires an explicit client possession proof before activating the key and grant. The candidate is not authority while pending; existing rotated keys receive only the configured short overlap. Caller-owned approval memory is cleared after the phases settle, and async adapters join blocking service phases before closing it. Approval phase state machine (`src/cadrumo/application/user_profile/automation_approval_session.py`), recipient delivery and activation (`src/cadrumo/application/user_profile/automation_approval_session.py`), threaded phase adapter (`src/cadrumo/application/user_profile/automation_execution.py`)

Reduction and resume are separate lifecycle paths. Denial rechecks human authority under the shared guard, advances profile lock generation where relevant, invalidates live automation sessions, persists the denial, and records whether cleanup remains pending. Resume requires a fresh password bound to the selected grant set and current lock generation; it reactivates only selected grants and still-valid keys, preserves their original expiries and permissions, and leaves optional automation custody independent of a human-only profile unlock. A durable denial remains a fence until reconciliation and explicit resume complete. Durable denial and cleanup receipt (`src/cadrumo/application/user_profile/automation_lifecycle.py`), deny ordering and selected resume (`src/cadrumo/application/user_profile/automation_lifecycle_service.py`), resume publication (`src/cadrumo/application/user_profile/automation_lifecycle_service.py`)

The registered automation operations consume proposals and passwords through ephemeral-secret declarations, persist only safe request/receipt identities, record an unknown effect before irreversible publication, and settle the terminal receipt after activation. Human inventory, approval, and decline have explicit human access and typed allowlisted public projections; ordinary enrollment proposal entry uses the existing operation access owner. Missing runtime capabilities refuse explicitly. Executor sequencing and secret consumption (`src/cadrumo/application/user_profile/automation_operations.py`), registered operation definitions (`src/cadrumo/application/user_profile/automation_operations.py`), human-only inventory projections (`src/cadrumo/application/user_profile/automation_enrollment.py`)

Two archive families are exposed. The sealed archive operations provide local export, ciphertext mirroring, and reconciliation of the selected profile’s archive journals. They require exact profile/subject binding and human access, keep provider I/O outside the commit fence, record effect uncertainty before handoff, and validate returned receipts against the operation’s terminal scope and effect. The portable v3 bundle path instead reads the profile plus work units, ledger transactions, calculation revisions, filing records, and structured secure-object namespaces. It can produce an explicit local cleartext file or a passphrase-encrypted envelope. Archive operations and projections (`src/cadrumo/application/user_profile/archive_operation.py`), archive registration (`src/cadrumo/application/user_profile/archive_operation.py`), portable bundle assembly (`src/cadrumo/application/user_profile/bundle.py`)

Portable publication uses a durable journaled sequence. The target is anchored before publication and held under an exclusive per-target lock. The service serializes in memory, writes a `PREPARED` journal before staging cleartext in a restrictive sibling temp, atomically replaces the destination and fsyncs its parent, marks the journal `COMPLETED`, then emits the fixed-time profile-export event before clearing the journal. Reconciliation distinguishes an unpublished orphan from a digest-matching or completed durable publication, emits the event idempotently, and removes both the journalled temp and hardened-writer inner temps. It runs before a new publication to avoid overwriting the only reference to old staged bytes. Export admission and recovery-before-write (`src/cadrumo/application/user_profile/bundle_export.py`), journal-before-staging (`src/cadrumo/application/user_profile/bundle_export.py`), durable replace and event (`src/cadrumo/application/user_profile/bundle_export.py`), crash reconciliation (`src/cadrumo/application/user_profile/bundle_export.py`)

The portable-export contracts derive carried and excluded personal-data categories from the actual bundle schema and custody coverage manifest, refusing unclassified fields rather than silently narrowing a subject-access disclosure. Encryption uses the composed profile-record crypto policy for Argon2id costs and exact salt length, with canonical base64 fields and associated data; the bundle envelope carries explicit schema and KDF markers. Derived carried/excluded categories (`src/cadrumo/application/user_profile/bundle_export_contracts.py`), encrypted envelope and KDF window (`src/cadrumo/application/user_profile/bundle_encryption.py`)

## Knowledge, security, and implementation assessment

Strong protections include exact-profile and boot/connection/client binding, explicit non-wildcard access sets, period and disclosure limits, current native login reobservation, monotonic plus UTC expiry, typed refusals without request operands, secret-free inventory projections, server-selected native secret stores, and staged approval that withholds authority until client-side possession is proven. Durable denial is persisted before acknowledgement and reported independently from native credential cleanup. Archive and portable-export outcomes preserve effect, coverage, audit, and omitted-data facts instead of treating a successful function return as proof that every side effect completed.

The main remaining boundary is composition. These contracts and services rely on the trusted lifecycle owner, custody adapter, native OS secret store, protected client channel, archive storage adapter, journal repository, and event repository to supply the stated invariants. This chunk does not prove those implementations’ atomicity, filesystem permissions, cryptographic key erasure, or containment behavior. In particular, `ApprovalSession.close` clears references after phases settle but Python immutable or provider-held copies are outside what these fields can guarantee.

One recovery-reporting caveat deserves attention. Ordinary per-journal failures are returned in `reconcile_failures`, but the pre-publication sweep’s broad exception handler for an unscoped caller logs the failure and returns an empty tuple so export proceeds. The result can therefore look as if recovery found no failures even when the global scan itself could not complete; test this path and consider preserving a safe aggregate “reconciliation unavailable” fact. Scoped callers do refuse unreadable ownership scans. Pre-publication recovery fallback (`src/cadrumo/application/user_profile/bundle_export.py`), scoped scan refusal (`src/cadrumo/application/user_profile/bundle_export.py`)

The portable bundle intentionally excludes namespaces under the structured custody profile, and the excluded category list is what prevents a subject-access result from implying complete disclosure. A caller must present both carried and excluded categories. A cleartext-local transport still places sensitive profile data on the operator-selected destination; the implementation stages it restrictively and journals cleanup, but endpoint security and the caller’s destination choice remain material. The sealed recovery archive is a distinct confidentiality/restoration surface and should not be conflated with portable bundle export. Declared exclusions (`src/cadrumo/application/user_profile/bundle_export_contracts.py`), cleartext/encrypted transport selection (`src/cadrumo/application/user_profile/bundle_export.py`)

## Dependencies and follow-up

Trace access decisions through the production lifecycle owner and operation guards; confirm every UI and runtime path reobserves native login and current policy before private reads or effects. Verify the concrete native custody stores and client-side enrollment protocol, especially denial cleanup reconciliation and lost acknowledgements after candidate delivery. For exports, inspect the journal repository, hardened atomic writer, target locking, encrypted bundle reader/import path, bucket-event repository, and transport destinations. Test concurrent same-target export/reconcile, crashes before and after atomic replace, event failure after durable publication, inner-temp cleanup, scoped versus unscoped scan failure, omitted namespace reporting, access-scope narrowing, proof expiry/rollback, and session revocation while approval phases are in flight. No tests or exports were run.
