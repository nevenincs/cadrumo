## IVA projection and apportionment

The repository-backed IVA path checks the bucket of both transaction and prorrata readers, resolves the current register coordinates under a caller-owned pinned authority, and reads only the filing-window partition where the period supports one. It obtains any named capital-good acquisition rows outside the window by ID so a quarter can validate year-level investment reciprocity without classifying those rows into the quarter. Full-catalogue mode instead loads and classifies every row. Active rows that clear the per-transaction classifier contribute typed observations; excluded rows become bounded reason-coded issues, and reviewed-excluded rows disappear by explicit operator decision. Repository and date-partition flow (`src/cadrumo/application/aggregation/iva_ledger.py`) Investment acquisition reciprocity (`src/cadrumo/application/aggregation/iva_ledger.py`)

The binding resolver first obtains canonical, revision-selected IVA values and then changes only deducible-quota bindings. General prorrata applies one provisional percentage; special prorrata applies the percentage according to each input classification; differentiated sectors partition by declared sector and require explicit identity/classification where applicable. Bases and output quotas remain unchanged. The annual mandatory-special comparison aggregates the year once, resolves the same observations under general and special regimes, and returns no result for absent register data, negative totals, no deductible bindings, or sectorized registers, which are explicitly deferred. Investment acquisition reciprocity and single-consumption checks protect related special cases. Canonical binding and prorrata application (`src/cadrumo/application/aggregation/iva_ledger.py`) Sector partitions (`src/cadrumo/application/aggregation/iva_ledger.py`) Annual comparison limits (`src/cadrumo/application/aggregation/iva_ledger.py`)

The counterparty gate distinguishes registration identity from establishment. Intra-community supply requires a non-Spanish EU VAT identification state; export categories require no EU-member establishment and either a positively known third-country location or an uncatalogued but syntactically assigned country that may represent a gap in the local country table. Missing or contradictory facts become typed issues instead of defaulting to a favorable tax category. The function resolves export categories from dated registry facts. ## Filing evidence and membership

The filing snapshot stores versioned row fingerprints for fields the implementation considers material, plus a richer evidence bundle containing primitive row facts, readable labels, invoice/attachment references, and legal/source citations. Cosmetic transaction descriptions and counterparties are excluded from the fingerprint. V1 snapshots remain compared under V1 and explicitly report that they do not cover the current fact set; V2 is the current default. Evidence capture checks that its rows exactly match the snapshot’s row IDs. Fingerprint field sets (`src/cadrumo/application/aggregation/ledger_filing_snapshot.py`) V2 additions (`src/cadrumo/application/aggregation/ledger_filing_snapshot.py`) Evidence bundle construction (`src/cadrumo/application/aggregation/ledger_filing_snapshot.py`) Exact row coverage (`src/cadrumo/application/aggregation/ledger_filing_snapshot.py`) Version-aware drift comparison (`src/cadrumo/application/aggregation/ledger_filing_snapshot.py`)

A materiality gap needs prompt verification. The V1/V2 fingerprint lists omit transaction facts read by the IVA projection, including operation_date, cash-accounting treatment and payment evidence, counterparty VAT-identification state, and investment/rectification identity. Those inputs can affect filing-period placement, settlement splits, admission, or the deduction authority while all currently fingerprinted values stay unchanged. The counterparty gate directly reads identification state, and the IVA classifier uses operation date and cash-accounting evidence before producing observations. Consequently, an edit to one of these omitted facts can leave the snapshot hash unchanged and the calculate-time drift gate may not recognize material IVA drift. Add a new fingerprint version for the full calculation-relevant field set and verify sealed historical comparison behavior. ## Withholding capture and filing arrivals

The ledger-payment withholding builder translates an outgoing EUR payment into a shared producer command for work income or ordinary movable-capital income. The request supplies income terms, recipient status and kind-specific evidence; the ledger supplies identity, payment date and net settlement. It checks active/outgoing state, exact transaction identity, settlement not above gross less withholding, resident status and cadence. Work income uses payment recognition and Modelo 190 detail; ordinary capital income requires perceptor identity and exigibility, and a later payment year requires Modelo 193 pending-payment evidence. Payload-free refusals avoid retaining invoice or income figures in the exception. Capturing ordinary capital evidence into Modelo 123 does not make a window calculable: the code explicitly refuses until the annual rent-count definition is supported. Ledger-payment capture contract (`src/cadrumo/application/aggregation/ledger_payment_withholding.py`) Capture builder and validation (`src/cadrumo/application/aggregation/ledger_payment_withholding.py`)

The Modelo 193 materializer is a read-only view over active Modelo 123 allocations. It asks the selected annual edition which years support a pending-payment flag, rejects duplicate or incomplete allocation provenance, and produces a pending row with a prescribed generic recipient so the unpaid holder is not exposed. A later settlement emits the same economic allocation for the actual recipient and carries an explicit advisory that the payment-year base/withholding authority is unresolved. This keeps a transparent uncertainty marker on amounts that the design does not settle. It creates no separate annual cache or second Modelo 123 row. Supported pending-disclosure years (`src/cadrumo/application/aggregation/m193_phase_materialization.py`) Phase validation and materialization (`src/cadrumo/application/aggregation/m193_phase_materialization.py`) Pending recipient substitution (`src/cadrumo/application/aggregation/m193_phase_materialization.py`) Settled prior-accrual row (`src/cadrumo/application/aggregation/m193_phase_materialization.py`)

Modelo 303 supplier-regime arrival derives participation from the same canonical IVA observations and rejects period mismatch, out-of-period observations, duplicate IDs, or disagreement between the boolean and its source IDs. Prorrata transition arrival derives applicable terminal periods from the selected revision’s filing schedule and carry bindings, then checks current-year completeness, consistent transition kinds, and prior-year special-regime evidence for revocation. There is a generation-pinning inconsistency in that transition model. The public resolver accepts a caller-held PinnedAuthorityOperation and uses it to decide whether the period is applicable, but constructing the result triggers a Pydantic validator that calls an is_applicable property which opens bundled_indexed_authority() afresh. The revocation validator also calls the default special-regime vocabulary without receiving the caller’s operation. If a non-default or retained historical generation is reachable, the same input can be selected under one authority and revalidated under another. Carry the pinned operation through validation or pass an already-resolved applicability result; trace callers to confirm the reachable impact. ## Quality and security assessment

The modules have strong typed boundaries, row-level exclusions, immutable evidence, registry-selected binding semantics, and explicit failure states. Bucket-bound repository checks and date-partitioned reads limit the amount of ledger data opened; membership is read-only; payment capture delegates writes to a shared producer; and the M193 pending view replaces payee identity with a generic record. The filing-evidence bundle nevertheless contains tax IDs, dates, descriptions, invoice and attachment references, and financial facts, so storage and presentation controls remain important outside this chunk. No tests are included among these six modules and none were run. Cross-module dependencies that need synthesis include source-mesh resolvers, transaction/prorrata and investment repositories, withholding producer/recognition, annual calculation and verification gates, and the calculation-revision snapshot model. None of the bundled legal assertions were independently verified.
