## Capabilities and mechanisms

This chunk completes an accountant review-package workflow around a filing-grade Modelo calculation. The build operation loads one exact-profile calculation revision and its parent work unit, exports the filing artifact into a temporary directory beside the selected output, checks that the revision and work-unit catalogues have not changed during export, and then packages the result. The build routine enforces matching work-unit/revision and registry coordinates and accepts only `VERIFICADO_COMPLETO` or `PRESENTADO` revisions. The final receipt includes the manifest, member count and export-event id, but not package bytes. Build request and manifest contract (`src/cadrumo/application/modelo/review_package_operation.py`), export, concurrency check, and package creation (`src/cadrumo/application/modelo/review_package_operation.py`), filing-grade package gate (`src/cadrumo/application/modelo/review_package.py`)

Six registered exchange operations let an operator sign a package, counter-sign a supplied signature, encrypt a package for a registered recipient, decrypt an envelope, encrypt feedback for the originator, and import received feedback. They delegate to the existing package/signature/encryption services instead of reimplementing them. Private key material, decrypted bytes, ciphertext, and feedback plaintext stay out of generic operation facts; typed results expose human-readable receipts. The exchange operation fences concrete local-file, key, audit, and replay writes and computes `NONE`, `UPDATED`, `PARTIAL`, or `UNKNOWN` from confirmed writer outcomes. Exact-profile checks and the result projector ensure that the released receipt matches the requested route and settled effect. The taxpayer's recipient registry stores other people's public X25519 keys, never their private keys. It derives a SHA-256 fingerprint from the raw key for out-of-band human checking, validates key shape at the registry boundary, and refuses duplicate recipient IDs even when hydrating a stored register. Add, list and remove are available as exact-profile CLI operations. Add and remove write the registry before appending the corresponding audit event, and explicitly report partial effect if the later event write fails. The access resolver grants profile-scoped commit authority but sets `requires_human=False`; because these operations alter which key receives financial packages, confirm that this is the intended authorization policy in the wider composition. Review-package signing adds authenticity to the base package's checksum integrity. It signs the package manifest's SHA-256 digest with a per-profile Ed25519 keypair provided through a secure key capability. Signing first verifies the archive; verification rechecks current member hashes and the current manifest digest, then checks the signature against an explicitly supplied trusted public key rather than trusting the envelope's embedded key. The private key appears in the application only as a transient in-memory model around capability operations. Counter-signing binds an accountant's Ed25519 signature to the operator's original signature bytes and a note. Feedback can be unstructured, with no counter-sign receipt, or carry a formal receipt. On import, the originator decrypts and parses the feedback and, when a receipt exists, verifies both signature layers against the local reviewed archive and caller-supplied trusted public keys. Missing trust key or failed verification refuses instead of recording formal approval. ## Knowledge, safety, and implementation assessment

The product facts come from registry snapshots, persisted calculation revisions and verification reports, work-unit/profile state, and explicitly trusted recipient keys. The strongest controls here are exact-profile and revision-coordinate checks, compare-and-swap writes, atomic calculation/file co-commits, sealed-revision package eligibility, per-member integrity plus independent signer verification, and typed receipts that exclude secret material. Package ZIPs and final decrypted outputs are still explicit plaintext files written to operator-chosen paths; the concrete file adapter's path policy and the secure-object key adapters are outside this chunk. SHA-256 fingerprints require a genuine out-of-band comparison; the application cannot authenticate that human channel.

Two follow-ups deserve focused verification. First, feedback import does not visibly consume the nonce even though the same operation ports expose the replay guard and the direct decrypt route uses it. Second, recipient add/remove deliberately consist of a registry write followed by a separate audit append, so a failure can leave changed trust state with only a partial-effect receipt and no matching event. Both are clearly bounded places to test. Also confirm that build callers bind the correct export and unit/revision pair, and that recipient mutation's `requires_human=False` matches product policy. No assigned test files were present, so behavior remains unexercised here.
