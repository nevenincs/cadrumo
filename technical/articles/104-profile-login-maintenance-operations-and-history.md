## Capabilities and mechanisms

The profile lifecycle owns capsule creation, restore, selection, and delete coordination. Restore requires agreement among profile UUID, password envelope, sentinel, record session, envelope digest, and DEK epoch; it proves the session key against the sentinel, rejects arbitrary extra files, stages the database, and authenticates its current profile record before publication. A restore must identify which authority proved the key, and recovery enrollment remains an explicit later action. Lifecycle restore checks (`src/cadrumo/application/user_profile/lifecycle.py`)

Human login has two intentionally different doors. `login_profile` selects a target and performs a durable profile handover. `authenticate_profile_for_invocation` unlocks a named profile for one process without changing the active pointer or minting an acceleration receipt, so a command using `--profile X` does not silently change later commands’ default profile. Login resolves only a UUID or exact label through the live-profile resolver, evaluates throttling before password derivation, and authenticates the target’s own password envelope and sentinel into unbound candidate memory. A failed proof records backoff; the configured or callback password is the only credential channel described here, with no recovery or ambient-provider fallback. Login and invocation doors (`src/cadrumo/application/user_profile/login_session.py`), non-selecting invocation authentication (`src/cadrumo/application/user_profile/login_session.py`)

The handover is a durable A-to-B journal. It publishes B’s pointer, binds B’s live bucket and record sessions, optionally stores a split-knowledge acceleration receipt, writes the activation event, and only then closes A’s in-process authorities and revokes A’s durable receipt. Failure during promotion restores A and the pointer and erases B’s receipt. Recovery distinguishes pre-activation interruption, where B must be reauthenticated and the work replayed, from a witnessed activation, where it completes retirement of A without reopening the transition. Receipt identity is tied to profile, password-custody generation, DEK epoch, and deadlines. If the host lacks a usable OS keychain, login still works for that process, but no session key is written to ordinary disk. Durable promotion and rollback (`src/cadrumo/application/user_profile/login_session.py`), handover journal phases (`src/cadrumo/application/user_profile/login_handover.py`)

The session model separates the process-local DEK session, the optional persisted acceleration receipt, and AEAT’s encrypted application session. Session expiry has a sliding idle deadline and fixed absolute cap. Resume binds only the requested profile, checks its current custody generation/DEK epoch, re-establishes the record authority under the supplied pinned schema context, zeroizes the exact returned mutable key buffer, and closes a displaced in-process session. Logout strongly closes live and record authorities, removes durable acceleration, clears the active pointer, and refreshes language state. Failed-login throttle is preserved on ordinary revocation and reset on successful proof; deletion also removes the throttle for a future profile reusing the identity. Resume authority (`src/cadrumo/application/user_profile/login_session.py`), logout and session close (`src/cadrumo/application/user_profile/login_session.py`)

Login surfaces first receive a non-authenticating inventory with four distinct states: recognized, empty, concurrent change, and degraded. The chooser cross-checks its choice list against a profile-summary observation; an unreadable or changing store cannot masquerade as “no profiles.” The attempt adapter turns authentication, throttle, and missing-profile failures into a frontend-neutral refusal. Inventory reconciliation (`src/cadrumo/application/user_profile/login_interaction.py`)

The profile operation catalogue exposes view, scalar and wizard-patch edits, workforce-year updates, descendant-family replacement, repeatable-row add/update/remove, setup completion, bundle export, and logout. Requests bind an exact profile and usually the record revision plus content digest. Executors place mutations inside irreversible sections, record effects, retain private result operands, and project only safe revision/count/row identity to the caller. Bundle export consumes its passphrase through a short-lived ephemeral secret and requires an absolute destination. Logout returns a subject reference rather than attempting to persist a result after it has closed the active profile’s encrypted operand store. Mutation executors and safe results (`src/cadrumo/application/user_profile/operations.py`), bundle export executor (`src/cadrumo/application/user_profile/operations.py`), public schema registrations (`src/cadrumo/application/user_profile/operations.py`)

Operation access is an admission check, not a response capability. It confirms profile binding, the registered contract digest and frontend, then intersects profile, session, ancestor and grant scopes for operation, action, periods, and destination-bound disclosures. Provider, backend, published-authority, and transaction readiness are evaluated independently. For `RESPOND`, the access evaluator returns only scope evidence; the separate interaction owner must still prove and consume the response capability. Exact-scope admission (`src/cadrumo/application/user_profile/operation_access_policy.py`), response scope only (`src/cadrumo/application/user_profile/operation_access_policy.py`)

The history operation reads a complete event catalogue for one explicit profile under a pinned authority, then applies exact inclusive time and optional event-type/object/actor filters. The typed result verifies event count, uniqueness, sort order, profile identity, and filter membership; it is released only against a successful, effect-free terminal receipt for the same subject. History read (`src/cadrumo/application/user_profile/history_operation.py`), receipt-bound result release (`src/cadrumo/application/user_profile/history_operation.py`)

Profile validation projects flat values over the pinned profile-key catalogue and returns missing required, present required/optional, unknown keys, and completeness counts. Conditional IVA and cross-field requirements share the completeness functions covered in Stage-2-102. Language rendering never reads encrypted storage on the event loop: the application refreshes a process snapshot at composition/session/preference boundaries, and a non-secret bucket hint supports locked-profile surfaces. The hint is best-effort convenience state, not an authority source. Key validation projection (`src/cadrumo/application/user_profile/keys_validation.py`), language snapshot refresh (`src/cadrumo/application/user_profile/language_resolver.py`), locked-profile hint (`src/cadrumo/application/user_profile/language_resolver.py`)

## Security and implementation assessment

The strongest design feature is the promotion ordering: B is proven before A is touched; durable pointer publication precedes activation; A’s acceleration is revoked only once B is durably usable; and a monotonic handover witness makes crash recovery explicit. The code also makes a deliberate distinction between selection and one-invocation authentication, enforces an online throttle before expensive Argon2 work, ties resumed receipts to current custody metadata, and treats OS-keychain absence as process-scoped rather than persisting a DEK in plaintext. Candidate promotion (`src/cadrumo/application/user_profile/login_session.py`), receipt session port (`src/cadrumo/application/user_profile/login_session_port.py`)

Private profile values and digests remain in the encrypted operand result; public projections suppress values and content fingerprints. The history API is deliberately powerful because it returns the exact selected event fields, but the operation’s access policy classifies this as profile/tax data and binds release to the requesting destination and registered result schema. Validation’s `valid` flag is computed from missing-required keys; unknown keys are reported separately, so callers should not interpret `valid` as meaning that the input had no unknown paths. Validation result semantics (`src/cadrumo/application/user_profile/keys_validation.py`), history disclosure policy (`src/cadrumo/application/user_profile/history_operation.py`)

Two practical limits remain. First, ephemeral secret consumption narrows credential lifetime, but bundle export converts the memoryview into immutable `bytes` and a Python `str`, then only rebinds the local string after the call. Those copies cannot be reliably overwritten; confirm the underlying export call does not retain them longer than necessary. Second, acceleration persistence and key erasure are delegated to the concrete session port and OS keychain; static application code cannot prove the provider’s buffers or hardware-backed storage behavior. The language hint similarly catches all read/write failures and falls back to configured language, which is appropriate for presentation but means it is not durable evidence of the encrypted preference. No assigned source provides runtime test results, and none were run. Ephemeral passphrase conversion (`src/cadrumo/application/user_profile/operations.py`), language fallback handling (`src/cadrumo/application/user_profile/language_resolver.py`)

## Dependencies and follow-up

Trace login and lifecycle into the concrete bucket-session and custody adapters, acceleration-receipt/keychain storage, active-pointer transaction, `ProfileRecordRepository`, profile-bucket scanner, and workflow event repository. Test interrupted handover at every phase, pointer movement by a competing process, receipt loss/expiry, same-profile relogin, process-local login without keychain, wrong-profile session cleanup, and activation-event replay. Trace operation admission into the central operation owner, terminal response capability, encrypted operand store, registered projection publisher, and each mutation adapter. Verify that large history projections remain within frontend limits and preserve pagination/size behavior at surrounding layers; no paging is implemented in the assigned history reader itself. For export, test secret cleanup after cancellation and failures and verify the local destination’s atomic/recovery guarantees.
