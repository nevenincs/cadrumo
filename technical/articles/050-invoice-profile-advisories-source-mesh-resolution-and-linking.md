## Scope

This chunk covers six invoice-application modules (1,751 lines; 17,811 measured proxy tokens). I read every assigned range in four bounded pages. The modules evaluate two taxpayer-profile facts, provide a simplified-invoice advisory, project catalogue invoices into calculation sources, and persist invoice-to-transaction links. This is static inspection only. Statutory statements in comments and diagnostics are product data, not independently verified legal conclusions.

## Profile-derived invoice facts

The issuer-establishment predicate answers a narrow question for an issued simplified invoice: whether the issuer’s profile makes the counterparty tax ID advisory apply. It reads the profile’s IRPF residency flag as a proxy for IVA territorial establishment in the TAI. The module expressly identifies the axis mismatch: Spanish IRPF residency also includes Canarias and Ceuta/Melilla, which are outside the TAI. The current proxy therefore over-reports establishment for those cases and may demand a counterparty NIF unnecessarily; the limitation is described as pinned by a named test, though no test source or execution was part of this chunk. The predicate intentionally has no received-invoice counterpart and is advisory-only. Establishment proxy and limitation (`src/cadrumo/application/invoices/issuer_establishment.py`) Issued simplified-invoice condition (`src/cadrumo/application/invoices/issuer_establishment.py`)

The self-counterparty predicate compares the invoice counterparty identifier with the taxpayer profile through the shared identity-equivalence function. It does not require a valid Spanish checksum, which allows comparison for foreign identifiers, and treats missing data as “not the same,” not as a match. Its documentation scopes self-dealing as invalid for the operations currently modeled and calls out autoconsumo as an unmodeled exception to revisit if the domain grows to represent it. Self-counterparty comparison (`src/cadrumo/application/invoices/self_counterparty.py`)

The simplified-invoice advisory keeps four outcomes distinct: required, not required, already identified, and issuer unknown. It checks for an existing tax ID before reading the taxpayer profile. A missing active bucket, absent profile, or selected read failure becomes `ISSUER_UNKNOWN`, so the caller does not present a missing-data state as a clean “not required.” The shared predicate supplies the legal condition; this module resolves profile state and returns the outcome. A separate helper obtains legal-reference identifiers from a dated registry mapping using the current Madrid date, which is provenance retrieval rather than a legal review of the rule. ## Invoice source-mesh projection

`InvoiceCatalogueSourceResolver` is a read-only source resolver for collectible invoices, payable invoices, and combined M347/M349 declaration sources. It first checks which invoice source kinds the selected calculation revision declares; combined-direction bindings activate both issued and received sources. If none are active it returns empty. Otherwise it loads the bucket-composed catalogue, maps the explicit invoice-persistence failure to a storage-degradation resolution rather than a zero, filters invoices by period and bucket context, and returns bindings, M349 detail rows, linked transaction IDs, diagnostics, and provenance fingerprints. An unattributed invoice is treated as belonging to the catalogue it was loaded from; only a populated conflicting bucket ID is excluded. An invoice with no counterparty tax ID has no third-party declaration observation. A foreign-currency invoice without a euro equivalent is withheld and receives a diagnostic; the conversion helper refuses to use face value as euros. M347 excludes intracommunity operations so they route to M349, but otherwise preserves third-party residency. Its operation claves A/B derive from invoice direction; C/D/E require both a taxpayer declaration-role membership and a transaction fact; F/G derive from travel-agency mediation. Clave C substitutes the beneficiary whose amount was collected for the payer named on the invoice. The M347 role facts are loaded from the profile for each invoice observation. A missing profile is treated as an empty role set, while other profile-load failures are not caught locally in this helper, so degraded profile behavior should be checked with its repository and source-mesh caller. Observation and currency gate (`src/cadrumo/application/invoices/source_resolver.py`) M347 role load and observation (`src/cadrumo/application/invoices/source_resolver.py`) M347 classification (`src/cadrumo/application/invoices/source_resolver.py`)

For M349, an explicit operation type takes precedence and is checked against the invoice’s direction. When absent, the resolver derives only the claves represented unambiguously by the invoice category, with triangulation handled independently. The code documents that claves M/H share the same ordinary category as E and require an explicit operation type to distinguish post-importation supplies; R/D/C concern non-invoice stock movements. Contradictory M349 declarations, such as an exempt category with a repercuted IVA amount or a category impossible on the invoice side, are omitted from that declaration and produce visible diagnostics. Missing category alone is not disqualifying when an explicit clave exists. The inferred-E advisory is aggregated and only emitted if any invoice anywhere in the loaded bucket has the third-country import category; the diagnostic then lists the current inferred invoices. That deliberately avoids alarming every ordinary EU supplier where no prior import can distinguish the claves. The test is bucket-wide rather than period-bounded in this module, so confirm whether a historical or unrelated import should continue to activate the advisory for a later period. The diagnostic does not alter the derived clave or stop filing. Bucket-wide inference trigger and message (`src/cadrumo/application/invoices/source_resolver.py`)

## Bidirectional invoice links

The pure linking function applies the domain invoice-side and transaction-side link services and returns both updated catalogues. The repository function requires explicit co-commit ports, checks the invoice belongs to the active bucket (allowing a legacy unattributed row in its owning store), canonicalizes the transaction ID, and obtains revision witnesses for both catalogues. It writes the transaction update and invoice secure-object write together, with optional caller-supplied secure writes such as bucket-event history. Revision mismatch refuses before either side is replaced, preventing a one-sided link after a concurrent catalogue change or mid-write failure. In-memory bidirectional link (`src/cadrumo/application/invoices/transaction_linking.py`) Revision-guarded atomic persistence (`src/cadrumo/application/invoices/transaction_linking.py`)

## Assessment and follow-up

This slice preserves distinctions that matter to users and calculations: uncertain issuer facts are not converted to a negative advisory; storage failure is not represented as zero invoice data; ambiguous IVA categories do not silently choose a clave; and invoice/transaction links are revision-guarded across both catalogues. The known establishment proxy is explicitly over-strict and should be replaced only with a genuinely territorial taxpayer fact. Follow-ups are to verify profile-read failure behavior for M347 roles, establish whether the bucket-wide inferred-clave trigger should be time-scoped, and trace the resolver’s binding/diagnostic consumers to confirm omitted observations always remain visible to the operator. The module docstrings cite rules but do not prove current legal accuracy. No tests were inspected or run.
