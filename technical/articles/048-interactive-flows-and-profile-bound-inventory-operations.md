## Interactive flow capabilities

A domain can describe a paged flow with typed widgets, requiredness, closed choices, localized copy references, legal-reference zones, answer-validator IDs, prior-answer visibility gates, section-exit validators, and repeating groups. Definitions reject duplicate page IDs, gates that do not point to earlier pages, repeating counts that lack an earlier integer source, malformed widget/choice combinations, and incomplete per-mode checkpoint declarations. Repeating groups are bounded (default maximum 50). The wizard bridge projects the existing catalogue one way into this substrate, preserving question IDs and gates and converting choice-bearing text questions into select widgets; checkpoint policy remains an explicit caller choice. The pure engine is the flow authority. It recomputes visible pages from canonical answer tokens, commits only currently visible targets, runs widget and registered validators, advances across section boundaries only when exit checks pass, and produces immutable successor states. If an answer controlling later visibility changes, already-entered dependents become stale rather than being silently erased; shrinking a repeating group similarly preserves its orphaned answers as stale. Compare-select deferral remains visible and blocks submission until resolved. Review includes visible rows and stale hidden orphans, aggregates required/invalid/stale/deferred and cross-field blockers, and allows submission only when none remain. Built-in validators canonicalize booleans, choice sets, checkbox tokens, integers, ISO dates, decimals, and paths before domain-specific validators run. Decimal parsing rejects exponent notation and non-finite values; validation verdicts pass interpolation context through the shared redaction function. The line frontend is a sequential terminal surface over the engine, supports injected I/O for headless driving, refuses unsupported non-TTY/Windows console hosts before prompting, and provides a grouped review/edit/restart/submit loop. Secret widgets use password prompts and mask the previously committed answer in terminal output. One data-handling caveat is explicit: the optional post-commit callback receives the canonical answer, including a secret page’s raw value; the code warns consumers not to log it but cannot enforce that rule. The scripted driver consumes canonical tokens in the engine’s visible order, allows defaults only for optional pages, refuses underflow/overflow, and returns only a passing review. Checkpointing is a per-mode port. A mode declaring it unavailable refuses a save; an available mode without an injected store refuses before the frontend begins. Successful submit in the line frontend discards any checkpoint so a submitted run does not remain resumable. ## Inventory service and registered operations

The inventory application service coordinates a bucket-scoped repository and bucket-event history port. It can create, list, show, append movements, preview FIFO/PMP valuation through the domain calculator, record a closing-authority bundle, and remove an activity/year ledger. Purchase movements require the structured acquisition-cost authority and reject legacy parallel cost fields. Movement candidates are validated against the latest revision-guarded ledger before persistence, protecting valuation checks from stale concurrent reads. Create/remove are likewise delegated to guarded repository verbs because they rewrite a shared ledger document. Closing-authority writes validate under the repository guard, are replay-aware, and intentionally emit no bucket event because the ledger and event repositories do not share a transaction. Service and command contracts (`src/cadrumo/application/inventory/service.py`) Service operations (`src/cadrumo/application/inventory/service.py`) Movement guard and event (`src/cadrumo/application/inventory/service.py`) Closing-authority transaction boundary (`src/cadrumo/application/inventory/service.py`)

The registered worker surface defines list, create, movement-add, valuation-preview, and closing-authority operations. Requests are strict hidden-input models with a profile ID; financial inputs cross the public boundary as decimal strings. The executor requires the request payload type and definition ID to match, binds work to the exact profile, resolves read authority and adds commit permission for the mutating operation IDs. It moves blocking repository work to a thread. Mutations enter an irreversible cancellation section, mark effect `UNKNOWN` before the work, await completion through cancellation, and then persist a typed result or a known pre-commit refusal. This allows the operation framework to reconcile ambiguous completion rather than reporting a false no-effect result. Valuation preview is included among guarded operations because it writes an audit event even though it does not change the ledger. Private results are closed by operation/outcome and checked against the terminal receipt before public projection. Ledger outputs keep quantities, costs, and valuation results needed by the operator, but omit acquisition-evidence contents and replace closing-authority documents with fingerprints. Refusal projections carry bounded codes/reasons and selected identifiers, not full exception text. ## Assessment and follow-up

The strongest flow properties are centralized transition semantics, revalidation on resume, explicit stale/deferred blockers, and a shared review gate across interactive and scripted entry. The main flow security dependency is the caller-supplied checkpoint store’s compliance with encrypted domain persistence; the secret commit callback is another trusted boundary, and path-widget tokens are only lexically accepted/expanded here, so filesystem consumers need their own path authority. Flow state and definitions use frozen models around some mutable dictionaries, with immutability also documented as a caller convention.

Inventory has stronger admission and result boundaries: exact profile correlation, scoped commit authority, typed hidden inputs, guarded latest-candidate writes, cancellation effect tracking, and receipt-matched redacted outputs. Audit events for create, movement, and valuation use the literal actor `runtime`; if human-level attribution is required, this module does not carry that identity into those event calls. The direct `InventoryService` also has `show` and `remove`, but the registered operation set in this chunk has no corresponding registered show/remove worker; synthesis should trace whether another authorized entrypoint exposes them. Event writes after ledger writes are not atomic, while the worker correctly keeps the effect unknown if an exception interrupts this span. No tests or runtime evidence were inspected here.
