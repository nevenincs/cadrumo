## Capabilities and mechanism

**Importing an external filing.** The import path treats AEAT-origin evidence as the authoritative baseline for later amendments. Source values are checked against the target work unit and registry snapshot: casilla identifiers must be declared, required numeric casillas must be present, input must be nonempty, and retained source lexicals must parse back to the same canonical values. The work unit is selected under an active-natural policy or created at the law-selected registry revision. Receipt-bound PDF and live-capture evidence must resolve to stored justificante metadata matching tax id, modelo, year, and period; CSV register evidence is linked through its own reference. Imported content becomes a PRESENTADO calculation revision and a current AEAT-origin filing record, while source-kind metadata distinguishes official inputs from locally filed values. external_import_actions.py (`src/cadrumo/application/modelo/external_import_actions.py`), external_import_actions.py (`src/cadrumo/application/modelo/external_import_actions.py`), and external_import_actions.py (`src/cadrumo/application/modelo/external_import_actions.py`).

**Reconciling the filing chain.** The reconciliation function is an explicit state machine. An already recorded register reference is idempotent. A pending local record is confirmed when its content matches AEAT within registry verification tolerance or when receipt totals provide the available comparison; receipt-only confirmation is identified as such. Comparable disagreement creates an AEAT-backed successor and marks the pending record discrepant. If content cannot be compared, required M303 filing-instance evidence is absent, or a correction lacks enough declaration-kind/baseline information, the result is UNVERIFIABLE with stable notices. A first AEAT entry can be appended directly. Successful transitions update the filing chain, calculation/work-unit pointers, observation layers, and event through one revision-guarded co-commit. CSV identity is normalized for idempotency; changed-casilla and affected-record detail is returned in the result, while the audit event stores counts and digests. filing_chain_reconciliation.py (`src/cadrumo/application/modelo/filing_chain_reconciliation.py`), filing_chain_reconciliation.py (`src/cadrumo/application/modelo/filing_chain_reconciliation.py`), and filing_chain_reconciliation.py (`src/cadrumo/application/modelo/filing_chain_reconciliation.py`).

**Internal filing remains distinct from AEAT acceptance.** The local file action requires a sealed, law-current revision and its exact approved verification report; it rechecks profile readiness, required inputs, IVA evidence and reconciliation, cross-period prerequisites, filing-instance evidence, and workflow gates before changing status. It supports safe idempotent retry of an already-filed revision. A new local filing creates a pending record with no AEAT acceptance, supersedes the previous current record, advances work-unit pointers, and emits local lifecycle events. Its cross-period observation is marked app_filing and remains nonofficial: later calculations may carry it forward, but dependent filing gates still require official evidence. For M303, a single resolved result disposition is stored with that observation and can feed the IVA history projection. Preparation checks that the history and observation stores share a backing context before writes are assembled. filing_actions.py (`src/cadrumo/application/modelo/filing_actions.py`), filed_revision_observation.py (`src/cadrumo/application/modelo/filed_revision_observation.py`), and filed_revision_observation.py (`src/cadrumo/application/modelo/filed_revision_observation.py`).

**Profile-scoped registered operations.** Import, list, view, and exact-record selection wrap application reads/writes in registered operation contracts. The import request permits exactly one input source—bounded canonical decimals or a local spreadsheet—and caps casillas, notice context, and result size. Its worker checks operation and profile identity, active bucket, concrete repository ownership, and law-current work-unit coordinates. Spreadsheet parsing runs in a worker thread with cancellation completion; mutation runs in an irreversible section, and the projected receipt must agree with the terminal effect. Listing is capped at 4,096 records and validates profile, filters, uniqueness, ordering, UTC timestamps, and AEAT-confirmation consistency. Viewing returns the selected receipt plus official and pending-local observation layers and override audit data, bounded by the selected filing period. Exact-record selection also verifies the returned work-unit coordinates. List access is whole-profile; view and selection bind disclosure to the admitted period. filing_record_import_operation.py (`src/cadrumo/application/modelo/filing_record_import_operation.py`), filing_record_import_operation.py (`src/cadrumo/application/modelo/filing_record_import_operation.py`), filing_record_list_operation.py (`src/cadrumo/application/modelo/filing_record_list_operation.py`), filing_record_view_operation.py (`src/cadrumo/application/modelo/filing_record_view_operation.py`), and filing_selection_operation.py (`src/cadrumo/application/modelo/filing_selection_operation.py`).

The exact-profile ownership helper rejects repository/profile mismatches and verifies record-to-work-unit coordinates before returning either object. The canonical filing projection round-trips domain receipt and settlement facts through strict wire types. The repository factory is bound explicitly through a ContextVar, so absence of composition is an invariant failure rather than a hidden repository choice. filing_record_ownership.py (`src/cadrumo/application/modelo/filing_record_ownership.py`), filing_projection.py (`src/cadrumo/application/modelo/filing_projection.py`), and filing_repository.py (`src/cadrumo/application/modelo/filing_repository.py`).

**Local output and filer-facing findings.** The shared local-file sink checks destination shape and replacement intent before staging bytes, stages beside the target, discards unpublished data, and rechecks replacement atomically at publish. ## Knowledge, security, and quality

The central authority distinction is strong: local filing can support calculation carry-forward but cannot impersonate AEAT evidence; reconciliation is what promotes a pending observation into an official layer. The registered import path also derives taxpayer identity from the exact profile and checks it against justificante data. Hidden-input request/result models and allowlisted projections limit what crosses operation boundaries. The filing-record view intentionally exposes casilla amounts and replaced values, but only as tax-valued disclosure bound to one admitted period. Full list disclosure is broader and requires whole-profile admission.

Several static boundaries merit validation. The sink’s upfront check proves that a parent exists and is a directory, but does not itself test writability; opening/writing the staged file is not wrapped in the sink’s OSError translation, so actual permission failures may escape the advertised typed path refusal. The observation preparation helper also opens its own bundled registry operation when deriving the M303 IVA-history state rather than receiving the caller’s pinned operation. Finally, direct callers of external_import_actions may omit repository capabilities and trigger bound/default repository factories; registered operation execution supplies exact-profile ports, but integrations should prefer that path. These observations were not runtime-tested.
