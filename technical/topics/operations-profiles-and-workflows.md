## Registered work and operator guidance

The operation supervisor is the common execution boundary for work that can outlive a frontend call. Submission resolves an exact registered definition and host authority, writes a `CREATED` journal before returning, and stores sensitive request material by secure reference rather than in the ordinary journal. Start rechecks the definition and secret requirements, journals `RUNNING` before invoking the executor, and checks authority at task entry. Effectful code enters an irreversible section under a commit guard; cancellation is deferred until that section settles. Cleanup precedes a terminal receipt, and deadline overrun can leave a visible `SETTLING` state instead of claiming completion. Restart reconciliation uses leases and checkpoints, retaining `UNKNOWN` effect where a prior attempt may have crossed a side-effect boundary. This is a substantial durability contract, but a supervisor drain alone cannot prove containment of a host-owned callback or process. Submission (`src/cadrumo/application/operations/_supervisor_submission.py`), execution (`src/cadrumo/application/operations/_supervisor_execution.py`), settlement (`src/cadrumo/application/operations/_supervisor_settlement.py`), recovery (`src/cadrumo/application/operations/_supervisor_reconciliation.py`), [analysis](../articles/089-durable-operation-execution-access-and-public-projections.md).

Definitions declare durability, replay, storage, secret, conflict, effect and deadline capabilities with cross-axis validation. An observer receives an anchored event cursor; an interaction response requires a digest-bound review and a process-local bearer tied to operation, interaction, revision and actor. A transient financial operand is kept in memory while only safe checkpoint state is durable. A restart between delivery and acknowledgement is therefore explicitly uncertain, not a fabricated success. The registry validates exact operation/schema coverage and credential-free durable shapes; host access resolution binds profile, frontend, period and action. One narrower recovery question remains: the local `expire_lapsed` path clears its in-memory financial wait, but the report did not establish a matching durable checkpoint write. Likewise, construction of the supervisor was not shown to invoke the operand broker's owner-restart reconciliation. Those are lifecycle integration checks, not proof that a user-visible operation loses money or bypasses consent. Capability axes (`src/cadrumo/application/operations/capabilities.py`), interactions (`src/cadrumo/application/operations/interactions.py`), financial operand (`src/cadrumo/application/operations/financial_operand_submission.py`), registry (`src/cadrumo/application/operations/registry.py`), [analysis](../articles/090-operation-contracts-observation-and-transient-operands.md), [analysis](../articles/091-operation-authority-registry-and-private-input-custody.md).

Operator guidance is a separate contract layer. The action catalogue gives each remedy a stable identity, canonical command target and provenance for its arguments; verdicts can also say that no recovery action exists. Live resolution joins that declaration to exactly one reconciled CLI leaf, requiring every input and schema identity to match before presenting a command. The surface contract inventories `config` and `app` families, capability/effect policy, localized help and parser aliases. Its manifest compares declared families, command leaves, exposure, schemas and exclusions symmetrically, making an omitted or ambiguous route an explicit refusal. JSON success emission can add a sandbox notice, but does not itself authenticate the bucket. `cli_argv_for` serializes an already validated mapping and silently omits absent inputs, so its consumer must enforce requiredness and allowed values. This is a caller contract; the report did not establish a malformed live route. Catalogue (`src/cadrumo/application/operator_actions/catalogue.py`), action resolution (`src/cadrumo/application/operator_surface/action_resolution.py`), surface reconciliation (`src/cadrumo/application/operator_surface/manifest.py`), argv projection (`src/cadrumo/application/operator_surface/command_ports.py`), [analysis](../articles/092-operator-action-and-command-surface-contracts.md).

## Read models, review and discovery

The overview calendar combines pinned registry schedules, positively established taxpayer applicability, holiday adjustments, local Modelo work, and already-loaded filing observations. It refuses to guess a persona when the taxpayer model is absent. A coverage partition accounts for every recognized obligation as surfaced, excluded, advised or out of scope, so an empty date window does not imply the product knows of no obligation. Agenda and backlog then rank the same underlying rows around explicit dates. Crucially, local draft/readiness state, observed AEAT submission, verified justificante and attention-worthy events remain independent axes. Evidence precedence is deterministic; contradictory receipt references remain conflicts. A verified justificante requires matching identity coordinates or a storage-verified artefact reference. The assemblers do not fetch AEAT data themselves, and their legal schedule has not been externally validated here. Calendar (`src/cadrumo/application/overview/calendar.py`), coverage (`src/cadrumo/application/overview/coverage.py`), evidence merge (`src/cadrumo/application/overview/calendar_evidence.py`), [analysis](../articles/093-overview-calendar-filing-evidence-and-readiness-views.md).

Other overview projections offer an applicability explanation, Home availability zones, status next actions, period pipeline readiness and a six-step data-preparation walkthrough. `overview.read` registers six read kinds with command-specific request constraints and closed snapshots; its projector releases only an exact-profile, successful, no-effect receipt. The pipeline operation checks loaded work-unit period and bucket before using the pure builder, and whole-profile ledger counters require whole-profile access. Explain includes the profile tax ID among its facts, so authorized output and log consumers need a deliberate field policy; the assigned code proves neither unauthorized disclosure nor field-level masking. Data preparation treats a non-null expense evidence pointer as covered without itself proving the pointed-to record exists; storage referential integrity is the missing premise. Explain (`src/cadrumo/application/overview/explain.py`), Home (`src/cadrumo/application/overview/home.py`), pipeline admission (`src/cadrumo/application/overview/pipeline_operation.py`), read result (`src/cadrumo/application/overview/read_result.py`), [analysis](../articles/094-overview-explain-home-pipeline-and-registered-read-projections.md), [analysis](../articles/093-overview-calendar-filing-evidence-and-readiness-views.md).

The unified review queue merges transactions, invoices and draft findings into typed, ordered items. It recomputes approved drafts against current inputs to reveal stale approvals without changing stored approvals. Profile tax-ID matching and authority coordinates limit draft inclusion; registered queue and item reads revalidate profile scope and no-effect receipts. One source adapter converts tax-ID resolution failure into `None`, after which pending drafts appear empty; an outer status must distinguish source unavailability from a clean queue. Invoice rows likewise lose the internal classification reason in their generic summary. Cross-workbench search is intentionally an ephemeral snapshot of already-admitted Ledger, declarations, AEAT-sync and Modelo projections. Query strings are bounded and absent from responses; private record identities become process-keyed HMAC result IDs, which cannot serve as durable bookmarks. Destination admission is carried forward but must be rechecked on navigation. Private search documents still hold actual terms and must not be generically serialized or logged. ## Profile authority and custody

Profile authority is expressed as exact, owner-issued leases and scopes, never merely a supplied profile or session ID. Human login and API-key admission bind current custody generation, DEK epoch, runtime boot, connection, authenticated client and deadlines. API-key grants, key lineage, profile scope and requested scope intersect; delegated leases narrow scope and cannot outlive parents. Access is re-evaluated under an owner guard spanning a registered effect, while a response-scope guard alone does not mint a response capability. Retirement removes leases from the authorization map before fallible worker cleanup and retains cleanup for retry. The runtime contracts make the same distinction between transport-proven native peers and routing coordinates, with digest-pinned chunk transfers and separate owner-stop consent. The concrete OS transport, native login witness and worker containment remain adapter/host responsibilities. Access scope (`src/cadrumo/application/user_profile/access_policy.py`), lease policy (`src/cadrumo/application/user_profile/session_authority_policy.py`), retirement (`src/cadrumo/application/user_profile/session_authority_lifecycle.py`), runtime protocol (`src/cadrumo/application/runtime/contracts.py`), [analysis](../articles/101-profile-access-automation-custody-and-portable-exports.md), [analysis](../articles/106-profile-session-authority-access-leases-and-delegation.md), [analysis](../articles/096-unified-review-queue-and-local-runtime-contracts.md).

Automation enrollment separates consent from authority. A reviewed proposal has a digest over requester, custody binding, purpose, exact scope and expiry. Fresh human proof is bound to the full request, current profile state, native login and short time limits. Approval publishes an inactive candidate, delivers its secret through a bound protected recipient, and activates the grant only after possession acknowledgement. Denial persists before acknowledgement and invalidates automation sessions; resume requires new password proof and names the grants to restore without extending their original permissions or expiry. Python-held secret copies and native client custody still require concrete implementation review. Encrypted profile custody has two distinct export paths: a sealed archive for recovery and a portable v3 subject-access bundle with declared carried and excluded categories. The portable path offers an explicit local cleartext file or passphrase envelope; publication journals `PREPARED`, stages a restrictive sibling file, atomically replaces and fsyncs the destination, then emits the event and reconciles interrupted publications. An unscoped pre-publication scan can log a broad failure and return an empty failure tuple, so that recovery-status path merits a test. Archive restore proves the capsule password and sentinel before lifecycle publication; the archive header reveals narrow identity/time metadata and does not enroll recovery. Profile record replacement compare-and-swaps the authenticated row and bucket-event lineage in one batch. Create, restore, select and delete use journals, inventory witnesses, pointer compare-and-swap and explicit recovery states. Deletion takes a profile/inventory-bound human challenge, refreshes legal and filing holds, and never treats a retention override as permission to bypass a legal hold. It revokes local secrets and moves the capsule to a transaction tombstone before final removal; its receipt explicitly does not claim remote deletion. A changed filing source that remains in the same `held` disposition may evade the final disposition-only comparison when an override is used, so the relevant source digest needs a focused race test. Login similarly distinguishes durable profile selection from authentication for one invocation. Its A-to-B handover proves B first, publishes B, and retires A only after a durable activation witness; a missing OS keychain permits process-only login rather than plaintext acceleration. Masked overviews use schema sensitivity before fallback heuristics; a separately gated facts stream can disclose canonical values. Recovery-code enrollment requires password proof, one-time code delivery and possession echo, while passphrase rotation rewraps custody and retires automation. The rehead-before-envelope replacement sequence needs adapter-level crash testing. ## Local workflow boundary

The workflow engine stages profile, obligation, optional inbox and prior-filing reads, bucket inputs, draft checks and local preflight. Its successful result still has no submission ID: it does not transmit a declaration. `FILE` and `VERIFY` have different deadline treatment, with exact target and ambiguity checks. Optional live sources can make the local path contact AEAT; a present invalid certificate may also block local preflight despite skipped auth-readiness flags, so host wiring and intended offline behavior warrant verification. Persisted state and runs use encrypted secure-object ports with optimistic revisions; reset records an event before deleting the state row. A reset docstring promises a content hash, but the actual fingerprint has metadata only, a concrete documentation mismatch. Resume requires a qualifying aborted run and refuses ambiguous natural targets. Exact-run and inventory reads bind profile and, where supplied, period scope; public results require successful no-effect receipts. Engine (`src/cadrumo/application/workflow/engine.py`), reset (`src/cadrumo/application/workflow/persistence.py`), resume (`src/cadrumo/application/workflow/resume.py`), run reads (`src/cadrumo/application/workflow/run_read_operation.py`), [analysis](../articles/109-workflow-execution-and-local-filing-orchestration.md), [analysis](../articles/110-workflow-results-snapshots-and-history-disclosure.md).

These findings come from static source review. They establish declared contracts and local checks, not live AEAT behavior, current legal accuracy, native OS containment, adapter atomicity or executed test results. The most valuable integration checks are effect/cleanup reconciliation, exact authorization at every frontend and storage boundary, crash recovery around custody publication and passphrase rewrap, and whether unavailable evidence is rendered distinctly from an empty queue or calendar.
