## Session custody and identity

The login flow resolves active-profile preference, local readiness and live-read opt-in, enters exact-profile custody, and refuses pending recovery. It probes existing persisted state, obtains a provider/profile acquisition lock, then probes again before authenticating. Browser-state writes are staged during provider work and published only after verification and the operation effect guard. Certificate and Cl@ve providers have distinct target-aware contracts; Cl@ve Móvil needs a direct persisted-session probe. The application validates persisted metadata, provider kind and UTC dates, and compares expected profile tax identity with the returned session identity. Cl@ve profile credentials win over settings only when a session serves the exact active bucket. Browser/session adapters still own concrete token encryption and remote navigation behavior. Session lifecycle (`src/cadrumo/application/auth/sessions.py`) Staged publication (`src/cadrumo/application/auth/operator.py`) Identity comparison (`src/cadrumo/application/auth/sessions.py`) Credential scope (`src/cadrumo/application/auth/sessions.py`) ([038](../articles/038-operator-authentication-session-custody-and-access-contracts.md), [039](../articles/039-authenticated-session-lifecycle-and-identity-binding.md))

Named certificates have per-profile source records. Selection uses a witnessed active-profile route, and a named passphrase comes only from its profile secret backend, never an unnamed global fallback. The local source probe can report missing, unreadable, expired and expiring material without contacting AEAT. Secret changes pass through a one-use ephemeral slot and a secret-free durable intent with retry/completion witnesses. Registered mutations require a human, exact-profile operation subject, and a matching receipt before public results expose only reduced path/count facts. Auth diagnostics are stored behind an encrypted profile port; list/detail projections omit URL queries and raw HTML/screenshot content and fingerprint private identities. These are meaningful application controls, while backend encryption and retention are separate adapter claims. Certificate route (`src/cadrumo/application/auth/credentials.py`) Secret intent (`src/cadrumo/application/auth/certificate_source_operations.py`) Diagnostic redaction (`src/cadrumo/application/auth/diagnostics.py`) ([037](../articles/037-authentication-certificate-sources-and-diagnostic-privacy.md), [038](../articles/038-operator-authentication-session-custody-and-access-contracts.md))

Logout and reset use durable cleanup intents that snapshot provider scope, session/lock presence and certificate-source witnesses. Cleanup removes only records that still match its observed provider/configuration or source registration; events record the result. Reset currently permits clearing a held acquisition lock. Whether that is unsafe depends on the live owner's cancellation/publication behavior; this report does not establish such a race. A separate, concrete acquisition-lock race is visible when initial lock-file inspection fails: the recovery path can delete a newly readable, replaced live lock because its comparison has no expected bytes. Under that specific interleaving, two processes can believe they own acquisition. The session flow's two probes reduce the window but do not repair a broken lock primitive. One identity boundary remains conditional: the session model accepts any nonempty identity string, while final comparison skips a value that normalizes to blank. Provider constructors or persisted-session probes may reject that earlier; trace those producers before calling it a reachable bypass. The Cl@ve target URL also needs its caller allowlist and adapter navigation policy to establish the network boundary. ## Registers, files, and workbook storage

The capital-goods register is a bucket-bound list/declaration service; calculation of annual regularization belongs to another application component. Its declaration operation checks governed kind/regime vocabulary, validates the record, enters an irreversible write section, and matches the public result to a terminal receipt and updated register. Bucket maintenance is currently a read-only deletion assessment plus target-lock helper. It refuses linked/unreadable bucket roots and missing or invalid retention snapshots, then records a capsule fingerprint for the later reset workflow to recheck. An absent retention snapshot is unknown, not an empty filing set. Register operation (`src/cadrumo/application/bienes_inversion/registered_operation.py`) Bucket assessment (`src/cadrumo/application/bucket_maintenance/service.py`) ([040](../articles/040-capital-goods-register-and-bucket-deletion-assessment.md))

Storage management derives inventory, initialization and reclaim targets from a shared taxonomy. Reclaim excludes durable state and exports, checks all targets, containment, link-like paths and protected descendants, and requires explicit confirmation at service level. Inventory distinguishes unresolved profile paths from checked absence, but unreadable enumeration/size can degrade to zero; a concurrent path replacement between preflight and recursive deletion remains a filesystem threat-model question. Ledger-import diagnostics are preview only. They use the same classifier as persistence for stored fingerprints, within-batch repeated fingerprints and transaction-ID collisions, but their 'original file' check tests readability rather than matching source bytes. Reclaim policy (`src/cadrumo/application/storage_management/service.py`) Inventory (`src/cadrumo/application/storage_management/service.py`) Shared import classifier (`src/cadrumo/application/transactions/import_classification.py`) ([100](../articles/100-storage-lifecycle-management-and-ledger-import-diagnostics.md))

The calculation-sheet package builds one registry-stamped plan for Google Sheets and offline XLSX. It distinguishes editable inputs and Detalle rows from protected computed, tariff, provenance and guidance cells; formula translation refuses unsupported operations. It can render local workbook bytes with validated size and SHA-256, while a separate injected Google adapter can apply a plan remotely and record a sync run. Parity tooling compares local Decimal results, Google Sheets readback and caller-supplied expected values. A partial or unauthenticated expected-value map does not certify legal correctness, and the harness itself writes a remote spreadsheet. Sync-run records pair a bucket event with reached-unit coverage, retaining partial failures separately from divergences. Shared plan (`src/cadrumo/application/storage/calc_sheets/engine.py`) Offline bytes (`src/cadrumo/application/storage/calc_sheets/workbook_export.py`) Parity limits (`src/cadrumo/application/storage/calc_sheets/parity_harness.py`) Sync provenance (`src/cadrumo/application/storage/sync_runs/persist.py`) ([098](../articles/098-registry-backed-calculation-workbook-plans-and-parity.md), [099](../articles/099-workbook-materialization-and-sync-run-provenance.md))

The strongest general pattern is exact-profile custody plus typed effect and evidence records. The lock replacement race deserves a targeted interleaving test; other follow-ups are provider identity normalization, held-lock reset coordination, reclaim path changes, and failed remote apply plus failed sync-record persistence. Static inspection did not run auth, storage mutation, workbook parity, or AEAT access.
