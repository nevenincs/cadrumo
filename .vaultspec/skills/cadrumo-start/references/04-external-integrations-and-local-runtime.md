# External integrations and local runtime

The local runtime client uses verified native IPC, separate bounded document/secret frames, exact boot/connection/profile/session identity, and worker custody/operation/authorization channels. Clients connect only to a verified runtime and report unavailability; running state is distinct from authenticated or settled operations. Linux containment uses pidfds/cgroups; Windows uses a kill-on-close Job Object and token/desktop checks. These source-level controls need platform/race testing. AEAT browser adapters authenticate by certificate or Cl@ve, then read censal facts, filed declarations, IVA wallet, notifications, NIF-IVA/GROI and expedientes through guarded host/path/action routes. Captures carry hashes and registry references. A notification-document fetch requires a prior `leida=True` row, but the adapter depends on its caller for a fresh, same-taxpayer record. Fresh Cl@ve landing acceptance is weaker than later verification; missing persisted landing metadata can make a diagnostic probe start a challenge. Captured 303 compensation assumes `refunded=False`, requiring downstream refund reconciliation. Google Sheets is a remote writer and checked readback surface; offline XLSX is a separate local artifact. OAuth/Drive require scope and ownership markers. Encrypted-byte mirroring verifies object hashes and publishes manifests only for complete namespace pushes. LLM readers distinguish model proposals from deterministic grounding; canonical off-host invoice extraction binds fresh consent to stored source bytes, while generic dispatch relies on callers for that binding. Strong scoped concerns include potentially duplicated Sheets metadata on a replayed structural batch, `USER_ENTERED` literal formula interpretation, stringified missing OAuth refresh tokens and a generic Drive write/read hash-contract mismatch. ## Runtime lifecycle policy

The runtime is supervised by the shared native manager core. On Windows, optional machine installation supplies a machine-start SCM lifecycle broker that launches per-user managers with genuine user logon tokens; user installation supplies unprivileged login startup. The broker owns no taxpayer runtime or profile credentials under SYSTEM. Every running Cadrumo GUI establishes supervision: an existing installed manager keeps ownership, otherwise the GUI acquires the same session lock and hosts the shared core. It observes external ownership and takes over when released, verifies runtime readiness through native IPC, and drains only its owned supervisor on close. Other clients never start, stop or supervise the runtime; they report typed unavailability. Development and CI never register boot or login startup; installed boot/login acceptance runs only on disposable hosts. Windows manager/runtime admission must not reject Session 0, elevation, or absence of a desktop witness. Preserve native same-account peer identity, exact process ownership and real profile credential authentication. Observe desktop locking when a desktop is bound; verified non-desktop logons have no screen-lock surface. Recovery follows supervisor lifetime until explicit stop or session-end. Platform containment remains required for owned workers. The optional-installation and ownership amendment is authorized in `2026-10-04-runtime-manager-architecture-adr` and `2026-10-04-desktop-shell-adr`.
