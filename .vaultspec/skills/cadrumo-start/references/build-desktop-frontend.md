# Desktop frontend

Build scripts admit configured repository preset directories through `scripts/build-paths.mjs`; they reject linked or external output roots and mismatched source/cache manifests. Cargo output uses the selected manifest's `desktop_cargo` path. [Path admission](../../../../native/desktop/scripts/build-paths.mjs), [Cargo driver](../../../../native/desktop/scripts/tauri.mjs).

The desktop window's web layer is the private npm package `cadrumo-desktop-frontend` in `native/desktop/frontend`: React 19, TypeScript 6, Vite 8, CSS-first Tailwind 4, Radix and cmdk through shadcn-style primitives, lucide icons and xterm.js 6. The product entry is `index.html` loading `src/main.tsx`, which uses `tauriHost()` when `isTauri()` and otherwise a browser host that fabricates nothing; `scenarios.html` mounts the same `App` on a simulated host through `src/dev/main.tsx`, and `startup.html` with `src/startup.ts` is the product loading page, a second Vite input. There is no router or state library: a rail, three columns (agent, TUI, docs) and a bottom panel (console, Python, logs) are driven by `App` and hooks in `src/shell/`. The shell presents what the host reports and grants no authority: sign-in success comes only from the host answer, and an unreadable log is shown as unavailable, not empty. Every backend capability sits behind the `Host` interface; the Rust side is covered in [the Tauri shell reference](build-tauri-desktop-shell.md), and the agent column's backend in [the agent integration reference](agent-integration.md). [package](../../../../native/desktop/frontend/package.json#L6), [entry](../../../../native/desktop/frontend/src/main.tsx#L14), [Host port](../../../../native/desktop/frontend/src/shell/host.ts#L114), [columns](../../../../native/desktop/frontend/src/App.tsx#L162).

The packaged flow is CMake-driven; development is npm-driven. `desktop-frontend-install` runs the read-only `frontend-install.mjs --check`; missing or mismatched dependencies require explicit `just setup-desktop-frontend` (the lock-aware `frontend-install.mjs setup`) outside the build; `desktop-frontend-build` runs `frontend-build.mjs`, which runs `npm run build` only when fingerprinted inputs changed. `npm run build` is `tsc --noEmit && vite build` and empties the product directory in the CMake build tree. There is one build: the desktop has no CMake project or build tree of its own, and every frontend dev, check, build and test path reads the repository build named by `CADRUMO_CMAKE_BINARY_DIR` (`build/<preset>`). Its `desktop-frontend-generated` target writes the chrome strings (`chrome-strings.json`), the palette (`palette.css`) and the pinned provider icons (`provider-icons.json`); it compiles no Rust. Vite reads those generated files as virtual modules (`virtual:desktop-strings`, `virtual:desktop-palette.css`, `virtual:desktop-provider-icons`), while `virtual:desktop-content` resolves through an identity module in `vite.config.ts`, and a missing generated one fails with "has not been generated ... Build the desktop-frontend-generated target, or run just dev"; chrome strings come only from the generated catalogue. `npm run dev` runs `scripts/dev.mjs`, which only serves: it refuses options, never configures or builds, and stops unless `CADRUMO_CMAKE_BINARY_DIR` names a configured build whose generated inputs exist. It serves Vite on the fixed ports in `native/desktop/development-server.json` (development 15370, preview 15371, documentation fixture 15372, Storybook 6006); an occupied port is an error. `just dev` publishes the registry authority if stale, then builds the repository build's `desktop-frontend-dev` target, which builds `desktop-frontend-install` and `desktop-frontend-generated` first and then runs `dev.mjs` with the build's environment. Playwright's development server runs the same `dev.mjs` against the build under test. `check` runs tsc, ESLint, the `node --test` guards, a `node --check` of `../scripts/tauri.mjs`, and Prettier over the frontend plus `../scripts`, `../tests` and `../CMakeLists.txt`. Others: `test`, `preview`, `format`, `storybook`, `storybook:build`, `shots`, `benchmark`; `vite build --mode scenarios` builds the minified development entry the benchmarks use. CMake also exposes `desktop-frontend-check` and `desktop-frontend-test` (worker count and last-failed from `CADRUMO_DESKTOP_FRONTEND_TEST_WORKERS` and `_LAST_FAILED`). [scripts](../../../../native/desktop/frontend/package.json#L6), [dev server](../../../../native/desktop/frontend/scripts/dev.mjs#L12), [CMake](../../../../native/desktop/CMakeLists.txt#L156), [build script](../../../../native/desktop/scripts/frontend-build.mjs#L79), [virtual inputs](../../../../native/desktop/frontend/vite.config.ts#L22), [just dev](../../../../justfile#L56).

`src/ipc/contract.ts` is types plus terminal frame tags: a `HostCommands` table of command to `{args, result}` covering window, startup, sign-in, manager, profiles (`profile_*`, including census and views), user profile, runtime attendance, desktop setup and Google, about, presentation, desktop environment, terminal, logs, diagnostics, clipboard, menu, open-external, the agent column (`agent_*`, including skills, conversations and observation), provider settings (`provider_settings_*`) and agent access keys (`agent_access_*`), plus channel payloads and the documentation postMessage bridge. Every argument carries a per-launch `ShellToken`, added by `hostCall`; `tauriHost` reads it once from `window.__CADRUMO_SHELL__`, and its agent methods come from `tauriAgent(call)`. Four raw-body commands carry a secret as the request body with the token and other fields in headers: `sign_in_submit`, `profile_create` and `profile_password_change` (password) and `provider_settings_set` (key); `terminal_write` likewise takes raw input bytes. They are documented in comments and invoked directly rather than listed in the table. No schema library validates payloads at run time, and nothing generates or tests agreement between `contract.ts`, the Rust handlers and `native/CONTRACT.md`, which has no entries for the `agent_*` commands. The scenario host in `src/dev` implements the same port from fixtures, with agent, agent-access and provider-settings fixture hosts beside it. Terminal output has flow control: a `data` frame carries a `drawn()` callback, and the host withholds more output until the renderer reports the bytes drawn (`terminal_ack`). The agent column is `components/AgentColumn.tsx` with about twenty components in `components/agent/` (transcript, composer, approval, question and consent prompts, documents, attachments, history, skills, provider selection), most with stories, over the typed modules `shell/agent*.ts` (session, views, live stream, permission, clarification, choice, catalog, access, documents, skills, staging, words). The column receives the provider catalogue the host reports and never hardcodes which providers or lanes exist; provider keys are set in `components/settings/ProviderSettings.tsx` over `shell/providerSettings.ts`, and agent access keys in `AgentAccess.tsx`. `agent_documents` returns the stored-document page, and `agent_attach` opens a file dialog and uploads through the gateway attachment policy. [column](../../../../native/desktop/frontend/src/components/AgentColumn.tsx), [session](../../../../native/desktop/frontend/src/shell/agentSession.ts), [settings](../../../../native/desktop/frontend/src/components/settings/ProviderSettings.tsx), [fixtures](../../../../native/desktop/frontend/src/dev/agentFixtureHost.ts).

`AttendanceRequests.tsx` is a whole-window person approval overlay, backed by the exact runtime holder rather than agent model state. It shows bounded live candidate process/image/scope and records one allow/reject through the Host; expired asks disappear and polling grants no activity extension. Service administration remains available before agent startup, enabling credential repair after a refusal. Provider metadata comes from the actual full agent catalog, offline health is unknown/unselectable and no model/provider list is invented by UI. Generic automation access uses `desktop.automation_access` and the logout `automationAccessRemains` result; it is distinct from service providers. [Attendance UI](../../../../native/desktop/frontend/src/components/AttendanceRequests.tsx), [Host port](../../../../native/desktop/frontend/src/shell/host.ts), [Tauri adapter](../../../../native/desktop/frontend/src/shell/tauriHost.ts), [provider settings](../../../../native/desktop/frontend/src/shell/providerSettings.ts).

Generated chrome combines independent service `locales/{en,es,ca,hu}.yml` and tax/generic catalogue owners under collision and placeholder policy. The tax loader imports no sibling catalogue. Service-owned `desktop.agent`/`desktop.providers` and pane/rail labels live outside tax resources; actual tax auth providers and evidence extraction remain tax owned. [Locale projection](../../../../dev/locales/desktop_chrome.py), [ownership transfer](../../../../dev/locales/service_catalogues.py), [CMake source inputs](../../../../native/desktop/CMakeLists.txt).

Colour is generated from the documentation theme and mapped to roles (`bg-card`) in `theme.css`, dark under `[data-scheme="dark"]`; lengths, type, radii, layers and motion are tokens in `tokens.css`. The `ui/` primitives wrap Radix, cmdk and lucide and import nothing from shell or IPC. Custom ESLint rules: `token-styles` rejects arbitrary px/rem/ms values, literal and default-palette colours and numeric `z-`/`duration-`/`delay-`; `component-names` requires PascalCase components and kebab-case primitives. Built-in restrictions ban re-exports, development code in the product, and `@tauri-apps/*` outside the listed adapter files. A stylesheet checker, run as a node test rather than by ESLint, confines pixel lengths to `tokens.css` and colours to `theme.css`. At build time the `product-boundary` Vite plugin refuses development modules in the product bundle. [theme](../../../../native/desktop/frontend/src/styles/theme.css#L1), [tokens](../../../../native/desktop/frontend/src/styles/tokens.css#L1), [primitive](../../../../native/desktop/frontend/src/components/ui/button.tsx#L11), [rules](../../../../native/desktop/frontend/dev/eslint/design-system.mjs#L3), [boundaries](../../../../native/desktop/frontend/eslint.config.js#L7), [product boundary](../../../../native/desktop/frontend/vite.config.ts#L100).

Playwright has two projects: `product` serves a fresh `vite build` through `vite preview` with no host or a faked `__TAURI_INTERNALS__`, and checks the bundle for development leakage; `scenarios` drives `scenarios.html` (axe audits in both schemes, keyboard, touch, manager flows, agent, agent-access and provider specs). `playwright.scenarios.config.ts` runs the scenarios project alone and starts only `npm run dev`. Storybook (`.storybook/`) is a separate catalogue; `shots` photographs it without baseline comparison. Node tests for the build scripts live in `native/desktop/tests/*.test.mjs`; the frontend's own node tests are the ESLint and stylesheet guards under `dev/eslint/tests`, and there is no Vitest or Jest. The tests call themselves presentation evidence, and the README lists what only a packaged window shows, such as runtime sign-in, native menus, the real content security policy and PTY sessions; a live agent run against the packaged window is the separate `just desktop-agent-live` lane. Observations to check: the `design-system` spec holds a few token-to-geometry cases, not token conformance; `terminal-theme.spec.ts` runs the repository `.venv` Python at load; the test server builds without `tsc`. [Playwright](../../../../native/desktop/frontend/playwright.config.ts#L29), [axe audit](../../../../native/desktop/frontend/tests/scenarios/accessibility.spec.ts#L11), [limits](../../../../native/desktop/frontend/README.md#L478).

## Working notes

- A new host command needs a `HostCommands` entry, a `Host` method with its `tauriHost` implementation (agent commands under `tauriAgent`), a scenario-host or fixture answer and the Rust handler; raw-body commands bypass `hostCall`. [raw body](../../../../native/desktop/frontend/src/ipc/contract.ts#L774)
- The agent column shows what cadrumo-agent reports: providers, lanes and models come from the host's catalogue, never from frontend constants. [catalog](../../../../native/desktop/frontend/src/shell/agentCatalog.ts)
- Define a design measure once in `tokens.css`; components name roles or tokens, never values. [design system](../../../../native/desktop/frontend/README.md#L196)
- No CSS modules, barrels or forwarding components; a component module exports components and types only; icons come from `ui/icon.tsx`; chrome strings use `python -m dev.locales set-batch`, then rebuild `desktop-frontend-generated` (or rerun `just dev`). [CSS](../../../../native/desktop/frontend/README.md#L216), [barrels](../../../../native/desktop/frontend/README.md#L253), [icons](../../../../native/desktop/frontend/README.md#L291), [strings](../../../../native/desktop/frontend/README.md#L298)
- Check, build, test and catalogue commands need `CADRUMO_CMAKE_BINARY_DIR` set to the absolute repository build directory (`build/<preset>`); the CMake targets and `just dev` set it, and `npm run dev` refuses to start without it. [build directory](../../../../native/desktop/frontend/README.md#L29)
- Before finishing run `npm run check`, then `npm test`. [check and test](../../../../native/desktop/frontend/README.md#L467)
