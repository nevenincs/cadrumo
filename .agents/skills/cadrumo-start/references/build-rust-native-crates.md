# Rust native crates and their build

There is no Cargo workspace: `native/application`, `manager`, `installer`, `launch_guard`, `platform` and the Tauri crate in `native/desktop/src-tauri` each have their own manifest and `Cargo.lock`. `cadrumo-application` is a binary-less library (package verification, version discovery, publication state, child processes); its `platform` feature pulls in `cadrumo-platform`, the sole owner of storage-root and child-environment policy and of a fixed-width C ABI (`rlib` from Cargo, `staticlib`/`cdylib` from CMake). `cadrumo-manager` is the per-user runtime manager binary. `cadrumo-installer` is a Windows-only `cdylib`/`rlib` of MSI custom-action exports plus the `cadrumo-msi-maintenance` runner. `cadrumo-launch-guard` is a C-ABI `staticlib`. The hosts in `native/interpreter` (`posix/host.c`, `windows/host.c`, bridge `python.c`) are C and link the platform and launch-guard static libraries. The desktop crate is one more consumer of application, platform and installer under the same build rules. [manager](../../../../native/manager/Cargo.toml#L37), [platform](../../../../native/platform/Cargo.toml#L6), [desktop](../../../../native/desktop/src-tauri/Cargo.toml#L21).

CMake owns every Rust build and Cargo owns dependency freshness. The pin is `rust` in `native/toolchain.json` (1.96.0, per-target triples); there is no `rust-toolchain.toml` or `.cargo` config, and manifests state only `rust-version = "1.96"`. The platform adapters compare `rustc --version` (not cargo) with the pin and take the toolchain from `CADRUMO_RUST_ROOT` (default rustup directory on Windows, required on POSIX). `cadrumo_cargo_command` wraps each call with `RUSTC`, `RUSTDOC`, `CARGO_TARGET_DIR` (`cargo/native` in the binary directory) and linker settings; targets run `cargo build --locked --target <triple> --profile dev|release`. Targets: `rust_application` and `rust_manager` (ALL), `rust_platform`, `rust_launch_guard`, `rust_installer` (Windows). `native_contract` generates `contract.rs/.h/.json`; crates read them through `CADRUMO_CONTRACT_RS` (`include!(env!(...))`, so a bare `cargo` invocation fails to compile), `CADRUMO_NATIVE_CONTRACT` and `CADRUMO_ID_*`. CTest cases: `application.rust`, `application.package`, `manager.rust`, `manager.supervision`, `installer.rust`, `launch_guard.rust`, `platform.resolver`. No `just` recipe runs cargo, clippy or rustfmt; reach a single target with `just build-native <Config> <target>`, and clippy exists for these crates only as the CMake target `check_manager_lifecycle`. [toolchain](../../../../native/toolchain.json#L2), [Rust.cmake](../../../../native/cmake/Rust.cmake#L3), [manager targets](../../../../native/cmake/Manager.cmake#L46), [recipe](../../../../justfile#L668).

The manager supervises the packaged runtime host (`bin/cadrumo-runtime`, started with `--storage-root`, `--storage-identity`, `--expected-version`, `--supervised`). The supervisor is a state machine with readiness and heartbeat bounds, bounded drain and termination, and a restart policy (backoff to 60 s, a bounded number of restarts per 600 s window). An existing owner is adopted only when its boot record matches pid, creation time, session and image; otherwise it is reported foreign and never stopped. Ownership uses a session mutex, a start claim and a Quit marker. Windows IPC is a named pipe with a closed request grammar whose peer is checked for session, SID, image and liveness. Cutover starts a designated successor that must reach an authenticated acknowledgement before the hand-over commits; failed versions are suppressed until a newer release or Retry. Only Windows has a run path: elsewhere `main` writes `manager_platform_unavailable` and exits with the startup-failure code. The Linux and macOS halves are implemented in source with unit tests, and the macOS AppKit adapter states that no entry point calls it. These are source-level controls; containment and race behaviour need OS-level testing. [entry](../../../../native/manager/src/main.rs#L192), [non-Windows exit](../../../../native/manager/src/main.rs#L56), [supervisor](../../../../native/manager/src/supervision/supervisor.rs#L39), [restart policy](../../../../native/manager/src/supervision/restart.rs#L21), [peer check](../../../../native/manager/src/ipc/windows.rs#L246).

The installer runner reads a verified plan and drives an MSI transaction: artifact digests, ownership and scope admission, an owner pipe that authenticates `msiexec`, Restart Manager use checks, version and registration MSIs, then publication recorded after commit. `unregister` keeps version payloads, `remove-version` removes one release; a commit followed by a publication failure is reported as pending rather than rolled back. The launch guard takes a shared removal lease on the package root before CPython loads (a null handle means unmanaged) and grants removal exclusion only. The C hosts refuse `LD_*`/`DYLD_*` on POSIX, restrict DLL search on Windows, load the pinned CPython and the bridge, and call `cadrumo_python_main`, which refuses any CPython other than the generated pin before an isolated start and Python bootstrap. [runner](../../../../native/installer/src/runner.rs#L1), [launch guard](../../../../native/launch_guard/src/lib.rs#L20), [bridge](../../../../native/interpreter/python.c#L34).

Scoped observations needing a check against current code: the contract's startup-lifetime section still describes the manager refusing full-elevation tokens and non-interactive sessions, which the runtime lifecycle policy in [the local runtime reference](04-external-integrations-and-local-runtime.md) no longer permits as admission refusals; re-read the manager entry before relying on either text. The POSIX custody clear compares two no-follow opens, then unlinks by name, against a comment promising a verified handle. The exit classifier treats code 1 as a launch failure while the Windows process module names 1 as the forced-termination code. The platform manifest's `panic = "abort"` profiles apply only when it is the root package. Windows hands `CMAKE_LINKER` to Cargo directly, POSIX goes through linker admission. [startup contract](../../../../native/CONTRACT.md#L1384), [clear](../../../../native/manager/src/custody/posix.rs#L194), [exit codes](../../../../native/manager/src/supervision/exit.rs#L13), [termination code](../../../../native/manager/src/supervision/windows.rs#L42), [profiles](../../../../native/platform/Cargo.toml#L10).

## Working notes

- Path, storage-root and environment policy lives only in `native/platform`; the `contract.*` files are generated, never hand-authored. [owner](../../../../native/CONTRACT.md#L215), [rule](../../../../native/CONTRACT.md#L127)
- The application `.rlib` is not a runtime file; `fixture-test-mode` is refused in release builds. [statement](../../../../native/CONTRACT.md#L138), [guard](../../../../native/manager/src/lib.rs#L5)
- Gated tests: `supervision.rs` is Windows-only, `custody_conformance` needs `CADRUMO_TEST_PYTHON`, the installer kit test is `#[ignore]`, window smoke needs an interactive logon; `live-python-tests` and `live-package-tests` have no CMake wiring in these crates. [supervision](../../../../native/manager/tests/supervision.rs#L6), [smoke](../../../../native/CONTRACT.md#L1226)
- Login start: MSI authoring writes a per-scope `Run` value launching the manager with `--sign-in`. No installer launches the manager or runtime during installation, and Linux/macOS packaging adds no services, scheduled tasks or automatic launch. [Run](../../../../dev/packaging/native/windows_msi.py#L168), [no launch](../../../../native/CONTRACT.md#L1592), [no services](../../../../native/CONTRACT.md#L1679)
