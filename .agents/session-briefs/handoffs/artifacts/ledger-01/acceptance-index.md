## Import filename and row criterion

LE12 requires both frontends to let users inspect provenance. LE3 requires import/replay behavior, and LE8 requires encrypted evidence custody. `RawProvenance` already stores a basename and one-based source row in the encrypted transaction catalogue; invoice provenance carries the same fields. The installed wheel's public TUI transaction detail did not display either field, its invoice detail displayed only the source path, and CLI `ledger track` JSON omitted both while text omitted the row. This was a **presentation gap under LE12**, not missing persisted provenance or evidence custody.

Commit `83dcd72d79` adds `filename:row` to both TUI details and `source_filename`/`source_row_index` to CLI track JSON, plus a row in CLI text. Focused CLI integration and mounted TUI tests passed 2/2 at `20260922T043815.707118Z-pytest-74220-274450dd`. The display is now **installed-proven for these paths** on wheel `cc29…0b509c`, built from a detached checkout of exactly that commit (`installed-ledger-provenance-wheel-cc29-receipt.json`). One CSV-imported received invoice and one CSV-imported bank-statement transaction, each at row 2, show their filename and row through public CLI JSON and text and through installed TUI details. The `__init__` hash matches the `6c8d` wheel's because that file did not change between the two sources, so the wheel SHA-256 is the distinguishing identity. The `6c8d` and `4336` receipts were not rerun or edited and still do not attest to this display; public JSON tracking on those older wheels has no filename/row fields.

The matrix receipt extends this from CLI CSV to **every supported import path** on the same wheel. That covers statement CSV/TXT, XLSX, OFX/QFX (with the `ofx` extra) and N26 PDF, plus invoice CSV/TSV/XLSX/XLSM, each imported through both CLI and TUI and read back through both. Delimited and workbook sources store the physical row, with the header as row 1. OFX and N26 PDF have no row concept: they store the 1-based transaction ordinal in the document, and the frontends display that number after the filename. The N26 page number is stored only in encrypted raw fields and is shown on no public surface. Not proven, with the reason recorded in the checkpoint inventory: the mapped-tabular lane for unrecognised headers (needs the `llm` extra plus an on-host model), OFX without the extra (typed refusal, code-cited), non-N26 PDFs and unsupported invoice extensions (refusals, code-cited), and legacy `.xls`, which has no import provider. The prior encrypted import/reopen tests establish persisted provenance for their exercised paths; a filename or row label alone is not secure evidence custody.
