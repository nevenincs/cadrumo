# `code-dedup-sweep` audit: `semantic duplication sweep: 29-searcher RAG inventory`

## Scope

Campaign shape: 8 domain leads x 4 semantic searchers (32 dispatched, 29 returned, 3 killed by server-side throttling). Evidence channel was vaultspec-rag semantic search only - no file reads, no git, no tests. Every site below is RAG-reported and UNCONFIRMED against HEAD; each carries the symbols a targeted rg pass must confirm before any edit. Recall is partial: the code index was mid-rebuild throughout and one probe returned index_unavailable, so a thin domain means "no signal", never "no duplication".

Blind spots (rate-limit casualties, never searched): login/credentials/tokens (D4.2), taxpayer-identity validation (D4.3), censal facts and profile-fact bindings (D4.4).

### gate-blind-spots-alias-evasion | critical | two structural gates report green against violations they cannot see

ADDENDUM - GATE BLIND SPOTS, a finding class more serious than any single duplication below.

Two independent structural gates report green against violations they are architecturally unable to see, because each matches a literal NAME rather than the shape of the thing it guards.

1. `src/cadrumo/tests/test_parsing_enrollment_inventory.py::test_no_bare_date_fromisoformat` asserts zero bare `date.fromisoformat(` calls survive in production modules. It PASSED (2 passed in 25.45s) while `entrypoints/cli/_common.py::_parse_iso_date` called `date.fromisoformat` directly - because that module imports `from datetime import date as _date` and calls `_date.fromisoformat(...)`, and the gate's AST helper `_fromisoformat_call_linenos` requires `func.value.id == "date"`. Any aliased import evades the gate silently. Confirmed empirically by the agent that fixed the call site (commit 57f8711287), not inferred.

2. `src/cadrumo/tests/test_wizard_prompter_singularity.py` enforces one live prompt authority tree-wide, but its detection rule keys on a DIRECT `questionary` import. A rival prompter reaching questionary indirectly through a re-export would not trip it. Reported by the D3.3 searcher independently of finding 1.

These are the same defect: a gate whose pattern does not fit the data's possible shapes returns a clean negative that reads as proof of compliance. Every "this surface is single-homed" claim backed by such a gate is unverified until the gate itself is checked against an aliased or indirect form. Remediation is to make the AST checks alias-aware and binding-aware (resolve import aliases, follow re-exports), and to add a self-test per gate that plants an aliased violation and proves the gate catches it - a gate with no anti-tautology proof cannot be trusted.

Audit implication: the whole class of AST-based structural gates in this repo needs the same review - the modelo-string-literal gate, the lazy-import policy gate, the import-hygiene scanner, the duplication runner, and the prompter-singularity gate all pattern-match names.

### refuted-2-dual-binding-validator-convention | info | the premise is false; the raise-style helpers are invariant bodies, not dead siblings

REFUTED 2 - "dual binding-validator convention still live" (was D1-1). Verdict: the premise is false. The four raise-style `validate_ledger_<family>_aggregation_binding_definition` functions are NOT uncalled siblings - they are the invariant bodies the registered accumulating validators delegate to, each via `return invariant_diagnostics(binding, "<family>", <raise-style check>)` at _ledger_bindings.py:1376, :1389, :1422, :1439. `invariant_diagnostics` (_binding_selector_utils.py:306-324) runs a raise-style check, catches RegistryValidationError, and converts it to one accumulating diagnostic string, so the `list[str]` never-raise contract is intact end to end. This two-layer shape is the norm, not a ledger anomaly: 15 of 24 dispatch entries use it (counterpart, invoice, the four detail-record families, donativo, previous-filing, irnr, impatriado, renta_expense), and `_BINDING_VALIDATOR_REGISTRY` holds exactly one accumulating entry per BindingSourceKind. Deleting the four would have deleted the op/fact enforcement itself - sum-only aggregation op, closed fact set, casilla scoping - a genuine under-validation regression. Gates: 83 passed sequential on the targeted binding suites, 3019 passed parallel across the whole registry test tree. Nothing changed, no commit.

### expense-gasto-source-kind-naming-not-a-duplicate | medium | not duplication, but a real and larger naming defect on both stems

ADDENDUM - EXPENSE/GASTO SOURCE KINDS: not duplication, but a real and larger naming defect. Verdict from a full investigation against HEAD.

NOT A DUPLICATE, and structurally proven so. The two source kinds are disjoint by modelo and the disjointness is ENFORCED, not conventional: `_RentaLedgerExpenseSelector.modelo: Literal[Modelo.M100]` (registry/_ledger_bindings.py:680) versus `_RentaLedgerGastoSelector.modelo: Literal[Modelo.M130]` (:1267), with disjoint casilla domains (`_RENTA_100_FIRST_SLICE_CASILLAS`, 14 boxes, versus `_RENTA_130_GASTO_CASILLAS = {"02"}`). Registry-build validation refuses any binding that would cross them. Token map: `ledger_renta_expense_aggregation` appears only in M100 revisions 2024 and 2025 (28 binding files, 14 casillas x 2 years); `ledger_renta_gasto_aggregation` only in M130 `2019-y-siguientes` (1 binding, casilla 02).

The observations also diverge hard, so a collapse was never available: M100's `RentaDeductibleExpenseObservation` (domain/renta/_ledger_expenses.py:206) carries 27 fields, is category-routed SpendingCategory->CasillaId, and holds proportionality_kind / applied_ratio / invoice_evidence_status / reconciliation_status / legal_references, produced by `evaluate_renta_deductibility` against a CategoryProfile plus usage ratios, statutory caps, exclusive-use and residence CCAA, on an annual `0A` window. M130's `RentaGastoObservation` (application/aggregation/_renta_gasto_ledger.py:103) carries 4 fields: a flat taxable_base x business_proportion projection, no category axis, one fixed casilla, cumulative quarterly window. Forcing the 4-field path through 27-field constraints would have been the harm.

THE DEFECT THAT IS REAL, and it is broader than the sweep stated. The split is already deliberate and documented in three places (core/aggregation.py:252-261, which itself cites the Spanish-stem rule; registry/_ledger_bindings.py:1221-1231; application/aggregation/_renta_gasto_ledger.py:28-31) - so this is not forgotten cleanup. What survives is that BOTH names are wrong: the M100 token is English-stemmed, AND bare `gasto` on the M130 token is ambiguous, because the M100 first-slice boxes are gastos too - casilla 0203 is literally labelled "Gastos financieros" and all 14 sit under section ["rendimientos_actividades_economicas", "estimacion_directa"]. Renaming only the English one would leave the trap half-set.

Grandfathering question, resolved: `aeat-spanish-stem-naming` states that already-public pre-rule identifiers keep their names, and the M100 token predates the rule (ADR 2026-05-08 versus the rule of 2026-06-02), so the rename was discretionary rather than mandated. Operator directive overrides that clause - a Spanish/English pair naming one concept family is not acceptable - so both tokens are to be renamed, using vocabulary sourced from the registry itself: M100 -> `ledger_renta_gastos_estimacion_directa_aggregation` (the section tag on all 14 casillas), M130 -> `ledger_renta_gastos_pago_fraccionado_aggregation` (the AEAT term for M130).

HARD CONSTRAINTS on the rename. Enum VALUES must stay byte-identical to the tokens stored in registry TOML, so the enum and the authoring tree move in ONE commit or not at all - a partial sweep is strictly worse than nothing here, because the registry validates the whole working tree on load and a half-swept tree breaks suite collection for every concurrent agent. Both new tokens MUST retain the `ledger_` prefix: `LEDGER_BINDING_SOURCE_KINDS` (core/aggregation.py:420) is derived via `source.value.startswith("ledger_")` - correctly derived rather than hand-listed, which answers the parity question, but a prefix change would silently drop the kind out of ledger-readiness routing and fail OPEN.

FULL RENAME SURFACE, for whoever executes: registry/_ledger_bindings.py (67 sites), application/aggregation/_modelo_bindings.py (27), registry/_bindings.py (20, including the selector-model dispatch table at :869/:871 and the validator dispatch table at :959/:961, both keyed by the enum member), registry/__init__.py (12), 29 registry TOML files, core/aggregation.py, _source_mesh.py, _calculation_source_policy.py, _calculation_preparation.py, _modelo_discovery_cli.py, domain/renta/_ledger_expenses.py and _first_slice_routing_integrity.py, roughly 15 test modules, and 6 docs/_sequences/*.json recorded-output contracts which must be REGENERATED rather than hand-edited.

STANDALONE DEFECT AND RENAME TRAP, found independently: domain/renta/_ledger_expenses.py:39 and :210 hardcode `LEDGER_RENTA_EXPENSE_SOURCE = "ledger_renta_expense_aggregation"` as a raw string literal plus a `Literal[...]` annotation instead of deriving from `BindingSourceKind`.
