## Findings

### selection-change-retires-the-agent-tree | medium | Changing a tax role's model tears down the person's running agent tree and its in-flight reply.

The selections record is written under the same `provider-settings` capability as the credential records, at `src/cadrumo_agent_service/providers/persistence/store.py:39` and `:41`, so a commit moves the capability-wide records generation that `observe_generations` reports as the provider-settings generation (`src/cadrumo_agent_service/providers/persistence/store.py:198`). `AgentService._change_model_roles` then calls `_replace_superseded` unconditionally (`src/cadrumo_agent_service/service.py:390`), `AgentHostController.superseded` compares the live generations against the ones the ready tree started under (`src/cadrumo_agent_service/host/controller.py:294`), and the scheduled start retires that tree through `_retire`, which closes the agent's input, allows its grace and then terminates the whole tree (`src/cadrumo_agent_service/host/controller.py:384`). Selecting a model for the text-extraction role therefore ends an unrelated chat conversation's streaming reply. Nothing here breaks the letter of an accepted constraint: constraint 9 of `2026-10-13-provider-settings-adr` enumerates the teardown triggers as security events including a credential-generation change, and the new ADR's constraint 6 authorises storing the selection in the per-profile provider settings, so the coupling follows from an authorised placement rather than from unauthorised scope. It is unrecorded, and `P05.S24` will put the control in front of the person and make it routine. The fix is to key the restart trigger on the credential-bearing records only, so that a non-secret selections write forgets the kept reads without superseding the tree; the generation the agent was started under does not carry the selection, which the service reads per run.

### selections-read-decrypts-every-lane-credential | medium | A non-secret listing decrypts one stored API key and refetches the agent catalogue per role.

`ModelRunService.selections` loops the role vocabulary and calls `_resolve` for each (`src/cadrumo_agent_service/providers/application/model_runs.py:105`), and `_resolve` calls the credential resolver (`src/cadrumo_agent_service/providers/application/model_runs.py:148`) purely to learn whether the lane is unavailable; the resolution's credential material is discarded. Each resolve performs its own record read (`src/cadrumo_agent_service/providers/application/resolution.py:227`), which decrypts that lane's SECRET record and builds its secret value, and `_resolve` then calls the gateway's `accepted_media` (`src/cadrumo_agent_service/providers/application/model_runs.py:152`), which is a fresh provider-catalog GET to the agent gateway on every call (`src/cadrumo_agent_service/adapters/agent_background_runs.py:123`). One selections read for a fully configured profile therefore decrypts four credential records and issues four identical loopback catalogue fetches to answer a read whose own docstring says nothing in it is secret. The test pins the selections record to one read (`src/cadrumo_agent_service/providers/application/tests/test_model_runs.py:293`) but bounds neither the credential reads nor the gateway calls, so the record is read once while the credential and media state is read per role and can disagree inside one answer. Resolve each distinct lane and its accepted media once per selections read and reuse the result across the roles that name it.

### gate-stops-short-of-three-file-kinds | medium | The model-definition gate scans no Rust, TypeScript or environment template, and no later Step adds those rows.

Constraint 1 of `2026-10-25-agent-owned-models-adr` requires that no model name, digest, size, licence, default, candidate list or ranking exist in any Cadrumo language or file kind, naming Python, Rust, TypeScript, data files, settings defaults and environment templates. `dev/quality/tests/test_no_model_definitions.py:18` states its stop honestly, Python under the five `src` packages plus TOML under `src/cadrumo/_data/dependencies`, with the Rust engine, the desktop and `dev/` out of scope, and its three rows each catch a representative defect in an isolated fixture and pass a representative clean module (`dev/quality/tests/test_no_model_definitions.py:217`), which is what `P01.S07` asked for. The gap is forward: `P03.S18` and `P05.S28` only shrink the burn-down list, and no Step adds a row for `native/application`, `native/desktop` or `env/.env.example`, the three places the ADR's own problem statement names as carrying duplicated pins today. The size and licence axes are ungated in every scanned language as well. Once `P04` strips the Rust pins, nothing prevents their return. Extend the gate's roots and name the added rows in the Step that empties the burn-down list.

### unreadable-record-without-a-revision-cannot-be-reset | low | An unreadable selections record whose read carries no revision has no recovery route.

`_selections_status` projects an unreadable record with the read's own revision (`src/cadrumo_agent_service/providers/application/service.py:519`), which `UnreadableModelRoleSelections` allows to be absent (`src/cadrumo_agent_service/providers/application/ports.py:78`) whenever the runtime's reply is present but revisionless or carries an unexpected state (`src/cadrumo_agent_service/providers/persistence/store.py:113`). `reset_model_roles` requires a 64-hex guard (`src/cadrumo_agent_service/providers/application/service.py:351`), so in that state every role refuses as lane-unavailable and no API call can clear the record. The desktop surfaces the state faithfully as an unreadable snapshot with no guard (`native/desktop/src-tauri/src/agent/model_roles.rs:99`). The shape is inherited from the provider records, whose reset carries the same guard, so this is a pre-existing pattern rather than a regression; it is worth closing for both at once rather than for the selections record alone.

### unknown-role-reads-as-no-selection | low | A role outside the vocabulary refuses NO_SELECTION rather than naming an unknown role.

`ModelRunService.lookup` maps an invalid role onto the no-selection code (`src/cadrumo_agent_service/providers/application/model_runs.py:95`), and a test fixes that behaviour (`src/cadrumo_agent_service/providers/application/tests/test_model_runs.py:168`). It fails closed and matches the amended constraint 7's wording, so nothing is unsafe, but a caller that sends a misspelled role is told the person has not configured it, which points the operator at the selection surface for a defect in the caller. The closed refusal set has no room for this today; naming it is a wire change, so it belongs with `P05.S25` if it is taken at all.

## Recommendations

- Reopen `P01.S03` for the first finding, or carry it as an explicit consequence. The decision a follow-on ADR must make, if the owner prefers the current behaviour: whether a non-secret per-profile setting stored beside the credentials participates in the agent tree's generation binding, or whether that binding covers credential-bearing records only. This review does not make that choice.
- Resolve lanes and accepted media once per selections read, for the second finding. This is within `P01.S02`'s file ownership and needs no new authority.
- Name the gate's added roots and rows in `P05.S28` rather than leaving Rust, TypeScript and the environment templates permanently ungated, for the third finding.
- The two low findings are recorded, not scheduled. The unreadable-without-revision route should be closed for the provider records and the selections record together, which is outside this plan's scope.
- Observation rather than a finding: the selections port added by `S04` has no shipped-entrypoint reader yet. `P05.S25` is its consumer, and `dev/runtime_lifecycle/tests/test_service_model_run_relay.py` exercises it meanwhile. This is planned preparation, unlike the hosted-tier table `S06` deleted for having no reader at all.
