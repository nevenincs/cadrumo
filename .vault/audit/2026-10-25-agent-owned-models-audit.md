## Findings

### selection-change-retires-the-agent-tree | medium | Changing a tax role's model tears down the person's running agent tree and its in-flight reply.

The selections record is written under the same `provider-settings` capability as the credential records, at `src/cadrumo_agent_service/providers/persistence/store.py:39` and `:41`, so a commit moves the capability-wide records generation that `observe_generations` reports as the provider-settings generation (`src/cadrumo_agent_service/providers/persistence/store.py:198`). `AgentService._change_model_roles` then calls `_replace_superseded` unconditionally (`src/cadrumo_agent_service/service.py:390`), `AgentHostController.superseded` compares the live generations against the ones the ready tree started under (`src/cadrumo_agent_service/host/controller.py:294`), and the scheduled start retires that tree through `_retire`, which closes the agent's input, allows its grace and then terminates the whole tree (`src/cadrumo_agent_service/host/controller.py:384`). Selecting a model for the text-extraction role therefore ends an unrelated chat conversation's streaming reply. Nothing here breaks the letter of an accepted constraint: constraint 9 of `2026-10-13-provider-settings-adr` enumerates the teardown triggers as security events including a credential-generation change, and the new ADR's constraint 6 authorises storing the selection in the per-profile provider settings, so the coupling follows from an authorised placement rather than from unauthorised scope. It is unrecorded, and `P05.S24` will put the control in front of the person and make it routine. The fix is to key the restart trigger on the credential-bearing records only, so that a non-secret selections write forgets the kept reads without superseding the tree; the generation the agent was started under does not carry the selection, which the service reads per run.

### selections-read-decrypts-every-lane-credential | medium | A non-secret listing decrypts one stored API key and refetches the agent catalogue per role.

`ModelRunService.selections` loops the role vocabulary and calls `_resolve` for each (`src/cadrumo_agent_service/providers/application/model_runs.py:105`), and `_resolve` calls the credential resolver (`src/cadrumo_agent_service/providers/application/model_runs.py:148`) purely to learn whether the lane is unavailable; the resolution's credential material is discarded. Each resolve performs its own record read (`src/cadrumo_agent_service/providers/application/resolution.py:227`), which decrypts that lane's SECRET record and builds its secret value, and `_resolve` then calls the gateway's `accepted_media` (`src/cadrumo_agent_service/providers/application/model_runs.py:152`), which is a fresh provider-catalog GET to the agent gateway on every call (`src/cadrumo_agent_service/adapters/agent_background_runs.py:123`). One selections read for a fully configured profile therefore decrypts four credential records and issues four identical loopback catalogue fetches to answer a read whose own docstring says nothing in it is secret. The test pins the selections record to one read (`src/cadrumo_agent_service/providers/application/tests/test_model_runs.py:293`) but bounds neither the credential reads nor the gateway calls, so the record is read once while the credential and media state is read per role and can disagree inside one answer. Resolve each distinct lane and its accepted media once per selections read and reuse the result across the roles that name it.

### gate-stops-short-of-three-file-kinds | medium | The model-definition gate scans no Rust, TypeScript or environment template, and no later Step adds those rows.

Constraint 1 of `2026-10-25-agent-owned-models-adr` requires that no model name, digest, size, licence, default, candidate list or ranking exist in any Cadrumo language or file kind, naming Python, Rust, TypeScript, data files, settings defaults and environment templates. `dev/quality/tests/test_no_model_definitions.py:18` states its stop honestly, Python under the five `src` packages plus TOML under `src/cadrumo/_data/dependencies`, with the Rust engine, the desktop and `dev/` out of scope, and its three rows each catch a representative defect in an isolated fixture and pass a representative clean module (`dev/quality/tests/test_no_model_definitions.py:217`), which is what `P01.S07` asked for. The gap is forward: `P03.S18` and `P05.S28` only shrink the burn-down list, and no Step adds a row for `native/application`, `native/desktop` or `env/.env.example`, the three places the ADR's own problem statement names as carrying duplicated pins today. The size and licence axes are ungated in every scanned language as well. Once `P04` strips the Rust pins, nothing prevents their return. Extend the gate's roots and name the added rows in the Step that empties the burn-down list.

### unreadable-record-without-a-revision-cannot-be-reset | low | An unreadable selections record whose read carries no revision has no recovery route.

`_selections_status` projects an unreadable record with the read's own revision (`src/cadrumo_agent_service/providers/application/service.py:519`), which `UnreadableModelRoleSelections` allows to be absent (`src/cadrumo_agent_service/providers/application/ports.py:78`) whenever the runtime's reply is present but revisionless or carries an unexpected state (`src/cadrumo_agent_service/providers/persistence/store.py:113`). `reset_model_roles` requires a 64-hex guard (`src/cadrumo_agent_service/providers/application/service.py:351`), so in that state every role refuses as lane-unavailable and no API call can clear the record. The desktop surfaces the state faithfully as an unreadable snapshot with no guard (`native/desktop/src-tauri/src/agent/model_roles.rs:99`). The shape is inherited from the provider records, whose reset carries the same guard, so this is a pre-existing pattern rather than a regression; it is worth closing for both at once rather than for the selections record alone.

### unknown-role-reads-as-no-selection | low | A role outside the vocabulary refuses NO_SELECTION rather than naming an unknown role.

`ModelRunService.lookup` maps an invalid role onto the no-selection code (`src/cadrumo_agent_service/providers/application/model_runs.py:95`), and a test fixes that behaviour (`src/cadrumo_agent_service/providers/application/tests/test_model_runs.py:168`). It fails closed and matches the amended constraint 7's wording, so nothing is unsafe, but a caller that sends a misspelled role is told the person has not configured it, which points the operator at the selection surface for a defect in the caller. The closed refusal set has no room for this today; naming it is a wire change, so it belongs with `P05.S25` if it is taken at all.

### catalogue-bounds-narrower-than-upstream | medium | Three upstream-legal values make Cadrumo refuse the whole provider catalogue.

`CatalogModelFacts.size_bytes` is `PositiveInt` (`src/cadrumo_agent_service/providers/domain/catalog.py:181`), but cadrumo-agent declares and serves `size_bytes` with `ge=0` (`src/cadrumo_agent/providers/declared_catalog.py:175`, `src/cadrumo_agent/api/schemas/provider_catalog.py:149`). Cadrumo bounds a model id at 256 characters (`catalog.py:33`, `:177`) where upstream allows 512 (`src/cadrumo_agent/providers/provider_catalog.py:107`), and the lane count at 64 (`catalog.py:27`, `:318`) where upstream allows 128 (`provider_catalog.py:109`). Because the parser validates the document whole, one such value in any lane refuses the entire catalogue. Every lane's provider settings, selections and runs then become unavailable, not just the lane that carries the value. This review reproduced it on the agent's real declared document: setting one Ollama model's size to 0, or one hosted model id to 300 characters, each made `parse_provider_catalog` raise `CoreValidationError`. The same narrower size bound in the live read (`src/cadrumo_agent_service/adapters/served_catalog_models.py:63`) silently drops the lane's live catalogue. It fails closed and the current document parses, so nothing is unsafe. Fix: align the parser to the upstream bounds, using a non-negative size and the upstream id and lane limits. A model id the selection wire cannot carry (`src/cadrumo_agent_service/providers/domain/record.py:179`) should be refused at selection for that model only. Also make `ModelRunLane.size_bytes` non-negative (`src/cadrumo_client/contracts/model_runs.py:129`).

### non-evidence-off-host-runs-always-refused | medium | The service requires consent for every off-host run, but the tax side binds consent only for evidence, and the test double hides the mismatch.

`ModelRunService.run` refuses `consent_missing` for any run without a binding on a lane that reads off-host (`src/cadrumo_agent_service/providers/application/model_runs.py:180`). The tax dispatch gate lets a request that is not evidence-derived through with no token (`src/cadrumo/adapters/outbound/llm/client.py:858`). It then builds the binding only from an evidence-derived token (`client.py:1082`, `agent_consent_binding` in `src/cadrumo/adapters/outbound/llm/consent.py`). Such a request, for example the public-corpus readers at `src/cadrumo/adapters/outbound/llm/evidence_draft_text.py:351` and `evidence_draft_vision.py:293`, therefore always fails `consent_missing` on every hosted lane. The tax side surfaces this as an `LLMConsentError` the person cannot satisfy. Nothing leaves the host, so this is not a consent breach. However, the two halves disagree about what consent covers, and ADR constraint 4 ties the token to the digest-bound evidence consent. The recording service the client tests use does not apply the rule (`src/cadrumo/adapters/outbound/llm/tests/model_run_support.py:77`). As a result, `test_a_completed_run_returns_the_reply_and_names_the_lane_that_served_it` asserts success for a consent-less run on an off-host lane (`src/cadrumo/adapters/outbound/llm/tests/test_agent_dispatch.py:88`), which the real service refuses. Fix: settle which runs need a binding. Either the header carries whether the body is evidence-derived and the service requires consent only then, or the tax side refuses a non-evidence off-host dispatch before lookup. Then make the recording double enforce the same rule, so the client tests cannot pass on a path the service refuses. Today only development public-corpus callers reach this path, but `P03` routes every reader through it.

### lookup-does-not-reapply-the-role-rules | low | A stale vision-role selection resolves at lookup even when the current entry no longer marks it vision-capable.

`selection_refusal` applies the runnable, vision-input and vision-entry rules only when the person selects (`src/cadrumo_agent_service/providers/application/model_role_selections.py:75`, `:80`). At lookup, `_LaneAnswers.answer` checks only that the current entries still list the model (`src/cadrumo_agent_service/providers/application/model_runs.py:223`). Live facts win over declared ones (`src/cadrumo_agent_service/providers/application/lane_entries.py:28`). A vision-role selection made against a declared `vision: true` entry therefore still resolves when the running agent's live entry says false or null, and the lookup reply carries `vision` false for the vision role. Upstream backstops this: the agent refuses an image for an Ollama model that reads none (`src/cadrumo_agent/providers/background_inputs.py:112`), and a non-runnable lane is refused `background_lane_unsupported`. So the effect is a later and less specific refusal, not a wrong read. Fix: run `selection_refusal` against the current entries at lookup, and refuse a role the selection no longer serves with the same code as a stale model.

### refusal-mapping-gaps | low | Some upstream run-start refusals that mean an unusable lane read as a failed run.

`_REFUSALS` (`src/cadrumo_agent_service/adapters/agent_background_runs.py:64`) maps the background-admission codes and `provider_not_selectable`, `provider_unavailable`, `unknown_model` and `model_not_installed`. It does not map the rest of the upstream `SelectionErrorCode` set (`src/cadrumo_agent/providers/selection.py:91`). `provider_not_executable` (`src/cadrumo_agent/api/routes/_gateway_run_start.py:211`, `:363`) and `unknown_provider` describe a lane that cannot run, but they reach the tax side as `run_failed`, a provider error, instead of the configuration refusal `lane_unavailable`. A busy agent's 503 admission refusal carries a bare string detail (`_gateway_run_start.py:732`), so `_refusal_code` reads no code (`agent_background_runs.py:352`) and the busy agent also reads as `run_failed` rather than `service_unavailable`. Every case fails closed and is not retried. Fix: map `provider_not_executable` and `unknown_provider` to `lane_unavailable`, and map a 503 start to `service_unavailable`. `model_required` and the effort codes cannot arise from a background request that names a model and no effort, so they can stay unmapped.

### keyless-lane-shows-the-wrong-address | low | The desktop shows the agent's default Ollama address, not the supervised one the agent is launched against.

For a keyless lane the provider row shows `provider.defaultBaseUrl` (`native/desktop/frontend/src/components/settings/ProviderSettings.tsx:290`). That is the catalogue's declared default, which for the agent's Ollama lane is port 11434. The service launches the agent with `CADRUMO_AGENT_OLLAMA_BASE_URL` set to the supervised `LOCAL_AI_SERVER_ADDRESS` (`src/cadrumo_agent_service/host/launch_environment.py:71`, `:287`; `src/cadrumo/core/config_runtime_fields.py:20`). The person is therefore shown an address no run uses. Fix: show no address for a keyless lane, or project the supervised address the service launches with into the status entry.

### three-catalogue-reads-per-run | low | One run reads the agent's served catalogue up to three times, with no shared snapshot.

Deciding a lane fetches the served catalogue for accepted media (`src/cadrumo_agent_service/adapters/agent_background_runs.py:149`) and again for the live entries (`src/cadrumo_agent_service/service.py:744`). Starting the run fetches it a third time for the honoured options (`agent_background_runs.py:181`). Each read is up to 256 KiB over loopback. The tax side's own lookup repeats the first two. The reads are separate snapshots, so one run's media, entries and options can come from different agent generations. The effect is bounded, because the agent re-checks each at admission. Fix: read the served document once per lookup or run and derive all three from it.

### operator-endpoint-measures-another-server | medium | The Ollama endpoint override still steers status and load admission, but no run goes there.

`cadrumo_llm_ollama_chat_url` (`src/cadrumo/core/config_runtime_fields.py:27`) was the direct adapter's dispatch address. After `S15` its only readers are probes: the local-reader status and readiness read the installed inventory through `local_ai_settings` (`src/cadrumo/application/local_reader.py:115`), the program row and the host probe read it (`src/cadrumo/application/provisioning_host.py:153`, `:204`), and the client's headroom check reads the resident set from it when it measures contention (`src/cadrumo/application/provisioning_runtime.py:68`, `:117`, reached from `src/cadrumo/adapters/outbound/llm/client.py:597`). Every local run, though, goes through cadrumo-agent, which the service always launches against the managed address (`src/cadrumo_agent_service/host/launch_environment.py:71`, `:287`). With an operator endpoint configured, which `uses_managed_local_ai` still honours (`src/cadrumo/core/component_records.py:385`), the status reports a model installed or missing on one server, and admission measures residents on that server, while the run loads on the other. The ADR's amendment to rust-provisioning constraint 7 makes the managed server the one the agent's `ollama` provider connects to, so the setting no longer has a dispatch meaning. Its description still promises one ("override for non-localhost Ollama deployments"). The fix is either to retire the override, so every probe reads the managed server, or to launch the agent against the same configured address. Choosing to keep an operator-run server is a follow-on decision. Nothing leaves the host and the run itself is unaffected, but the readiness and contention answers can describe a server that serves no run.

### model-names-and-local-only-wording-remain | medium | Shipped docstrings and the `--vision-model` help still name models and describe the deleted local path.

Constraint 1 forbids a model name in any Cadrumo file kind. `src/cadrumo/application/ledger/llm_classification.py:479`, `:790` and `:1192` document `vision_model` as overriding the settings default local vision model, for example `qwen2.5vl:7b`. `src/cadrumo/application/provisioning_runtime.py:134` illustrates name matching with `qwen3` tags. The `--vision-model` help in all four locales names `qwen2.5vl:7b` and says it defaults to the configured model (`src/cadrumo/locales/en/cli.yml:3085`, with the same key in `es`, `ca` and `hu`). The model-definition gate passes because its documented stop excludes docstrings and does not scan YAML (`dev/quality/tests/test_no_model_definitions.py:18`). The wording is also wrong now, not just non-compliant. `resolve_llm_evidence` says a scan or image is read by the local Ollama vision model, needing no cloud consent (`llm_classification.py:205`). In fact it goes to the person's selected vision lane, which refuses without consent when that lane reads off-host. The option it documents as an override is refused (`src/cadrumo/entrypoints/ledger_llm_composition.py:65`), and `:291` still cites the deleted provisioning probe. The help keys go when `P05.S25` removes the option, but no Step owns the Python docstrings. Reword them in place, without a model name, and have `P05.S28` decide whether the gate's stop extends to docstrings and the locale catalogues.

### reviewed-operation-lane-cannot-prove-the-review | medium | The reviewed-operation lane now gates on a model in the store, but the review needs an admitted agent service with a selection.

`S18` changed the lane to proceed whenever the Ollama store it serves on port 11434 holds any model (`dev/runtime_lifecycle/mcp_proof_support.py:254`). Its docstring says that is the prerequisite (`dev/runtime_lifecycle/reviewed_operation.py:24`). The review it then submits, `ledger.classify.review`, reaches a model only through the profile's admitted agent service and the person's text-role selection. The lane admits no service and stores no selection. Even with both present, the agent would read from the managed server, not the lane's port 11434 (`src/cadrumo_agent_service/host/launch_environment.py:71`). With a model present, the review therefore ends with a `service_unavailable` or `no_selection` refusal. The lane reads that as a contradicted step (`reviewed_operation.py:179`), not as unproven. A product that behaves as designed will fail the acceptance lane. Fix: until a selection surface exists (`P05.S25`), record the review as unproven when it refuses for an absent service or selection. Afterwards, admit the service, store a selection and serve the model on the managed address.

### vision-model-refused-only-on-image-reads | low | `--vision-model` is refused only when the read reaches the vision path.

Ruling (f) has the option refuse with a typed condition. The refusal is built only inside `make_vision_classifier` (`src/cadrumo/entrypoints/ledger_llm_composition.py:248`). That is reached only when the evidence is images (`src/cadrumo/application/ledger/llm_classification.py:296`, `:370`). A classify with `--vision-model` on a text-layer document, or with no linked evidence, succeeds and silently ignores the option. It fails safe, since no model is chosen by the name. But the operator gets no signal that the option no longer means anything. Refuse at the command boundary whenever the option is present, or carry this until `P05.S25` removes it.

### batch-consent-refusal-closes-no-role | low | A batch on an off-host text or vision lane refuses every document one by one rather than pausing the role.

The batch never carries consent, so on a lane whose entry reads off-host the client's gate refuses each document with `EVIDENCE_OFF_HOST_DISPATCH_PERMITTED` (`src/cadrumo/adapters/outbound/llm/client.py:821`). That verdict has no `model_run_refusal` fact and no role, so `_reader_refusal_role` closes nothing (`src/cadrumo/application/ledger/batch_ingest.py` `_InferenceLaneState.close_on_refusal`). Every later document of the role is attempted and refused for the same role-level reason. `src/cadrumo/entrypoints/tests/test_evidence_batch_reader_lane.py:99` fixes this as intended, and nothing leaves the host, so this is not a consent defect. However, a batch-wide configuration condition reads as N document refusals instead of one pause naming the role, and each attempt costs a lookup round trip. Consider having the consent gate state the role, so the batch pauses the role as it does for a model-run refusal.

## Recommendations

- Reopen `P01.S03` for the first finding, or carry it as an explicit consequence. The decision a follow-on ADR must make, if the owner prefers the current behaviour: whether a non-secret per-profile setting stored beside the credentials participates in the agent tree's generation binding, or whether that binding covers credential-bearing records only. This review does not make that choice.
- Resolve lanes and accepted media once per selections read, for the second finding. This is within `P01.S02`'s file ownership and needs no new authority.
- Name the gate's added roots and rows in `P05.S28` rather than leaving Rust, TypeScript and the environment templates permanently ungated, for the third finding.
- The two low findings are recorded, not scheduled. The unreadable-without-revision route should be closed for the provider records and the selections record together, which is outside this plan's scope.
- Observation rather than a finding: the selections port added by `S04` has no shipped-entrypoint reader yet. `P05.S25` is its consumer, and `dev/runtime_lifecycle/tests/test_service_model_run_relay.py` exercises it meanwhile. This is planned preparation, unlike the hosted-tier table `S06` deleted for having no reader at all.

- `P02` review: reopen `P02.S08` for `catalogue-bounds-narrower-than-upstream`, or take it as a routine correction within that Step. It needs no new authority.
- For `non-evidence-off-host-runs-always-refused`, a follow-on decision, as an amendment to the consent constraint of `2026-10-25-agent-owned-models-adr`, must settle whether an off-host agent run that carries no taxpayer evidence needs a consent binding. That choice decides whether the run header gains an evidence marker. Resolve it before `P03.S12` routes the readers through this path. This review does not make the choice.
- Close `lookup-does-not-reapply-the-role-rules` and `refusal-mapping-gaps` within `P02.S10` and `P02.S08` file ownership when convenient. `keyless-lane-shows-the-wrong-address` fits `P05.S24`, which already owns the desktop selection surface.
- Consequence, not a finding: with cadrumo-agent `821f4ff`, only `ollama_api` declares any model with `vision` true; every hosted lane's models state none. Under constraint 6 and the second amendment, the vision role is therefore selectable only on the local lane until the agent states vision for hosted models. The owner should know this before `P05` puts the control in front of the person.
- Observation: a lane whose entry says `reads_off_host` false is trusted even if its auth kind is a key and its base URL is https. Constraint 4 makes the flag authoritative, and upstream sets it false only for its loopback Ollama transport (`src/cadrumo_agent/providers/registry.py:215`).
