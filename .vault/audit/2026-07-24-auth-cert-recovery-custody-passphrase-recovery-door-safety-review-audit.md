# `auth-cert-recovery-custody` audit: `passphrase and recovery CLI door safety review`

## Scope

Independent, fresh-context safety review of the `P04` passphrase and recovery CLI door — `config passphrase change`, `config recovery status/create/rotate/verify`, and the flat `config recover` — its secure-input channels, its 24-word BIP-39 mnemonic display and no-echo retype-to-commit flow, and the recovery-key wrapping/unwrapping primitives underneath. This closes the asymmetry the campaign's own close-honesty review flagged: the sibling certificate-secret door (`P05`/`P07`) received a dedicated review (`2026-07-17-auth-cert-recovery-custody-audit`, verdict PASS); this door had not.

**Verdict: FAIL pending remediation.** One High finding blocks a clean PASS. Two Medium/Low findings are real but do not themselves block. Every other invariant this review checked held.

Every claim below is grounded in code read at HEAD (`9a8de9d40a`) and, where practical, in a freshly re-run gate rather than a cited number taken on trust: `test_config_recovery_lifecycle.py` (5 passed, matching its exec record exactly), `test_help_without_secrets.py` + `test_tty_error_locale.py` (22 passed, 1 unrelated failure — see below), `test_config_custody_profile_lifecycle.py -k passphrase` (1 passed, isolated re-run). The stdlib `getpass` module backing `prompt_secret_no_echo` was read directly from this project's own venv (`cpython-3.13.11-windows-x86_64-none/Lib/getpass.py`) rather than assumed from memory, since the finding below turns on its exact Windows-path source.

One unrelated failure surfaced while re-running gates and is excluded here per the standing full-tree-gate ownership discipline: `test_data_verb_still_refuses_without_passphrase` now fails because `app ledger list`'s refusal message leads with "No active profile" rather than citing `CADRUMO_SECRET_PASSPHRASE`. Tracing the message to its source (`src/cadrumo/entrypoints/cli/__init__.py`, the `No active profile` refusal path, and the new `config login` verb referenced alongside it) shows this is the concurrently in-flight `login-session`/profile-pointer campaign reordering session-bootstrap precedence, not this door. The anti-tautology guarantee itself is intact — the verb still refuses (`returncode != 0` still holds) — only the literal message-text assertion is stale. Four further failures in `test_config_custody_profile_lifecycle.py` (`No such command 'logout'`/`'switch'`, and a profile-selection-precedence count mismatch) are the same peer churn already identified and excluded in the prior close-honesty review; none touch a passphrase or recovery verb, and the isolated `-k passphrase` re-run above confirms the door's own round-trip test is unaffected.

## Findings

### getpass-windows-fallback-unguarded | high | The no-echo prompt inherits two unguarded Windows-specific `getpass` failure modes, neither of which is exercised by any test

`prompt_secret_no_echo` (`src/cadrumo/entrypoints/cli/_config/_secure_input.py:94-112`) guards only `sys.stdin.isatty()` before calling and `EOFError` after calling `getpass.getpass(prompt)`. On `win32`, `getpass.getpass` dispatches to `win_getpass` (confirmed live in this venv: `getpass.getpass.__name__ == "win_getpass"`), whose CPython 3.13.11 source (`Lib/getpass.py:96-115`, read directly from this project's own interpreter) has two properties this wrapper does not defend against:

1. `win_getpass` opens with `if sys.stdin is not sys.__stdin__: return fallback_getpass(prompt, stream)` (line 98). `fallback_getpass` prints "Warning: Password input may be echoed." to stderr and reads the value via `input.readline()` with terminal echo left ON (`Lib/getpass.py:119-125`). Any layer upstream of this project's own code that replaces `sys.stdin` — a wrapping terminal/pty layer, a supervising process, an IDE-integrated terminal, a library that normalises encoding by re-binding `sys.stdin` — silently downgrades every passphrase, recovery-code, and 24-word retype prompt from no-echo to echoed, while the module's own docstring promises "the typed value is never echoed." This project's own production code never reassigns `sys.stdin` (confirmed by grep across `entrypoints/` and `core/`), and a bare interpreter in this environment shows `sys.stdin is sys.__stdin__ == True`, so the normal `aeat` invocation path is not demonstrated to trigger this — but the check the wrapper performs (`isatty()`) does not detect or prevent it, so the guarantee rests entirely on no upstream layer ever doing this, which is not enforced anywhere.
2. `win_getpass` calls `msvcrt.putwch`/`msvcrt.getwch` directly (`Lib/getpass.py:102-115`) with no exception handling around either call. A terminal environment where the process has no attached native Win32 console — a real, common configuration for Windows terminal emulators built on pty/pipe layers rather than the native console subsystem — can make `msvcrt.getwch()` raise `OSError`, which propagates out of `win_getpass`, out of `getpass.getpass`, and out of `prompt_secret_no_echo` uncaught (only `EOFError` is caught). This is the same failure shape the coordinator flagged from earlier today's keychain-guard incident: an exception from a Windows-specific call outside the anticipated hierarchy. The project's global `command_error_boundary` sweep (`apply_command_error_boundary_recursively`, confirmed applied to the full Typer tree including `_config`) does catch this as a last resort and wraps it in `CliUnexpectedBoundaryError` rather than letting a fully raw traceback reach the operator — so this is not a full crash-to-raw-traceback defect — but it means the module's specific, promised "REFUSED, exit 2, localized" contract (e.g. `cli.config.custody.errors.non_interactive_secret_required`) does not fire; a generic unexpected-error path fires instead, giving the operator no actionable explanation that their terminal cannot support no-echo input.

Neither failure mode has any test coverage. Every existing proof of the create/rotate/passphrase-change/recover flow (`test_config_recovery_lifecycle.py`, `test_config_custody_profile_lifecycle.py`) drives the CLI through a subprocess with non-interactive stdin, which the `sys.stdin.isatty()` guard refuses before `getpass.getpass()` is ever reached (`P04.S28`'s own exec record discloses this: "the CLI create/rotate verbs are TTY-only by design, so the captured harness proves their refusal path"). The real `getpass.getpass()` call — the only place either failure mode can fire — has never executed under this project's test suite. Full live reproduction (typing a secret at a real degraded terminal and observing echoed characters) requires an interactive terminal this review's non-interactive harness cannot provide; that reproduction was not performed, and this finding should be read as code-level and stdlib-source-grounded rather than empirically observed end to end.

### no-audit-trail-for-passphrase-and-recovery-mutations | medium | The most sensitive custody mutations in the campaign emit zero bucket events

`change_passphrase`, `create_recovery_code`, `rotate_recovery_code`, and `recover_secret_store` (`src/cadrumo/application/user_profile/_custody.py`) mutate the file secret store's passphrase or its independent recovery capability — the two operations that directly govern access to everything else the vault holds — and none of them constructs or appends a `BucketEventType`. A grep of `src/cadrumo/domain/buckets/_event.py` finds no `RECOVERY` or `PASSPHRASE` member at all, and none of the custody-door files import any bucket-event append helper. This is asymmetric against this same campaign's own precedent: certificate secret set/remove (`P02`/`P05`) emits a crash-resumable, correctly-classified `AUTH_CERTIFICATE_SOURCE_SECRET_SET`/`_ROTATED`/`_REMOVED` event proven by a forced-failure-then-retry test, and auth logout/reset (`P01`) emits distinct events per the plan's own description. An operator (or an investigator after a suspected compromise) has no persisted, queryable trail of when a vault passphrase was rotated or a recovery code was created, rotated, or consumed — only whatever the operator happened to see printed to their terminal at the time, which is not durable evidence.

### recovery-plaintext-not-zeroised | low | Recovery-key and mnemonic material is carried in immutable `bytes`/`str` throughout, so it cannot use the substrate's own zeroise primitive

`master_key.zeroise()` (`_zeroise.py`) requires a mutable `bytearray` and is used to wipe the steady-state `BucketSession` KEK/DEK buffers on lock (`_bucket_session.py:402-403`, `_persisted_session.py:345/644/733`). `RecoveryKey.raw` (`_recovery.py:76`), the mnemonic `str`, the unwrapped master-key `bytes` returned by `unwrap_recovery_envelope`, and the live DEK read via `file_provider.get_master_key()` inside `_enroll_recovery` (`_recovery_facade.py:344`) are all plumbed as plain immutable `bytes`/`str` and never converted to a wipeable buffer, so none of them can be zeroised — Python's `bytes`/`str` immutability makes this architecturally impossible without first converting them. This is consistent with the substrate's own disclosed limitation (`_zeroise.py`'s docstring: "zeroisation in Python is best-effort... there is no portable Python primitive that can reach" transient `bytes` copies) rather than a new regression — but the exposure window is structurally wider here than on the `BucketSession` steady-state path, because a full-strength plaintext DEK exists as an unzeroisable `bytes` object on every single recovery mint, unwrap, and passphrase-change call, not only in an edge case.

### recovery-enrollment-manifest-flag-can-desync | low | A crash between the atomic envelope install and the profile-manifest flag write can leave the manifest stale, though the real source of truth is unaffected

`_enroll_recovery_code` (`_custody.py:172-187`) calls `operation(...)` (the atomic, verified recovery-envelope install) and only afterward, as a separate, non-atomic step, calls `_mark_active_profile_recovery_enrolled` to flip `recovery_enrolled=True` on the profile manifest. A process kill between the two leaves a genuinely-enrolled recovery envelope on disk while the manifest flag still reads `False`. This is functionally low-risk: `config recovery status` and `verify_recovery_code` read `recovery_status(path=...)` directly against the envelope file, never the manifest flag, so the operator-visible truth is unaffected — the manifest flag's only exposure is wherever it is read as a UI hint (not traced further in this review's scope) rather than as a security-relevant gate.

## Recommendations

Wrap the `getpass.getpass(prompt)` call in `prompt_secret_no_echo` with an explicit `except OSError` alongside the existing `except EOFError`, routing both to the same instructive `cli.config.custody.errors.non_interactive_secret_required` refusal, so a console-less terminal produces the module's own promised specific refusal rather than falling through to the generic unexpected-error path. Separately, add an explicit `sys.stdin is sys.__stdin__` check (or document why it cannot be checked) before calling `getpass.getpass`, refusing instructively rather than silently accepting the stdlib's echo-fallback — this is the one failure mode that leaks the secret itself rather than merely degrading the refusal message, and it is the one this finding rates High for. Add a real-behavior regression for both conditions rather than a monkeypatch: a subprocess launched with a genuine alternate stdin (a real OS pipe rather than a console handle) gives `sys.stdin is not sys.__stdin__` for free in that fresh interpreter, with no patching of the code under test, and exercises the actual `fallback_getpass` echo path; a subprocess spawned console-less (e.g. Windows `DETACHED_PROCESS`/`CREATE_NO_WINDOW` creation flags) gives a real `OSError` from `msvcrt.getwch()` with no patching either. Today neither condition is exercised by anything.

Add `BucketEventType` members for passphrase change and recovery create/rotate/recover, and emit them from `_custody.py` at the same commit point the corresponding operation durably completes, matching the crash-resumable event-emission shape the certificate-secret door already established in this campaign. Given these operations are inherently interactive (never automated-agent-retried the way `certificate secret set` is), the crash-resumable *retry* half of that precedent likely does not need duplicating — only the *audit-trail* half does.

The two Low findings do not need immediate action: the zeroisation gap is a pre-existing, disclosed, project-wide Python limitation rather than a new defect, and the manifest-desync window is cosmetic given the file-based source of truth. Note them so a future pass touching this surface does not re-introduce them as a false "already covered" assumption.
