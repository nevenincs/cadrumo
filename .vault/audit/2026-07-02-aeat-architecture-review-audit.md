# `aeat-architecture-review` audit: `high-level architecture review`

## Scope

High-level architecture review of the `aeat` package driven through vaultspec-rag
semantic search (production-biased sweeps with domain filters) plus targeted
read/grep confirmation. Surfaces reviewed: the bundled corpus and legal-grounding
layer, the registry authoring-to-snapshot pipeline, the calculation engine
(`_formula_runtime` and its graph helpers), the bindings/source-mesh framework
including cross-period and cross-modelo reference, the hexagonal layering
contracts (`.importlinter`), and the type-escape and module-size profile of the
production tree. No code was executed; conclusions rest on semantic discovery,
file reads, and the standing vault/audit record.

Scope extension (operator directive, same session): the data-persistence layer
(`adapters/persistence/` — the SQLite bucket database, the encrypted
secure-object substrate, envelope/blob/secret stores, master-key management,
and bucket layout) is audited as its own surface, and ALL deferrals surfaced
by this audit are promoted from observations into regression scope — each is
registered below with a concrete remediation shape and verification gate so
the audit is directly actionable.

### Baseline observations (healthy spine, for context)

The registry authority flow matches its ADRs: `ValidatedRegistryAuthority` is the
single production snapshot boundary, `select_revision` is the single
law-determined period-to-revision resolver, and an AST regression gate pins the
no-`revision_id`-injection ruling. The source mesh enforces exclusive binding
ownership at merge (`merge_source_resolutions` raises on duplicate owners across
all value channels), resolver enrollment is gated structurally, and relation
prefill is live on the operator calculate path. Type-system escapes are modest
and concentrated at genuine third-party boundaries (63 of 92 production
`dict[str, Any]` occurrences sit in the Google Sheets/Drive adapters; 50 `cast()`
calls are spread thin with no hot spot). These are non-findings recorded so the
findings below are read against an otherwise coherent spine.

## Findings

### hexagonal-inversion-deferred | high | Two hexagonal seams are blanket-waived: application→adapters wildcard and ~20 grandfathered domain→adapters production edges

The layered contract in `.importlinter` carries a blanket wildcard
`aeat.application.** -> aeat.adapters.**` ("full inversion would require a major
refactor and is deferred", sanctioned by the 2026-04-30 restructure ADR sec.
538). The wildcard makes the gate blind to every NEW application→adapters
coupling — the layer direction is unenforced on that seam, so erosion there is
invisible by construction. Separately, roughly twenty PRODUCTION domain modules
import the persistence substrate directly (`domain.modelos._repository`,
`domain.filing._repository`, `domain.transactions._repository`,
`domain.buckets._event_repository`, `domain.fincas._repository`,
`domain.submission._repository`, `domain.usage_ratios._service`,
`domain.modelos._participation_index`, and siblings), each individually pinned
as "full inversion (Protocol + adapter injection) deferred to a future
refactor". The per-domain-repository co-location is ADR-sanctioned
(secure-persistence-foundation series), but the aggregate is that the
domain layer has a standing structural dependency on `adapters.persistence`,
i.e. the hexagon's strongest invariant (domain purity) is the one with the
largest waiver set. Neither deferral is tracked by an open plan step; the
deferrals live only as comments inside the gate's exception ledger.

### import-gate-ledger-drift | medium | The .importlinter exception ledger is mechanically appended, duplicated, and misfiled — the gate audits the code but nothing audits the gate

The 815-line `.importlinter` shows unaudited mechanical growth: the
"Autogenerated additions for test-topology refactoring" block at lines 715-743
is duplicated verbatim at lines 744-772 (29 identical entries twice); the same
duplication pattern appears at lines 62-64 vs 144-147 and 214-221; and several
comment blocks describing contract N+1 (the S21, S22, S23 narrative headers)
physically sit inside contract N's `ignore_imports` list, so autogenerated
entries appended under them land in the wrong contract's exception set (e.g.
`test_referential_integrity_part1 -> aeat.application.diagnostics`, a
domain-not-application edge, is also registered under the no-renta-in-registry
contract). Every contract sets `unmatched_ignore_imports_alerting = warn`, so a
stale or misfiled entry never fails anything. Roughly 600 of the 815 lines are
ignore entries, the large majority test-file edges. The structural cause is the
interaction of two rules: tests live inside domain packages
(`tests-live-under-domain-tests-folders`) while roundtrip discipline mandates
real adapters, so every new roundtrip test manufactures a cross-layer edge that
must be hand-pinned — the ledger grows on every test campaign and nothing
ratchets it down.

### modelo-carveouts-in-generic-layers | medium | Per-modelo special cases accrete inside the generic engine and orchestrator with no declared extension surface

The generic layers carry named carve-outs for specific modelos: the domain
formula runtime (`_formula_runtime.py`) hard-codes M210 IRNR sentinel rate
values (negative in-band magnitudes that the application layer must rewrite
post-engine via `_rewrite_m210_sentinels` in `_verification_actions.py`) and an
`_M100_IMPUTATION_YEAR_DAYS` constant; the registry validator carries the M303
iva-wallet slot carve-out (`_IVA_WALLET_OWNED_RELATION_TARGET_BINDINGS` in
`_validate_relation_sources.py`); and the application orchestrator strips the
M303 compensation binding from the previous-filing resolver via
`_previous_filing_resolution_excluding_iva_compensation` in
`_calculation_actions.py` (with a function-local import of
`MODELO_303_IVA_COMPENSATION_BINDING_ID`). Each carve-out is individually
ADR-grounded and tested, but the aggregate pattern is that adding or hardening a
modelo can require editing generic domain/application modules rather than
extending a declared per-modelo surface. The M210 sentinel channel is the
sharpest instance: a domain engine emitting reserved negative Decimals that a
higher layer must recognise and rewrite is an implicit cross-layer contract
carried by convention (comments + one rewrite site), not by a type.

### calculation-orchestrator-hub | medium | `_calculation_actions.py` is the de-facto coordination hub for mesh enrollment, precedence, overrides, and exclusions

`src/aeat/application/modelo/_calculation_actions.py` (1,377 lines) owns the
live resolver-enrollment tuple, the caller-override rejection ladder (lock
sources vs carry sources, ADR ruling D2 extended), the novel-source-kind gate,
the unhandled-source diagnostics wiring, the M303 exclusion shim, and the
casilla-input validation — while its siblings `_verification_actions.py`
(1,710 lines, the largest production module in the package) and the registry
domain modules (`_applicability.py` 1,579, `_formula_runtime.py` 1,560,
`_schema.py` 1,472, `_loader.py` 1,400) form the size top-ten. None is
pathological in isolation, but the calculate/verify orchestrators are where
every cross-cutting ruling (precedence, exclusivity, carry, advisory surfacing)
is implemented as sequential inline guards; the precedence ladder exists only as
ordered code plus comments referencing ADR rulings, not as declared data the
way binding ownership is. New rulings keep landing here (the file is named in
three of the last month's ADR series), so the hub keeps thickening.

### legal-grounding-self-reference | medium | The corpus-faithfulness gate is structurally self-referential and its literals are triple-authored

`verify_legal_catalogue` validates each legal entry's `required_text` against
the bundled corpus excerpt — but the excerpt, the `required_text`, and the
per-article test pins are all authored by the same agent workflow, so the gate
proves internal consistency, not BOE faithfulness (the rule
`legal-grounding-verifies-bundled-authoritative-corpus` documents three
shipped defects from exactly this topology: the DT-32ª fabrication, the M210
art. 25.1.f staleness, and the menor-tres 3.000-vs-2.800 corpus figure error).
Architecturally the residual is twofold. First, there is no independent oracle
in the loop: nothing periodically reconciles the bundled corpus against live
BOE consolidated text, so corpus staleness is discovered incidentally, by
campaign. Second, the `required_text` tuples are duplicated a third time as
literals in per-article registry tests (`test_catalogue_verification*.py`,
per-modelo registry tests), so a legitimate corpus refresh must be swept
through TOML, HTML, and test literals in lock-step — maintenance weight that
grows linearly with grounding coverage and invites exactly the
wrong-figure-baked-into-test failure mode the rules already record once.

### core-resources-runtime-inversion | low | core/resources is the innermost layer only at import time; at runtime it loads domain packages

`aeat.core.resources._repos` reaches every domain package (registry, iva,
deadlines, manuals, normatives, user_profile, apoderamientos, categories)
through function-local deferred imports inside `Repository._load` /
`_resolve_authority`. This is ADR-sanctioned (resource-management-api ADR
2026-05-16, lazy loading per Q5) and each edge is individually pinned in the
core-not-outer contract, so it is recorded here as an accepted-risk
observation, not a defect: the module graph stays acyclic, but the runtime
dependency direction is core→domain, and `resources()` acts as a global
service-locator singleton that production application code reaches for
directly (e.g. `resources().modelos.authority` inside modelo actions). The
practical consequence is that "core has no outward knowledge" holds only
statically; any behavioural regression in a domain loader manifests inside a
core accessor, and test isolation of core requires the full domain tree.

### bundled-data-weight-unbudgeted | medium | The in-wheel data tree grew 311→516 MB with no size budget, and the wheel also ships every test module and fixture

`src/aeat/_data` now weighs 516 MB (265 MB `corpus/aeat_official`, 176 MB
`corpus/manuals`, 48 MB `registry`), up from the ~311 MB recorded by the
2026-05-16 corpus-registry-packaging audit — a +65% trajectory in about six
weeks with no declared ceiling and no gate that would notice the next doubling.
The hatchling wheel target is `packages = ["src/aeat"]` with no exclude, so the
installed wheel additionally carries `src/aeat/tests` (11 MB of fixtures
including the PDF corpus) and every per-domain `tests/` folder mandated by the
test-topology rule. Bundling the corpus is a deliberate ADR decision
(offline-verifiable legal grounding), and in-package tests are a deliberate
topology decision — but their composition means every taxpayer install pays
roughly half a gigabyte plus the full test surface, and the growth is
unmonitored. This compounds with the licence-clean shipping rule: the more the
bundled corpus grows, the larger the surface the licence discipline must cover.

### dual-registry-format-standing | low | The inline vs fragmented registry revision format split is permanent surface with no convergence plan

At least ten modelo revisions still declare bindings/formulas inline in
`revision.toml` (117, 126, 128, 187, 188, 194, 231, 361, both 369 schemas,
plus the M303 2009 revision documented in the rules) while 35 modelos use
fragmented subdirectories. The loader normalises both into one strict schema,
and the `registry-revision-content-inline-or-fragmented` rule now warns
assessors — that rule exists because the split already produced two wrong
"parse-only / not calc-grade" verdicts on real under-declaration defects. The
architectural point is that the mitigation is a discipline rule aimed at
humans and agents, not a structural fix: every future structural assessment
tool, audit sweep, and coverage script must implement both formats forever, or
the registry converges on one format and the hazard class is deleted. No plan
tracks convergence.

### bindings-framework-mid-consolidation | low | The bindings/cross-period framework is architecturally sound but carries three concurrent unification campaigns as in-flight state

The bindings framework's contracts (single validator dispatch, typed
aggregation ops, single source-kind taxonomy, provenance-at-parity, exclusive
mesh ownership) all landed via the 2026-06-14 hardening ADR and are gated. But
the vault shows the framework still mid-consolidation: binding-vocabulary CLI
cohesion (59%), binding-resolver contract unification (57%), and silent-zero
base aggregation (72%) are all open plans touching the same surface, and the
cross-domain continuity epic carries 206 alerts. This is recorded as review
context, not a defect: a reviewer or new agent reading the bindings surface
today sees three partially-applied target states, and the standing risk of
partially-landed unification is exactly the drift class the campaign-close
honesty-review rule exists for. The framework should not accrete new source
kinds or resolver conventions until the two contract-unification plans close.

### fanout-wildcard-hidden-application-edges | medium | The application→adapters wildcard hides 80 production modules' worth of coupling

Enumerating what the `aeat.application.** -> aeat.adapters.**` wildcard
suppresses: 80 production application modules import adapters directly,
spanning every application subpackage (`aggregation`, `auth`,
`bucket_maintenance`, `calculations`, `evidence`, `filing`, `inventory`,
`invoices`, `ledger`, `live`, and more). The dominant target is
`adapters.persistence.storage` (the secure-object substrate), with
`adapters.outbound.aeat.*` (sede/auth) second. This is not 80 defects — the
per-domain-repository and outbound-wiring patterns are sanctioned — but it is
the measured size of the seam the layered gate cannot see. Any future
inversion effort should know its denominator: 80 modules, not "a few wiring
sites".

### fanout-domain-adapter-inventory | medium | Twelve production domain modules bind to the persistence adapter, and `domain.fincas` already demonstrates the ports alternative in-tree

The full production domain→adapters inventory: `buckets._event_repository`,
`submission._repository`, `submission._engine`, `invoices._repository`,
`modelos._repository`, `modelos._filing_repository`,
`modelos._calculation_repository`, `modelos._verification_repository`,
`modelos._runtime_repository`, `modelos._participation_index`,
`modelos._protocols`, `transactions._repository`, `filing._repository`/
`_complementaria_repository`/`_runtime_repository`, `usage_ratios._service`
(≈40 files match adapter references; most imports are function-local inside
repository methods). The notable counter-example: `domain.fincas` no longer
imports the substrate — it declares `_repository_ports.py` and the concrete
implementation lives in `adapters.persistence.profile.fincas`. The
"full inversion deferred to a future refactor" comment is therefore
outdated in one important way: the target pattern is already proven and
shipping in this codebase; the remaining eleven domains have a worked
in-tree template to follow, and the `.importlinter` fincas entries
(`domain.fincas._repository -> ...`) are now stale ledger residue from the
pre-inversion layout.

### fanout-stale-ledger-entries | medium | Eight modules pinned in the .importlinter ledger no longer exist, including two production packages

Cross-checking every ignore entry against the filesystem: 8 referenced
modules are gone — production: `aeat.domain.normatives` (the whole package
was removed; only the `_data/corpus/normatives` data tree remains),
`aeat.core.resources._repos.normatives`, `aeat.domain.fincas._repository`
(replaced by the ports layout); tests:
`core.resources._repos.tests.test_normatives`,
`domain.fincas.tests.test_repository`,
`domain.fincas.tests.test_roundtrip_anti_tautology`,
`application.workflow.tests.test_live`, and one more test module. The
core-not-outer contract's stated premise — "each edge is pinned individually
so a NEW non-deferred core->outer import is still caught" — is intact, but
its dual is not: a DELETED edge is never noticed because
`unmatched_ignore_imports_alerting = warn`. The normatives entries have
outlived their entire subsystem.

### fanout-modelo-carveout-inventory | medium | Seventeen generic registry modules carry per-modelo tokens; the pattern splits into legitimate modelo-keyed data and true logic branches

Enumerating the carve-out surface precisely. In
`domain/calculations/registry/`, 17 non-test modules match per-modelo tokens.
Two sub-patterns must be distinguished. Modelo-KEYED DATA is fine and by
design: `_applicability.py` (applicability rules are per-modelo data),
`_censo_modelos.py` (the censo modelo set), `_queries.py` (per-modelo query
projections). Modelo-BRANCHED LOGIC in generic evaluators is the debt:
`_formula_runtime.py` (M210 sentinel emission, M100 imputation-days
constant), `_validate_relation_sources.py` (M303 wallet slot carve-out),
`_schema_formula.py`, `_relation_aggregation.py`, `_validate_cross_domain_snapshot.py`
(renta/M100 routing), `_validate_extraction_profiles.py`. On the application
side the codebase already knows the right shape — dedicated per-modelo homes
exist (`_m303_m349_reconcile.py`, `_m036_lifecycle.py`, `_iva_wallet_gate.py`,
`_prior_payment_advisory.py`) — but generic modules still embed per-modelo
constants and branches: `_projection.py` (34 per-modelo token matches, the
M130→M100 continuity projection inlined), `_calculation_actions.py` (25),
`_verification_cross_period.py` (11), `_calculation_preparation.py` (10),
`_filed_revision_observation.py` (8). The gradient shows the convention is
drifting: new per-modelo behaviour sometimes gets a named module, sometimes
a branch in the hub.

### fanout-two-tier-deferral-ledger | low | Deferred work is first-class where it is data, invisible where it is comments

The codebase runs two deferral regimes of very different quality. The GOOD
tier: `DEFERRED_SOURCE_KINDS` in `application/aggregation/_source_mesh.py`
enumerates six deferred binding sources each with a reason and an ADR pointer
(M184 atribución, M232 related-party, M720 foreign-asset, M360 refund — all
Sheets-pull-only; bienes-inversión and prorrata regularización — blocked on
the prorrata-definitiva store per the 2026-07-01 ADRs), plus a RESERVED tier
for taxonomy headroom, and every deferred source surfaces a standing operator
advisory rather than a silent blank. Deferral here is typed, enumerated,
reasoned, and user-visible. The INVISIBLE tier: the application→adapters
inversion ("deferred", `.importlinter` comment), the domain-repository
inversion ("deferred to a future refactor", `.importlinter` comment), and the
submission verifier relocation ("Moving the concrete class to adapters is
deferred", `domain/submission/_protocols.py`) — none of which exists in any
plan, ADR status, or issue. The architecture already owns the right pattern;
the structural deferrals just never adopted it.

### fanout-layer-weight-profile | low | Application (108k lines) outweighs domain (74k); the weight is workflow gating, and the architecture is defended by ~73 bespoke structural gates

Measured production profile: core 118 modules / 24k lines; domain 345 / 74k;
application 314 / 108k; adapters 222 / 52k; entrypoints 120 / 41k (~301k
production lines total, 1,601 test modules, 25 domain and 28 application
subpackages). Application being ~1.5× domain is unusual for a hexagonal
design, but spot-checking the draft-build slice shows the weight is genuine
orchestration rather than misplaced domain rules: aggregates
(`CalculationRevision`, `ModeloDraft`, `WorkUnit`) and the calculation engine
live in domain, while application holds the workflow state machine, the
verify/file/amend gates, the precedence ladder, and the cross-period
clean-state enforcement — the regulatory-safety choreography that IS this
product's feature set. The complexity is held in check by an unusually large
in-house enforcement ecosystem: 73 test files run AST-level structural gates
and 38 more run inventory-style sweeps (decimal enrollment, modelo-string
usage, docstring links, schema conformance, resolver enrollment…). This is
the project's answer to complexity-vs-maintainability, and it mostly works —
but the gates are themselves ~111 bespoke programs, and the `.importlinter`
findings above show the enforcement layer receives no enforcement.

### fanout-lazy-import-soft-graph | medium | ~815 function-local imports make the runtime dependency graph systematically denser than the static graph the linter audits

Production code contains roughly 815 indented (function-local) relative
imports against 160 `TYPE_CHECKING` blocks — several hundred genuine
runtime-deferred imports after discounting type-only guards. The idiom is
used deliberately to break module-load cycles and soften layer edges: the
domain repositories lazy-import the secure-storage substrate per method, the
core resource repos lazy-import domain loaders, the error registry runs a
deferred-bind queue for circular-import windows
(`core/errors/_registry.py`), and `application/overview/_coverage.py`
defers an import explicitly "to break a module-load cycle". Combined with
`exclude_type_checking_imports = true`, the consequence is architectural:
the import graph the layered contract audits is the import-TIME graph, while
the runtime dependency graph is materially denser and points in more
directions. Layering conclusions drawn from the linter (including this
audit's) systematically understate coupling; a cycle "fixed" by deferring an
import has been hidden, not removed.

### fanout-legal-grounding-scale | low | Grounding coverage is structurally complete (447/447 entries carry corpus_ref and required_text); the self-reference risk is concentrated, not pervasive

Exact numbers for the legal-grounding finding: 31 legal TOML files declare
447 entries, and ALL 447 carry both a `corpus_ref` and a non-empty
`required_text` — coverage discipline is complete, not aspirational. The
bundled excerpt corpus is 318 HTML files. Test-side re-pinning of
`required_text` literals is limited to ~27 assertion sites, so the
"triple-authoring" burden is concentrated on the high-value articles rather
than pervasive. This sharpens the original finding rather than softening it:
with coverage at 100%, the remaining systemic risk is exactly the
self-reference topology (author writes excerpt and required_text together)
and corpus staleness against live BOE — the two failure modes that have each
already shipped a defect.

### fanout-bindings-open-steps | low | The three bindings campaigns' remaining steps are enumerable and small; closing them removes the mid-consolidation state

The open remainder is modest: binding-vocabulary-cli-cohesion has six open
steps (W04.P07.S22–S24, W05.P08.S25–S27) of 27;
binding-resolver-contract-unification has one (P05.S18) of 21, with the
fold-in-carry unification plan linked as grounding; silent-zero-base
aggregation has five of 18 open. The cross-domain continuity epic remains
the large one (339/409 steps, 206 alerts). Given how small the two contract
plans' tails are, the cheapest way to discharge the
bindings-framework-mid-consolidation finding is simply to finish and close
them before any new source kind or resolver convention lands.

### persistence-baseline | low | The SQLite/encrypted-substrate implementation is the strongest layer audited; recorded as context for the two findings below

The persistence layer (adapters/persistence: sql 3,146 lines, master_key
3,328, envelope 1,462, bucket 1,483, blob_store 937, crypto 639, secret_store
520, plus 6,042 lines of in-package tests) is architecturally the cleanest
surface in the codebase. Verified properties: AES-256-GCM AEAD with fresh
random nonces and HKDF per-context key derivation; the per-bucket DEK is
wrapped under an Argon2id-derived KEK with the bucket id bound into the AAD
(a wrapped DEK cannot be re-mounted under another bucket); envelope AAD binds
(classification, hkdf_context) and is checked before any crypto attempt;
every file write in the substrate (envelopes, blobs, manifest, master-key
material) is tmp-sibling + fsync + `os.replace` + parent-dir fsync; the
SQLite engine pins `foreign_keys=ON`, `busy_timeout`, `journal_mode=WAL`, and
`synchronous=NORMAL` with the durability tradeoff documented and justified
(local build-and-export store, never live submission); all repository
operations run inside `session_scope` transactions and `apply_batch` gives
all-or-nothing multi-namespace batches with per-write policy enforcement and
session-freshness checks; the no-legacy rule is genuinely upheld (zero
migration/ALTER machinery — "the schema is whatever the current ORM
defines"); plaintext at rest is confined to `SensitivityClass.CORPUS` in the
blob store with digest verification on both plaintext and ciphertext reads;
and the namespace registry declares per-namespace sensitivity, custody scope,
and disposition as typed data — the deferral-as-data pattern this audit
recommends elsewhere, already realised. Zero TODO/FIXME/deferred markers in
the persistence production tree.

### persistence-global-engine-lifecycle | medium | Module-global engine cache and active-session state leak lifecycle management to callers

The engine layer keeps a module-global cache (`_engines: dict[str, Engine]`
keyed by database URL, `storage/sql/engine.py`) alongside the process-global
active-bucket session state that `runtime.py` reports on. The lifecycle
consequences show up at the call sites: CLI lifecycle tests must call
`dispose_engine()` four or more times inside a single test to force the
cached engine to follow a profile switch, and the profile-rename test
choreographs `dispose_engine()` before every phase. That test friction is
the visible symptom of a real property: engine identity does not
automatically track bucket-session identity, so a stale engine for a
previous bucket URL can outlive a profile switch inside one process. Today
the readiness runtime (`ROUTE_NOT_ACTIVE_BUCKET`) and session-freshness
checks in `secure_objects` backstop misuse, but the coupling is enforced at
use-time, not at the lifecycle boundary. Remediation shape: bind engine
disposal into the bucket-session close/switch path (one owner for both
lifecycles) and add a regression that a profile switch in-process cannot
observe the prior bucket's engine; the scattered `dispose_engine()` calls in
tests then become deletable.

### persistence-multi-store-crash-windows | medium | Bucket state spans four stores whose composed operations are convention-guarded; the crash-window matrix is not itself a tested artefact

A profile bucket's durable state spans four sibling stores: the plaintext
`manifest.toml` (labels/pointers), the encrypted SQLite database (plus its
WAL sidecar), the content-addressed blob store, and the keystore
(`bucket.dek.json`). Every individual write is atomic (fsync + rename, or a
SQL transaction), and multi-store verbs are guarded by the
single-writer/composition discipline (`composition-service-no-parallel-write-path`)
plus repair/diagnostic verbs. What does not exist is a declared crash-window
matrix: for each composed verb (create profile, rename, delete
soft+hard, bundle import/export, key rotation across envelope + blob + SQL
stores), which inter-store orderings are possible after a crash at each
boundary, and which of those the repair verb provably recovers.
`_rotation.py` shows the right instincts (probe-miss semantics, per-file
error counters, idempotent re-runs), but rotation spans three stores and its
partial-failure end-states are validated only implicitly. Remediation shape:
author the matrix once as a reference document, then pin each recoverable
end-state with a crash-injection test around the existing repair verbs
(the roundtrip-discipline anti-tautology pattern applied to crash windows).
Also fold the WAL sidecar into every at-rest plaintext-scan and
sealed-archive surface (the engine docstring already warns that a raw-file
scan must read the `-wal` sidecar too; the shared test helper honours it,
and the sealed-archive writer should be pinned to the same guarantee).

## Deferral regression register

Per operator directive, every deferral surfaced by this audit is regression
scope. Each item carries its locus, remediation, and verification gate.

- D1 application→adapters wildcard. Locus: `.importlinter` layered contract
  (`aeat.application.** -> aeat.adapters.**`); 80 production modules ride it.
  Remediation: replace the wildcard with per-package pinned edges
  (mechanical); then burn pinned edges down opportunistically via ports.
  Gate: layered contract passes with the wildcard removed and a count-ratchet
  on pinned application→adapters entries.
- D2 domain-repository inversion (~11 domains). Locus: the per-domain
  `_repository` modules pinned in `.importlinter` (buckets, submission,
  invoices, modelos ×6, transactions, filing ×3, usage_ratios,
  participation_index). Remediation: migrate per the in-tree `domain.fincas`
  template (`_repository_ports.py` in domain, concrete class under
  `adapters.persistence.profile.*`). Gate: the domain→adapters pinned-edge
  set in `.importlinter` reaches zero production entries; roundtrip suites
  stay green per domain migrated.
- D3 submission verifier relocation. Locus: `domain/submission/_protocols.py`
  ("moving the concrete class to adapters is deferred"). Remediation: move
  the concrete verifier to adapters behind the existing protocol. Gate: the
  deferral comment is deleted and no submission module appears in the

## Recommendations

- Ratchet the `.importlinter` exception ledger: deduplicate the repeated
  autogenerated blocks, re-file the entries that sit under the wrong contract,
  flip `unmatched_ignore_imports_alerting` to `error` so stale entries fail
  loudly, and add a simple count-ratchet (current entry count may only
  decrease) so the ledger cannot silently grow. The duplicated blocks prove
  nothing currently reads this file end to end.
- Replace the blanket `aeat.application.** -> aeat.adapters.**` wildcard with
  per-package pinned edges (mechanical, no code change) so NEW
  application→adapters couplings become visible again, and register the
  deferred domain-repository inversion as a tracked plan item instead of a
  ledger comment — even if the decision is "wontfix, per-domain repositories
  are the accepted pattern", that decision should live in an ADR status, not
  an ignore list.
- Give per-modelo engine special cases a declared home: replace the M210
  negative-Decimal sentinel channel with a typed unresolved-rate outcome the
  application layer consumes explicitly, and move per-modelo constants and
  exclusion sets (M100 imputation days, M303 wallet ownership) toward
  registry-declared data so the generic runtime and orchestrator stop
  accreting named-modelo branches.
- Add an independent freshness loop for the legal corpus: a periodic
  operator-run reconciliation of bundled numeric amounts/rates against live
  BOE consolidated text (the three shipped corpus-figure defects were all of
  this class), and de-triplicate `required_text` by having per-article tests
  assert against the loaded catalogue rather than re-declaring the literal
  tuples.
- Declare a size budget for `src/aeat/_data` with a CI gate, and decide
  deliberately whether test modules and PDF fixtures belong in the shipped
  wheel (a hatchling exclude is one line); revisit whether the 441 MB
  `aeat_official` + `manuals` corpora should ship as an optional data extra.
- Author a convergence decision for the inline registry revision format:
  either migrate the remaining inline revisions to the fragmented layout and
  delete the dual-format tolerance, or declare inline frozen-for-legacy in an
  ADR so tooling authors know the split is permanent.
- Consider expressing the calculate-path precedence ladder (caller > borrador
  > mesh backend > profile; lock vs carry sources) as declared data with a
  conformance test, the way binding ownership already is — today it exists
  only as ordered guard code plus ADR-reference comments in
  `_calculation_actions.py`.

Fan-out additions:

- Use `domain.fincas` as the worked template for the domain-repository
  inversion: it already declares `_repository_ports.py` in domain with the
  concrete implementation in `adapters.persistence.profile.fincas`. The
  "deferred to a future refactor" comments predate this precedent; migrating
  the remaining ~11 domains is now a mechanical, template-driven campaign
  rather than an open design question.
- Purge the eight stale `.importlinter` entries (the normatives pair
  outlived its entire subsystem; the fincas entries outlived the ports
  migration) as part of the ledger ratchet, and add the "does every pinned
  module still exist" check to whatever audits the ledger.
- Adopt the `DEFERRED_SOURCE_KINDS` pattern for structural deferrals: the
  two inversion deferrals and the submission-verifier relocation should each
  be a tracked item with a reason and an owning ADR, not an ignore-list
  comment. The codebase already demonstrates that deferral-as-data works.
- Set a policy boundary for the function-local import idiom: it is the right
  tool for the ADR-sanctioned core-resources loaders, but using it to break
  module cycles inside a layer hides real coupling from every static gate.
  A cycle discovered should be restructured or documented, not deferred out
  of the import graph; consider a periodic runtime-import audit (grimp on
  the executed graph) to keep the soft edges visible.
