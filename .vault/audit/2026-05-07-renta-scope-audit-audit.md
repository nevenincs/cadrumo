# `renta-scope-audit` audit: `renta scope audit and gaps inventory`

## Scope

This is a rolling audit of the persisted Modelo 100 Renta registry schema,
its legal references, and its mini-model coverage against the actual scope
of a Renta declaration. It is the foundation of a typed-out singular plan
that lists exec steps required for full Renta coverage.

The audit is generated by `scripts/audit_renta_scope.py` which runs against
the live registry on every commit. Re-run produces an up-to-date findings
JSON at `.vault/audit/{date}-renta-scope-audit-findings.json`. This
markdown document captures the prose interpretation, the typed-substrate
onboarding context, and the closed-list of exec steps surfaced by the
audit.

The audit covers four verification layers:

- Layer 1: per-revision casilla classification (input_kind distribution,
  computed vs bound vs manual, never-read casillas).
- Layer 3: mini-model coverage scorecard — group casillas into the AEAT
  mini-model partition (Anexo A, Anexo B per-CCAA, capital inmobiliario
  per-property, ganancias y pérdidas per-transaction, atribución de
  rentas, regímenes especiales) and compute coverage % per group.
- Layer 4: legal grounding inventory — which Ley / RD / Orden articles
  are catalogued, cited, orphan-substrate, or cited-but-uncatalogued.
- Layer 7: scenario archetype coverage — which Renta filing archetypes
  (employee, autónomo direct estimation normal, autónomo simplified,
  autónomo objective estimation, family unit, capital gains transactions,
  CCAA-specific deductions) have at least one synthetic test scenario
  exercising the chain end-to-end.

Layer 2 (per-formula coverage map), Layer 5 (cross-modelo mini-API audit),
and Layer 6 (external-surface mini-API audit) are deferred to follow-up
audit slices; they require deeper formula introspection and corpus byte-
range validation that the current driver does not yet perform.

### Layer 8 — Test honesty inventory

Classifies every Renta test as one of three kinds:

- **Behaviour test** — asserts at least one non-zero numeric output
  derived from at least one non-zero numeric input. The math actually
  has to compute correctly for the test to pass. These tests catch
  formula swaps, dropped operands, and inverted negates.
- **Structural test** — asserts presence/absence of registry elements
  (formulas registered, articles catalogued, no orphans). Catches
  removal/rename regressions but does NOT test computation.
- **Vacuous smoke pattern** — all-zero inputs AND all-zero expected
  outputs. The chain computes `0 = 0 + 0 - 0 + ...` which never
  fails. False coverage signal — looks like a behaviour test, behaves
  like nothing.

| File | Tests | Kind | Zero asserts | Non-zero asserts | Non-zero inputs | Vacuous pattern |
|---|---:|---|---:|---:|---:|:---:|
| `test_renta_2025_synthetic_profile.py` | 2 | behaviour | 8 | 31 | 47 | no |
| `test_renta_chain_behaviour.py` | 8 | behaviour | 1 | 16 | 42 | no |
| `test_renta_cuota_chain_contract.py` | 8 | structural | 0 | 0 | 0 | no |
| `test_modelo_100_drift_detection.py` | 8 | structural | 0 | 0 | 0 | no |
| `test_schema_hygiene.py` | 8 | structural | 0 | 0 | 0 | no |

**Total numeric assertions**: 9 zero + 47 non-zero. **Files with
vacuous-smoke pattern**: 0 of 5.

**2026-05-07 cleanup pass:** the audit's first run flagged 7 vacuous
zero-input zero-output tests (one per supported ejercicio in a
parametrized scenario plus one standalone 2025 boundary case). They
asserted that all-zero input produces all-zero output for ~14
casillas × 6 years = 84 zero numeric assertions, none of which tested
anything observable. Removed in the same commit that adds Layer 8.
The test count went 45 → 38 with no loss of behavioural coverage:
chain calculation across years is already exercised by the
parametrized 30k employee scenario which produces non-zero outputs
in each year.

A new schema-hygiene guard at
`test_renta_synthetic_scenarios_do_not_pass_with_pure_zero_inputs_to_zero_outputs`
flags any future Renta scenario whose inputs and expected outputs are
all zero. New vacuous tests will trip this guard at PR time.

## Typed-substrate onboarding (VAT in-flight work)

The VAT domain has been driving a typed-substrate rollout that the Renta
exec plan must integrate from day one. Recent commits in this work:

- `c2fc4e24` Promote `Invoice.iva_category` from `str | None` to
  `VATCategory | None` — replaces a free-form string with the substrate-
  typed enum from `src/aeat/domain/vat/`.
- `c285c81b` Type-harden `Invoice.counterparty` country axis with
  `EUMemberState` bridge.
- `cc4259b8` Add `Invoice.iva_classification_for_line` typed accessor.
- `799d50a3` Track typed counterparty + iva_classification accessor in
  roll-out ledger.
- `688609e5` Legal-basis binding verification + LIVA arts 90/91 corpus
  (introduced the pydantic-typed binding surface that any registry-side
  legal binding now consumes).

The pattern surfaced by this in-flight work that must be inherited by the
Renta exec plan:

- **No free-form strings for substrate axes**. Every Renta domain field
  that asks "what kind of X is this?" must use a strict-frozen pydantic
  v2 enum with closed membership rather than a `str | None` field.
  Examples that need typing:
    - Renta `RentaIncomeType` — closed enum across `trabajo`,
      `capital_mobiliario_general`, `capital_mobiliario_ahorro`,
      `capital_inmobiliario`, `actividades_economicas_directa_normal`,
      `actividades_economicas_directa_simplificada`,
      `actividades_economicas_objetiva`, `ganancias_perdidas_general`,
      `ganancias_perdidas_ahorro`, `imputacion_rentas`, `atribucion_rentas`.
    - Renta `RentaCCAA` — closed enum mirroring `EUMemberState` shape but
      for the 17 Spanish autonomous communities + Ceuta + Melilla. The
      `ZCCAD` casilla currently binds to a free-form string profile key
      and must instead bind to the typed enum.
    - Renta `EstimacionDirectaModalidad` — closed enum {`normal`,
      `simplificada`} replacing the binding selector that maps casilla
      0168 string values "N"/"S".
- **Legal-basis binding verification** — every Renta formula's
  `legal_refs` must resolve through the same pydantic-typed legal binding
  surface that the IVA work introduced (`688609e5`), so the binding
  carries article id, BOE permalink, evidence_tier, and the corpus byte-
  range that anchors the `required_text`.
- **Per-line typed accessors** — the Renta-side equivalent of
  `Invoice.iva_classification_for_line` is a `RentaCasillaClassification`
  accessor on the per-row inputs (per-property real-estate row, per-
  transaction capital gains row, per-employer trabajo row) that returns
  the typed mini-model classification rather than ad-hoc string parsing.

The exec plan downstream of this audit must include explicit slices for
these typed-substrate ports.
