W01-P002-002 | HIGH | New `config auth` commands implement auth behavior in the CLI layer instead of a backend API
`src/aeat/entrypoints/cli/_config.py:431` through `src/aeat/entrypoints/cli/_config.py:443` writes auth state directly via `workflow_state_repository()`, `src/aeat/entrypoints/cli/_config.py:454` through `src/aeat/entrypoints/cli/_config.py:475` builds status output from workflow state in the command handler, `src/aeat/entrypoints/cli/_config.py:478` through `src/aeat/entrypoints/cli/_config.py:482` implements `config auth test` as a direct call to `auth_status`, and `src/aeat/entrypoints/cli/_config.py:513` through `src/aeat/entrypoints/cli/_config.py:524` deletes persisted sessions/locks and resets `AuthState` from the CLI. This violates the apex/backend-boundary rule that CLI commands delegate to centralized backend services and the config-auth ADR requirement that `test` verify provider readiness through backend implementations, mutations emit bucket-scoped events, and output uses the shared emitters. It also makes `clear --provider ...` unsafe because the command resets all workflow auth state regardless of the requested provider.
