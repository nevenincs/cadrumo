# `corpus-search-model-cache-capability-gap` audit: `model2vec capability check silently discards the revision pin and the app-controlled cache directory`

## Scope

This audit examines the shared model2vec loader behind the corpus-search semantic stack (`application/corpus_search/_model_loader.py`), consumed by both the build-time embedding precompute (`_embed_build.py`) and the runtime query embedder (`_query_embed.py`). The loader wraps `model2vec.StaticModel.from_pretrained` behind a runtime capability check that inspects the installed callable's signature before deciding which keyword arguments to pass through. The pinned dependency range is `model2vec>=0.8,<1`; the installed and locked version is 0.8.2. This audit verifies, against the real installed package source, whether the capability check still delivers the two guarantees its own docstrings and prior research claim: a pinned, reproducible model revision, and a download rooted under the app-controlled storage root rather than the operator's global Hugging Face cache.

## Findings

### model2vec-capability-gate-drops-both-guarded-kwargs | critical | the installed model2vec 0.8.2 accepts neither `revision` nor `cache_dir`, so both are silently dropped on every load

`load_static_model` builds its keyword arguments by inspecting `inspect.signature(model2vec.StaticModel.from_pretrained).parameters` and only forwarding `revision` or `cache_dir` when the name appears in that set. The installed model2vec 0.8.2 declares `from_pretrained(path, token=None, normalize=None, subfolder=None, quantize_to=None, dimensionality=None, vocabulary_quantization=None, force_download=True)`. Neither `revision` nor `cache_dir` is a parameter of this signature, confirmed by direct introspection of the installed package. Both `if` branches in the loader therefore evaluate false on every call in the currently pinned dependency range, and `kwargs` reaches `from_pretrained` empty. This is not a hypothetical edge case; it is the behaviour of the exact version the project ships today.

Three consequences follow from the same silent drop:

1. The pinned model revision (`POTION_MODEL_REVISION`, a concrete commit SHA) is never passed to model2vec. Internally, `StaticModel.from_pretrained` calls `model2vec.persistence.load_pretrained`, which calls `_resolve_folder`. When the given path is not an existing local directory, `_resolve_folder` calls `huggingface_hub.snapshot_download(str(path), repo_type="model", token=token)` with no revision argument at all, so the download resolves whatever the Hugging Face Hub currently serves as the model's default branch, not the pinned commit. The docstring at the top of `_embed_build.py` states the revision pin exists so that "a first-use download is reproducible and cannot silently pull a re-published model." That claim is false against the currently installed dependency: the pin is recorded for provenance in the persisted build result but never enforced against the actual download.

2. The app-controlled cache directory (`cadrumo_local_storage_root / "search-models"`, constructed by `search_model_cache_dir`) is never passed to model2vec either. Because `cache_dir` is dropped, `_resolve_folder`'s call to `huggingface_hub.snapshot_download` also omits `cache_dir`, so the download lands in the Hugging Face library's own default cache (`HF_HUB_CACHE`, normally under the operator's home directory), not under the app's storage root. `QueryEmbedder._ensure_model` still creates the app-controlled `search-models` directory via `mkdir`, so the directory exists on disk but is never populated; the actual weights live outside the one state root the module docstring in `_query_embed.py` claims they are rooted under. A roughly 1 GB `models--minishlab--potion-multilingual-128M` directory dated the same day as this audit was found in the real global Hugging Face cache on this machine, corroborating the mechanism independently of source reading.

3. `force_download` is a model2vec library default, not something the capability check even attempts to override: the loader's accepted-parameter check never inspects or sets `force_download`, so whatever model2vec 0.8.2 defaults to applies unconditionally. That default is `True`. Per its own docstring, `force_download=True` means "the model is only downloaded if it is not already present in the cache" is NOT the active behaviour; a `True` value skips the loader's own `maybe_get_cached_model_path` short-circuit and unconditionally calls `huggingface_hub.snapshot_download` on every load. `huggingface_hub`'s own `snapshot_download` still resolves against its local cache by ETag, so this does not necessarily re-transfer the full weight payload on every call, but it does require a network round trip on every model load rather than a fully offline load from a previously populated cache, contradicting the intended build-once-reuse shape described in the `QueryEmbedder` docstring ("cached for the embedder's lifetime" describes only the in-process object cache, not the on-disk download behaviour). This third consequence is not itself a symptom of a version-signature mismatch: the loader never attempts to pass `force_download` in any of its accepted-parameter branches, on any model2vec version, so this gap exists independent of whether `revision`/`cache_dir` happen to be accepted.

### existing-test-cannot-catch-any-of-the-three | high | `test_cache_dir_is_rooted_in_storage_root` asserts the wrapper's own stored attribute, never what model2vec receives

`src/cadrumo/application/corpus_search/tests/test_query_embed.py::test_cache_dir_is_rooted_in_storage_root` constructs a `QueryEmbedder` and asserts `embedder.cache_dir == tmp_path / "search-models"`. `QueryEmbedder.__init__` sets `self._cache_dir` directly from `search_model_cache_dir(settings)` before any model2vec call is made; the `cache_dir` property simply returns that stored value. The test therefore proves only that the constructor computed the expected `Path` and stored it as an attribute. It never calls `_ensure_model` or `load_static_model`, never inspects what `model2vec.StaticModel.from_pretrained` is actually invoked with, and never crosses the boundary where the silent drop happens. A version of `load_static_model` that computed `cache_dir` correctly and then discarded it entirely (as the installed model2vec version in fact causes it to do) would pass this test identically to a version that threaded it through correctly, because the test's assertion sits entirely on the near side of the pass-through. The test is real and not tautological on its own narrow claim, but its narrow claim is not the claim that matters: it verifies construction-time bookkeeping, not runtime delivery of the guarantee the surrounding docstrings promise.

### general-shape | high | a capability check quietly converts "the installed library cannot honour this contract" into "proceed without the contract"

The pattern in `load_static_model` is a defensive compatibility check: rather than asserting the installed dependency supports the features the code was written against, it probes the signature and conditionally omits the argument when unsupported. This makes the CODE forward-compatible with a library that dropped or renamed a parameter (it will not raise `TypeError`), but it does so by silently degrading the SYSTEM's guarantees rather than failing loudly or falling back to an equivalent mechanism. The same shape was independently found and named in the corpus-registry model loader (see `defensive-capability-check-silently-drops-the-guarantee` in the project memory index), where `if "x" in signature(...).parameters` similarly turned "this version cannot honour our pin" into "proceed without it", dropping both a revision pin and an app storage root guarantee at once. This is the second independent occurrence of the identical failure shape against the identical class of guarantee (revision pinning plus storage-root confinement), which suggests the pattern itself, not just this one call site, warrants scrutiny wherever a similar `inspect.signature(...).parameters` gate exists in the tree.

### prior-art-already-flagged-the-cache-dir-half | medium | the project's own research record already named this gap as deferred residual hardening and it was never closed

`.vault/exec/2026-07-02-agent-harness-refoundation/2026-07-02-agent-harness-refoundation-W06-P13-S80.md` records at authorship time that "the `cache_dir` is passed to `from_pretrained` only when the installed model2vec signature accepts it; finalising the exact download/cache behaviour and the pinned commit SHA remains the research doc's open item." The close audit `2026-07-02-agent-harness-refoundation-audit.md` tracked this as finding H2, carried forward as a follow-up item. `2026-07-02-agent-harness-operability-followup-research.md` records that the follow-up landed (commit `cc1504bfa4`) but its own resolution table states explicitly: "Residual minor hardening: pin `POTION_MODEL_REVISION` from `main` to a commit hash, and perfect the app-cache-dir passthrough (this model2vec version routes the download to the default HF hub cache)." The revision constant was subsequently pinned to a commit SHA (confirmed at HEAD: `POTION_MODEL_REVISION = "73908c3438cf03b6a01bcb9611d62b23d0726f08"`), but the cache-dir passthrough was left as acknowledged, un-gated residual hardening and was never closed with a Step or a test. This audit additionally establishes something the prior record did not: on the currently pinned and locked model2vec version, the `revision` argument is ALSO silently dropped, not only `cache_dir`. Whether that is a further regression since the prior note (a later model2vec release removing `revision` support) or was already true and unnoticed at the time cannot be determined from the vault record alone; either way, the revision-pin guarantee is not merely undocumented risk today, it is confirmed absent.

## Recommendations

Resolve the model2vec `revision`/`cache_dir` gap by having the loader obtain the model through `huggingface_hub` directly rather than relying on model2vec's own `from_pretrained` path resolution. `huggingface_hub` 1.25.1 (already present in the resolved lock, currently only as a transitive dependency of the dev-only `vaultspec-rag` tool, not as a declared dependency of the `cadrumo[search]` extra) exposes `snapshot_download(repo_id, revision=..., cache_dir=..., ...)`, both of which model2vec's own call to the same function omits. `model2vec.persistence._resolve_folder` checks `folder_or_repo_path.exists()` first and returns the path unchanged, with no network access and no dependence on `force_download`, when the given path is already an existing local directory. Handing `StaticModel.from_pretrained` a LOCAL directory path obtained from an app-driven `huggingface_hub.snapshot_download(model_id, revision=pinned_revision, cache_dir=app_storage_root)` call would restore both guarantees without depending on model2vec's own kwarg surface at all, verified against the installed `model2vec.persistence.datamodels.FOLDER_LAYOUTS`, whose native model2vec layout (`config.json`, `model.safetensors`, `tokenizer.json` at the snapshot root) matches exactly what `snapshot_download` lays out for a model2vec-native repository. This is a genuine product behaviour change on a network-reaching path and needs an explicit decision before implementation, including: whether to declare `huggingface-hub` explicitly on the `cadrumo[search]` extra. An earlier revision of this audit claimed a clean `pip install cadrumo[search]` would not receive it, and that is WRONG, corrected here on measurement: model2vec 0.8.2 declares `tokenizers>=0.20`, and `tokenizers` requires `huggingface-hub>=0.16.4,<2.0` as an unconditional base dependency, so the chain `cadrumo[search]` to `model2vec` to `tokenizers` to `huggingface-hub` delivers it to an end-user install. There is therefore no latent import failure to fix. Declaring it directly remains defensible as making a real, load-bearing dependency explicit rather than relying on a transitive edge that a future model2vec or tokenizers release could drop, but it is a hygiene choice and not a defect; deciding the offline/no-network behaviour when a prior snapshot already exists under the storage root; and deciding whether `force_download` should be explicitly forced to `False` once the loader owns the download step directly.

Strengthen or replace `test_cache_dir_is_rooted_in_storage_root` so it proves what actually reaches model2vec, not only what the wrapper stores. The test can, without any network access, substitute a lightweight stand-in for `model2vec.StaticModel` (module-level, real object, not a mock of the loader under test) exposing a `from_pretrained` classmethod with a deliberately narrow signature matching the installed library's real signature, and assert on the keyword arguments the substitute actually received when `load_static_model` calls it. This crosses the boundary the current test stops short of, without downloading anything, and would fail today against the real `load_static_model` implementation because `cache_dir` and `revision` are never delivered. A second, complementary assertion should pin the installed model2vec version's own `from_pretrained` signature against the parameter names the loader depends on (`revision`, `cache_dir`), so a future model2vec upgrade that restores or further narrows the accepted parameters is caught as a signature-drift regression rather than silently changing behaviour again. Neither change requires network access; both are expressible entirely against the installed library's real signature and a real stand-in object standing in for the boundary, not a mock returning what the test expects.


## Adjudication update (2026-08-01)

The findings above stand as measurements and are unchanged. The Recommendations section is OVERTAKEN: the accepted `2026-07-31-semantic-search-precompile-boundary-adr` considered the loader-hardening recommendation as option O1 and explicitly declined it, resolving every finding in this audit by deletion of the runtime semantic stack instead (`_model_loader.py`, `_query_embed.py`, `_embed_build.py`, and the `search` extra are retired by the boundary plan). No agent may dispatch or land work implementing the recommendation. Commit `4dd9810c8f` (fix(corpus-search): pin snapshot model resolution, 2026-08-01 06:48) executed the declined recommendation the morning after the ADR's acceptance because this annotation did not yet exist; its subject files are deleted by the in-flight boundary plan.
