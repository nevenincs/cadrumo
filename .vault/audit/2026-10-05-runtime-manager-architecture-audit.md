### unconfirmed-runtime-termination | high | Forced-stop completion is reported while an adopted runtime remains alive

2026-10-07 integrated review: REVISION REQUIRED for the supervision core. In `native/manager/src/supervision/supervisor.rs:1063`, terminate discards the operating-system termination result, immediately emits Terminated, and calls ended with RuntimeExit::Terminated when either exit is observed or the five-second termination bound expires. An expired deadline is not evidence of process death. The Windows owner deliberately permits inspection-only adoption when opening PROCESS_TERMINATE fails (`native/manager/src/supervision/windows.rs:108`), so this is a reachable permission case, not just a hypothetical OS failure.

A source-linked Windows probe started the actual fixture runtime, retained the original CreateProcess handle, denied PROCESS_TERMINATE on subsequent opens while allowing query/synchronization, and disabled SeDebugPrivilege only in the short-lived probe process. The supervisor adopted the process; graceful delivery was deliberately unavailable; forced stop then produced Terminated, Exited(Terminated), and Stopped(Unknown). The retained original handle independently proved that the fixture was still running after supervision returned. Cleanup used that original handle and confirmed exit. The original unrestricted host-token attempt could terminate the process; the restricted attempt reproduced the defect without changing machine privileges, real-user storage, login registration, or product code. Evidence is `build/manager-implementation-audit/termination-probe.log` and the ignored source-linked probe in `build/manager-implementation-audit/src/main.rs`.

Preserve the distinction between termination requested, termination failed, confirmation timed out, and confirmed process exit. Emit Exited only after the held process signals exit; do not release supervision ownership merely because the wait budget ends. A bounded caller can receive an unconfirmed-stop result while monitoring retains the handle. Preserve Unknown effects and propagate the new failure/timeout reason through the closed diagnostics and log consumer. Regression coverage must include an adopted inspection-only handle and an unconfirmed termination deadline. This finding reopens P02.S09; P02.S10's OS acceptance remains independently open.

### backoff-erases-unknown-effects | medium | Ordinary stop after a crash incorrectly reports settled effects

`native/manager/src/supervision/supervisor.rs:729` returns Stopped with Effects::Settled for any ordinary control request during restart backoff, although the failed process may just have produced EffectsUnknown. The source-linked fixture probe crashed after readiness with 0xC0000005, observed EffectsUnknown and RestartScheduled, and then sent Request::Stop. The returned outcome was Stopped { effects: Settled }. Evidence is `build/manager-implementation-audit/backoff-probe.log`. The existing `native/manager/tests/supervision.rs:606` case expects the settled result and therefore does not protect the contract.

Retain the failed process's effects state through backoff and every stop result. Having no currently running process does not establish settlement of prior work. Add a regression that independently observes the crash and requires Unknown after Stop and StopIfIdle; retain the restart-claim release assertions. This is an internal supervisor-outcome defect; the current desktop dispatch acknowledgement does not expose it as a financial settlement receipt.

### boot-record-parent-junction | medium | Adoption reads bypass the hardened custody record owner

The supervisor contract requires boot-record reads and writes through the hardened custody local-record primitives. `native/manager/src/supervision/boot_record.rs:106` instead checks only leaf metadata and then calls File::open. It neither pins nor refuses reparse-point parents and leaves a check/open race at the leaf. The normal reader in `native/manager/src/custody.rs:101` pins the parent chain and uses platform no-follow opens.

A deterministic Windows probe placed an otherwise valid boot record behind a .runtime directory junction inside an isolated synthetic root. The manager reader accepted it; the custody reader rejected the same path as a reparse-point directory. Evidence is `build/manager-implementation-audit/boot-record-probe.log`. Use the existing custody owner and preserve absence/unreadable distinctions, bounded bytes, and closed decoding; cover junction parents and replacement races.

This proves a filesystem-contract gap, not privilege escalation or arbitrary-process adoption. The subsequent held-process PID/creation stamp, image/package/version, session and elevation checks still apply and must remain.

### manager-responses-and-consumers | low | Launch acknowledgement and runtime availability remain distinct

The bare manager executable is long-lived and currently accepts bare startup, --version and an internal breakaway argument, rather than a service-control CLI. Its own process exits use 2 for unsupported invocation, 77 for native admission refusal, 69 for startup/platform failure, and 0 for successful completion, already-running ownership or dispatched breakaway. These are separate from the runtime's reserved exit-reason table. GUI-subsystem stderr is a bounded diagnostic, not a reliable desktop response transport; admitted startup failures display a generic native message. Early admission/job-escape failures precede durable log configuration and do not establish persistent per-root logging.

For manager-launched runtimes, private non-inheritable JSON-line streams carry ping, stop, stop-if-idle and session-end, with ready, heartbeat, stopping, busy and malformed/oversized refusal replies (`native/manager/src/supervision/protocol.rs`). PID, version, storage identity, admission and ping freshness are checked. Ready is a runtime assertion on that private channel; verified native client status remains the application's availability authority. EOF or a broken manager channel does not itself kill the runtime. An adopted runtime has no attached private channel and receives native graceful signals through its held identity.

The desktop uses a short-lived isolated Explorer-dispatch helper, whose bounded JSON is {dispatched: bool, os_code: nullable integer}. `native/desktop/src-tauri/src/manager.rs:256` requires helper success plus dispatched=true and no OS code; Tauri returns Dispatched, Unmanaged or Unsupported, or a typed bounded error. This means Windows accepted a launch request, not that the manager or runtime is ready. `native/desktop/frontend/src/shell/signIn.ts:344` polls canonical status for up to 90 seconds after dispatch and accepts runtimeAvailable only from that status. Manager lifecycle logs are parsed as closed fields in `native/desktop/src-tauri/src/logs/manager.rs` and projected through the existing log viewer; they do not grant profile authentication or operation authority. Verified public manager-control IPC and CLI/TUI/MCP manager requests remain unimplemented by design at this stage.
