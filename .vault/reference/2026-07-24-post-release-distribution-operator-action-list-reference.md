# `post-release-distribution` reference: `Operator action list for the 19 externally-blocked steps`

## Summary

Nineteen of this plan's twenty-six steps are open, each annotated with a
precondition no agent can satisfy. This document turns those annotations into an
ordered list of things a person does, with the exact command or click-path, what
each one unblocks, and an honest cost. Every precondition below was re-verified
against the live repository and this workstation on 2026-07-25 rather than taken
from the plan text. Three of the plan's stated preconditions did not survive that
check and are corrected in place; one previously unrecorded safety gap was found.

Nothing here was executed. No variable was set, no repository created or made
public, no workflow dispatched, no release altered.

## The two decisions

These are not chores. They need a person to choose, and the rest of the list
partly depends on which way they go.

### Decision one: the hand-published v0.2.1 release

A public, non-draft, non-prerelease `v0.2.1` release exists, marked Latest,
published 2026-07-21 at 12:46 UTC against commit `9235e8cabc`. It never went
through the publication workflow. It carries eight assets: the six Python
distributions, the MCPB bundle, and an evidence manifest. It lacks the release
cohort manifest, the Python cohort manifest, the Scoop manifest, the Homebrew
formula, and both Claude zips.

Two consequences. The digest gate cannot verify against it, because the cohort
manifests it would check are simply absent, so the GitHub reacquisition step is
unreachable while this release stands as the promotion. And it is a live public
artifact that makes an implicit availability claim, published ahead of the
documentation gate that exists to stop exactly that.

The options, plainly:

Replace it. Delete or retag `v0.2.1`, let the publication workflow mint the tag
itself as part of a real promotion. Cleanest result, and the digest gate then has
the full cohort it expects. Costs whatever goodwill a deleted public tag costs,
which for a project with no announced users is close to nothing.

Supersede it. Leave `v0.2.1` alone and promote `v0.2.2` as the first authoritative
release. Nothing public disappears, but the Latest marker moves and `v0.2.1`
remains permanently unverifiable, so the close audit has to carry an explicit note
about a public release that predates the authority.

Reconcile it. Attach the missing cohort members to the existing release by hand.
Not recommended. It reproduces by hand the exact bypass that caused the problem,
and the resulting assets would carry no provenance from the workflow that is
supposed to be the only thing allowed to produce them.

The recommendation is to replace it, because the whole point of the protected
workflow is that published bytes and the cohort manifest are minted together.

### Decision two: the missing evidence for the three green Python rows

The three Python platform rows are honestly closed against packaging smoke run
`29657832151`, and the run record still exists, so the closures stand. The
evidence release that backed them does not: there is no `evidence-smoke-29657832151`
release, and the oldest surviving evidence draft is `evidence-smoke-29747367504`
from 2026-07-20. The artifacts are gone.

A correction to the stated cause. This was attributed to someone dispatching the
evidence garbage-collection workflow with its default keep-of-three. That workflow
has never run: its total run count is zero. Something else removed the older
drafts, or that run's draft was never sealed. The practical consequence is
unchanged, but the cause should not be recorded as a garbage-collection mistake,
because it was not one, and a fix aimed at the retention default would fix
nothing.

What it costs: the rows must be regenerated by a fresh green three-OS packaging
smoke run. That is not extra work, because the publication gate independently
requires a recent smoke run whose evidence draft is sealed, and the operator has
to name that run's id when dispatching publication. So the regeneration is
already on the critical path. The only real constraint is ordering: the green
smoke run must happen before promotion, and its id must be the one handed to the
publication workflow.

## The blocker the plan understates

The plan describes the packaging campaign as red at its first step because a
frozen description digest has drifted, remedied by a one-line re-pin. That is no
longer what is happening, and the difference matters because it changes the first
action.

Every packaging smoke run since 2026-07-22 has failed; twelve consecutive runs
are failure or cancelled. In the most recent run the cohort build succeeded and
the Linux oracle leg passed, so the preflight is not aborting every leg. Three
distinct causes remain:

The Linux and macOS wheel legs failed on a stale test that asserted the identity
verifier still reports a failure, from before the harness-identity migration made
it pass. That test has already been corrected on main, renamed to state what it
actually checks, so this cause is spent and should not recur.

The Windows legs failed at checkout with a not-a-git-repository error. The
self-hosted Windows runner's workspace is wedged. The runner itself reports online
and idle, so this is workspace state rather than a dead host.

The macOS oracle leg exited 127, which is a missing executable on that host, not a
product failure.

Separately, and only locally: the identity verifier currently exits non-zero in
this worktree because the MCP input-schema builder cannot resolve an
`app maintenance profile_bundle_reconcile` subtree and refuses rather than
shipping an argument-free schema. That verb is uncommitted work in flight in the
shared tree, not on main, so continuous integration does not see it. It is
mentioned only so that a local run of the verifier is not misread as a main-branch
regression.

The honest position is that nobody knows whether current main is green, because
the last several runs were against commits that carried the since-fixed test. The
cheapest way to find out is to dispatch one smoke run and read it, which is the
first action below.

## The one safety gap found during verification

The four protected environments named by the publication workflow all exist:
`pypi`, `pypi-data-manuals`, `pypi-data-official`, and `release`. The plan reads
this as satisfying the human release gate, saying only the operator opt-in and the
environment approval remain.

Every one of the four carries zero protection rules. There are no required
reviewers on any of them.

Existence is not protection. The publication workflow's own refusal text lists,
as its second prerequisite, creating the `release` environment with required
reviewers, and calls that approval click the human release gate. That gate does
not currently exist. If the opt-in variable were set today, publication would run
through to PyPI with no approval prompt, and the only remaining human checkpoint
would be the act of setting the variable itself.

This should be fixed before the opt-in is set, not after, and it is cheap: add the
operator as a required reviewer on each of the four environments. It appears in
the ordered list below at the point where it must happen.

## The ordered action list

Stages A and B are independent of each other and can be done in either order or
in parallel. Everything from C onward is strictly sequential.

### Stage A: get one green cohort

Nothing downstream can start without this, and it gates both the missing evidence
rows and the publication dispatch.

A1. Dispatch one packaging smoke run against current main and read the result.
Cost: minutes to start, roughly half an hour to finish. This is a diagnostic, not
a fix: it establishes whether the since-corrected test was the only product-side
cause. Unblocks nothing by itself, but every estimate below depends on its answer.

A2. Unwedge the self-hosted Windows runner workspace. The runner is online and
idle; its working directory is the problem. Clearing the runner's work folder for
this repository and letting the next run re-clone is the normal remedy. Cost:
minutes. Unblocks the Windows Python row and, with it, two thirds of the reason
the three-OS matrix cannot go green.

A3. Fix the missing executable behind the macOS oracle leg's exit 127. The runner
is online; something on the path is absent. Cost: minutes once the log names the
command, but it is a real investigation if it does not. Unblocks the macOS Python
row.

A4. Re-run the smoke workflow until all three operating-system rows are green in a
single run, and confirm that run sealed its evidence draft as a release tagged
`evidence-smoke-` followed by the run id. Note that run id. Cost: one run per
attempt. This single artifact satisfies both the regeneration of the three lost
Python evidence rows and the publication workflow's fourth prerequisite.

### Stage B: the accounts and repositories

None of these depends on Stage A. Three are seconds of clicking and are the
cheapest unblocking in the entire list.

B1. Make the Scoop bucket repository public. It exists and is private. Cost:
seconds, in the repository settings. Unblocks the clean Scoop acquisition proof
and, later, the public Scoop reacquisition, neither of which can reach a private
bucket.

B2. Make the Homebrew tap repository public. Same situation, same cost. Unblocks
the public Homebrew tap reacquisition.

B3. Create the marketplace repository. The repository variable names it and the
push token already exists as a secret, but the repository itself does not, so the
publication workflow's marketplace push would refuse. Cost: seconds. Unblocks the
public marketplace plugin acquisition and the Claude artifact namespace and
description reacquisition.

B4. Register trusted publishing on PyPI for all three project names, with this
repository as publisher, the publication workflow as the workflow, and `release`
as the environment. The root `cadrumo` name does not exist on PyPI at all and is
not even reserved; the two companions exist only as placeholder reservations at
version zero. Cost: minutes in the PyPI web interface, three times. Unblocks the
entire PyPI half of promotion, and reserving the root name is worth doing today
regardless of when publication happens.

B5. Add the operator as a required reviewer on all four protected environments.
Cost: minutes. This is the safety gap described above, and it must be done before
the opt-in variable is set.

### Stage C: arm and promote

C1. Dispatch the Scoop and Homebrew acquisition workflows against the green smoke
run from A4 and note their run ids. Both currently fail, and their remaining
blockers are physical: the Scoop lane needs the Windows host in Windows-container
mode, and the Homebrew ARM64 row needs a host that is currently offline. Those are
D-stage items; the x86-64 Homebrew and macOS ARM64 rows have already gone green
once and should again. Cost: two dispatches plus their run time.

C2. Mint the four Claude evidence rows locally and upload them to a draft release,
noting that tag. Two of the four depend on the in-app captures in Stage D, so this
step cannot complete before those. Cost: minutes once the captures exist.

C3. Set the repository variable that arms publication to true. Cost: seconds. This
is the point of no return and should be the last thing done before dispatch, after
B5 has put a reviewer gate in place.

C4. Dispatch the publication workflow with the packaging run id, the Scoop and
Homebrew run ids, and the Claude evidence release tag, then approve the
environment prompt when it appears. Cost: minutes plus run time. This is the step
that unblocks all five reacquisition steps at once, and it is the single highest
-leverage action in the list.

### Stage D: the physical and in-app work

D1 through D3 can be done at any time and are independent of everything above.

D1. Enable Windows Sandbox on this workstation. The feature is confirmed
Disabled. Enabling it requires administrator rights and a reboot. Cost: minutes
plus a reboot. Unblocks the Windows Sandbox installation proof.

D2. Switch the Windows host's Docker to Windows-container mode when the Scoop
lanes need to run. Docker currently reports a Linux server, which is why the Scoop
acquisition preflight refuses; that preflight is correct and must not be weakened.
Note the tradeoff: the mode is exclusive, so Linux-container work on that host
stops while it is switched. Cost: minutes to switch, and it should be scheduled
rather than left switched. Unblocks the clean Scoop acquisition gate and the
public Scoop reacquisition.

D3. Bring the Linux ARM64 host back online, then resolve the argon2 bindings
build dying with a SIGILL under the Homebrew Python 3.13 toolchain. Bringing it
online is minutes. The SIGILL is a real investigation: an illegal instruction in a
source build usually means the compiler is emitting instructions the host does not
implement, so the likely paths are a prebuilt wheel, a different toolchain, or a
build flag pinning the target architecture. Unblocks the one remaining red
Homebrew row and the ARM64 column of the support matrix.

D4. In Claude Desktop, type one tax prompt in a real conversation against the
installed bundle. Everything else for that step is already captured, including a
full protocol handshake; this one human-typed prompt is the entire remaining
sliver. Cost: seconds. No agent can do this.

D5. Install Cowork for real and make one in-app tool call. Cost: minutes. No
capture exists at all for this one, so it is a fresh capture rather than a sliver.

D6. The client identity inventory completes on its own once D4 and D5 land,
because its Claude Code entry already carries real session evidence and the other
two entries are waiting on exactly those captures. Cost: nothing beyond D4 and D5.

### Stage E: reacquire, document, audit

Everything here is mechanical once C4 has promoted a cohort. The tooling for all
five reacquisition steps is already written and reviewed, and each executes
post-publication.

E1. Run the five reacquisition steps: PyPI, the GitHub release cohort, the public
Scoop bucket, the public Homebrew tap, and the marketplace plugin, plus the MCPB
per-client repeat and the Claude namespace and description verification. Cost:
minutes each, assuming their channels are public and promoted.

E2. Write the availability documentation and the support matrix, naming only
channels with passing post-public evidence. The documentation gate is fail-closed
and currently passes vacuously because the README makes no positive acquisition
claim. Of the eleven required distribution rows, five have real passing evidence
today.

E3. Run the close audit against retained evidence, including an explicit
reconciliation of whichever way Decision one went.

## What the fastest useful path looks like

If the goal is the shortest distance to a product a person can install, the
ordering that matters is: do B1, B2, and B3 today because they are seconds and
they unblock three steps between them; do B4 today because reserving the root
PyPI name costs minutes and its absence is embarrassing rather than merely
blocking; do B5 before anything is armed; then spend the real effort on Stage A,
because a green cohort is the one thing with no substitute and every remaining
step is downstream of it.

D4 deserves separate mention. It is one typed sentence in a chat window, it
finishes a step that is otherwise fully captured, and it costs seconds. It is the
best effort-to-progress ratio in this entire document.
