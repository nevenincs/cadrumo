# `mcp-parity` reference: `admitted surface defects`

This record lists what is wrong or fragile in the part of the Cadrumo MCP surface that is already open, and the safeguards that live outside the operations. Every locator is relative to the root of this repository, on branch `feature/tui` at commit `85f84a2680`, read on 2026-10-10 by static analysis with nothing executed; the tree had uncommitted changes made by another session. It states facts about the code as it is. It records no decision and no recommendation. The registry, the three surfaces and the closed operations are in `2026-10-10-mcp-parity-surfaces-and-registry-reference` and `2026-10-10-mcp-parity-closed-operations-reference`; the sign-in and lease mechanics are in `2026-10-10-mcp-parity-sign-in-doors-reference`.

## Summary

Of 266 registered operations, 123 list the MCP frontend and 116 are reachable through it. Within that open part, the following hold today.

- Eight groups of sensitive writes are reachable with no confirmation, digest or secret channel on the MCP path, although the command line or the terminal interface applies one where a safeguard exists at all (section 1).
- Seven definitions list MCP and cannot run: six have no access resolver and one declares a secret MCP cannot send (section 2).
- Seven open operations carry a host path in their request, and an eighth that cannot run does too. None of the file-taking operations read checks where a path points beyond an extension list and, for some fields, an absolute-path rule (section 3).
- A table of safeguards that live in the command line or terminal interface rather than in the operation is in section 4, and request fields that hold a value standing for a human act or a taxpayer decision are in section 5.
- Three list definitions share a capability set that permits an update, and a session without the commit action is refused at the commit section, after the operation has started (section 6).
- A repeated key returns the earlier operation whatever its outcome. Cadrumo's accepted record on ledger-add idempotency chose a caller key and rejected content-derived identity (section 7).
- Discovery, session and demand-side limits are in sections 8 to 10.

The boundary with the tax agency is unchanged by anything below. `AeatAccessGate.require_live_write` always raises (`src/cadrumo/core/access_gate/gate.py:96-107`). Its only production call site is command-line dispatch (`src/cadrumo/entrypoints/cli/_command_runtime.py:346`), reached only for a command whose policy sets `live_write` (`:341-342`), and no command spec sets it. A tool call does not pass through that dispatch; on that path the boundary holds because no registered operation submits anything. `modelo.work.file` writes a local record only (`src/cadrumo/application/modelo/operation_definitions.py:975-981`). The `live.*` operations are read-only captures.

## 2. Seven definitions that list MCP and cannot run

Six have no access resolver. Resolution raises `OPERATION_UNAVAILABLE` for a registration without one (`src/cadrumo/application/operations/access_resolution.py:478-491`).

- `user-profile.automation-request`, `-rotate`, `-renew` and `-scope`: the registration passes a resolver only for the three human definitions (`src/cadrumo/application/user_profile/automation_operations.py:77-83,443,450`), and only those three are limited to the command line and terminal interface (`:413-417`). The four proposals list every frontend.
- `export.google-sheets`: every frontend (`src/cadrumo/application/export/google_operation.py:556`); the registration is composed without a resolver (`:574-591`). The command line submits it (`src/cadrumo/entrypoints/cli/runtime_modelo_spreadsheet_push.py:62-70`).
- `local-reader.provision`: every frontend (`src/cadrumo/application/local_reader_operation.py:111`); registered without a resolver (`:115-131`).

The seventh, `user-profile.bundle-export`, has a resolver and declares an ephemeral secret with a five-minute lifetime (`src/cadrumo/application/user_profile/operations.py:219-229`). The MCP `execute` tool does not start an operation whose receipt carries a secret requirement (`src/cadrumo_harness/mcp/admitted_operations.py:119-121`). The client refuses to send a secret from any frontend but the command line and the terminal interface (`src/cadrumo/adapters/local_runtime/frontend_client.py:310-316`), and so does the runtime (`src/cadrumo/entrypoints/runtime/profile_connection_operations.py:89-90`; `src/cadrumo/entrypoints/runtime/operation_host.py:385-392`). Its request also carries an absolute `destination` path (`src/cadrumo/application/user_profile/profile_operation_contracts.py:287-302`). What state a submitted operation of this kind is left in was not traced.

Correction, 2026-10-10, from a second reading while the guard was built: the six `output_root` rows above overstate what the runtime does. What the closed file-taking operations do with the bytes: evidence add copies them into the encrypted attachment store (`src/cadrumo/adapters/persistence/storage/attachment.py:305-313`) and keeps the path as the operator typed it (`src/cadrumo/application/ledger/evidence.py:756-768`); statement import parses them and stores rows whose provenance keeps the basename and a content digest (`src/cadrumo/domain/transactions/raw_transaction.py:52-86`). ## 6. Operations described as reads whose profile permits an update

The inventory, prorrata and capital-goods registrations build every definition, list included, with `RECORDED_IDEMPOTENT_SECURE_INPUT_UPDATE_CAPABILITIES` (`src/cadrumo/application/inventory/registered_operation.py:107`; `src/cadrumo/application/prorrata_register/registered_operations.py:95`; `src/cadrumo/application/bienes_inversion/registered_operation.py:97`). Its permitted effects include an update (`src/cadrumo/application/operations/capabilities.py:238-250`; `src/cadrumo/core/operations.py:88-94`). Their resolvers add the commit action only for the mutating ids (`src/cadrumo/application/inventory/registered_operation.py:66-90`; `src/cadrumo/application/prorrata_register/registered_operations.py:56-58`; `src/cadrumo/application/bienes_inversion/registered_operation.py:78-80`). `ledger.inventory.valuation.preview` is in the mutating set despite its name (`inventory/registered_operation.py:66-73`). The public contract lists `permitted_effects` per definition (`src/cadrumo/application/operations/registry.py:104`).

Refusal for a session without the commit action comes at the commit section, not at submission.

- The scope check is per action (`src/cadrumo/application/user_profile/operation_access_policy.py:46-57`). The commit action is requested only when an executor opens its irreversible section (`src/cadrumo/application/operations/_execution_context.py:82-96`; `src/cadrumo/entrypoints/runtime/operation_authority.py:475-479`).
- The effect recorder checks only that the definition permits the effect, not that a guard is held (`src/cadrumo/application/operations/_execution_context.py:233-245`).
- Before the commit section the following can already have happened to a session that lacks it.
  - For a live capture, a provider browser process is built and owned and the acquire phase is announced (`src/cadrumo/application/live/live_operation_execution.py:60-70,130-148`). The authenticated session is then acquired through `ensure_live_authenticated_session`, which with no guard acquires without one and with a guard stages session writes and publishes them inside it (`src/cadrumo/application/live/session.py:70-97`); what the acquisition does with the guard internally was not read.
  - The local classifier runs in the acquire phase of the review operations, before the commit section (`src/cadrumo/application/ledger/llm_review_execution.py:276-326`, against `:193-197`).
  - The submission stores its request, writes a journal record and takes the definition-subject lease (`src/cadrumo/application/operations/_supervisor_submission.py:81-96,147-177`). A second submission of the same definition and subject is refused while the first is unsettled (`src/cadrumo/application/operations/_supervisor_lease.py:185-230`), which the host reports as `OPERATION_UNAVAILABLE` (`src/cadrumo/entrypoints/runtime/operation_host.py:306-308`).
  - Read-only live reports are stored without an irreversible section (`src/cadrumo/application/live/live_operation_execution.py:105-116`).

## 7. Replay and idempotency as built

- A claim binds the definition id, the subject reference, a digest of the key, the operation id and the request reference (`src/cadrumo/application/operations/persistence/idempotency.py:13-46`). The request reference is a content address of the payload (`src/cadrumo/adapters/persistence/operations/secure_references.py:82-84`; `src/cadrumo/application/operations/_supervisor_submission.py:87-96`).
- The claim is built whenever the submit carries a key (`_supervisor_submission.py:137-143`). I found no check against the definition's declared replay policy in that path. The declared policy differs by definition: none for `modelo.reconcile.import` (`src/cadrumo/application/operations/capabilities.py:186-198`), idempotent submit for the profile writers (`src/cadrumo/application/user_profile/operations.py:139`), resumable for the review operations (`src/cadrumo/application/ledger/llm_review_operation.py:156`).
- Resolution scans every journal file under the exclusive journal lock and returns the earlier operation id without reading its lifecycle or outcome (`src/cadrumo/adapters/persistence/operations/journal.py:243-268,282-285`; `_supervisor_submission.py:144-146`). The claim has no expiry in the code read.
- The same key with a different request is refused: the scan raises `operation idempotency key is bound to a different request` (`journal.py:253-264`), which the host maps to `OPERATION_UNAVAILABLE` (`src/cadrumo/entrypoints/runtime/operation_host.py:306-308`).
- A replay returns the earlier submission but does not revive its response capability (`operation_host.py:300-305`).
- The key is optional on the MCP `execute` tool (`src/cadrumo_harness/mcp/protocol_contract.py:91-98`) and is passed through unchanged (`src/cadrumo_harness/mcp/admitted_operations.py:134`); the tool never generates one. A lost submit reply returns `unresolved` with the request id and definition id (`admitted_operations.py:138-145`).
- The command line's generic submit sets no wire key (`src/cadrumo/entrypoints/cli/runtime_registered_operation.py:134-143`). `ledger.add` and evidence add carry their own key as a payload field (`src/cadrumo/application/ledger/ledger_add_contracts.py:85`; `src/cadrumo/entrypoints/cli/runtime_ledger_add.py:168`). The terminal interface passes a wire key when its caller gives one (`src/cadrumo/entrypoints/tui/operations/runtime_controller.py:267-275`).
- Stored invocations are pinned to the definition contract digest, which a result request carries (`src/cadrumo/application/operations/frontend_requests.py:418-433`).

What Cadrumo's accepted record on ledger-add idempotency decided: `.vault/adr/2026-06-30-ledger-add-idempotency-adr.md`, status `accepted` (`:14`). Its problem is that a retried `ledger add` double-writes because the transaction id folds the current time (`:22-26`). It weighed three mechanisms (`:69`).

- Chosen, option (b), a caller-supplied key: "The agent passes a stable key per logical add; a second add with the same key returns the existing row as a no-op" and "Genuine duplicates remain expressible (two distinct keys, or the keyless append path)" (`:80-84`). A reused key with different content is refused, not overwritten (`:139-142`). The keyless path stays an append "that supports two identical same-day cash payments by construction" (`:143-147`).
- Rejected, option (a), content-fingerprint dedup: "it cannot distinguish a retry from a genuine second identical same-day movement" without a clock read or an override flag (`:71-79`). It is kept only as a non-blocking advisory.
- Rejected, option (c), a content-only id: "it makes the id itself collapse two legitimate identical same-day movements into one row", which "would convert a genuine second cash payment into a silent overwrite" (`:85-88`).

## 8. Discovery limits

- `search` iterates the ids of the session's effective scope and issues one contract request per id, all under one 30 s deadline fixed at the start of the call (`src/cadrumo_harness/mcp/admitted_operations.py:43,64,83-95`; `src/cadrumo/adapters/local_runtime/frontend_operation_client.py:107-120`). It skips ids refused as `frontend_denied` or `operation_denied` and lets any other refusal fail the whole search (`admitted_operations.py:89-92`). It has no limit, paging or filter argument (`src/cadrumo_harness/mcp/protocol_contract.py:85-89`), ranks lexically (`src/cadrumo_harness/mcp/operation_search.py:16-28`) and returns the contract without the request schema (`admitted_operations.py:95`). `execute` also issues a contract request first (`:107`).
- A grant lists exact ids; the scope has no operation wildcard (`src/cadrumo/application/user_profile/access_contracts.py:78-93`), so `search` shows only ids already granted.
- The public contract holds no subject-reference form (`src/cadrumo/application/operations/registry.py:80-110`); the request schema describes the payload. `subject_ref` is free text of 1 to 256 characters (`src/cadrumo/application/operations/models.py:46`; `src/cadrumo_harness/mcp/protocol_contract.py:95`). Forms in use include `profile:<uuid>` (`src/cadrumo/core/operations.py:163-169`) and, for the census review, the raw profile UUID, while its own prepare step uses the prefixed form (`src/cadrumo/entrypoints/tui/aeat_sync/runtime_handoff.py:158,447`).
- Reading a result needs the operation id and terminal revision from `observe`, and the contract digest and result schema identity from `describe` (`src/cadrumo/application/operations/frontend_requests.py:418-433`; `src/cadrumo_harness/mcp/admitted_operations.py:182-184`). A result is read in 32 KiB pages with a 16 MiB document ceiling (`src/cadrumo/application/runtime/projection_pages.py:19-20`), which is up to 512 pages under the same 30 s deadline.

## 9. Session limits on the key route

- A key session has a lease of at most five minutes (`src/cadrumo/application/user_profile/access_contracts.py:28,179-180`; `src/cadrumo/application/user_profile/session_authority_admission.py:172`). - A review response capability is held in memory by the profile worker's operation host, keyed by operation id with the submitting session (`src/cadrumo/entrypoints/runtime/operation_host.py:94,108,301`). A response is refused unless the same session submitted the operation and the capability is present (`:525-532`); a new session, a replayed receipt or a reattached operation cannot obtain it (`:540-543`).
