# mcp-purpose-authentication reference: current authentication and process boundaries

Inspected the working tree on 2026-09-26, branch feature/mcp, base commit ef8ad07c1911ff68a46b0ee41f73b15a5a96624c. This is source evidence, not an execution or security certification. The worktree contains unrelated edits. Semantic search returned index_unverifiable; discovery continued through the complete paged ADR inventory and targeted source reads. No taxpayer data or secrets were inspected.

## Summary

### Profile password, acceleration receipt and AEAT login are different authorities

Normal profile authentication is owned by `src/cadrumo/application/user_profile/login_session.py:870`. Named invocation authentication has its own non-selecting entry at line 913. The module distinguishes the password-unlocked in-memory bucket session, the optional local acceleration receipt, and an AEAT session persisted inside encrypted profile storage.

The acceleration receipt contains an authenticated encrypted wrap of a profile DEK; its random wrapping key resides separately in the OS keychain. Receipt metadata binds profile identity, custody generation, DEK epoch and idle/absolute deadlines. It is not OAuth and has no remote counterparty. The implementation uses the v2 keychain service and a profile/session UUID pair; the older custody ADR still mentions a v1 account shape, which must not be copied into new work. Evidence: `src/cadrumo/adapters/persistence/storage/custody/acceleration_receipt.py:1`, mint at 709 and resume at 1026.

Current fallback settings are 15 minutes idle and 240 minutes absolute, with an absolute-setting ceiling of 720 minutes. Resumption preserves the original absolute deadline. Keychain failure can leave a process-local login, not a durable credential. Evidence: `src/cadrumo/core/config_runtime_fields.py:234`; `src/cadrumo/application/user_profile/login_session.py:479` and 1510.

The shared admission sequence reuses a bound session, resumes a receipt, then asks a supplied credential journey. Its reviewed input contract has no durable automation-grant admission path. The credential branch checks that the resulting session serves the returned outcome profile; a replacement design must also independently compare that profile with the requested target. Evidence: `src/cadrumo/application/user_profile/session_admission.py:125`.

### Existing operation supervision is the shared execution foundation

The application already defines OperationSupervisor for durable execution, owner leases, interactions, reconciliation and settlement. OperationComposedServices and compose_operation_services expose the public submission, observation, result, response, cancellation and detach doors. OperationRegistry owns registered definition contracts; these are distinct from the recovery-action catalogue. Evidence: `src/cadrumo/application/operations/supervisor.py:108`, `src/cadrumo/application/operations/composition.py`, `src/cadrumo/application/operations/registry.py`.

The production TUI OperationController submits and observes through those services and separately binds actor response authority. Observing an operation does not recover its apply/reject bearer. Evidence: `src/cadrumo/entrypoints/tui/operations/controller.py:48`. The persistence adapters already own journal, lease, secure-reference and financial-operand custody implementations under `src/cadrumo/adapters/persistence/operations/`. Generic operation metadata and canonical encrypted domain records have different retention contracts. A future local service can host these application services; source presence does not prove every existing executor is resumable or service-safe.

The accepted 2026-08-11-tui-architecture-adr owns this operation platform. Its later amendments replace package facades with direct defining-module imports, retire code-resident governance receipts, and restrict CLI TUI launch to the opaque `aeat app tui` child process. Its canonical roll-up plan owns unfinished platform migration. This feature must distinguish new authentication integration from that existing work.

### CLI and TUI have concrete credential and session seams

The installed TUI composes the shared profile-session admission service and its own credential screens; login, sign-out, handover and expiry are application outcomes around a fresh profile-inventory loop. Evidence: `src/cadrumo/entrypoints/tui/installed_session.py`, `src/cadrumo/entrypoints/tui/secret/login.py`. It is not a CLI command browser.

The CLI custody command declarations reside in `src/cadrumo/entrypoints/cli/config/_custody_command_specs.py`, joined by `command_specs.py`. `src/cadrumo/entrypoints/cli/config/secure_input.py` owns explicit bounded strict-JSON stdin/descriptor input, conflict-before-read selection, one-shot descriptor closure and no-echo interactive prompts. Windows inherited handle-to-descriptor mapping is explicitly different from POSIX descriptor inheritance. These channels accept credential inputs, not general secret-bearing output; safe API-key delivery is new work.

These source seams provide no reviewed API-key enrollment/list/rotate/revoke or separate automation-session management surface. CLI/TUI parity therefore requires new application-owned operations and independently usable projections, not a TUI link to CLI commands. The authenticated-human visibility policy is owned by 2026-09-04-tui-architecture-authenticated-tui-visibility-adr; it does not establish full-owner authority for a future restricted API-key login.

### The current MCP identity gate is an observation flag

SessionIdentityState records only whether an identity read happened. It stores no authenticated principal, immutable target, grant, deadline or revocation generation. A local read may proceed without that observation; mutation and AEAT-reaching calls generally require it. Known identity-changing commands rearm it. This is useful historical intent, but is not a credential or a complete cross-process binding. Evidence: `src/cadrumo_harness/mcp/identity_gate.py:99`, 134; construction in `src/cadrumo_harness/mcp/server.py:798`.

Application session publication is explicitly process-wide, with one unlocked profile per process. Target comparison is distinct from mere session presence, and the key accessor checks expiry. A service serving several profiles cannot adopt ambient process state as its routing authority. Evidence: `src/cadrumo/adapters/persistence/storage/master_key/active_session.py:95`, 117, 212.

Logout closes the current process binding, revokes selected profile acceleration and clears the durable active selector. This code does not establish a service-wide registry of separately revocable agent grants. Evidence: `src/cadrumo/application/user_profile/login_session.py:409`.

### The MCP secret bootstrap conflicts with the desired custody boundary

The launcher option --profile-secrets-file accepts a file containing a passphrase. The reader unlinks it, resumes the ambient profile, retains the passphrase in module globals and serializes it onto later CLI stdin. Unlinking a plaintext file does not make its creation compliant with the secure-storage-only rule; the retained Python string is also not proof of erasure. Evidence: `src/cadrumo_harness/mcp/main.py:111`; `src/cadrumo_harness/mcp/_profile_secret_channel.py:1`. This is a replacement requirement, not a recommended enrollment mechanism.

### Process provenance differs from older warm-runtime descriptions

The installed entrypoint is cadrumo-mcp; serving uses the Python MCP SDK and stdio. `pyproject.toml:33` currently declares mcp>=2,<3, so older v1 advice is historical. `src/cadrumo_harness/mcp/server.py:1300` constructs one server and anchors it to the stdio client.

Despite its name and stale warm-runtime prose, run_cli_in_process launches the installed CLI through run_captured. Thus a historical ADR or an inprocess telemetry label cannot prove execution was in the MCP process. Evidence: `src/cadrumo_harness/mcp/inprocess.py:125`; `src/cadrumo_harness/mcp/call_runtime.py:369`. The surrounding transport still has a thread timeout whose own documentation permits later background completion: `src/cadrumo_harness/mcp/_transport.py:452`. This source review did not exercise timeout outcomes.

The stdio watchdog uses Windows pipe-owner/ancestor process handles and POSIX ancestor observations, with bounded pre-exit hooks. It protects a client-owned adapter lifetime; it is not authentication and is not the lifecycle owner a persistent service needs. Evidence: `src/cadrumo_harness/mcp/_stdio_lifetime.py:1`, 156.

The MCP subprocess runner uses taskkill /T on Windows and process-group termination on POSIX; its Windows fallback can kill only the immediate child. Separately, custody contains supervised KDF process controls and Windows Job support. Neither source presence nor July audit completion proves current cross-platform containment. Evidence: `src/cadrumo_harness/mcp/call_runtime.py:133`; `src/cadrumo/adapters/persistence/storage/custody/_kdf_process.py:21`, 156.

### Published public authority is separate from private persistence

IndexedRegistryAuthority follows a descriptor and owns generation readers; operations acquire a pinned authority context. The current authority descriptor resolves to a content-addressed SQLite publication. A configured authority root does not fall back to the bundled copy. Evidence: `src/cadrumo/domain/calculations/registry/authority.py:557`, 867, 930; `src/cadrumo/domain/calculations/registry/authority_store.py:171`.

The accepted indexed-storage ADR supplies the publication, integrity, source-closure and lease contracts. These are public tax/profile-schema declarations, not taxpayer records. A profile's authentication cannot certify a calculation, select a tax year, or promote an advisory capability.

### AEAT authentication is separately verified

AEAT sessions use the provider/session orchestration in `src/cadrumo/application/auth/sessions.py:1` and encrypted persistence in `src/cadrumo/adapters/outbound/aeat/auth/session_store.py:1`. Provider verification and taxpayer identity checks are additional requirements; a local automation credential cannot guarantee that a certificate, Cl@ve flow, representation or remote session will remain usable.

No durable-backend, calculation, filing, packaged-client or OS-matrix acceptance tests were run in this design session. All remain separate validation obligations.

### Installed transport and profile admission, 2026-09-27

`entrypoints/runtime/bootstrap.py` installs `cadrumo-runtime` and starts an isolated interpreter before application imports. POSIX replaces the process; Windows retains a waiting launcher. The Windows execve/environment crash and its installed-launch correction are recorded in the audit/ledger. Relevant upstream evidence: https://github.com/python/cpython/issues/137934 and https://github.com/python/cpython/issues/143327.

`entrypoints/runtime/main.py` binds installed version, absolute root and physical storage identity before claiming an endpoint. `adapters/local_runtime/server.py` hosts bounded independent native-verified connections. Readiness does not open custody or confer application authority. After handshake, native non-consuming readiness separates idle connections from incomplete frames: idle peers remain connected, partial frames retain a total deadline, and stop wakes idle connections without cross-thread handle closure.

`application/runtime/installation.py` and `adapters/local_runtime/installation.py` own the anchored nonsecret installation identity and its distinct short transaction lock. Creation binds native owner and physical root atomically; corrupt or mismatching records refuse. Public status does not create it. `windows_login.py` uses retained peer process/token, LSA logon identity and fresh WTS generation/lock evidence. Uncertain eligibility refuses before credentials. The current runner has network logon in session 0, so positive interactive-login acceptance remains unproved.

`application/runtime/profile_access.py` defines explicit profile login, session status/refresh/lock and frontend binding. `entrypoints/runtime/profile_connections.py` performs native login preflight, sends a one-use secret-ready response and consumes a separate bounded secret frame. API client routing derives from protected grant records; existing verifier/unwrap admission proves possession. The server assigns connection identity. IDs, routing claims and requested scopes are not authority. `profile_host.py` composes one session authority, denial guard, control store and immutable worker per profile. Polling retires expired/lost authority; optional native-store failure fences automation independently of password access.

### Immutable profile workers and containment

`application/runtime/profile_worker.py` defines closed private commands. `adapters/local_runtime/profile_worker.py:ProfileWorkerProcess` starts the installed isolated worker in a creation-time Windows job, checks the actual connected peer belongs to that job and OS owner, and completes cohort/root/boot readiness before secret delivery. Custody-control and operation channels have distinct verified namespaces and locks. Non-Windows worker containment remains unavailable; platform completion is not claimed.

`master_key/profile_worker_binding.py` pins worker/profile/boot and physical root for the process lifetime. `active_session.py` checks that target. `profile_worker_custody.py` tracks independent leases, checks generation/DEK epoch, expires them using UTC and monotonic clocks and releases bucket/derived keys after the last lease. Its protected section defers physical key replacement/release while an independently authorized effect settles, without retaining logical access for revoked sessions.

`login_session.py:authenticate_profile_candidate` performs throttled password-envelope/sentinel proof without retargeting ambient custody. `entrypoints/runtime/profile_login.py` holds a bounded candidate until exact admission. `session_owner.py` connects existing ProfileSessionAuthority activation, refresh, human proof, lineage retirement and worker-loss fencing. Worker loss permanently invalidates that owner; replacement requires fresh admission.

### Operation execution and authority

`application/operations/authorization.py:OperationExecutionAuthority` extends the existing supervisor. Submission checks precede persistence; START checks precede durable admission and actual executor entry. Reconciliation checks resumable authority before lease takeover and at actual re-entry. `_execution_context.py` composes COMMIT authority with existing irreversible-section ownership, serializing different tasks while allowing same-task nesting. `user_profile/session_authority.py:operation_guard` keeps the thread-affine profile denial lock held through a protected body. Existing compositions without this port remain part of the pending private CLI/TUI migration.

`application/runtime/worker_authorization.py` defines strict permit/release/acknowledgement contracts. `adapters/local_runtime/worker_authorization.py` authenticates the actual control-pipe worker PID and job membership before accepting owner-resolved policy. Each permit holds the runtime guard on one dedicated thread, expires no later than the session or 30 seconds, and requires exact release. Ambiguous/missing release contains native descendants before unlocking. Callback signalling and settlement are separate to avoid joining a callback while holding its needed profile guard. `worker_authorization_client.py` uses independent verified channels and cancellation-complete acquisition/release, including late permits.

`application/operations/access_port.py` and `access_resolution.py` bind coordinate/readiness resolution to the existing OperationPublicDefinitionRegistrationV1. Exact request model, contract digest and host-owned profile/destination/frontend/action must agree. Missing resolution refuses. The field and repeatable-row mutation owners resolve profile-wide period-independent work; their real writes and encrypted result persistence run inside the COMMIT boundary with cancellation-complete worker-thread waiting. Calculation, filing, export and ambient logout do not acquire runtime authority merely by appearing in the registry.

`entrypoints/runtime/operation_host.py` pins the published authority lazily and hosts the actual production operation composition on one persistent loop. `operation_authority.py` binds admitted invocation operands/session and re-resolves current registered policy at execution/effect boundaries. Child tasks inherit no held permit. Separate custody-control I/O permits retirement while an operation waits for runtime authority. Bounded aggregate host drain and durable authority-generation provenance remain unfinished.

### Canonical retry and fresh continuation

`OperationSubmissionService.submit` distinguishes new invocation from canonical idempotent replay. Only new invocation reserves a process-local response capability. Same-actor, other-actor and replacement-host retries return the original receipt without issuing response authority. `OperationComposedServices.response` handles missing proof through the existing unavailable authority.

`OperationSupervisor.stored_invocation` loads pinned exact operands for the trusted host, never as a frontend payload. Fresh observation resolves those operands against current policy without retargeting execution. `continue_operation` excludes live local execution/settlement, checks exact active owner/token and delegates expired/absent lease classification to existing reconciliation. Created intent may start; only declared resumable checkpoints resume. The installed worker requires a fresh RESUME guard before rebinding idle intent, followed by separate actual START/RESUME and COMMIT checks. IDs and root keys never reconstruct transaction-specific response credentials.

Cross-profile, missing, stale-contract or damaged operands produce an allowlisted unavailable refusal. `OperationRegistry.decode_request_payload` rejects duplicate members/nonfinite literals before strict registered hydration, including JSON nested inside an operand frame. Conflicting idempotency and busy-subject refusals do not kill unrelated profile sessions.

### Public operation projections and disclosure

`application/runtime/operation_access.py` defines closed discovery, submit, start, resume and bounded observation requests over canonical contracts. Domain payload decoding remains in the immutable worker. `entrypoints/runtime/operation_projection.py` verifies the native worker's policy coordinates against the actual connection/session/profile/frontend/destination/action and invocation. It does not accept client-supplied policy or readiness. Submission receipts carry no response capability; lifecycle acknowledgements make no effect-success claim.

`application/operations/frontend_requests.py:OPERATION_OBSERVATION_PROJECTION_ID` identifies the canonical observation projection. Consent names that projection, operation-metadata category and exact enrolled destination. Human scope includes this independent projection; API output intersects reviewed grant consent. Worker observation writes occur inside their native authorization permit. The runtime then independently acquires fresh authority and retains it through the actual final native write, whose deadline is clipped to remaining session validity. Partial write failure closes the channel instead of retrying a refusal frame.

`VerifiedRuntimeConnection` correlates every reply to request, connection and boot. `RuntimeProfileConnections.operation` never holds the profile denial lock while waiting for worker operation callbacks. Registry-only discovery rechecks live scope under that lock and makes no domain-readiness claim. Guarded result/review/response projection wiring, durable publication/input provenance, private CLI/TUI convergence and complete platform lifecycle acceptance remain pending. Unsupported backend/calculation/filing functions remain unavailable.
