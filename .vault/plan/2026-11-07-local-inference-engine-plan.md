# `local-inference-engine` plan

Bundle a pinned llama-server as the default local engine, keep Ollama as a selectable second engine, and move all model fetching for both engines into Rust, with an identical local model experience.

## Description

Approved 2026-11-07

Authorization basis: the operator's first-hand ruling of 2026-11-07 to the orchestrating session, plus the coordinator's plan approval on 2026-11-07 with two binding adjustments, the executor tier rebalance and the integration model, both recorded below. The ruling: llama.cpp is the primary, prebundled default engine, Ollama support remains behind an agent-settings engine switch, and model acquisition changes internally while the experience stays identical. The coordinator approved steps (a) to (d) of that work on the same day and required this plan.

The plan implements `2026-11-07-local-inference-engine-adr` (accepted). Evidence is `2026-11-07-local-inference-engine-research` (native and agent coupling, CPU pass) and `2026-11-07-local-inference-engine-audit` (the `ollama_api` thinking defect).

Decision coverage. The local inference engine ADR governs every Step. It amends three accepted ADRs, and P01 applies those six amendments before any code Step executes:

- `2026-10-18-dependency-provisioning-unified-setup-adr` D1: the `local_ai` item is the selected engine's program. It bounds P03.S18 and P04.S21.
- `2026-10-24-rust-component-provisioning-adr` constraints 3, 8, 9 and 12: item shape, Rust-owned fetch and integrity, the `cpu_only` floor, and per-engine server start. They bound P03.S12 to P03.S18 and P04.S21.
- `2026-10-25-agent-owned-models-adr` constraint 9: progress from manifest sizes. It bounds P02 and P03.S14 to P03.S16.

The audit recommendations name choices for cadrumo-agent's owners. P02.S09 settles them within the audit's stated bounds: no thinking for structured extraction, a typed think-only refusal mapped onto the existing `output_invalid` or `run_failed` codes, a no-content deadline and one visible bounded retry. A new tax-side refusal code would need its own decision and is out of scope. The default vision route is settled by the 2026-11-07 amendment to the local inference engine ADR, from the GPU pass; P05.S25 keeps the remaining measurement work.

The ADR's Implementation hypotheses stay free inside its constraints: the build-pin file and format, how context reaches a router load, the router flags, the Hugging Face store namespace, how the desktop tells the manager which engine to run, and the Vulkan probe and macOS signing detail. If neither the preset route nor an undocumented per-load argument carries cadrumo-agent's context, the single-model-process fallback needs its own evidence first and is raised to the coordinator.

Coordinator constraints:

- Every Step is scoped to one repository, cadrumo or cadrumo-agent, named in its row.
- Every Step names its executor: `vaultspec-standard-executor` (Sonnet, high effort) for bounded work, `vaultspec-high-executor` (Opus, medium effort) for architecture-sensitive work. Smoke and acceptance Steps are always Opus.
- Tier rebalance (coordinator, 2026-11-07). Opus keeps the llama-server program and supervisor (P03.S17), router residency (P02.S07), the Rust registry and Hugging Face fetch clients (P03.S14, P03.S15, with P03.S16 that replaces the pull), the `/v1` chat model and lane contract (P02.S05), the engine record v3 and its migration with its admin action (P04.S19), and the packaged smoke (P05.S26). Sonnet takes pin and staging (P03.S10, P03.S11), pin generalisation (P03.S12), setup item enrolment (P03.S18), catalogue artefacts (P02.S03) and the audited `ollama_api` thinking fix (P02.S09, in progress). The Steps that were already Sonnet and are not fakes, the base URL (P04.S20), locales (P04.S22), the selector UI (P04.S23) and the default flip (P05.S27), also carry an Opus review. Each Sonnet Step above that carries an Opus review states it in its text, and the Step does not close before that review. The fake servers (P02.S04, P03.S13) and the gateway endpoints (P02.S08) stay Sonnet without a named review. P01 ran on Opus before this rebalance.
- Integration model (coordinator, 2026-11-07). Every P03 and P04 Step lands in `feature/tui` as soon as it is verified. Ollama stays the active default engine until the P05 packaged smoke passes, so the engine record defaults to Ollama until P05.S27 flips it. Each landing keeps tui compiling and the desktop app working, and needs a root build slot from the coordinator. cadrumo-agent Steps land in the cadrumo-agent main.
- Lane-contract requirement from the GPU pass: on llama-server b12184, `qwen3:4b` (Qwen3 4B Thinking 2507, from the Ollama blob) ignored `chat_template_kwargs` `enable_thinking:false`, spent 400 tokens thinking and returned only empty answers (schema-valid 0/5). P02.S05 therefore requires reasoning suppression for structured extraction, a typed refusal for think-only replies, and a re-run of that measurement cell as acceptance.
- Known gap: on the bundled Vulkan build `qwen3-vl:2b` generates at about 128 tok/s, against 261 to 267 tok/s on Ollama and on CUDA, about half. The remedy is the optional CUDA build, later. The gap does not block the 4b vision default (`2026-11-07-local-inference-engine-research`, GPU pass).
- Rust and CMake verification runs only in the root build tree `X:\code\cadrumo`, in a slot the coordinator sequences with the DESKTOP session. Never run cargo or cmake in a worktree. Never run `uv sync` or `just init` in a worktree.
- Prebundling must pass the existing component-pin and packaging-inclusion checks.
- The cadrumo-agent worktree is based on cadrumo-agent main after the Codex sync. Tell the coordinator before it starts.
- All work lands in `feature/tui` through the coordinator.

Out of scope: a CUDA build, vLLM, bundled model weights, and any Python provisioning, probing or launching of either engine.

## Parallelization

- P01 runs first. No code Step executes until its amendments are applied.
- P02 and P03 may run in parallel after P01, in separate worktrees. P02 owns the cadrumo-agent repository only. P03 owns `native/`, `dev/packaging/`, `dev/env/` and the `dev/quality/tests/test_no_model_definitions.py` gate in cadrumo only. Their write ownership is disjoint.
- Inside P02, P02.S02 and P02.S03 come first. P02.S04 precedes P02.S05 to P02.S07, which are sequential. P02.S08 and P02.S09 may run beside P02.S05 to P02.S07; P02.S09 shares `graph/enums.py` with P02.S02, so it starts after P02.S02 lands.
- Inside P03, P03.S10 then P03.S11 form the bundling track. P03.S12, P03.S13 and P03.S14 to P03.S16 form the acquisition track, and the two tracks may run in parallel. P03.S17 needs P03.S11, P03.S12 and P03.S13. P03.S18 needs P03.S16 and P03.S17.
- P04 depends on the P02 lane id (P02.S02) and the P03 engine contract (P03.S17 and P03.S18). Inside P04, P04.S19 and P04.S20 may run in parallel. P04.S21 needs P04.S19. P04.S22 precedes P04.S23.
- P05 runs after P04. P05.S27 runs last, after P05.S26 passes. P05.S24 precedes P05.S25 and P05.S26. P05.S25 waits for the coordinator's GO.
- Vault metadata writes (plan checks, ledger rows, index) and commits are serialized through one writer.
- The root build slot is serialized by the coordinator. Any Step whose verification needs cargo or cmake records the pending check and hands it to that slot rather than running it in a worktree.
