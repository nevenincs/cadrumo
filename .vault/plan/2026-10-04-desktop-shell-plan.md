# `desktop-shell` plan

Compose the Tauri desktop application as a React shell hosting the bundled user documentation, two persistent terminal sessions and a backend log flyout.

## Description

Approved 2026-10-04

Authorization basis: the user's explicit 2026-10-04 Tauri application spec to the orchestrator session (CADRUMO-BUILD-TAURI-TECHNICAL), plus the user decisions relayed by the designer session on 2026-10-04: a React shell at the app origin with the documentation in a cross-origin iframe served by the `cadrumo-docs` scheme; all four languages bundled (en, es, ca, hu); https and mailto links open in the system browser and everything else is refused; restart on Enter after a session exits; desktop-host events in the log flyout; docs-only zoom; remembered window and panel layout. Runtime management is on hold pending the user's ruling; see the blocked dependency below.

### Decision coverage

No new ADR. Every choice here is an implementation choice inside the user's explicit spec and the accepted decisions:

- `2026-10-03-application-packaging-interpreter-foundation-adr` governs the packaged interpreter, the fixed environment projection, package layout ownership (`native/package-layout.json`, `native/CONTRACT.md`) and the rule that native code supplies installation-relative bootstrap while Python owns Settings. Steps S01, S02, S04, S05 and S11 operate inside it. Tauri itself was settled by the user on 2026-10-03.
- `2026-10-04-application-distribution-adr` governs identity, the shared CMake/CPack graph and the rule that the Tauri executable is the desktop entry. S01, S08 and S10 extend that graph without a second identity or inventory.
- `2026-10-03-runtime-without-service-manager-adr` is the interim stance that predates this application work and is linked as the current accepted record. The user's 2026-10-04 framing: the runtime needs a manager, because without one MCP servers can never connect; the CADRUMO-RUNTIME-MANAGEMENT workstream owns that design, with an installer-side background manager as the preferred direction, and the user has not yet ruled. In this plan the TUI tab launches `python.exe -m cadrumo.entrypoints.tui` and shows that process's own output (S04); every runtime-dependent behavior is S12, a required dependency on that workstream, held until the ruling.
- The proposed `2026-10-03-application-packaging-adr` sketched a separate Tauri landing `index.html` beside `docs/index.html`. The user's 2026-10-04 spec supersedes that sketch in intent: the shell has no landing content and opens on the documentation index. Its proposal status is unchanged; this plan does not accept or amend it.
- Private-data rule (`.claude/rules/05`): the log flyout shows only records already redacted at write time by `SecretScrubbingFilter` in `src/cadrumo/core/logging.py`, plus native diagnostics that carry no payloads. Rust creates no new log files and reads no file outside the projected log directory. PTY output is not logging.

Open plans touching this code and the boundaries kept: `2026-10-04-application-distribution-plan` S05 owns build-path centralization; `2026-10-03-application-core-packaging-plan` owns `native/application/` internals (S04 adds only `ProcessRole::Repl` in `native/application/src/process/status.rs`); `2026-10-03-tui-all-mcp-integration-plan` owns `src/cadrumo` TUI changes (this plan changes only `src/cadrumo/core/logging.py` to hoist one constant); `2026-09-24-docs-build-performance-plan` S04 and S05 own `dev/deploy/docs_static_site.py` and the release workflow, which S03 does not touch.

### Composition

The window URL stays the shell `index.html` served from `frontendDist` (origin `http://tauri.localhost` on Windows). The shell embeds the documentation in an iframe whose source is the docs index for the preferred language on the `cadrumo-docs` scheme (origin `http://cadrumo-docs.localhost` on Windows, `cadrumo-docs://localhost` elsewhere). Terminals and the flyout live in the shell document and survive every docs navigation. Documentation is not embedded in the executable and is not in `frontendDist`: it ships as package files under `docs/user/` in the owner's apex layout (English at the apex, `es`, `ca` and `hu` under `docs/user/<lang>/`, matching the language switcher) with a docs manifest written by S01, and the Rust handler in S05 serves it read-only. The package manifest carries the docs manifest as one hashed member; interpreter startup never stats the roughly 63,000 docs files, the artifact verifier checks the full inventory, and S05 checks membership per request.

Options rejected, with evidence read on 2026-10-04:

- Docs as top-level pages with the shell injected through a Sphinx template or `WebviewWindowBuilder::initialization_script`: every page navigation is a full document load, which destroys the xterm.js instances; the PTY survives in Rust but the TUI screen and REPL scrollback do not. Replaying raw PTY bytes into a fresh terminal is not a correct repaint.
- Tauri multi-webview (separate docs and shell webviews in one window): the pinned `tauri 2.12.1` gates it behind the `unstable` Cargo feature (`tauri-2.12.1/Cargo.toml:130`, `unstable = ["tauri-runtime-wry?/unstable"]`); the flyout overlay would need Rust-side layout of overlapping WebView2 controllers; Playwright cannot drive the layout.
- Same-origin iframe (docs under the shell origin): simpler keyboard focus and history reads, but docs JavaScript (jQuery, Furo, mermaid, d3, pagefind) would run on the IPC origin. The user chose the cross-origin iframe with a postMessage bridge.

IPC origin finding that shapes S02, S05, S07 and S10: Tauri's `is_local_url` (`tauri-2.12.1/src/webview/mod.rs:1961-1999`) treats every registered custom URI scheme as local, so a page on the `cadrumo-docs` origin would pass the origin check and resolve capabilities as `Origin::Local` for the main webview (`src/webview/mod.rs:2005-2050`). Capabilities cannot be scoped to a frame origin inside one webview. Therefore the refusal is this application's own, and it does not rely on top-frame-only injection: on Windows wry injects every initialization script into subframes and ignores `for_main_frame_only` (`wry-0.57.0/src/lib.rs:1029`, `src/webview2/mod.rs:516-519`), and Tauri's own `__TAURI_INTERNALS__` and invoke key reach the docs frame (`tauri-2.12.1/src/manager/webview.rs:160-184, 425-441`). The barriers are:

- S02 mints a per-launch token of at least 32 bytes from `getrandom` and injects a self-gating script that returns unless `window.top === window` and `location.origin` equals the shell origin computed at runtime per `use_https_scheme` (`tauri-2.12.1/src/protocol/mod.rs:32-38`); the token is exposed once through a configurable getter that deletes itself after the first read. Every app command, including the moved interim `diagnostics_snapshot`, verifies the token.
- S02 registers `Builder::channel_interceptor` (`tauri-2.12.1/src/app.rs:1763`) so every channel frame is delivered through `webview.eval` into the top document and nothing sits in the fetchable `plugin:__TAURI_CHANNEL__|fetch` queue, which is ACL-exempt (`src/webview/mod.rs:2079-2082`) and uses sequential ids (`src/ipc/channel.rs:73-83`). S04 measures interceptor throughput under a flood.
- S05 sends `connect-src 'self'` on every `cadrumo-docs` response, including the pagefind worker script, because IPC responses carry `Access-Control-Allow-Origin: *` (`src/ipc/protocol.rs:49-52`); this is the barrier against the fetch transport.
- S07 grants no plugin JS command to the webview and uses no plugin click interception, wrapping clipboard, menu and opener use in token-guarded app commands.
- S10 proves refusal, not absence, from inside a docs frame: `invoke`, an `ipc.localhost` fetch, `window.ipc.postMessage`, `chrome.webview.postMessage` and channel fetch ids `0..N` during a terminal flood; nothing may be delivered or consumed, and the shell must receive every byte.

Contingency: if S10 observes any delivery to the docs frame, the fallback is a separate docs webview through Tauri's `unstable` multi-webview feature; the composition keeps the shell at the top and the docs in their own origin either way.

CSP pair. Origins are computed at runtime, never hard-coded: Windows `http(s)://cadrumo-docs.localhost` and `http(s)://tauri.localhost`, Linux `cadrumo-docs://localhost` and `tauri://localhost`, plus the `devUrl` origin in development; the S05 handler also checks the request host because wry intercepts any `http://cadrumo-docs.*` host (`wry-0.57.0/src/custom_protocol_workaround.rs:12-19`). Shell (`tauri.conf.json.in`, S01): the current policy with `frame-src 'none'` replaced by the docs origin for the build's platform; no `'wasm-unsafe-eval'` is needed on the shell origin. Docs (S05 response header on every response, with `X-Content-Type-Options: nosniff`): `default-src 'self'; script-src 'self' 'wasm-unsafe-eval' <sha256 hashes from the docs manifest>; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; worker-src 'self'; object-src 'none'; frame-src 'none'; frame-ancestors <runtime shell origin>; base-uri 'self'; form-action 'self'`. The closed MIME table adds `.pf_meta`, `.pf_index`, `.pf_fragment`, `.pf_filter`, `.pagefind` and `pagefind-entry.json` to html, css, js, mjs, json, woff2, svg, png and `application/wasm`. S05 probes `ICoreWebView2_22` (iframe and worker interception on a custom scheme) and `ICoreWebView2Settings3` at startup and refuses with a typed error when either is missing; S11 records the minimum WebView2 runtime. Evidence: the built English `index.html` carries one executing inline `<script>` and one `application/json` script, loads `pagefind/pagefind.js` through `cadrumo-docs.js`, and Furo's search form GETs `search.html`. Pagefind instantiates WebAssembly, hence `'wasm-unsafe-eval'` on the docs origin only. The built page also carries `https://cdn.jsdelivr.net/npm/mathjax@3/es5/tex-mml-chtml.js`; S03 removes it, and S01's remote-reference refusal cannot pass until S03 lands.

Docs manifest consumed by S05 (written by S01; field names are S01's to fix, semantics are these): language list with the entry path per language, a sha256 inventory of every shipped file, and the sha256 of each executing inline script. Build-only `.doctrees`, `_sources` and `.buildinfo` do not ship. Measured 2026-10-04: about 108 MB and 15,700 files per language, about 435 MB for four; a full four-language build takes at least 12 to 18 minutes. Content renders from committed goldens; only the sequence check gate needs a current authority, and whether the desktop lane skips it (`CADRUMO_DOCS_SKIP_SEQUENCE_CHECK`) is an open question for the user.

### Storage root pin (S02 defect fix)

Read on 2026-10-04: `configured_storage_root()` (`src/cadrumo/core/storage_environment.py:19-27`) anchors the default `var/storage` at `project_root()`, which is the repository when the module runs from a checkout and otherwise `Path.cwd()` (`storage_environment.py:10-16`); the Settings default uses the same anchor (`src/cadrumo/core/config_state_root.py:92-108`). The native host resolves the same default from the process cwd when no `pyproject.toml` ancestor exists (`native/platform/src/lib.rs:30-39, 57-62`) and sets `CADRUMO_LOCAL_STORAGE_ROOT` before Python starts (`native/platform/src/lib.rs:137`), so the fixed query's `os.environ` dump should already carry an absolute root and `environment.rs` passes it to every child. Two consequences stand regardless: in installed mode the root follows the launch cwd of `cadrumo.exe` (a Start menu launch anchors storage under the launch directory), and the designer's review reports a nested `<launch>/var/storage/var/storage` for the GUI child. S02 settles this by emitting the Settings-owned storage root variable (name taken from `Settings.storage_env_var_names()`, `src/cadrumo/core/config.py:1026-1031`) in the projection set to the resolved root, so host, TUI, REPL and CLI passthrough agree whatever their cwd, and proves it with a regression test in a relocated packaged layout without storage variables: each child kind's effective storage root equals `projection.storage`, and the CLI passthrough matches. Choosing the delivered per-user storage default for the packaged application stays a storage-owner decision and an open question for the user; `native/CONTRACT.md:66-68` lists it as open.

### Session model

One live PTY session per kind, `python` and `tui`, in `native/desktop/src-tauri/src/terminal/`. `terminal_open` refuses a kind that is already live (`session_unavailable`). After `exited` the entry stays readable until the next `terminal_open` for that kind replaces it; restart is frontend-only (the next Enter calls `terminal_open`). `terminal_close` terminates and settles with the existing 3 s bounded join and returns only when settled. Window close attempts both kinds even if one fails, each with the same bound; a settlement failure keeps the window open and is logged, as today in `app.rs`. A top-frame page load (the shell document reloading) settles or replaces both sessions. Bounds per session: input 8 queued writes of at most 64 KiB, with the frontend retrying `queue_full`; reader chunk 8 KiB; unacknowledged output window 512 KiB with resume below 128 KiB, enforced by pausing the PTY reader on a condvar or timed wait that also watches `stopped`, so settle wakes it inside the 3 s bound and no byte is dropped; the child then blocks on its own write. Acks carry a cumulative offset and are refused for a replaced session. PTY bytes no longer enter the diagnostics capture ring (`native/desktop/src-tauri/src/terminal/mod.rs:194` stops copying output); diagnostics keep events only.

Tab A runs `python.exe` with no arguments: the host applies isolated configuration itself (`native/interpreter/windows/python.c:22-43` forces `isolated`, `use_environment = 0`, no site, no bytecode, `safe_path`), so `-I`, `-E`, `-s` and `-B` are redundant and `PYTHON*` variables are ignored; an interactive terminal makes `Py_RunMain` start the REPL and the host prints its own banner. Environment is the existing child projection, which after S02 carries the pinned storage root, so cwd no longer selects storage. The REPL starts in the user home and never inside the storage root, so a relative REPL write cannot land plaintext in custody; the TUI starts in the projected storage root as today. Both kinds share one child environment. Tab B runs `-m cadrumo.entrypoints.tui`, otherwise unchanged. The TUI reports runtime refusal itself (`src/cadrumo/entrypoints/tui/installed_session.py:192-201` writes the reason and exits 1); the tab shows that output and offers Enter to restart. Nothing else about the runtime is designed here.

### Transport

Terminal output moves from polling to one Tauri Channel per session carrying tagged frames, so a single channel index orders data and lifecycle (`tauri-2.12.1/src/ipc/channel.rs:281-315`): a data frame carries PTY bytes, and `started`, `exited` and `failed` frames carry lifecycle. S04 defines the frame encoding (one tag byte followed by the payload is the expected shape; the final layout is S04's). Rust sends the `exited` frame only after the last data frame and the joined workers, as `Session::read` already orders today. All frames pass through the `channel_interceptor` into the top document. `terminal_write` accepts both a raw body and a bounded JSON byte array, because Tauri switches to the postMessage transport for the page's life after one fetch failure (`@tauri-apps/api` `ipc-protocol.js:24, 59-70`); headers are a plain object; both paths are tested. Logs use one `Channel<LogBatch>` per subscription at most ten batches per second; polling stays only for `diagnostics_snapshot`, which the flyout no longer needs. Raw channel payloads are supported by the pinned Tauri (`tauri-2.12.1/src/ipc/channel.rs:143-183`).

### IPC contract

Field names may change in S08; semantics are user-approved. `HostFailure` is the existing serialized `ApplicationError` (`code`, `operation`, `message`). Every app command takes `token` (the launch token) and refuses a mismatch with `invalid_arguments`.

- `desktop_environment{token}` -> `{outputLanguage, docs:{origin, languages:[{code, entry}]}}`. `outputLanguage` comes from Settings through the fixed Python query; `entry` is the manifest entry path for the apex layout.
- `terminal_open{token, kind: "python"|"tui", cols, rows, frames: Channel<TerminalFrame>}` -> `{session: u64}`. `TerminalFrame` is a tagged frame: `data(bytes)` | `started{pid}` | `exited{code: number|null}` | `failed{error: HostFailure}`; encoding fixed by S04.
- `terminal_write` with either a raw body (<= 64 KiB) or a bounded JSON byte array of the same limit, and headers as a plain object `{x-cadrumo-session, x-cadrumo-token}`; refuses `queue_full` beyond 8 pending writes and the frontend retries.
- `terminal_ack{token, session, offset}` with a cumulative byte offset, refused for a replaced session; `terminal_resize{token, session, cols, rows}` (2..=1000 each); `terminal_close{token, session}` -> `{}` when settled, else `cleanup_failed`.
- `logs_subscribe{token, records: Channel<LogBatch>}` -> `{subscription, state}`; `logs_unsubscribe{token, subscription}`. `LogBatch` = `{records: LogRecord[], dropped: u64, state: LogSourceState}`. `LogRecord` = `{seq, source: string (open enum, currently "python"|"host"), timestamp: string, timestampMs: number|null, level: "DEBUG"|"INFO"|"WARNING"|"ERROR"|"CRITICAL"|null, logger: string|null, message: string, detail: string|null, process: null | {role, pid}}`. `LogSourceState` = `{kind:"available"|"missing"|"unreadable", detail: string}`. Backlog 5,000 records, host ring 10,000, lines over 16 KiB truncated, decode lossy UTF-8.
- `open_external{token, url}`: only `https:` and `mailto:` schemes; everything else refused. Implemented with the `opener` crate (or `open_js_links_on_click(false)` on the webview), never plugin click interception, because plugin initialization scripts reach subframes.
- `shell_clipboard_read{token}` -> `{text}`; `shell_clipboard_write{token, text}` (<= 1 MiB); both over the clipboard-manager Rust API.
- `shell_context_menu{token, items:[{id, label, enabled}], x?, y?}` -> `{chosen: id|null}`: synchronous shape, implemented as an async command. `popup_at` blocks until the menu closes (`muda-0.20.0/src/platform_impl/windows/mod.rs:906-935`); a `run_on_main_thread` sentinel then resolves `null` deterministically after any pending `MenuEvent`. Item ids are namespaced `ctx/<popupSeq>/<item>`, a busy mutex refuses a second open popup, `&` is escaped on Windows, and `x`, `y` are a `LogicalPosition` in shell CSS pixels (iframe rect plus border plus `clientX`/`clientY`, no `devicePixelRatio`); `None` means the cursor position for pointer-opened menus.
- Window state (size, position, maximized) is restored by the `tauri-plugin-window-state` Rust side; no JS surface.

Shape changes against the designer's proposal, for the orchestrator to relay: one tagged-frame channel per session replaces the `output` plus `events` pair; `terminal_ack` carries a cumulative `offset`; `terminal_write` accepts a JSON byte array as well as a raw body; clipboard and context menus are app commands over the plugins' Rust APIs instead of granted plugin JS commands, so the docs origin cannot reach `plugin:clipboard-manager|read_text` or menu commands; `shell_context_menu` coordinates are optional; every command carries `token`; `LogRecord.source` is an open enum. Note for S09: the shell accepts a bridge `open-external` only when `navigator.userActivation.isActive` and under a rate limit, and browser-mode tests need a stand-in docs origin. Docs bridge (`cadrumo-desktop` envelope, version 1; docs to shell `ready`, `location`, `theme`, `shortcut`, `open-external`, `context-menu`; shell to docs `keymap`, `command`, `zoom`) is the designer's spec and is implemented on the docs side by S03 and on the shell side by S09.

### Log aggregation

Source of truth is the Python rotating log file: `default_log_file_path()` under the projected logs directory, written by every Python child that calls `configure_logging()` (TUI, CLI, REPL code that reaches it) with the line format `%(asctime)s [%(levelname)s] %(name)s: %(message)s` (`src/cadrumo/core/logging.py:864`), already scrubbed. S02 hoists that literal into `LOG_FILE_FORMAT` and the projection returns it so Rust holds no copy. Rust tails the current file and its `.1..N` rotations by offset, detects rotation by shrink or identity change, tolerates late, skipped or racing rotation on Windows (a rename can fail while a writer holds the file), never infers process exit from file events, and attaches continuation lines (tracebacks) as `detail`. Profile workers are not assumed to log to `cadrumo.log`; the reader adds no storage, log or Settings variable beyond the Settings projection. Host records are events only: the existing `Diagnostics` events (`native/application/src/diagnostics/mod.rs`) and terminal lifecycle failures. PTY bytes and captured child output never enter diagnostics or the flyout (private-data rule); S04 stops the copy at `terminal/mod.rs:194`. Records are not persisted anywhere new.

### Build and package graph

S01 owns the docs target, staging and manifest; CMake makes the desktop host and the package stage depend on it. S13 stages `cadrumo.exe` at the package root beside `python.exe` through a separate desktop declaration in the platform mapping (`native/platforms/windows-x64.json`) fed by the desktop artifact locator written by `native/desktop/scripts/tauri.mjs`; the `entrypoints` map in `native/package-layout.json` stays reserved for C-host console scripts (`dev/packaging/native/layout.py` refuses names outside `[project.scripts]`, and `native/cmake/platforms/Windows.cmake` compiles `host.c` per entry). The copy happens in `assemble.py` before manifest hashing, at the same spot as the entrypoint copy, and the executable joins `startup_files`; the stage depends on `desktop-host-build`; the `CADRUMO_DESKTOP_EXECUTABLE` registration rule in `native/CONTRACT.md` is reconciled so the distribution definitions name the staged file. Frontend assets build with Vite into `frontendDist` and are embedded by Tauri as today; Debug and Release keep the existing Cargo profile mapping in `native/desktop/scripts/configuration.mjs`. The package manifest hashes the staged docs like every other file. The development flow stays `vite dev` and `vite preview` for the shell in a browser; the Rust scheme serves development docs only from a staged tree carrying the docs manifest, selected by `CADRUMO_DESKTOP_DOCS_ROOT`, never from the port-8788 docs server. S02 adds `getrandom` (already in Tauri's graph) and S07 adds the `opener` crate (or uses the webview's own link policy), `tauri-plugin-clipboard-manager` and `tauri-plugin-window-state` to the desktop `Cargo.toml` and `Cargo.lock` (builds run `--locked`); S07 also adds a feature-gated `webview2-com 0.39.1` dependency to `native/platform/Cargo.toml` (or a small separate crate) for the `ICoreWebView2Settings3` casts, because the desktop crate forbids `unsafe` and the platform crate is a C-host staticlib/cdylib, coordinated with its owner. Pinned crates: tauri 2.12.1, wry 0.57.0, webview2-com 0.39.1, muda 0.20.0, portable-pty 0.9.0. No JS plugin packages are added, so `package.json` is untouched outside S09.

### Required dependency: runtime management (held pending the user's ruling)

The TUI, the MCP servers and every registered operation need a running local runtime; the TUI without one exits with its own refusal line. Runtime management is a required dependency of the TUI tab. Its design belongs to the CADRUMO-RUNTIME-MANAGEMENT workstream (installer-side background manager preferred) and waits for the user's ruling, which also decides how the interim no-service record is amended or superseded. Until then this plan presents only the TUI process's own output, and S12 holds every affordance that depends on the manager: availability presentation beyond the TUI exit line, start or attach from the desktop app, retry policy, and the handling of runtime authentication prompts and timeouts that surface inside the TUI. No executor runs S12 before the ruling.

Questions for the user and the RUNTIME-MANAGEMENT session: which process owns the runtime lifetime while the desktop app is open and after it closes; what the desktop app may show when the TUI exits because no runtime is reachable; how authentication prompts and runtime timeouts inside the TUI tab should be presented or relayed; and which record will carry the ruling so S12 can link it.

### Other open questions for the user

- The delivered per-user storage default for the packaged application (storage-owner decision; today the root follows the launch cwd in installed mode).
- Whether the desktop docs lane may skip the sequence check gate (`CADRUMO_DOCS_SKIP_SEQUENCE_CHECK`).
- Whether `python.exe` in Tab A should expose `--check-package` or stay a plain REPL.
- Whether S01's remote-reference refusal should also reject `https://` links in page bodies (anchors) or only loaded resources; this plan assumes loaded resources only, with anchors routed through `open-external`.
