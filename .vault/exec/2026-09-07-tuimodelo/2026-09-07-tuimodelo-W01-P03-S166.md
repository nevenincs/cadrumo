# Shrink the unreachable-module ratchet by the capability module this phase's relocation frees, in the same commit as the relocation

## Scope

- `dev/quality/unreachable_module_ratchet.toml`

## Changes

- `M` `dev/quality/unreachable_module_ratchet.toml`
- `verify:` `python -m dev.quality.unreachable_module_ratchet` -> `exit 0, no stale and no regression`

## Notes

The ratchet named a module the preceding relocation deleted, so the accepted set no longer matched
the tree. The entry was removed and the allowed set went from ten to nine. The gate reports clean
with neither a stale nor a regression line, and the deleted module appears nowhere in its output.

THE SAME-COMMIT OBLIGATION WAS NOT MET, AND IT CANNOT BE MET HERE. A step that resolves a ratcheted
module must shrink that ratchet in the same commit. This repository runs an automatic commit
process that captured the relocation before the ratchet entry was removed, so the shrink lands in
a later commit whatever this step does, and rewriting history to merge them is forbidden. The
failure is recorded rather than papered over, because the obligation exists to stop a resolved
entry lingering, and the entry did linger across at least one commit.

The consequence generalises beyond this step and belongs with the plan rather than here: two of
the six standing obligations require a same-commit landing, and neither is satisfiable for any
multi-file change the commit process splits. That is a scheduling decision for the operator, not
something to redefine quietly in an execution record.

A CLAIM MADE EARLIER IN THIS STEP WAS WITHDRAWN. The step opened by asserting the gate was red
because of the stale entry. That was never established: a gate run launched before the fix exited
zero, but the entry was removed while that scan was still in flight, so the run may have read the
edited baseline and the pre-fix state is unknowable from it. The gate's own logic says a
listed-but-absent module should fail, but should is not did, and the evidence to prove it was
destroyed by editing an input underneath a running gate. The fix is correct on its own terms
regardless of what the gate did beforehand.
