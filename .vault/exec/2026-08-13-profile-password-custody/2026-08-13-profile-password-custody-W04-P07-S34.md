# Have Terra XHigh give bucket rename, bucket delete, retention-floor enforcement and archive inspect a successor owner after their removal from the maintenance service, or record each as deliberately retired with the operator route that replaces it

## Scope

- `src/cadrumo/application/bucket_maintenance/`

## Description

- Ground each of the four capabilities against the commit that removed them and the tree's current state.
- Rule retention-floor enforcement first and separately, per the row's instruction.
- Delete the dead command/result contract residue for the three retired composition verbs (`_contracts.py`).
- Correct the package docstring (`__init__.py`) to stop describing removed capability as live.
- Leave `_manifest_digest.py` and `_service.py` untouched; hand back anything that needed a change there.

## Outcome

**Removing commit for all four, one act:** `7c062ed17e feat(user_profile): make the custody capsule the sole profile authority` gutted `_service.py` from a ~244-line composition surface (rename, delete, archive, restore, export, import) down to locking plus four read-only projections (`assess_deletion`, `browse`, `disk_usage`, `deletion_target_locks`). Its own docstring already says so truthfully: "archive, restore, bundle import/export, legacy rename, and manifest-backed lifecycle mutation have no current implementation and are intentionally not exposed here."

**Retention-floor enforcement (ruled first, separately, per the row).** NOT retired — it is a live guard with a named successor already in flight, and inventing a second implementation here would violate the one-mechanism rule. `W04.P07.S77` gave the refusal its raise site: `_refuse_erase_inside_the_retention_floor` in `src/cadrumo/application/config_reset.py`, checked at the point bytes are destroyed inside `_delete_targets`, bite-proved by a real refusal test. `W05.P08.S137` restored the full retention detail (count, floor, safe-erase date) to the filing-retention projection instead of a bare boolean. `W05.P08.S155` gave the retention snapshot a producer at filing-persistence time (fail-closed on absence, best-effort on write). `W05.P08.S157` closed the absence/emptiness ambiguity by recording an empty snapshot at profile creation. The one open link in that chain is `W05.P08.S154` — open, unchecked, explicitly scoped to `src/cadrumo/application/bucket_maintenance/_service.py`, and its own row text says the contract is "now fully answerable but the producer still refuses every existing target for want of an authenticated retention assessment, which is the sole cause of fifteen failing reset recovery and concurrency modules." Verified live: `BucketMaintenanceService.assess_deletion` at `_service.py:95-124` still unconditionally raises `BucketDeleteRefusedError("current custody deletion requires an authenticated retention assessment")` for any existing target with a committed label — it has not yet been wired to the S137/S155/S157 data. Confirmed the bite: `pytest src/cadrumo/application/tests/test_config_reset.py` shows exactly this raise site failing six tests (`test_retention_preflight_pauses_before_auth_pointer_or_bucket_mutation`, `test_resume_converges_after_a_target_is_removed_out_of_band`, `test_status_is_a_read_only_journal_view`, `test_resume_pauses_once_when_target_content_changed_then_accepts_new_snapshot`, `test_resume_adds_changed_pointer_target_under_the_same_operation`, plus one auth-session-shaped failure), all pre-existing and unrelated to this Step's edits (`_service.py` was not touched). **`_service.py` is explicitly outside this Step's ownership** (assigned to S154), so no fix was attempted here; the successor owner is S154 by name, confirmed rather than assumed.

**Bucket rename.** The mutation primitive survived the removing commit under a different name: `ProfileCapsuleLifecycle.rename_label` in `src/cadrumo/application/user_profile/_lifecycle.py:149-164` delegates to the canonical custody transaction owner and is exercised by `application/user_profile/tests/test_capsule_lifecycle.py`. It is the successor. But it has **zero CLI callers** — grepped the whole `entrypoints/` tree for `ProfileCapsuleLifecycle` and `rename_label(`; only application-layer definitions and tests use it. `aeat config profile --help` lists `capabilities, censo, create, descendiente, edit, history, list, preflight, show, status, validate` — no `rename`. `src/cadrumo/entrypoints/cli/tests/test_config_profile_surface_inventory.py` still asserts `rename`/`delete`/`export`/`import`/`duplicate` are mounted verbs; confirmed live that `aeat config profile rename --help` exits with "No such command 'rename'." That inventory test, and the CLI-wiring gap it names, sit in `entrypoints/cli/**`, outside this Step's ownership; not fixed here, reported below.

**Bucket delete.** Same shape as rename: `ProfileCapsuleLifecycle.prepare_delete` / `confirm_delete` / `delete` (`_lifecycle.py:195-203`) is the successor primitive, and it is reachable — but its only production caller is the durable **all-profile** `application/config_reset.py::_delete_targets`. There is no single-target `config profile delete` (or equivalent) CLI verb; the sole operator route today that reaches deletion at all is `aeat config reset start --yes`, which durably erases every local profile in one operation, not one named bucket. Confirmed no other caller of `ProfileCapsuleLifecycle(...).delete(` exists outside `config_reset.py` and its own test. This is a real capability gap (single-target delete has no operator route), not something this Step is authorised to build; recorded for the row's own honesty rather than silently narrowed.

**Archive inspect (and archive/restore generally).** Genuinely retired with **no successor primitive at all**, unlike rename/delete. `ArchiveBucketCommand`/`RestoreBucketCommand`/`InspectBucketArchiveCommand` and their results existed only as this package's now-orphaned contract shapes; no equivalent method exists on `ProfileCapsuleLifecycle` (it has `create`, `restore`, `select`, `prepare_delete`/`confirm_delete`/`delete`, `recover_create` — `restore` there means password-authenticated sealed-archive restore per the `2026-08-13-sealed-archive-transport-successor-adr` / `2026-08-13-profile-password-custody-rollup-adr` roll-up, a different concept from reactivating a soft-tombstoned bucket). The CLI-side `_bucket_archive.py` and `_sandbox.py` modules under `entrypoints/cli/_config/` are gone from source (only stale `.pyc` in `__pycache__`), and `config profile archive ...` is unmounted. `entrypoints/cli/tests/test_profile_archive_roundtrip.py` still targets that dead surface; ran it under `-m integration` and confirmed 6 of 7 tests fail (`AttributeError: 'str' object has no attribute 'exit_code'` — the CLI runner returns a plain error string once `config profile archive` fails to resolve as a command). The one still-live primitive in the neighbourhood, `adapters/persistence/storage/bucket/_sealed_archive_reader.py`, has zero production callers anywhere in `src/cadrumo/` (grepped); it is dormant, not wired to any inspect verb. **Ruled retired, with no operator route to name** — inventing one would misstate the row's contract, since the row only authorises assigning ownership or recording retirement-with-route, not building new capability. The honest state is recorded here for the campaign, and the dead `entrypoints/cli/tests/test_profile_archive_roundtrip.py` suite and its `_config/__init__.py` docstring cross-references (`._bucket_archive`, `._sandbox`) are handed back below since both live outside this Step's ownership.

**Residue deleted, within ownership (`_contracts.py`, `__init__.py`; `_service.py`/`_manifest_digest.py` untouched).** `src/cadrumo/application/bucket_maintenance/_contracts.py` still declared `RenameBucketCommand`/`Result`, `DeleteBucketCommand`/`Result`, `ArchiveBucketCommand`/`Result`, `RestoreBucketCommand`/`Result`, `ExportBucketCommand`/`Result`, `ImportBucketCommand`/`Result`, `InspectBucketArchiveCommand`/`Result` — fourteen pydantic classes with no producer anywhere in `_service.py` and no consumer outside this file and the package's own already-narrowed `__init__.py` `__all__` (which never exported them). Confirmed zero references to any of the fourteen names anywhere else under `src/cadrumo/application/bucket_maintenance/`, and the one stray reference in the wider tree (`application/tests/test_config_reset_concurrency.py`, a subprocess writer-harness string importing `RenameBucketCommand` and calling `BucketMaintenanceService().rename(...)`) was already dead before this Step — that name was never in the package's `__all__`, so the import already raised `ImportError`; deleting the unused class definition changes nothing about that file's already-broken state. That file lives under `application/tests/`, not `bucket_maintenance/`, so it is not this Step's file to fix; named below for whoever picks up S154's "concurrency modules" thread. Deleted all fourteen classes plus the now-unused `Path` and `Hex64Str` imports. Rewrote the `__init__.py` module docstring, which still described rename/archive/delete/export/import and a whole removed sandbox lifecycle (`create_sandbox`, `discard_sandbox`, `archive_sandbox`, `restore_sandbox`, `merge_sandbox` — confirmed `_sandbox.py` does not exist anywhere under `application/`) as live composition verbs, and carried a dangling Sphinx cross-reference (`:func:`~._sandbox.preview_discard_sandbox``) inside `_contracts.py`'s `DiskUsageBucketCommand` docstring to a module that no longer exists; both corrected to describe the actual read-only surface and name the real successor primitives.
