# Have Sol Medium rule on the rehoming analyser asymmetry that accepts a module attribute fetched through a guarded variable while refusing the same fetch through a string literal, even though a literal is strictly the more determinate of the two, since that inversion is what made a genuinely closed command-line loader look unprovable and two independent pinned tests currently enshrine it, so overturning it means changing deliberately authored cases rather than fixing an oversight

## Scope

- `dev/quality/error_code_default_recovery_rehoming.py`

## Description

- Read `dev/quality/error_code_default_recovery_rehoming.py` whole (`_record_guarded_getattr`, `_dynamic_import_module_target_path`, and the surrounding closed-use machinery) and read `dev/tests/test_error_code_default_recovery_rehoming.py` whole, including the two pinned cases the row cites (`closed-dynamic-getattr`, `dynamic-package-getattr`).
- Located the real command-line loader the row references: `_lazy_loader` in `src/cadrumo/entrypoints/cli/__init__.py` (roughly lines 1158-1189). Its inline comment ("Read the attribute rather than fetching it by name... only this spelling lets a static reader see WHICH attribute a dynamically imported module can reach") is the author's own record of routing around exactly this rule.
- Reproduced the asymmetry with three standalone probe scripts run against `current_source_fingerprints` (not hand-read): a copy of the real `_lazy_loader` shape swapping `module.app` for `getattr(module, "app")`/`getattr(module, attribute_name)`, and a direct single-module `getattr(auth, name)` shape isolating `_record_guarded_getattr` itself.
- Confirmed empirically: on the real loader shape, `module.app` is accepted and `getattr(module, "app")` (literal) is refused with `E_REHOMING_DYNAMIC_IMPORT_MODULE`; a guarded-variable `getattr(module, attribute_name)` is ALSO refused there (the loader's guarded-domain closure proof only recognises `.attr` syntax, not any `getattr()` call). On a directly, statically imported single module (`from ... import auth`), `_record_guarded_getattr`'s own gate is reached directly: a guarded-variable fetch (`if name in {...}: getattr(auth, name)`) is ACCEPTED and correctly records the target reference when the guard set includes it, while the identical literal fetch (`getattr(auth, "CertificateLoadError")`) is REFUSED with `E_REHOMING_DYNAMIC_CALL`.
- Weighed the row's premise (a literal is strictly more determinate, so refusing it while accepting the variable form is backwards) against the analyser's actual constraint. The premise is true about *information content* but not about *proof cost*: a literal-name `getattr` always has an exact `.attr` equivalent that the analyser's existing closed-attribute-access machinery already proves (see the passing `outbound_auth.select_provider` case in the pinned suite); a guarded-variable `getattr` has NO `.attr` equivalent at all, because Python syntax does not allow a variable in attribute position. Accepting the literal would not close a soundness gap — it would just give the analyser a second spelling to prove forever for zero additional expressiveness.
- No source or test change was made. `dev/quality/error_code_default_recovery_rehoming.py` already carries a `_record_guarded_getattr` docstring (lines ~2459-2496) that states this same ruling, names the same two pinned tests, and warns that a prior author briefly widened the rule and had a "ten-case matrix" pass cleanly with only these two tests catching the regression. That existing documentation was independently verified rather than taken on faith, and it holds.

## Outcome

- **Ruling: the asymmetry is upheld, not overturned.** A canonical-spelling constraint, not an oversight: literal-name module-attribute fetches must be written as `.attr` and are refused as `getattr(module, "literal")`; a guarded-variable `getattr(module, name)` is the only way to write a genuinely dynamic-name fetch (no `.attr` spelling exists for it) and is accepted when the guard set is statically enumerable and every candidate resolves unambiguously.
- No code change to `dev/quality/error_code_default_recovery_rehoming.py`. No change to `dev/tests/test_error_code_default_recovery_rehoming.py` — the two pinned cases (`closed-dynamic-getattr` in `test_current_source_fingerprints_rejects_escaping_or_target_closed_import_module_use`, and `dynamic-package-getattr` in `test_current_source_fingerprints_rejects_unclosed_dynamic_package_import_module_use`) still assert exactly what they asserted before this Step: that a literal-string `getattr` on a target-relevant dynamically-imported module is refused.
- Documentation nuance recorded for the next reader: for both pinned cases, the module reference reaching `getattr` originates from an `importlib.import_module(...)` call, so the refusal these two tests actually observe fires from the import-module escape gate (`E_REHOMING_DYNAMIC_IMPORT_MODULE`, raised because the escape-closure heuristic recognises only `.attr` syntax as a closed consumer of an import_module result, not any `getattr()` call). `_record_guarded_getattr`'s own internal refusal (`E_REHOMING_DYNAMIC_CALL`) is the gate that fires for the simpler case of `getattr` on a directly, statically-imported module reference — reproduced independently in this Step's probes but not exercised by name in either pinned test. Both gates enforce the same policy; the docstring's claim that "two tests pin the rejection" is accurate, though the exact mechanism differs slightly from what a reading of `_record_guarded_getattr` alone suggests.
- The named real-world loader, `_lazy_loader` (`src/cadrumo/entrypoints/cli/__init__.py:1158-1189`), is already written in the accepted canonical spelling (`module.app`, not `getattr(module, "app")`) and passes clean today. Swapping it to a literal `getattr` reproduces the "unprovable" failure this row describes; swapping it to a guarded-variable `getattr` does not fix it either, because the loader's guard is over the *module name* (which module to import), not the *attribute name* (which the loader always fetches as the single literal `app`) — so the fix for a genuinely unprovable loader is to write the attribute access, exactly as this file's own docstring already advises.
- Gate bite-proof: constructed a case that SHOULD be refused (literal `getattr(auth, "CertificateLoadError")` on a statically-imported module exporting the target) and confirmed the analyser refuses it (`E_REHOMING_DYNAMIC_CALL`); constructed the accepted counterpart (guarded-variable form reaching the same target through an enumerable guard set) and confirmed it is recorded correctly. Both directions were exercised, not just the refusal.
- Verification run: `uv run --no-sync pytest dev/tests/test_error_code_default_recovery_rehoming.py -q`, full output captured to disk and read back. Result: `4 failed, 71 passed in 483.70s`. The two pinned tests this Step's ruling turns on (`test_current_source_fingerprints_rejects_escaping_or_target_closed_import_module_use[closed-dynamic-getattr]`, `test_current_source_fingerprints_rejects_unclosed_dynamic_package_import_module_use[dynamic-package-getattr]`) are NOT among the 4 failures and pass unchanged. The finding count did not move as a result of this Step, because this Step made no source or test edit.
