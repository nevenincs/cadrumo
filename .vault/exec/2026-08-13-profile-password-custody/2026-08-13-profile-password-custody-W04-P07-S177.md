# Have Sol Medium make a catalogue key co-land with the code that consumes it, since every shipped locale gate is a state comparison rather than a change comparison and therefore cannot see the moment a key is orphaned or a call site left uncatalogued, catching drift only after it lands, which is how two unrelated single commits each silently orphaned keys and created missing ones in the same move

## Scope

- `dev/locales/ and .pre-commit-config.yaml`

## Description

- Correct the row's scope path before building against it. `.pre-commit-config.yaml` does not exist: a commit consolidated the hooks into `prek.toml` and dropped the shadowed config. `prek.toml` is that file's successor and is where the hook was registered.
- Build the comparator as `dev/locales/_colanding.py`, reachable as `python -m dev.locales co-landing`. It resolves a revision pair, extracts the locale keys every modified Python module declared before and after, and holds two invariants over that delta: a key whose call site the change ADDS must exist in every catalogue as the change leaves them, and a key whose LAST call site the change removes must not be left standing in the catalogues.
- Add `scan_source_text` and `scan_namespace_markers_in_text` to the AST scanner so a module's keys can be extracted from a revision's content rather than only from a working-tree file, and extract the module-eligibility predicate as `declares_locale_keys` so the tree walk and the change-scoped scan share one definition. Two copies of that predicate would let one scanner see a key the other cannot, which is the failure mode this whole Step is about.
- Read the catalogues from the revision, not the working tree. The question is whether the key lands with its call site, so an unstaged catalogue edit sitting in the checkout is not part of the change being judged.
- Confirm the orphan direction against the whole tree before reporting, not against the changed modules alone. The change-scoped delta cannot distinguish a key that was retired from one that merely moved to another module, and calling a relocation an orphan is the false positive that would get this gate switched off first. The confirmation is lazy: it runs only when a change actually removed a call site, so an ordinary commit costs one `git diff --name-only` and a handful of blob reads.
- Derive the one exemption rather than allowlisting it. A command family the operator surface declares but has not built holds its catalogue strings: nothing reaches them so they have no call site, but they are not retirement residue either. That distinction already has an owner in the mounted-command-family register, so the gate reads the answer there and reports such keys as held rather than as findings. The gate carries NO hand-written allowlist at all, which is the strongest available answer to the rule that allowlists are where the judgement moves.
- Deliberately do not gate the third direction, a catalogue key added ahead of any call site. Bulk scaffolding and the registry authoring sweep both legitimately add catalogue content in their own commits, so that direction fires constantly on correct work, and the standing whole-tree audit already reports an uncatalogued surplus after the fact. A gate that cries wolf is disabled by whoever it first annoys, which recreates the problem it was built to solve.
- Make the empty-index case compare a change rather than report a vacuous pass. With nothing staged the verb falls back to the last landed commit, and a `BASE..HEAD` selector is accepted for a whole branch. An invocation that answers "clean" because it had nothing to look at would be indistinguishable from the gate not being installed.
- Prove the gate bites against real history, not only against fixtures. Replayed the three commits this campaign had already root-caused, plus the one discovered during the sibling Step.
- Prove it in isolation with eleven tests over real temporary git repositories built with real `git init` and real commits, asserting the green cases first so the gate is not merely red on everything.

## Outcome

- The gate exists, is registered, and refuses real historical defects.
- **Placement: a `prek.toml` local hook, verify-only, `pass_filenames = false`, on the default pre-commit stage.** It reads `git show` blobs and writes nothing, so it satisfies that file's stated verify-only, stash-free policy — the policy exists because an autofixing hook's stash-pop step has lost work in this repository before.
- **Rejected alternatives, and why.** A pytest gate: CI runs on a merged tree with no index, so a diff-aware check expressed as a test would be a state check wearing a change check's name, which is the exact substitution this row exists to undo. An installed `.git/hooks/pre-commit` script: the project deliberately does not install one, and a shared worktree with several agents committing concurrently makes a commit-time stash path actively dangerous. `.pre-commit-config.yaml`: retired, as above. The CI workflow: `.github/workflows/ci.yml` is another session's ownership, and it is named below as the follow-on placement, because a range-mode run over the pull-request range is the placement nobody can route around.
- **Honest limit of the chosen placement.** The hook script is intentionally not installed in this repository, so prek is a manual gate run before committing rather than a true commit-time interceptor. Under a manual all-files run the index is empty, which is why the fallback above exists. Until the CI range-mode run lands, this gate is a discipline with teeth rather than an interception.
- **Bite proofs, from real commits and from real temporary repositories.** Against the commit that added a `tr()` call site for a manager next-step advisory and touched zero locale files, the gate reports one uncatalogued-call-site finding naming all four catalogues and exits non-zero. Against the custody-retirement commit, it reports twenty-two findings and, in the same run, correctly HOLDS the seven `cli.config.passphrase.*` keys as owned by a declared-unimplemented family while flagging the twenty-one genuine `cli.config.custody.*` and `cli.config.recover.*` orphans beside them — the ruled discrimination working inside the gate rather than restated in it. In the temporary-repository suite, a commit that adds a call site without its entry reds, a commit that removes the last call site and leaves the key reds, a commit that lands both together passes, a commit that retires both together passes, a relocation passes, a docs-only commit passes, and a key named only in a test module is not treated as a call site. All eleven pass. Every proof was performed outside the repository or by reading committed history; no tracked file was mutated to produce a red.
- **Coverage is two of the four known incidents, not four.** The gate catches the two whose keys the AST scanner can see. It does NOT catch the profile-status rename, whose keys live in a `dict` constant named `_PROFILE_STATUS_KEYS` — a name carrying neither required locale-key suffix — read through a lower-cased local variable into `tr()`; that shape is invisible to the key scanner AND explicitly out of scope for the `tr(CONSTANT)` naming gate, so it is covered by no gate at all and is named here as a residual hole. It also does NOT catch the binding-source-kind commit, whose two catalogue labels are derived from a new enum member through the f-string registry rather than from a literal call site; the registry's own coverage gate covers those, as a state comparison. Stated plainly: this gate inherits the scanner's blind spots exactly, and claiming otherwise would overstate it.
- **Semantic staleness remains uncovered, and this gate does not touch it.** It compares key SETS. A catalogue value whose text names a retired verb stays structurally perfect in all four locales, so a change that retires the verb passes this gate cleanly while leaving four locales instructing the operator to run a command that no longer resolves — which is precisely what happened to the master-key passphrase-mismatch message through the whole recovery-facade retirement. That is a distinct failure mode needing its own detection, a content-staleness or dead-command-citation check, and it is NOT addressed here.
- **A second blindness, found during this Step and reached from the opposite direction.** Structural parity asserts that every required key is present in ALL FOUR catalogues, so it can see a key present in three; it cannot see a key present in NONE, because such a key is only ever reported as a missing-key count rather than as a rendering defect, and a `tr(..., default=...)` fallback silently covers for it in the meantime. Two live instances surfaced in this session: a manager next-step advisory rendering untranslated English in every locale including Spanish because its key existed nowhere and only the `default=` made it render at all, and an operation-declaration-breach error whose registry row named a key no catalogue carried. Both were landed with real values in all four catalogues. The co-landing gate DOES catch this shape at the moment of the change, in both its `tr()` literal and `message_key=` forms, which was confirmed directly rather than assumed. It cannot retrospectively find one that already landed; that remains the audit's job.
- Removing the now-redundant `default=` fallback at the manager next-step call site belongs to the owner of that CLI module, not to this row, and is named here as the follow-on.
- Recommend this row is marked complete. Both invariants are implemented, registered, proved against real defects, and their limits are stated rather than papered over. The checkbox was deliberately left unchecked for the lead to set.

## Notes

- **No new rule file was authored.** Codification is retired in this project, so the durable lessons are recorded here instead: derive an exemption from an existing authority rather than restating it; assert the green case before the red one; and state a gate's blind spots in the same breath as its coverage.
- **No exact count is a pass condition anywhere in the gate or its tests.** The assertions are on the property — which key, which catalogues, which finding kind — never on a tally.
- **Peer commits absorbed this Step's work while it was in progress.** Four "registry: continue authority-grade sweep" commits swept up the comparator, its tests, the scanner changes and the hook registration alongside their own unrelated registry content, so this Step's code is on main under peer commit messages rather than as its own diff. No `git add`, `git commit`, `git stash` or `git reset` was run here.
- **The first suite run crashed a worker under parallel pytest and printed a stack trace with no failure.** Re-running sequentially revealed the actual cause immediately: the new test module was missing the required architectural marker, so it had been collected and rejected rather than crashing. The local-execution rule's guidance to re-run sequentially before triaging held exactly.
- **The repository's own marker warning earned its keep.** An unmarked run of the new module printed a green result having executed zero tests, and the emitted warning line said so in as many words. Every run recorded here passed an explicit marker selection.
- The whole-catalogue audit count moved from 36 to 542 missing during this Step as the registry sweep landed further batches. It was never used as a signal; every claim here rests on a specific replayed commit or a specific temporary repository.
