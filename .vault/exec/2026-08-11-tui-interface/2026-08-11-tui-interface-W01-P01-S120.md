# Raise the signal on an execution record whose Step no longer exists, which the harness already detects and nobody would act on. THIS IS A PROMINENCE PROBLEM, NOT A COVERAGE GAP, and the distinction is the row: an earlier report claimed `vault check all` could not detect this at all. That claim was WRONG and is recorded here so it is not repeated. The `orphans` check does only fire on a missing parent PLAN -- but `exec-mapping` catches exactly this case and names it precisely: 'Execution record declares Step S115, which does not exist in parent plan', with a fix line. The wrong conclusion came from testing the ONE check whose name matched the concept and generalising to the tool, which is the wrong-subject shape this campaign keeps finding. WHAT IS ACTUALLY WRONG: the detection is one warning among thirty-two in that category, in a run reporting several hundred warnings overall, and it is a WARNING rather than an ERROR. So a committed inconsistency -- an execution record with real evidence behind it, attached to a closed Step that its plan does not contain -- produces no signal anyone reads. It was found only because `vault add exec` REFUSED with 'Step does not exist in this plan', which is a different surface reacting to the same fact loudly. DEMONSTRATED, not hypothesised: five rows were lost to a cross-lane plan overwrite while one of them kept its committed execution record, `vault check all` reported clean at the summary level throughout, and the same check went silent the moment the rows were restored. A detector that names the defect and then falls silent when it is fixed is working correctly; only its audibility is wrong. CONSIDER, without prejudging: promoting this specific finding to an error, or separating 'record points at a Step that does not exist' from the bulk mapping warnings, because that case means a plan and its evidence have diverged rather than that a document needs tidying. Do NOT resolve it by adding another check

## Notes

Authored by the team lead; the logic verified here by direct invocation.

The fix is ELEVATION, NOT DETECTION, and the row's constraint is what forced
that shape: the vault's `exec-mapping` check already names this defect
precisely. The gate reads that check's `--json` verdict and raises the
severity of one diagnostic class, filtering to the step-not-in-plan phrase and
leaving its siblings alone. Re-deriving plan structure would have created a
second authority free to disagree with a tool that is already right.

The two pre-existing entries are NAMED, NOT BLESSED. Both belong to other
campaigns, and only their owners can say whether a row was lost, renamed or
retired. Removing an entry when its owner resolves it is the intended
lifecycle; adding one to silence a fresh failure is not.

The vacuity guard carries more weight here than in the parse gate: a renamed
diagnostic string or a changed JSON shape would yield an empty result set and
pass silently, which is the exact failure this gate exists to prevent, one
level up. It asserts the baseline is non-empty so a gate that has stopped
reading real diagnostics fails loudly instead of going quiet.

IT WOULD HAVE CAUGHT TONIGHT. When a cross-lane plan overwrite removed five
rows, `exec-mapping` reported the orphaned record immediately -- as one warning
among twenty-eight, in a run that exits zero. It was found by accident, because
an unrelated `vault add exec` call refused loudly. This gate turns that into a
failure.

NOT CLAIMED: that the tree is currently clean. Under pytest, collection fails
at `ModuleNotFoundError: No module named 'cadrumo.core.errors._registry'` --
the module is deleted in the working tree while importers remain, from a live
peer sweep. The gate's logic was therefore proven by direct invocation. As
with the parse gate, what is recorded is a property of the gate, which holds
regardless of any lane's activity; the tree's state is a separate claim and is
not made.

WORTH KNOWING FOR THE PARSE GATE'S SCOPE: it reports zero unparseable files
during this same breakage. A deleted module whose importers remain is not a
syntax error, so that gate cannot see it. "Every file parses" and "every import
resolves" are different properties, and only the first is gated.
