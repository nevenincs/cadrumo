# Gate the modelo screens' painted geometry, which nothing currently checks. THE WORK IS NOT RESURRECTING A DEAD FUNCTION -- IT IS PUTTING A GATE IN FRONT OF A LIVE ONE THAT ONLY EVER RUNS WHEN A HUMAN CHOOSES TO. THREE FACTS, each verified: (1) `geometry_band` at `devtools/frame.py:120` is executed by NO TEST. Neither `geometry_band(` nor `capture(` appears in any test file under `src/` or `dev/`; every reference in the devtool-home tests is a NAME-ONLY export assertion. `capture` does have one real caller, `devtools/replay.py:22` -- but that is the standalone diagnostic replay runner, which the operation-catalogue census already declares as driving no operator-facing screen. So the precise state is ONE MANUAL CALLER, ZERO GATES. That is harder to find than an orphan: the symbol is not unreferenced, so an unused-symbol sweep clears it, and it is reachable only from a tool nobody runs in CI. (2) `ModeloWorkReview` appears ZERO times in `test_visual_verification.py`, whose eight enrolled surfaces are registration, form, status, status-populated, question, manager, manager-populated and login. The C2 workspace destinations are absent too. (3) So the three geometry properties -- painted past the side edges, a scrollable host that overflows but cannot scroll, and MULTIPLE VISIBLE VERTICAL SCROLL OWNERS -- are proven for five screen types, while the reader that could prove them for any screen is gated by nothing and the modelo surfaces are covered by neither. WHY THIS IS URGENT RATHER THAN TIDY: the 80x24 summary fix added `overflow-y: auto` inside the body's `ContentScroll` at `work_review.py:671`, which is exactly the nested-scroll-owner shape property (3) exists to catch. Running `geometry_band` by hand reports CLEAN at 80x24, 120x36 and 160x48 -- but that is a ONE-TIME MANUAL READING WITH NO GATE BEHIND IT, and the 58 passing view tests assert behaviour and content while asserting nothing about painted geometry. The next edit to that stylesheet can introduce a second visible scroll owner and nothing will say so, and its author will have the same reason to believe it is fine: a green suite over a screen whose geometry nothing checks. VERIFIED BY LUCK OF CONSTRUCTION, NOT BY DESIGN. Note also that a weaker version of this reader was rebuilt from scratch during that investigation by someone with no reason to know it existed -- uncalled capacity that is fully implemented, documented and CORRECT is likelier to be rebuilt than found. SEQUENCE THIS ABOVE `S107`: it has a concrete implementation path, it protects a fix that is currently unprotected, and unlike the size-set consolidation it waits on nothing

## Notes

PARTIAL: the enrolment half only, and the row stays OPEN. The gate provably
misses a live instance on the very screen it was built to protect, so
closing it here would be delivered-narrower wearing a complete checkbox.
The widening of the scroll-owner predicate is folded into the same row
rather than opened as a successor -- one row, one property -- and it is
sequenced BEHIND the layout fix, because widening first reds the modelo
screen on a live defect and the pressure then becomes to weaken the
detector.

Two changes. `ModeloWorkReviewApp` is enrolled as a ninth surface in
`_SURFACES`, so it now falls under the side-edge, scrollability and
both-appearances gates that covered eight surfaces and not it. And
`test_every_surface_reports_no_geometry_findings` drives the canonical
`devtools/frame.py:geometry_band` over every surface at every declared
size -- its FIRST test caller.

BITE-PROVEN TWICE, INDEPENDENTLY, both from outside the repo with no
tracked file touched. One widened the summary panel to 400 columns via a
CSS override; the other widened the header to 200. Each reported
`painted past the side edges` naming the offending widget and its region,
and each RED ONLY THE PATCHED SURFACE while the other eight stayed green.
Discriminating rather than globally sensitive is the property that
matters: a gate that reds everything on any injection proves only that it
runs.

WHAT THE GATE DOES NOT COVER, recorded because the omission is specific
and was found while landing it. `geometry_band`'s scroll-owner check
filters on `isinstance(host, ScrollableContainer)`. On this very screen
`#modelo-review-summary` is a `Static` carrying `overflow-y: auto`:
measured `allow_vertical_scroll=True`, `max_scroll_y=3`,
`show_vertical_scrollbar=True`, and enumerating every widget with a
visible vertical scrollbar returns TWO -- the body and the summary. So
the screen carries the defect that check is named for, and the check
cannot see it because one owner is a styled Static rather than a
container subclass. Opened as `S109`; do not read this record as
claiming that property is now gated for this surface. It is not.

CORRECTION TO AN EARLIER READING, kept because the reasoning was wrong in
both directions before it was right. The summary bound was first reported
as having passed the nested-scroll-owner check by luck of construction,
then corrected to having passed structurally because the check cannot
apply to a Static. Neither is accurate: the check does not apply, AND the
underlying defect is genuinely present. A failed bite proof has two
explanations -- the gate is inert, or the injection is outside its reach
-- and they are indistinguishable from the result alone. Read the
predicate before concluding either.

Also corrected: the single-scroll-owner property was NOT ungated before
this change. A sibling test proves it for the flow surface only, with a
bespoke many-page fixture, because that is where the defect was first
found. A gate written at the site of a defect inherits that defect's
scope, and its name usually does not say so.

The two failures in the full-suite run are the pre-existing
`status-populated` and `manager-populated` region-eviction pair, already
reported and handed back; they are untouched by this change and unrelated
to the modelo surface.
