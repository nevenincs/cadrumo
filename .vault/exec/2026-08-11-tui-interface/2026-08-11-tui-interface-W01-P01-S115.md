# State the discrepancy between what pytest collected and what it heard back, so a run with a hole in it announces the hole. THE DEFECT IS IN THE READER, NOT THE RUNNER. A thread-method timeout kills the worker PROCESS rather than raising inside the test, so the worker dies before reporting and its remaining tests are never redistributed. pytest's footer then states only what came back. DEMONSTRATED ON A REAL RUN of `entrypoints/tui/tests/test_registration_recovery_words.py`: five tests collected, `1 failed, 2 passed in 101.54s` reported, and TWO tests silently gone -- no error, no skip, no collected-versus-reported mismatch, and arithmetic that is internally consistent about what was reported while saying nothing about what was not. It is indistinguishable in shape from a complete run. WHY IT OUTRANKS THE HANG IT WAS FOUND CHASING: the hang costs time, this corrupts the reading of every red log in the tree -- including the runs both lanes were using to reason ABOUT the hang, each of which may have been missing tests neither knew about. A conclusion drawn from such a run is drawn from a population of unknown bounds. THE REMEDY IS ARITHMETIC, not detection of a failure mode: compare the session's collected total against executed-plus-deselected and report the shortfall. Subtracting deselected is what keeps it silent under the default marker selection, which deselects thousands. The collected total must come from the CONTROLLER after xdist merges its workers' collections, because that is the one figure that knows about tests a dead worker owned. BITE-PROVE IT AGAINST THE REAL MECHANISM by forcing worker death with an aggressive timeout, not by simulating a missing outcome, and prove the FALSE-POSITIVE side too: a heavily-deselecting run and a clean run must both print nothing, since a reporter that cries wolf on every ordinary invocation is worse than none. This is the sibling of the existing deselection reporter and belongs beside it: the two cover the two ways a run under-executes -- tests deliberately not selected, and tests lost -- and neither changes what executes, only what the reader is told

## Notes

Authored by the team lead; verified independently before this record was
written, because a report of a landed gate is not evidence that it bites. The
hook was read in full, its wiring confirmed at `conftest.py:172` beside the
deselection reporter, and all four runs above were re-executed here rather
than quoted.

The false-positive side is the half that decides whether this survives. The
default marker selection deselects thousands of tests on every invocation, so
a reporter that did not subtract deselected would fire on every run in the
repository and be muted within a day. Three separate silent controls, not
one.

Provenance, because the order matters and neither half is sufficient alone:
the truncation risk was raised from this lane after a thread-method timeout
destroyed a FAILED list, and the lead's own run supplied the count that showed
the same mechanism also loses tests that were never attempted. The second is
strictly worse than the first and was not predicted by it.

This does not resolve the intermittent timeouts recorded in `W04.P07.S114`
and makes no claim to. It makes a run that hits one legible instead of
misleading, which is a precondition for investigating it at all.
