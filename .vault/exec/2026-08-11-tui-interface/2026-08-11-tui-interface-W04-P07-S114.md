# Establish whether this tree's intermittent suite hangs are code at all, and do not accept an instrumented answer without its control. WHAT I FIRST REPORTED WAS RIGHT IN ITS SYMPTOM AND WRONG IN ITS DIAGNOSIS. I saw two tests in `entrypoints/tui/tests/test_registration_recovery_words.py` hang inside a full-directory run and reported `entrypoints/tui/secret/registration.py:481` -- `_confirm_recovery_possession` blocked on `resolved.wait(...)` in a Textual THREAD worker -- as 'the exact locus'. The stack is real; calling it the defect was an inference I did not label as one. THE DESIGN GAP AS DESCRIBED DOES NOT EXIST: the `while not resolved.wait(...): if not self.app.is_running: break` loop is not the only escape. `RecoveryWordsScreen.on_unmount` calls `_refuse_once()`, which calls `_on_cancel()`, which sets the very event the worker waits on, with a docstring saying it treats escape, shutdown and every non-confirm exit as refusal; the registration screen's own `on_unmount` releases every pending handoff as a third. Three guards. Do NOT add a fourth without first establishing a state none of them covers. Do NOT add a wall-clock bound: the existing comment rejects one correctly, since a deadline only races a slow machine and converts a hang into an intermittent flake, which is strictly worse. NOT REPRODUCIBLE, MEASURED FOUR WAYS: all FIVE tests pass individually at a 100s budget; the whole file passes twice, 44.21s and 45.11s; across three full-directory runs the timeout landed on a DIFFERENT test each time, once on `tests/test_relocation_parity.py::test_relocated_symbols_have_single_canonical_defining_modules_and_inert_facades`, whose stack is inside `_source_trees` READING SOURCE FILES. A test that only reads files off disk cannot stall on a UI event, so no single code defect spans the three. Stamped `PRE-RUN cpu=20.6% cpus=24 mem=45.9% processes=720 python_processes=50`. THE INSTRUMENTATION LESSON IS THE MOST TRANSFERABLE THING HERE, because 'is the confirmation ever sent' is a STATE question that load cannot touch, and instrumenting it STILL produced a false answer three times. Probe 1 wrapped `RecoveryWordsScreen.__init__`, hung the first test, and traced 'screen constructed, send never fires' -- which reads exactly like proof of the never-sent candidate. The control run immediately after passed 5/5, so the probe was the cause and the trace was worthless. Probe 2 additionally wrapped `_confirm`, which is `@on(Button.Pressed, ...)`-DECORATED: replacing that attribute detaches the handler from Textual's registry, so the button stops working and the wait becomes genuinely infinite -- a probe that manufactures the very defect it is looking for. Probe 3 touched only undecorated methods and hung at a different point again. NEVER MONKEYPATCH A DECORATED HANDLER OR A NODE CONSTRUCTOR, and run the unpatched control in the same session, not from memory of an earlier run. WHAT THIS DID ESTABLISH, at its honest grade: there is a reachable state -- screen constructed and pushed, confirm handler not firing, app still running, screen never unmounting -- in which the worker waits forever with NO error and NO diagnostic, because every existing guard keys on unmount or app-stop. That is a robustness gap worth a decision even though it is not shown to be the cause of the observed hangs. OPEN QUESTIONS, in order: whether the observed timeouts are I/O stalls on the network-backed mount (`aeat-local-execution` already names that failure mode) and whether the suite should refuse such a mount rather than hang on it; and separately, what the third exit condition should be for a handoff whose producer is mounted but inert. The first needs a quiet host, alongside `W06.P14.S348` and `S96`. A SECOND, CONTRADICTING DATA POINT, recorded because it does not resolve: an independent run of the same file by the team lead did NOT pass -- `worker 'gw0' crashed`, `1 failed, 2 passed in 101.54s`, hanging on `test_wrong_recovery_reentry_publishes_no_capsule`, the same test this row originally named. It carried NO `CADRUMO-HOST-LOAD` stamp, because the worker died before emitting one, so by this row's own rule it cannot speak to the environment question either. So `5 passed in 44.21s` and `hangs on that test` are both true at different moments, which supports intermittency and settles nothing. Neither lane has cleared it. That same run is what exposed the lost-test defect gated by `W01.P01.S115`: five collected, three accounted for, two silently gone. FOR ANYONE TRIAGING A RED LOG HERE: a `--timeout-method=thread` timeout KILLS THE PROCESS before pytest writes its summary, so a run hitting one loses its entire FAILED list with no trace anything was dropped -- three failures in the run above are still unidentified for exactly that reason. Never quote a failure count from a run that timed out

## Notes

PARTIAL: this closes the reachable-state gap only. The intermittent suite
timeouts this row was opened for are NOT addressed and the row stays open.
The disclaimer is in the code's docstring as well as here, because the row
does not travel with the file.

The guard keys on an invariant rather than a symptom, which is what makes it
safe: `push_screen` appends synchronously and `call_from_thread` returns only
after it has, so a pending handoff always has its screen on the stack.
"Unanswered AND unstacked" is therefore a state a waiting operator cannot be
in. That mattered more than the fix did -- a guard keyed on elapsed time or on
liveness would eventually abort a real operator mid-mnemonic and destroy a
live registration.

Confirmed across two consecutive polls, because the list is read from a
worker thread and a single torn read must not abandon a live registration.

The three existing guards are untouched and named in the new code comment.
They are deliberate and correct; the next reader must not mistake a fourth
escape for evidence the first three were inadequate.

Two of my own errors, recorded because each produced a confident wrong result
before being caught. The test first removed the words screen from
`app.screen_stack`, which returns a COPY -- so it induced nothing and the
guard looked broken when the test was. And the bite proof turns the hang into
a bounded FAILURE rather than a hang, because the test carries its own
deadline and asserts; that is the better shape, since a hanging bite proof
costs a timeout budget to read.
