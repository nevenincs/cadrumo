# Measure the legitimate population of direct create_work_unit callers and then close the filing-year gap that the select_revision caller audit structurally could not see, because create_work_unit is not itself a select_revision caller and so fell outside that audit's denominator entirely. It validates a supplied revision_id only for existence and for period-token membership, never against the filing year, so create_work_unit for modelo 303 filing_year 2026 carrying revision_id 2023-y-siguientes succeeds silently and builds a 2026 work unit under the 2023 revision's norms even though that revision's compiled period selector is capped at year_to 2025 and the authority resolves those coordinates to 2026-y-siguientes. Production is safe today only because every production caller resolves through resolve_registry_revision_for_work_target first, so the exposure is a FUTURE caller that does not, and the starting hypothesis to DISPROVE is a static gate constraining production call sites rather than a runtime refusal at the shared door, because whether a revision_id was law-resolved or hand-supplied is not visible in the arguments at all and a runtime predicate therefore cannot discriminate a fixture seeding a work unit from a production path that resolved correctly. Roughly ninety modules call create_work_unit directly, so the population must be measured before the mechanism is chosen

## Scope

- `src/cadrumo/application/modelo/_work_lifecycle.py and src/cadrumo/application/modelo/_registry_resources.py`

## Description

- Census every direct `create_work_unit` call site with `rg` across `src/cadrumo`: 98 references across 96 files. Excluding test paths and `test_`-prefixed files leaves exactly two non-test callers: `_work_lifecycle.py` (the definition site itself) and `_work_addressing.py` (`ensure_modelo_work_unit_for_active_target`, the sole production wrapper). All remaining ~90 call sites are test/fixture code.
- Read `resolve_registry_revision_for_work_target` (`_work_addressing.py`): it already implements exactly the law-determined-match assertion the gap needs (delegates to `select_revision` and refuses via `ModeloWorkRegistryYearMismatchError` naming both the requested and law-determined revision), but only `ensure_modelo_work_unit_for_active_target` calls it before reaching `create_work_unit` — the persistence door itself never re-confirms.
- Disprove the plan's starting "static gate over production call sites" hypothesis on the population evidence: with exactly one already-compliant production caller, a gate scoped to production call sites would be structurally near-vacuous (nothing left to enforce). The durable fix protects every caller, present and future, regardless of how it reached the door — matching the existing `aeat-registry-authority-flow` "Good" pattern ("a stored, literal or operator-supplied `revision_id` may only be asserted equal to that resolution") and the pre-existing D1 calc-time reconfirmation this same file already tests for a different chokepoint.
- Implement the fix in `create_work_unit` (`_work_lifecycle.py`): after the existing `reject_unknown_revision` / `reject_unknown_period_for_revision` checks, call `resolve_registry_revision_for_work_target(modelo=modelo, filing_year=filing_year, period=period, registry_revision_id=revision_id)` via a function-local import (module-level would cycle, since `_work_addressing.py` already imports `create_work_unit` from `_work_lifecycle.py` at module level — mirrors the existing function-local `_profile_readiness_gate` import already in this function). Update the docstring to document the new invariant.
- Add `TestS03CreateWorkUnitDoorReconfirmation` to `test_revision_id_d1_contract.py` (the file that already owned the D1 calc-time-assertion tests for this exact scenario): one test proving `create_work_unit` itself refuses M303/2026/1T with the real-but-year-wrong revision `2009-y-siguientes` (naming both revisions in the message, and proving no stray work unit is persisted), one proving the correctly law-determined revision `2026-y-siguientes` still succeeds unchanged.

## Outcome

- `create_work_unit` now re-confirms the law-determined revision at the persistence door itself, closing the gap for all ~90 direct callers rather than only the one production wrapper that already resolved through `resolve_registry_revision_for_work_target`.
- New targeted tests: 2/2 pass (`test_create_work_unit_refuses_a_revision_that_diverges_from_law_determined`, `test_create_work_unit_accepts_the_law_determined_revision`); all 10 pre-existing tests in the same file continue to pass unchanged.
- Full regression proof on `src/cadrumo/application/modelo/tests` (1666 tests, the directory holding ~85 of the ~90 direct callers): ran the suite twice, once with the fix and once with `_work_lifecycle.py` swapped back to the HEAD version (same test files both times). Baseline: 445 failed / 1221 passed. With fix: 444 failed / 1222 passed — the sole net difference is this step's own new refusal test (fails on baseline with no refusal, passes with the fix). Two additional list-order deltas (one file newly failing under the fix, two newly passing) were individually re-run in isolation and confirmed as pre-existing flakiness unrelated to the change: a documented registry-tree-fingerprint cache race (`RegistryLoadError: registry directory changed during cache fingerprinting`, reproduced only under xdist, absent with `-n 0`) and a test that deliberately drives real concurrent threads against a `threading.Barrier` (`test_concurrent_distinct_nonce_consumption_preserves_every_record`, no `create_work_unit` reference at all). Zero regressions attributable to this change across the full population sampled.
- The remaining ~20 direct-caller files outside `application/modelo/tests` (`application/aggregation/tests`, `application/calculations/tests`, `application/tests`, `application/workflow/tests`, `entrypoints/cli/tests`) could NOT be swept: partway through this step an unrelated, in-progress `git merge` (`MERGE_HEAD` `5d527f18...`, `Merge branch 'main' of https://github.com/nevenincs/cadrumo`) appeared in this shared worktree with 100+ conflicted files, including a literal unresolved conflict marker in `src/cadrumo/core/__init__.py` that breaks `conftest.py` import and makes the ENTIRE tree uncollectable by pytest tree-wide, not just this step's slice. Given the dominant population (85/90 files, 1666 tests) is fully swept with zero attributable regressions, and the mechanism itself (a direct call into the already-battle-tested `resolve_registry_revision_for_work_target`) has no dependency on which specific caller reaches it, the residual risk on the unswept ~20 files is low.
