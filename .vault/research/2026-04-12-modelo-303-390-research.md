# modelo-303-390 research (#62)

Date: 2026-04-12
Branch: `feature/62-modelo-303-390`
Issue: wgergely/aeat#62

## Question

Which casillas of Modelo 303 (quarterly IVA general regime) and
Modelo 390 (annual IVA summary) must the v1 builders produce, and
how does Modelo 390 reconcile against the four quarterly Modelo 303
drafts so that mismatches surface as `FilingValidationFinding`
records with severity ERROR?

## Constraints

- Pydantic v2 strict across every record. No dataclasses for
  boundary-crossing types. No bare `dict[str, Any]`.
- Builders live under `src/aeat/application/filing/_builders/` and are reached
  only via `aeat.application.filing.build_draft`. The `aeat.application.filing` public API
  does not change shape — the dispatch registry is keyed by modelo
  string.
- The casilla DB subpackage #23 is still in flight. The builders
  ship a hand-curated static casilla collection that conforms to
  the `aeat.application.filing._protocols.CasillaCollection` Protocol, exactly
  like `_modelo_130_schema.py`. Migration to #23 is a search/replace
  on one import.
- Formula trace rigor: the validator already checks that every
  casilla with `formula_inputs` is `COMPUTED` with a matching
  `formula_trace`. The builders MUST emit provenance that lines up.
- Trilingual contract: every user-facing string is
  `aeat.core.i18n.Translatable` (`es`/`en`/`hu`).
- No live tests; `@pytest.mark.unit` only.

## Modelo 303 — quarterly IVA general regime (2025)

Source: *Manual práctico IVA 2025*, AEAT (2025 edition), chapter on
"Modelo 303 — Autoliquidación", available at
`corpus/manuals/iva/2025/` (manifest already on main via #25; the
PDF is retrieved on demand and is not committed). The casilla layout
is public AEAT documentation and is additionally published in the
BOE-published modelo 303 order (Orden HAC/819/2024 and successor
orders for the 2025 form).

### v1 casilla coverage

The issue fixes the coverage at "IVA general regime, operaciones
interiores + deducible + resultado", specifically:

**Operaciones interiores — IVA devengado (régimen general)**

- `01` — Base imponible gravada al 4%
- `02` — Tipo 4%
- `03` — Cuota devengada = `01 × 0.04`
- `04` — Base imponible gravada al 10%
- `05` — Tipo 10%
- `06` — Cuota devengada = `04 × 0.10`
- `07` — Base imponible gravada al 21%
- `08` — Tipo 21%
- `09` — Cuota devengada = `07 × 0.21`

**IVA deducible (operaciones interiores corrientes + bienes de inversión)**

- `28` — Base imponible de operaciones interiores corrientes
- `29` — Cuota soportada deducible de operaciones interiores corrientes
- `30` — Base imponible de operaciones interiores con bienes de inversión
- `31` — Cuota soportada deducible de bienes de inversión
- `32` — Base imponible de importaciones de bienes corrientes
- `33` — Cuota soportada deducible de importaciones corrientes
- `34` — Base imponible de importaciones de bienes de inversión
- `35` — Cuota soportada deducible de importaciones de inversión
- `36` — Base imponible de adquisiciones intracomunitarias corrientes
- `37` — Cuota soportada deducible de adquisiciones intracomunitarias corrientes
- `38` — Base imponible de adquisiciones intracomunitarias de inversión
- `39` — Cuota soportada deducible de adquisiciones intracomunitarias de inversión
- `40` — Rectificación de deducciones
- `41` — Compensaciones régimen especial A. G. y P.
- `42` — Regularización bienes de inversión
- `43` — Regularización por aplicación del porcentaje definitivo de prorrata
- `44` — Total a deducir = `29 + 31 + 33 + 35 + 37 + 39 + 40 + 41 + 42 + 43`
- `45` — Resultado régimen general = `(03 + 06 + 09) − 44`

(Note: casillas 46–47 exist in the full AEAT form but carry régimen
simplificado totals, which are OUT OF SCOPE for v1. The builder
leaves them empty.)

**Resultado**

- `64` — Suma de resultados parciales = `45` (v1 simplification:
  no régimen simplificado contribution)
- `65` — % atribuible al Estado (default 100 for autónomos sin
  regímenes forales)
- `66` — Atribuible al Estado = `64 × 65 / 100`
- `67` — Cuotas a compensar de periodos anteriores (literal input,
  default 0)
- `69` — Resultado = `66 − 67`
- `71` — Resultado de la autoliquidación = `69`

A positive `71` is a "resultado a ingresar"; a negative `71` is
either "a compensar" (if not the last period) or "a devolver" (if
the last period). The builder surfaces the signed `71` and a sign
interpretation is left to the validator / submission engine.

### Cross-casilla rules (emitted as findings, not raised)

- **Rate check.** For each `(base, tipo, cuota)` triple
  `(01,02,03)`, `(04,05,06)`, `(07,08,09)`, the builder records the
  computed cuota and the validator surfaces an ERROR finding if the
  user provided a `cuota` literal that diverges from
  `base × tipo / 100`. In v1 only the base is a literal; tipo is a
  default constant and cuota is computed.
- **Total check.** `44` and `45` are computed. If the user supplies
  a literal for a computed casilla the validator emits a
  `formula-divergence` finding (already implemented upstream).

## Modelo 390 — annual IVA summary (2025)

Source: *Manual práctico IVA 2025*, chapter "Modelo 390 —
Declaración-resumen anual". The modelo 390 is declarative: every
annual total is the sum of the four quarterly modelo 303
counterparts, plus additional identification and non-arithmetic
informational casillas.

### v1 casilla coverage

The 390 form carries hundreds of casillas. v1 ships the arithmetic
backbone — identification is left to downstream UI — and reconciles
against the four 303 quarterly drafts:

**Identificación / ejercicio**

- `01` — Ejercicio (4-digit year, literal)

**Operaciones realizadas en régimen general (anual) — IVA devengado**

- `100` — Base imponible anual al 4% = sum of quarterly `01`
- `101` — Cuota anual al 4% = sum of quarterly `03`
- `104` — Base imponible anual al 10% = sum of quarterly `04`
- `105` — Cuota anual al 10% = sum of quarterly `06`
- `108` — Base imponible anual al 21% = sum of quarterly `07`
- `109` — Cuota anual al 21% = sum of quarterly `09`

**IVA deducible anual**

- `190` — Base imponible operaciones interiores corrientes =
  sum of quarterly `28`
- `191` — Cuota deducible operaciones interiores corrientes =
  sum of quarterly `29`
- `192` — Base imponible operaciones interiores bienes de inversión =
  sum of quarterly `30`
- `193` — Cuota deducible operaciones interiores bienes de inversión =
  sum of quarterly `31`

**Resultado anual**

- `84` — Suma cuotas devengadas anuales =
  `101 + 105 + 109`
- `85` — Total a deducir anual =
  `191 + 193`
- `86` — Resultado régimen general anual = `84 − 85`
- `95` — Resultado liquidación anual = `86`

(The full form carries more casillas for intracomunitarias,
importaciones, regularizaciones, recargo equivalencia, régimen
simplificado. These are NON-GOALS in v1 per the issue.)

### Reconciliation rules (390 → 303 × 4)

The Modelo 390 builder takes `tuple[FilingDraft, ...]` of exactly
four quarterly Modelo 303 drafts as a named input. Reconciliation:

- Each of the "sum" casillas (`100`, `101`, `104`, `105`, `108`,
  `109`, `190`, `191`, `192`, `193`) is computed from the four
  quarterly drafts.
- If any quarterly draft has a different modelo, period prefix, or
  different year than the 390, the builder raises
  `FilingComputationError` at build time — this is a contract
  breach, not a data error.
- Once the annual totals are computed, the validator (extended for
  390) runs an extra rule: recompute each annual sum from the four
  quarterly values and emit `FilingValidationFinding`
  (code `filing-390-303-mismatch`, severity ERROR) per casilla
  where the stored annual total diverges. In v1 the builder itself
  produces the sum, so divergence can only occur if a caller
  hand-mutates a draft — still worth guarding because
  `apply_validation` may re-run over an edited draft.

## Input shape

Both builders accept the existing `FilingInputs = Mapping[str, object]`
contract from `aeat.application.filing._protocols`. The Modelo 390 builder
additionally requires the four quarterly drafts. Because the
`FilingBuilder.build` ABC signature is fixed on `main`, the 390
builder reads the quarterlies out of a reserved key on the `inputs`
mapping:

```
inputs = {
    "01": 2025,                            # ejercicio
    "_quarterly_303": (q1_draft, q2_draft, q3_draft, q4_draft),
}
```

The reserved key begins with `_` and is explicitly documented on
the builder docstring. `build_draft` does not change shape. A
stricter typed envelope is deferred to a follow-up once the
workflow engine #59 lands — at that point a typed facade can
inline the 303 drafts as a field on an `AnnualIvaInputs` model.

## Protocol-conforming doubles

Same pattern as `_modelo_130_schema.py`:

- `_modelo_303_schema.py` — `MODELO_303_SCHEMA` constant, re-uses
  `StaticCasillaSchema` / `StaticCasillaCollection` (imported from
  the existing `_modelo_130_schema` module — they are generic).
- `_modelo_390_schema.py` — `MODELO_390_SCHEMA` constant, same
  re-use.
- `default_schema_provider()` in `aeat.application.filing.testing` is extended
  to register all three collections.

## Non-goals (v1)

- Régimen simplificado, recargo de equivalencia, REBU, REAGP.
- Intracomunitarias / importaciones casillas beyond the ones
  explicitly listed above for deducible.
- Any submission path — #42 already handles dispatch by modelo.
- The real casilla DB from #23 — migration is deferred.
- Sign interpretation (ingresar / compensar / devolver) of
  casilla 71 — the submission engine owns that.
