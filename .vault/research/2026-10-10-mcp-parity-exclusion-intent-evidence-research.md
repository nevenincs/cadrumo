# `mcp-parity` research: `exclusion intent evidence`

Cadrumo registers 266 operations. 123 list the MCP frontend, 116 are reachable through MCP, and 143 do not admit it (72 on the command line and the terminal interface, 71 on the command line only). The owner could not say from memory which of those 143 exclusions were intended, and asked for a judgement grounded in the rules that drive the application. This record collects the evidence for and against intent, family by family. It does not rule; a decision record does. Every locator is relative to the root of this repository, on branch `feature/tui` at commit `85f84a2680`, read on 2026-10-10 by static analysis with nothing executed; the tree had uncommitted changes by another session, and the only cited file among them is `.vaultspec/rules/04-external-integrations-and-local-runtime.md`, whose lines 5 and 7, the ones cited, are identical at that commit.

The evidence picture. The history records MCP being withdrawn only from authentication and grant-administration definitions; for ledger and modelo definitions no commit shows MCP being taken away, and no commit message gives a reason for any frontend set. The rule files reserve one class of operation to a person (workbench reads) and are otherwise descriptive. The shipped agent workspace tells agents to run command-line verbs whose operations are closed, and puts export and the local filed marker behind a verifier persona while the taxpayer files. Per the evidence verdicts in inquiry 5: 15 operations are rule-backed, 55 code-stated, 35 structural, 24 are ones the product expects an agent to do, 28 are inconsistent with open siblings, 5 predate the MCP frontend, and 29 have no evidence either way.

## Findings

### 1. How the frontend sets came to be

The MCP projection and the explicit all-frontends set were created on 2026-08-25 (`4254e0bd60`): `src/cadrumo/application/operations/registry.py:189-193` defines the member and `src/cadrumo/application/operations/registry.py:196-199` states that membership is explicit "so a new frontend is never granted to existing operations silently".

Eight modelo definitions pre-date the MCP feature series. Their first appearance in `src/cadrumo/application/modelo/operation_definitions.py` is 2026-08-26 for rename, discard, verify, file and export (`95ec17b73b`), 2026-08-26 for amend (`bc36b23966`), 2026-08-28 for edit-apply (`bd673aef67`) and 2026-09-26 for calculate (`ef8ad07c19`). The eight `permitted_frontends` sets in that file are all CLI plus TUI (`src/cadrumo/application/modelo/operation_definitions.py:569,699,929,1109,1408,1545,1728,1792`), and a pickaxe for `OperationFrontendProjection.MCP` over that file returns no commit. Seven of the eight were written one to three days after the enum member existed and about a month before the MCP purpose decision of 2026-09-26; calculate was written on that day. The Reference of that date says the eight modelo definitions "declare CLI/TUI only, so a future MCP registered-operation projection must refuse them unless their owner explicitly enrolls MCP" (`.vault/reference/2026-09-26-mcp-purpose-authentication-reference.md:343`), which records them as refused by default, not as decided. "Predates the MCP frontend" in this record means written before the registry-based MCP surface, whose commits include `16d221f48b` (2026-09-27, "Authenticate MCP calls by purpose and add the local runtime that serves them") and `3bb3b64787` (2026-09-30, "Checkpoint profile-bound MCP operation integration").

Every other closed definition was created inside the MCP feature series. A scan of the 84 non-test files under `src/cadrumo/application/` that hold a literal CLI-only or CLI-plus-TUI set read each file at its creating commit. The creating commits are dated 2026-08-25 (1 file, `src/cadrumo/application/auth/operation_definitions.py`, `60645f1be9`), 2026-08-26 (1, the modelo file above), 2026-09-27 (1, `src/cadrumo/application/user_profile/automation_operations.py`, `16d221f48b`) and 2026-09-29 to 2026-10-07 (81: 20 on 09-29, 32 on 09-30, 21 on 10-02, 5 on 10-03, 1 on 10-06, 2 on 10-07). 78 of the 84 were created with no mention of MCP or the all-frontends set; two of those later gained MCP-admitted agent siblings (`src/cadrumo/application/ledger/classify_operation.py` and `src/cadrumo/application/modelo/query_read_operation.py`, both at `a451478df4`). The other six were created as mixed or all-frontends files: `src/cadrumo/application/auth/apoderado_operation.py`, `src/cadrumo/application/live/borrador_100_operation.py`, `src/cadrumo/application/modelo/audit_operation.py` and `src/cadrumo/application/modelo/m036_operation.py` (all `a451478df4`, each with a human side and an agent side), plus the auth and automation files named above. Commits `3bb3b64787` and `a451478df4` carry the trailer `Vaultspec-Feature: mcp-purpose-authentication`.

### 2. What the rule files say

There are nineteen rule files, `.vaultspec/rules/00-architecture.md` to `.vaultspec/rules/16-bundled-knowledge-and-localization.md` (with `01` and `11` in two parts), one paragraph per line. They are descriptive of enforced controls and open concerns, and they say of the shipped agent material that it is "prompt material rather than enforcement" (`.vaultspec/rules/02-runtime-tui-and-agent-harness.md:7`). The one sentence that reserves a class of operation to a person is "Workbench reads are human-only and baseline-bound" (`.vaultspec/rules/11-modelo-work-and-revision-lifecycle-part-2.md:5`). A search for "human" across files 00 to 16 finds six other sentences, quoted below where they bear on the question; none reserves a ledger, classification or declaration-lifecycle act.

- Authority and model output. "CLI, TUI and MCP submit through registered operations. Command declarations, UI state and agent prompts cannot grant authority." (`.vaultspec/rules/00-architecture.md:29`). "Model extraction/classification is a proposal; deterministic registry logic owns regulated arithmetic, and grounding and human review have separate roles." (`.vaultspec/rules/00-architecture.md:35`). "model output, deterministic grounding and human confirmation must remain distinct" (`.vaultspec/rules/10-ledger-invoices-and-registers.md:7`). "Model classification remains a proposal until accepted" (`.vaultspec/rules/01-operator-interfaces-part-1.md:5`).
- Human review and confirmation. "re-extraction and per-finding human review precede canonical invoice creation" (`.vaultspec/rules/10-ledger-invoices-and-registers.md:3`). "explicit confirmation" is listed among the strongest controls without saying who gives it (`.vaultspec/rules/01-operator-interfaces-part-1.md:7`). Storage reclaim "requires explicit confirmation" (`.vaultspec/rules/08-authentication-and-storage-management.md:7`). Automation approval "withholds authority until protected delivery and possession acknowledgement" (`.vaultspec/rules/12-operations-profiles-and-workflows.md:7`).
- Human filing. The bundled agent material guides "independent review and human filing" (`.vaultspec/rules/02-runtime-tui-and-agent-harness.md:7`). "Export renders a selected fixed-width or XML layout to a local artifact and verifies bytes; it does not submit to AEAT." (`.vaultspec/rules/09-filing-and-live-state.md:3`). "A local calculation, verification, internal filing record, exported file and observed AEAT receipt are distinct states" (`.vaultspec/rules/01-operator-interfaces-part-1.md:3`). Local filing "creates a PRESENTADO revision whose AEAT status remains pending" and "Quickfile ends at local export" (`.vaultspec/rules/11-modelo-work-and-revision-lifecycle-part-1.md:3,7`). The product's own statement of who uploads: "leaving local filing artefacts for operator upload" (`.vaultspec/rules/13-core-authority-and-shared-controls.md:5`).
- Plaintext and secrets. "Persist private taxpayer, banking, credential, invoice, filing and evidence payloads only through approved encrypted custody ... A path or URL is not persisted evidence." (`.vaultspec/rules/05-persistence-and-secure-storage.md:13`). "Do not leak private payloads through logs, exceptions, command arguments, caches, scratch files, documentation or agent transcripts ... Explicit operator exports and consented integrations must follow their declared authorization, destination and data-lifetime contracts" (`.vaultspec/rules/05-persistence-and-secure-storage.md:15`).
- Hosted-model consent. "hosted-model extraction requires consent bound to the source bytes" (`.vaultspec/rules/00-architecture.md:45`). "canonical off-host invoice extraction binds fresh consent to stored source bytes, while generic dispatch relies on callers for that binding" (`.vaultspec/rules/04-external-integrations-and-local-runtime.md:7`). The registered path "requires stored evidence, per-call acknowledgement, a minted source-hash proof and a loaded-byte digest check" (`.vaultspec/rules/10-ledger-invoices-and-registers.md:5`). "Privacy permission for sending transaction or invoice text to a model is caller-owned." (`.vaultspec/rules/15-business-and-taxpayer-domain.md:7`).
- Local assertions. "M036 records and operator observations are local assertions; M145 is a payer communication" (`.vaultspec/rules/11-modelo-work-and-revision-lifecycle-part-1.md:5`); "trust in a recipient key still needs out-of-band checking" without saying by whom (`.vaultspec/rules/11-modelo-work-and-revision-lifecycle-part-1.md:7`).

### 3. The hand-off boundary the shipped agent workspace states

All paths in this inquiry are under `src/cadrumo_harness/_data/agent/`. The workspace has a README, seven personas, seven operator rules and 34 skill directories.

Who prepares. "You prepare a modelo declaration: you create the work unit, run the calculation, and read the resulting revision." (`src/cadrumo_harness/_data/agent/personas/cadrumo-modelo-preparer.md:3-5`). "You do not verify your own work ... You do not export or file. Preparation ends at a calculated, readable revision." (`src/cadrumo_harness/_data/agent/personas/cadrumo-modelo-preparer.md:31-33`).

Who verifies. "You are dispatched as an independent step: you do not share the preparer's reasoning" (`src/cadrumo_harness/_data/agent/personas/cadrumo-verifier.md:4-6`). "`aeat app modelo work verify` runs independently of the calculation step - do not treat a calculate result as self-certifying." (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-lifecycle-ordering.md:18-19`).

Who exports and records the local filed marker. "Because you are the independent actor that certified the filing clean, you own the irreversible handoff: only after a clean verify, produce the export (`aeat app modelo export`) and record the filing marker." (`src/cadrumo_harness/_data/agent/personas/cadrumo-verifier.md:34-39`; repeated at `:52-54`). The export skill says the marker comes later: "After the human files, optionally mark the local filing state with `aeat app modelo work file <work-unit-id>` to record the handoff, never to assert AEAT acceptance." (`src/cadrumo_harness/_data/agent/skills/cadrumo-exportar-declaracion/SKILL.md:28-30`). The ordering rule calls export and the marker "the terminal, irreversible steps of the local half" (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-lifecycle-ordering.md:22-25`).

Who files. "Your job ends at produce -> verify -> export; the taxpayer uploads the generated file in the AEAT portal themselves ... You prepare it; the human files it." (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-safety-handoff.md:6-12`). "You do not file or submit to AEAT. You prepare the artefact; the human files it." (`src/cadrumo_harness/_data/agent/personas/cadrumo-coordinator.md:30`). The same hand-off is stated in `src/cadrumo_harness/_data/agent/skills/cadrumo-exportar-declaracion/SKILL.md:27` and `src/cadrumo_harness/_data/agent/skills/cadrumo-preparar-modelo-100/SKILL.md:159-160`. Reconcile "runs after the human has actually filed outside the application" (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-lifecycle-ordering.md:26-29`).

What needs explicit human confirmation. "Obtain explicit human confirmation for destructive actions; a grant alone does not express that intent. CLI confirmation flags cited in a procedure do not authorize an MCP operation." (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-operating-rules.md:54-58`). Before a destructive custody action "the CLI requires `--yes` and you must not supply it to skip the question" (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-safety-handoff.md:35-41`). "Destructive verbs (`remove`, `reset`) require explicit confirmation." (`src/cadrumo_harness/_data/agent/personas/cadrumo-ledger-groomer.md:37-38`). Zero results and advisories are put to the taxpayer before export (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-honest-declaration.md:19-21`, `src/cadrumo_harness/_data/agent/skills/cadrumo-preparar-modelo-131/SKILL.md:77-79`); the amendment kind is "a legal classification ... never guess the kind silently" (`src/cadrumo_harness/_data/agent/skills/cadrumo-rectificar-declaracion/SKILL.md:27-29`); módulos figures come "from the taxpayer's own módulos worksheet" (`src/cadrumo_harness/_data/agent/skills/cadrumo-preparar-modelo-131/SKILL.md:40-44`); a notification document is refused "because the taxpayer must personally decide when to open it" (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-orientation-routing.md:65-67`). The 036 alta and baja are "filed in the AEAT portal (or by their gestor). This application records and derives; it does not file" (`src/cadrumo_harness/_data/agent/skills/cadrumo-cese-actividad/SKILL.md:46-48`, `src/cadrumo_harness/_data/agent/skills/cadrumo-inicio-actividad/SKILL.md:49-52`). If private access is absent the agent prepares "an authorization request for human approval" (`src/cadrumo_harness/_data/agent/README.md:24-26`).

Personas grant no authority. The preparer and verifier each say "Your persona grants no authority. Use MCP `status`, `search` and `describe` to inspect this connection's exact profile and permitted registered operations ... Follow this role's limits even if the approved grant is broader." (`src/cadrumo_harness/_data/agent/personas/cadrumo-modelo-preparer.md:42-45`, `src/cadrumo_harness/_data/agent/personas/cadrumo-verifier.md:58-61`). The ledger-groomer, classifier and onboarding personas keep family-level scope lines (`src/cadrumo_harness/_data/agent/personas/cadrumo-ledger-groomer.md:37-38`, `src/cadrumo_harness/_data/agent/personas/cadrumo-classifier.md:32-33`, `src/cadrumo_harness/_data/agent/personas/cadrumo-onboarding.md:30-33`).

### 7. Contradictions inside the product

1. Who records the filed marker, and when. The verifier persona records it as part of the hand-off after a clean verify (`src/cadrumo_harness/_data/agent/personas/cadrumo-verifier.md:34-39`); the export skill says after the human files (`src/cadrumo_harness/_data/agent/skills/cadrumo-exportar-declaracion/SKILL.md:28-30`); the safety rule ends the agent's job at export (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-safety-handoff.md:6-12`).
2. Hand-off verbs. The accepted harness record denies them per verb at the console and gives the verifier ownership (`.vault/adr/2026-07-02-agent-harness-refoundation-adr.md:96-97,172`); the persona has the verifier run them; the code enforces neither: a search of non-test files under `src/cadrumo_harness` for `elicit`, `destructiveHint`, `ToolAnnotations` and `readOnlyHint` finds nothing, and the registry admits neither verb, so the effect today is a flat refusal for every role.
3. Skills versus rules. The 34 skills name only command-line verbs, while the operating rule forbids building an operation from a command's spelling (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-operating-rules.md:37-42`, `src/cadrumo_harness/_data/agent/rules/cadrumo-operator-orientation-routing.md:131-132`); 21 of the 64 verbs map to a closed operation.
4. `aeat config auth configure` is instructed and closed: three files instruct it (inquiry 4 table), the definition was narrowed on 2026-09-30, and the Reference still records it as CLI, MCP and TUI (`.vault/reference/2026-09-26-mcp-purpose-authentication-reference.md:351`).
5. `ledger.add`. The accepted record and the persona designate the agent as the caller and require its key (`.vault/adr/2026-06-30-ledger-add-idempotency-adr.md:141-147`; `src/cadrumo_harness/_data/agent/personas/cadrumo-ledger-groomer.md:18-22`); the definition has been command-line only since creation (`src/cadrumo/application/ledger/add_operation.py:179`).
6. Destructive verbs. The operating rule and the groomer persona require human confirmation; `ledger.remove`, `ledger.reset` and `ledger.merge` are closed, while `ledger.invoice.remove` and `auth.session.reset`, also command-line `destructive`, are open, and the files setting `requires_human` that mix open and closed definitions set it only on the closed ones (`src/cadrumo/application/auth/apoderado_operation.py:157,200`). The rule files call the workspace "prompt material rather than enforcement" (`.vaultspec/rules/02-runtime-tui-and-agent-harness.md:7`).
7. The command-line `handoff` policy versus admission. `modelo reconcile import` carries it and `modelo.reconcile.import` admits MCP; `modelo export` and `modelo work file` carry it and do not.
8. README runtime commands. The README names five `aeat app runtime` commands (`src/cadrumo_harness/_data/agent/README.md:29-33,52-53`); the accepted runtime record removes runtime management and its commands (`.vault/adr/2026-10-03-runtime-without-service-manager-adr.md:40`, status `accepted`); no command-line spec registers a `runtime` group.
9. "Capability manifest". Six personas name it as an input (`src/cadrumo_harness/_data/agent/personas/cadrumo-verifier.md:10` and five others at line 9 or 10); it was the `contract` meta-tool of the deleted surface, which no longer exists, and the orientation rule describes `status`, `search` and `describe` instead (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-orientation-routing.md:121-132`).
10. Sign-in model. The accepted profile-access record says "agents authenticate with enrolled API keys or explicit attended delegation" (`.vault/adr/2026-09-26-mcp-purpose-authentication-profile-access-adr.md:203`) and rejects extending human login indefinitely "because delegation and human timeout would become the same authority" (`:36`); the owner's ruling is that MCP inside Cadrumo resumes the shared sign-in. This changes how every "a grant alone" sentence in the shipped rules reads.
11. Reference versus code. The Reference says eight modelo definitions are CLI and TUI only and lists them (`.vault/reference/2026-09-26-mcp-purpose-authentication-reference.md:343,358-365`); one of the eight, `modelo.work.calculate`, was first defined on the Reference's own date (inquiry 1).

### 8. The word "operator" names the agent in some records and the person in others

The operating rule opens "You are an LLM tax-advisor operator using Cadrumo's deterministic engine" (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-operating-rules.md:3`), and the ledger record says "The `aeat` CLI's target operator is an autonomous LLM agent" (`.vault/adr/2026-06-30-ledger-add-idempotency-adr.md:18`). Elsewhere the same word is the person: "the operator acknowledges that their sensitive data will leave the machine and be uploaded" (`.vault/adr/2026-06-10-llm-evidence-classification-adr.md:32-33`), and local filing artefacts are left "for operator upload" (`.vaultspec/rules/13-core-authority-and-shared-controls.md:5`). The consent handler uses both senses in one passage: "an agent consuming the envelope never sees prose" and "an operator must not act without" the caveat (`src/cadrumo/entrypoints/cli/_ledger_evidence_consent_cli.py:6-11`). It follows that a sentence such as "operator-declared header" (`src/cadrumo/application/modelo/m360_solicitud_operation.py:1-4`), "operator's typed applicability attestation" (`.vault/adr/2026-09-21-iva-workflow-m303-filing-evidence-authoring-adr.md:112`), "operator's per-filing ... election" (`src/cadrumo/application/modelo/export.py:349`) or "operator observations are local assertions" (`.vaultspec/rules/11-modelo-work-and-revision-lifecycle-part-1.md:5`) does not by itself reserve an act to a person; the surrounding record has to say who.
