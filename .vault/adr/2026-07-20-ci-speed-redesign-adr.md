# `ci-speed-redesign` adr: `per-push verification fits a ten-minute wall; the full campaign parallelizes` | (**status:** `accepted`)

## Problem Statement

Operator directive, 2026-07-20, verbatim: "we cannot have a test or build infrastructure that takes 50 mins per step. not for a trivial app like this." The measured baseline (packaging-smoke run 29747367504 attempt 2) confirms it: the Windows wheel leg took 34 minutes total, of which 26.3 minutes was the host-portable packaging campaign — five-plus flavor lanes run serially, each provisioning a fresh venv and re-installing the same wheels; the Ubuntu leg took 21 minutes (campaign 15.5), macOS 11 (campaign 8.3), and each of the six oracle-emit legs repeated a full checkout plus `uv sync` (roughly 2.4 minutes) to run a job whose real work is a download-install-probe. The separate `Cadrumo CI` workflow was worse than slow — it was broken: its unit step has not completed in months; every recent run that reached `Test (unit)` wedged for 3 to 5.5 hours with idle xdist workers until cancelled, because no per-test timeout exists anywhere, and the junit artifacts that would carry a duration profile are dead with the Actions storage quota. Every one of these workflows runs on every artifact-relevant push to main, which the shared-worktree agent fleet produces many times an hour.

The hard budgets set by the operator: the per-push pipeline wall is at most 10 minutes; no single step exceeds 10 minutes; the full release-candidate campaign remains the sole source of promotable `DistributionEvidence` (the evidence contract of the release-asset-transport and distribution-installation-readiness ADRs is not diluted) but should itself shrink.

## Considerations

- **What each flavor lane proves.** `core` proves the wheel cohort installs into a fresh uv venv and the installed CLI performs grounded tax work (the installed oracle); `pip-core` proves the same through plain pip in a stdlib venv; `sdist-core` proves the source distribution; `extras` proves the optional-extra graph resolves and imports; `split` proves the three-wheel cohort's byte-identical source verification; `browser` proves Chromium provisioning against the installed wheel; `dev` proves the frozen lock materialises a working developer environment; the Docker lanes prove a clean Linux image; `installed-oracles` replays both installed public transports. Only `core` answers the per-push question "did this push break the shipped artifact?"; every other lane proves a property of the release artifact set that changes when packaging metadata changes, not on the typical source push. That asymmetry is the licence for a quick/full profile split.
- **The flavor lanes are disk-disjoint.** Every smoke module writes into its own `var/packaging-smoke/<prefix>-<stamp>` work directory and reads the cohort directory read-only, so in-process concurrency needs no isolation work — only a bounded pool, because venv provisioning is disk-bound on the Windows runner.
- **The fleet shape rules out job-matrix parallelism for the flavor lanes.** One Windows runner, one macOS runner, and two Linux runners that share one physical machine: fanning lanes out as matrix jobs would queue on the single per-OS runner while paying a fresh checkout and sync per job. In-process concurrency inside the existing per-OS job is strictly better on this fleet.
- **Measured suite profile (first in months).** A local run of the unit suite in this redesign's worktree — 12,991 tests, `-n 4`, on the 24-logical-core workstation that hosts the runners, while contended by a concurrent pytest job — completed in 14:52 wall. The suite is healthy and parallelises; the CI hangs are a deadlock/timeout problem, not a throughput problem. At `-n auto` on an otherwise-idle runner the suite projects comfortably under 10 minutes, so per-push sharding across the two co-located Linux runners (which share CPU and would mostly contend) is not needed; a deterministic shard plugin ships tested and inert as the pressure-relief lever if the suite outgrows the budget.
- **The slowest tests are seconds, not minutes.** The measured `--durations` profile tops out at 58.7 s (one repo-walking audit test); a 300-second per-test ceiling is therefore pure headroom — it can only fire on a genuine wedge.
- **Evidence honesty constrains the quick profile.** Gate 2 of `publish-release.yml` verifies the promoted run's workflow path (`.github/workflows/packaging-smoke.yml`), conclusion, branch, and repo against the Actions API before trusting a byte. A per-push quick run must be structurally unable to enter that gate.
- **A latent coverage gap surfaced during grounding.** The integration-marked workflow conformance gates under `dev/packaging/tests` (the packaging-smoke, ci, transport, scoop/homebrew pins) are deselected by the default `-m unit` addopts in every invocation that reaches them, including the packaging preflight recipe — 113 gates were running nowhere in CI. The redesign gives them a per-push home.
- **Self-hosted caches.** `setup-uv`'s `enable-cache` round-trips the uv cache through GitHub's cloud cache — a win on ephemeral hosted runners, a pure network tax on this fleet where `~/.cache/uv` persists between jobs on the runner's own disk.

## Considered options

1. **Optimize the existing serial campaign in place** (venv reuse, hardlink clones): rejected — venv reuse across lanes weakens exactly what a lane proves (a fresh-environment install), and the measured cost is lane serialization, not any single lane.
2. **Flavor lanes as workflow matrix jobs**: rejected on fleet shape — single per-OS runners serialize the matrix anyway while multiplying checkout+sync costs.
3. **Per-push full campaign with concurrency only**: rejected — even parallelized, the Windows leg projects ~12-14 minutes, over budget, and burns the fleet on proofs no per-push consumer reads.
4. **Quick profile as an input/flag on packaging-smoke.yml**: rejected — a quick run would then share the workflow path Gate 2 pins, forcing the promotion gate to distinguish profiles by run metadata; a separate workflow file makes quick runs structurally non-promotable with zero new gate logic.
5. **Shard the unit suite across the two Linux runners per push**: rejected for now — the runners share one physical machine, so two `-n auto` shards mostly contend; the measured suite fits the budget in one job. The tested shard plugin ships as the scale-out lever.
6. **Changed-surface test selection per push**: rejected — an import-graph selector is the highest-bug-risk component on offer and this codebase's rules treat a false-green main as worse than a slow lane; the full suite fits the budget once the wedge class is fixed.
7. **Quick/full split with in-process lane concurrency, a dispatch-only full campaign, a two-job CI with a nightly full-conformance lane, and pytest-timeout everywhere** — accepted.

## Constraints

- The release-asset-transport ADR's invariants (single-creator drafts, terminal seal, layered Gate 2 verification, scrub-at-birth, GC namespace) are untouched; this ADR changes when and how fast workflows run, never what evidence is or how it is verified.
- **Trusted-source predicate (operator-approved reconciliation).** Every consumer of a full-campaign run — the scoop, homebrew, and claude acquisition lanes' source-run validation and `publish-release.yml` Gate 2 — replaces its former `event == push` pin with a rule of equal or stronger integrity: the run must still be the packaging-smoke workflow path and name, conclusion success, head repository this repo, and head branch `main`; its event must be either `push` (historical campaign runs stay promotable — the live-proved refusal of run 29746043967's failed source stands unchanged) or `workflow_dispatch` with the run's `head_sha` additionally verified to lie on `main` history via the GitHub compare API (`compare/main...<sha>` status `identical` or `behind`). The push pin only ever trusted the push router; the dispatch path verifies the actual commit ancestry, so the dispatch acceptance is strictly stronger, and dispatch already requires repo write access. The head-SHA-equals-`source_commit` binding and every downstream hash check are unchanged.
- The two GitHub-hosted acquisition legs stay blocked by the zero spending limit; out of scope here as in the transport ADR.
- The nightly schedule introduces the repo's first cron trigger. The operator's dispatch-only ruling was scoped to evidence GC (a destructive verb); the nightly lane is read-only conformance on idle self-hosted compute. If the operator extends the no-schedule ruling, the lane degrades to dispatch-only without structural change.

## Implementation

**D1 — Per-push packaging signal: `packaging-quick.yml`.** Three jobs, one per OS, each: checkout, frozen sync, `just packaging-quick` — which drives `dev/packaging/campaign.py --profile quick`: source preflight, one python-cohort build, one `smoke_core` fresh-venv install-and-oracle probe. No draft release, no assets, no evidence rows, `contents: read` only, cancel-in-progress concurrency, hard job ceilings. It carries the push trigger and paths-ignore set the full campaign used to hold.

**D2 — The full campaign is dispatch-only and stays the sole evidence source.** `packaging-smoke.yml` drops its push trigger; everything evidence-bearing about it (single-creator draft, per-OS legs, oracle-emit rows, terminal seal) is unchanged. Gate 2 of `publish-release.yml` accepts `workflow_dispatch` alongside `push` for the smoke run only.

**D3 — Flavor lanes run concurrently inside each leg.** `dev/packaging/campaign.py` owns the lane registry and three profiles (`quick`, `portable`, `ci`), builds the cohort exactly once, runs the profile's lanes on a bounded thread pool (default 3, `CADRUMO_PACKAGING_LANE_CONCURRENCY` override) with per-lane captured logs replayed on completion, then runs the serial installed-oracles pass for the non-quick profiles. The `just packaging-smoke` / `packaging-smoke-ci` aggregates route through the driver, so local and CI walls shrink identically. The driver also absorbs the dependency/source/preflight-command checks, removing their duplicated workflow steps (3.9 measured minutes on the Windows leg alone).

**D4 — CI splits into a two-job per-push lane plus a nightly full lane.** `ci.yml`: `cadrumo-static` (lint, relative imports, import architecture, types, semgrep, registry verify, oracle-binding audit, and the dev-tree unit+integration conformance gates — the previously-orphaned workflow pins' new per-push home) in parallel with `cadrumo-unit` (full unit suite, `-n auto`, `--durations=50` so every green run publishes a fresh profile). `ci-nightly.yml` (schedule 02:30 UTC + dispatch) runs the complete serial surface including the docs build, CVE audit, and hook replay, so every slow proof still gates main daily. `pytest-timeout` lands as a dev dependency with `timeout = 300` in the shared pytest config — the durable fix for the wedged-run class — and every new job carries an explicit `timeout-minutes` ceiling far below the 6-hour default.

**D4b — Do-once proof memoization (operator directive: "installability and tests should be ascertained only once — all repeated work must be done once, with work and envs reused").** The wheel cohort is a pure function of the committed wheel-relevant inputs, so an installability proof is content-addressed by `(proof kind, source fingerprint, environment fingerprint)`: the source fingerprint hashes the committed git object listing of `src`, `packaging`, `pyproject.toml`, and `uv.lock` (uncommitted drift in that scope yields no fingerprint — a dirty tree is never cached against nor served from cache); the environment fingerprint covers OS, architecture, OS release, exact CPython version, and exact uv version, so a toolchain bump invalidates every cached proof by construction — that is the whole invalidation policy, no TTL. `dev/packaging/proof_cache.py` stores pydantic-validated records in a runner-local store (`~/.cadrumo/proof-cache`, `CADRUMO_PROOF_CACHE_DIR` override). The quick profile becomes "ensure a proof exists for this identity": a hit prints the carried proof's provenance (origin commit, run id, timestamp) and exits in seconds — never silently re-stamped as fresh — so a push that leaves the wheel scope untouched costs checkout+sync only; a miss runs the probe and records the proof. Scope carve, stated deliberately: the FULL campaign's `DistributionEvidence` rows are never memoized in this change — every promotable row is still minted by a real run. The agreed follow-on policy for carried evidence (a carried proof satisfies a readiness row when its cohort digest and environment fingerprint match, recorded in the row as a carried proof with an origin-run pointer, with promotion still re-hashing actual bytes) is recorded here as the accepted design for the next pass; it touches the evidence schema, the readiness gate, and the scrub surface, and lands with its own tests rather than riding this redesign. Environment reuse at lane granularity is subsumed by proof memoization — an unchanged digest skips the lane entirely, which reuses the previous venv's work in the strongest possible sense (zero work), while a changed digest genuinely requires the fresh-venv install the lane exists to prove; within a rebuild, uv's hardlink link-mode against the persistent runner-local cache already makes installs mostly links, and wheels are built once per campaign by the cohort job (the quick profile builds per-OS only on a cache miss, since it deliberately owns no cross-job transport).

**D4c — Bounded caches that tolerate external pruning (operator ruling: hardware space is limited).** Every persistent do-once store is capped with a stated eviction policy, and treats an externally pruned entry as a plain cache miss (rebuild), never an error. The proof cache holds at most 512 records (~0.5 KiB each, under a megabyte total; `CADRUMO_PROOF_CACHE_MAX_RECORDS` override), evicted oldest-first by modification time at record time; a record deleted or truncated by the fleet's `ACTIONS_RUNNER_HOOK_JOB_COMPLETED` cleanup hooks simply misses and the next quick run re-proves and re-records — pinned by tests. The runner-local uv cache and any per-run residue are pruned to caps by those same runner-level hooks (owned by the fleet-hygiene work, not this ADR); uv tolerates cache pruning natively by re-downloading. No per-digest persistent venvs exist in this design (memoization skips the lane instead), so there is no venv store to bound.

**D5 — Repeated-cost removal on the self-hosted fleet.** `enable-cache: false` on every touched job: the runner-local uv cache persists between jobs, and the GitHub cache round-trip only added transfer time. The CI lanes also enroll in the repo's zero-Actions-artifact posture (review finding): the junit upload steps are removed — the duration profile lives in the job log — and a CI-scoped conformance gate now bans artifact actions from `ci.yml` and `ci-nightly.yml` the same way the transport gate bans them from the packaging workflows. Sparse/shallow checkout for the oracle-emit legs was evaluated and deferred: `uv sync --frozen` installs the project and therefore needs the full source tree, capping the achievable saving at the ~1.3-minute checkout against a real risk of breaking the editable install; revisit only if the legs' wall matters after the rest of this redesign.

**D6 — Conformance pins, updated honestly.** `test_packaging_quick_workflow.py` pins the quick workflow to exactly three probe jobs (no matrix, no growth), zero release/evidence surface, read-only permissions, capped ceilings, and pins the full campaign to dispatch-only triggers. `test_campaign.py` pins the lane registry to the justfile recipes and the quick profile to exactly the core probe. `test_ci_workflow.py` pins the two-job shape, the budget ceilings, the absence of the slow surfaces from the per-push lane, and the nightly lane's possession of all of them. `test_shard.py` proves the shard plugin is a deterministic partition with a real two-shard collection. No gate was deleted or weakened; the packaging-smoke structural gates were updated to the preflight-in-driver shape.

## Rationale

The redesign follows one principle: run each proof exactly as often as someone consumes it, and never serially when its inputs are disjoint. The per-push consumer asks "did this push break the product or the shipped artifact?" — answered by the static lane, the unit suite, and one fresh-venv install probe per OS, all of which fit the budget once the wedge class (no per-test timeout) and the duplicated fixed costs (preflights run twice, caches round-tripped through the cloud, five venvs built serially) are removed. The release consumer asks "is this exact byte set provably installable and grounded everywhere we claim?" — that question keeps every flavor lane, oracle replay, and evidence invariant, at dispatch cadence, parallelized only where the proofs are independent by construction. The quick/full boundary is enforced structurally (separate workflow path against Gate 2's pin) rather than procedurally, in the same spirit as the transport ADR's single-creator topology: the safe shape is the only shape that exists. The measured grounding is honest about its one weakness — the unit-suite projection extrapolates a local Windows `-n 4` contended run to a WSL `-n auto` runner — so the per-push unit lane publishes `--durations` on every run, making the next calibration a read, not another archaeology dig.

## Consequences

- The per-push wall drops from 34-minutes-when-healthy (and hours when wedged) to a projected ~9-10 minutes, with hard job ceilings guaranteeing a wedge dies in minutes. The projections are honest extrapolations from measured numbers, to be validated on the first runs and recalibrated from the now-always-published duration profiles.
- The full campaign roughly halves (~40 → ~20 min) with zero change to what it proves or mints; the evidence contract, transport invariants, and promotion gates are byte-for-byte in force. One trade-off taken under the campaign's authority: Gate 2 accepts dispatch-event smoke runs, which is a strict necessity of the trigger change, not a loosening of identity verification.
- Push cadence no longer taxes the fleet with release-grade proofs; the trade is that flavor-lane regressions (an extras dependency break, an sdist packaging slip) surface at the next dispatched campaign or nightly, not on the offending push. The quick core probe bounds the blast radius to non-core lanes.
- The docs build, CVE audit, and hook replay move from per-push to nightly-plus-dispatch: a regression there is caught within a day instead of an hour. This is the cadence trade-off the ten-minute budget buys; each still hard-gates main.
- The previously-orphaned 113 workflow conformance gates now run on every push — per-push coverage strictly increases even as wall time falls.
- New moving parts to own: the campaign driver (lane registry + profiles), the shard plugin (inert until needed), and the nightly lane's first cron trigger in the repo.
