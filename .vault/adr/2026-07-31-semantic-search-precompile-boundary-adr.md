# `semantic-search-precompile-boundary` adr: `semantic search is a precompile step: retire the runtime embedding stack` | (**status:** `accepted`)

## Problem Statement

Two accepted architectures for semantic search coexist in the project and pull in opposite directions. The documentation surface follows the precompile doctrine: decision D6 of `2026-06-10-docs-terminology-search-adr` makes the resident dev RAG a build-time compilation oracle whose outputs are laundered to identifiers and rankings before shipping, grounded in finding F3 of `2026-06-10-docs-terminology-search-research` (runtime reuse of the vaultspec-rag stack is not viable; build-time reuse is), and `2026-07-13-docs-terminology-search-adr` names the whole as the precompiled semantic-search architecture. The product surface went the other way: ruling R3 of `2026-07-02-agent-harness-refoundation-adr` chose a runtime hybrid lexical plus semantic corpus search for the MCP operating console, and its plan (wave W06, phases P13 and P14) shipped a runtime query embedder (`model2vec`, potion-multilingual-128M) behind the capability-gated `cadrumo[search]` extra, with corpus vectors built on the operator's machine on first use and the same embedder reused by the command-search meta-tool ranker.

The operator directive of 2026-07-31 makes the intent explicit: semantic search was always meant to be a precompile step. The product does not depend on a semantic runtime; it depends on vaultspec-rag compiling a search artefact that is published with the documentation and is not shipped inside the codebase. Independently, `2026-07-31-corpus-search-model-cache-capability-gap-audit` established that the runtime path fails its own guarantees on the pinned dependency versions: the model revision pin and the app-controlled cache root are silently dropped on every load, every model load requires a network round trip, and the weights land in the operator's global Hugging Face cache. A decision is needed on where the boundary sits, what is deleted versus kept, whether operator-facing capability changes, and in what order the tree moves so no shipped surface ever references a removed capability.

## Considerations

- The runtime semantic stack is a decided architecture, not silent drift: R3 of `2026-07-02-agent-harness-refoundation-adr` chose it deliberately, behind a licence gate that was later satisfied (MIT model). Retiring it is an amendment of R3, and this record says so; the drift framing is only accurate for the implementation defects the 2026-07-31 audit documents.
- F3 of `2026-06-10-docs-terminology-search-research` states the decisive structural constraint: arbitrary user queries cannot be pre-embedded; what can be precompiled is a term-to-result mapping, with embeddings used only as the build-time relevance oracle.
- The consumer install closure never carried the semantic stack: every consumer acquisition path (`dev/packaging` acquire and oracle scripts, the Claude plugin launch) installs `cadrumo[agent]`; `cadrumo[search]` is reachable only by a manual opt-in install. The default consumer experience is already the degraded lexical-only mode.
- The rule `shipped-search-licence-clean` bars shipping vectors, sparse weights, and raw scores in the package or built docs, and bars committing the heavy generated index; only laundered light data (identifiers, orderings, ratified synonyms) ships.
- The rule `no-legacy-compatibility` and the pre-release regime prefer deletion to shims; `retired-enum-members-need-consumer-reconciliation` governs the `RetrievalMode` narrowing; `aeat-docs-scaffolding-cli`, `aeat-locales-cli`, and `operator-harness-cites-live-cli-surface` bind the deletion sweep's collateral surfaces.
- Uncommitted peer work is in flight on exactly this surface (working-tree modifications to `_model_loader.py`, `_embed_build.py`, `pyproject.toml`, and the recall tests) implementing the 2026-07-31 audit's hardening recommendation. That recommendation is overtaken by this ruling; coordination is required before implementation so the peer's work is not clobbered and the peer does not harden a surface scheduled for deletion.
- The lexical index's Spanish stemmed column depends on `snowballstemmer`, currently gated behind the `search` extra, giving the lexical surface two shapes (stemmed and unstemmed) depending on install. `snowballstemmer` is a small, pure-Python, BSD-licensed package with no transitive weight.

## Considered options

- O1, keep the runtime stack and harden the loader (the 2026-07-31 audit's recommendation: drive the download through `huggingface_hub` directly with the pinned revision and app cache root). Rejected: it perfects a runtime the product is not meant to have; a grounding tool that downloads a roughly 0.5 GB model from a third-party hub on first query contradicts the offline, on-host posture the console is built around, and keeps `model2vec`, `numpy`, and `huggingface-hub` in the shipped dependency surface.
- O2, precompile the corpus vectors at release time and ship them, keeping only the query embedder at runtime. Rejected: query embedding still requires the model at runtime (the F3 structural constraint), so the network fetch and weight cache survive; and `shipped-search-licence-clean` bars shipping vectors in the package.
- O3, chosen: the shipped product carries no semantic runtime at all. Shipped retrieval is lexical, structured, and precompiled-data-driven only. Semantic value re-enters the product, if ever, only as laundered precompiled light data produced by the dev-side oracle, the exact shape the docs surface already uses.
- O4, delete the corpus grounding surface entirely. Rejected: lexical search over the bundled corpus and verbatim citation resolution are the core of R3's value and carry no semantic runtime; removing them would break the console's grounding mandate for nothing.

## Constraints

- Pre-release regime: `COMPATIBILITY_REGIME` is `PRE_RELEASE`, so deleted surfaces are deleted outright, with no read-tolerance, alias, or bridge.
- The docs-side precompile pipeline (`2026-06-10`, `2026-06-15`, `2026-07-13`, `2026-07-15` docs-terminology-search ADRs) is a stable parent and is not touched by this decision; this ruling brings the product surface into conformance with it.
- The shared worktree carries live peer WIP on the deletion targets; implementation must follow the worktree safety rules (no destructive git, explicit pathspec commits) and must reconcile or await the in-flight loader work before deleting those files.
- The deletion crosses gated collateral surfaces that each have an owning CLI or gate: apidocs stubs (`python -m dev.docs.apidocs scaffold` in the same commit), locale keys (`python -m cadrumo.locales`), the error registry, the MCP tool descriptions, and the operator harness documents bound by the rule-surface drift gate.

## Implementation

**R1, the boundary.** The shipped product retains exactly the retrieval surfaces that need no model: the FTS5 lexical index over the bundled corpus with the Spanish stemmed column, the exact citation lookup returning verbatim authoritative text, the terminology lookup, and the command-search per-column BM25 ranker with its pure-Python token-overlap fallback. The MCP corpus grounding tool (`cadrumo_corpus_search`) and the command `search` meta-tool remain, running on those surfaces only. `snowballstemmer` is promoted from the `search` extra into the core dependency set so the lexical index has one shape everywhere and the unstemmed degraded branch is deleted. Nothing in the shipped product loads an embedding model, computes or consumes vectors, or reaches the network for retrieval.

**R2, the compiled artefact.** The one semantic-search artefact the project depends on is the existing docs-search compilation: produced by the dev-side vaultspec-rag oracle on the dev box, laundered to identifiers, orderings, and ratified synonyms per D6 of `2026-06-10-docs-terminology-search-adr`, committed as light reviewable data, with the heavy Pagefind index regenerated at docs build and published with the documentation site, never committed and never wheeled, per D3 of `2026-06-15-docs-terminology-search-adr` and the `shipped-search-licence-clean` rule. Its guarantees are licence-cleanliness (laundering, approved-only enrolment), reproducibility (a deterministic compiler consumes the committed light data), and human ratification of synonym data. No product-shipped semantic artefact exists today and this decision creates none. A future, optional extension may compile a term-to-result expansion mapping or a related-provisions mapping for the corpus grounding tool through the same oracle-and-launder pipeline, shipped as light data; that is a pathway, not a commitment of this record.

**R3, deleted versus moved.** Deleted outright, with their tests, in one coherent sweep: the `search` extra in `pyproject.toml` (and its entry in the `all` aggregate) with the `model2vec`, `huggingface-hub`, and `numpy` pins, none of which have any other consumer in the tree; `_model_loader.py`, `_query_embed.py`, and `_embed_build.py` in `corpus_search`; the semantic and RRF-fusion halves of `_retrieval.py`, `_runtime.py` (`ensure_corpus_embeddings`, `load_corpus_embeddings`, the embedder wiring in `search_corpus`), and `command_search/_index.py`; the `QueryEmbedder`, embedding, and model-constant exports on the `corpus_search` facade; the `CorpusSearchDependencyError` error, its registry row, its locale keys, and every `pip install cadrumo[search]` hint; the semantic members of `RetrievalMode` with full consumer reconciliation; and the tests `test_embed_build.py`, `test_query_embed.py`, `test_hybrid_real_model_recall.py`, `test_hybrid_real_model_recall_live.py`, plus the semantic branches of `test_search_shippability.py`, `test_command_ranking_golden.py`, and the error-registration tests. Nothing moves to dev tooling: the dev side already owns its own compilation pipeline and reuses none of this code.

**R4, capability change, stated plainly.** For an operator who manually installed `cadrumo[search]`, semantic concept recall is removed from the corpus grounding tool and from command search: a natural-language query that shares no token or stem with the target text will no longer be bridged by an embedding. This is a real degradation of R3's stated goal that compliance queries need both exact-citation and concept recall, partially compensated by stemmed lexical recall, curated command aliases, and the optional future precompiled expansion artefact. For the default consumer (the `cadrumo[agent]` closure, every packaged acquisition path) nothing changes: they never had the semantic mode. In exchange the product loses its only runtime network-fetching retrieval path, its only third-party model dependency, the roughly 1 GB unpinned cache outside the app storage root, and the entire defect class the 2026-07-31 audit documents.

**R5, migration order.** First, coordinate the in-flight peer work on the loader so no agent hardens a surface scheduled for deletion. Second, one atomic explicit-pathspec commit rewires every consumer and deletes the semantic modules together: `search_corpus` and the command index drop their embedder parameters and semantic branches, the facade exports shrink, `RetrievalMode` is reconciled, the deleted modules' tests go with them, and the apidocs stubs are regenerated in the same commit, verified by clean collect-only. Third, the packaging and diagnostics commit: the `search` extra and its pins are removed, `snowballstemmer` moves to core, the lock is refreshed, the error-registry row and locale keys are retired through their owning CLIs, and the extras-reporting surface (`config check`) drops the capability. Fourth, the truth sweep: MCP tool descriptions, operator harness documents, and user documentation stop claiming hybrid or semantic retrieval, verified by the rule-surface drift gate and the docs build gates. At no intermediate commit does a shipped surface import or advertise a removed capability.

## Rationale

The operator's intent and the corpus's own doctrine coincide: the accepted docs-search records already establish that the expensive half of semantic retrieval runs once on the dev box and ships as laundered data, and F3 already names why a runtime is the wrong home for it. The product surface was the one place that decided otherwise, and that decision (R3's semantic half) is hereby amended: R3's grounding mandate, citation resources, lexical search, and on-host posture stand; its runtime embedding half is retired. This is an amendment with a stated reason, not a discovered inconsistency: R3 predates the operator's 2026-07-31 clarification and was implemented in a way that additionally broke its own reproducibility and storage-root promises, as the audit shows. The audit's findings are resolved by removal rather than by its hardening recommendation, which this record explicitly declines. The docs-terminology-search ADRs are not superseded or amended; this decision conforms to them. The packaging ADRs (`2026-06-28` product packaging, `2026-07-03` Claude ecosystem packaging) are unaffected in substance: the consumer closure was already `cadrumo[agent]`, and only the `all` aggregate shrinks.

## Consequences

- The shipped product becomes fully offline for retrieval: no model download, no Hugging Face dependency, no unpinned-revision hazard, no cache outside the app storage root. The dependency and licence surface shrinks by three packages.
- The honest cost is the R4 capability loss for `[search]` opt-in installs; the operator sees it stated in R4 rather than buried in a refactor.
- The in-flight peer hardening of the model loader is discarded by this ruling; that work was correct against the audit's recommendation and is overtaken, not refuted. The coordination step in R5 exists so this is an explicit handoff, not a clobber.
- The command-and-corpus vector-ranking duplication flagged by the 2026-07-31 semantic-code-deduplication campaign audit is resolved by deletion of the shared mechanics.
- The pathway stays open: because the corpus is static and chunk identifiers are stable, a laundered related-provisions or term-expansion artefact can later restore concept adjacency with zero runtime model, through the same pipeline and licence gate the docs surface already trusts.
- A future ADR reintroducing any runtime embedding surface must supersede this record explicitly; the boundary is now that the product ships no semantic runtime, not that one is merely optional.
