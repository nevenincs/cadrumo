# `informativa-party-name` adr: `Operator-declared party names for informative-return name fields` | (**status:** `proposed`)

Proposed 2026-11-11 by CALC-IVA within bounds set by the coordinator. Not accepted; no Step may execute on it.

## Problem Statement

Every AEAT informative-return design that lists a third party (declarado, perceptor, operador intracomunitario, arrendatario, afiliado, socio) carries a fixed-width party-name field, almost always positions 36-75 (40 characters), and the design prescribes its content: surnames first, then the given name, for a natural person; the complete razón social for an entity. Cadrumo fills these fields from free text that was never stated for this purpose. Modelo 347's `modelo-347-contraparte-row-nombre` and 349's `iva-349-operador-row-apellidos` read row field `party_legal_name`, which is `invoice.counterparty_name` (`src/cadrumo/application/invoices/source_observations.py:288`, `:456`, `:472`; folded in `src/cadrumo/domain/calculations/registry/invoice_row_materialization.py:92-145`). For a Facturae natural person that string is joined given-name-first (`src/cadrumo/adapters/inbound/einvoice/element_readers.py:99-117`), which is the reverse of the order the design requires. Modelo 190/193 perceptor names come from `WithholdingObservation.perceptor_legal_name`, entered by the operator or copied from an invoice counterparty name. Nothing enforces the design's order, a missing name exports as spaces because every party-name field is `required = false`, and an over-width name fails as a generic `RegistryValidationError` in the fixed-width codec (`src/cadrumo/domain/calculations/registry/fixed_width_codec.py:345`) instead of a typed refusal that tells the operator what to do. A repair inside 347 alone would leave the same defect in every other modelo that has the same field, so the mechanism is decided once.

## Considerations

- **Discovery.** `vaultspec-core vault list adr` and `vault search` (counterparty, party name, informativas export, perceptor, razón social, truncation) found no accepted ADR governing third-party names. Adjacent accepted records, none of which decide this: `2026-10-12-registry-header-requirements-adr` (reviewed, source-cited requirements on declarant header fields; a refusal names the profile fact the operator declares), `2026-10-03-modelo-347-fileability-adr` (one 347 row builder and renderer; it does not address the name), `2026-08-06-invoice-canonical-structure-adr` (the canonical invoice requires a non-empty `counterparty_name`, which is document text, not a filing name). This is therefore a new decision, not an amendment. The design text, the abbreviation searches and the registry inventory are recorded in `2026-11-11-informativa-party-name-research`. ## Considered options

- **Keep deriving from invoice `counterparty_name` and reorder in code. Rejected.** A free display string cannot be split into surnames and given name reliably. Compound surnames, particles and single-surname foreign persons make any split a guess, and a guessed order is filed as a stated fact.
- **Truncate or abbreviate to the layout width. Rejected.** No design sanctions it for a party name (see the searches above). A shortened razón social is no longer "completa", and silent truncation is forbidden by rule 09.
- **A 347-only fix in the 347 row builder. Rejected.** The same field and the same rule appear in 156, 180, 184, 190, 193, 194, 349 and 720. A per-modelo fix creates parallel mechanisms.
- **One operator-declared filing name per party, held as typed components, composed by a registry-declared rule, sized by the hydrated layout, refused with a door when missing or over width. Chosen.**

## Constraints

- **The operator states the name.** A party's filing name is an operator declaration with operator provenance. The application never derives it from document text, never reorders it, never splits it, never abbreviates it and never truncates it. Document-extracted names (invoice `counterparty_name`, Facturae `facturae_party_name`, withholding `perceptor_legal_name` copied from an invoice) may be shown to the operator as a suggestion, but they reach an export only after the operator declares them.
- **Party kind is declared.** The operator states whether the party is a natural person or an entity (persona jurídica, entidad sin personalidad jurídica or entidad en régimen de atribución de rentas), because the design's branch a) or b) depends on it. A contradiction between the declared kind and the form of a Spanish NIF is surfaced as a finding. It is never resolved silently in either direction.
- **Ruling on natural-person shape: three typed components, not one string.** For a natural person the declaration holds `primer_apellido`, `segundo_apellido` and `nombre` as separate stated components. The field value is composed exactly as the designs prescribe: "el primer apellido, un espacio, el segundo apellido, un espacio y el nombre completo, necesariamente en este mismo orden" (347 2025 lines 272-276; identical in 180, 184, 190, 193, 194 and 156, and in 349 through its declarant criterion). The design defines the field's content as an ordered composition of three named parts. A single free string cannot be checked against that order, and the strings Cadrumo actually holds are given-name-first. The components are the operator's words. The order and the single-space separators are the design's rule, carried as data on the registry layout and not as a Python constant. Composing them is the design's own formatting, not a derivation of the name. This satisfies CALC-PAGOS point 3 without the application reordering anything the operator wrote.
- **Entities: one string.** For an entity the declaration holds one `razon_social` string, the complete razón social or denominación, verbatim. A trade name is not admissible where the design says "En ningún caso podrá figurar en este campo un nombre comercial". The operator affirms this. The application does not detect it.
- **Minors.** The designs require the minor's own surnames and name in this field (the representative's NIF goes in positions 27-35). The same natural-person components apply to the minor.
- **Width comes from the layout.** The maximum is the `length` of the hydrated export-layout field for the exact revision being exported. No width constant exists anywhere. A design that widens or narrows the field changes the limit without a code change.
- **Missing or over width is a typed refusal with a door.** A row whose party has no declared name, or a declared natural person missing `primer_apellido` or `nombre`, refuses export. So does a composed value longer than the field. The refusal is a registered error code naming the modelo, the record and field, the party (by a non-identifying handle, never the NIF or name in the message), the layout width and the composed length. Its door is the operator action that states or restates the party's filing name. Because no design permits shortening, the door for over width lets the operator state a shorter rendering explicitly. That rendering is a declaration scoped to the party and the width, with operator provenance, never produced by the application. The generic codec error remains as a backstop and is never the operator-facing outcome.
- **Second surname absent.** A person with one surname (common for 349 operadores and foreign perceptores) can be declared only with an explicit "no second surname" statement. A blank is never read as absence. The designs do not say how to compose the field without a second surname. Until a source grounds it, such a row is advisory (calculation grade), not filing grade, and the export refuses with that reason. This is an open grounding question to settle before acceptance.
- **Scope.** The mechanism covers every export-layout field whose design states this party-name rule: the third-party binding-row fields listed under Considerations, the casilla-kind name fields of 165, 181, 185, 189, 270, 280 and 345 once their design text is confirmed field by field, and the declarant header fields of designs that state the same rule (the composition rule applies to the profile's existing `identity.*` facts, with no new store). 232 and 390 representative and joint-declaration names are included only where their design text is confirmed to state the rule. Each field's enrolment cites its design text, in line with `2026-10-12-registry-header-requirements-adr`.
- **Requirement.** Whether a field is required stays with the design and the reviewed-requirement mechanism of `2026-10-12-registry-header-requirements-adr`. This ADR adds no second requirement path. A field that the design or a reviewed requirement makes mandatory refuses a missing declared name. A field that neither makes mandatory still never receives an undeclared, document-derived name.
- **Affected prior wording.** None of the related accepted ADRs is contradicted. `2026-08-06-invoice-canonical-structure-adr` keeps `counterparty_name` as a required document field, and this ADR narrows its use: it becomes display only for filing purposes. `2026-10-03-modelo-347-fileability-adr` keeps its one row builder, which now reads the declared name. No amendment text is required.

## Implementation

We will add one operator-declared party filing name, one registry-declared composition rule and one typed refusal with a door, and switch every party-name binding to them. Outline only; hypotheses are marked.

- **Persisted location (hypothesis).** A `declared_filing_name` member on the per-counterparty confirmed-facts record next to establishment. It holds the party kind, either the three natural-person components or the entity's razón social, any width-scoped operator renderings, provenance (operator, instant) and revision. The record keeps the existing digest key and encrypted namespace, and a schema version bump migrates existing records with the member absent. Perceptores without a verifiable identifier (no key) cannot hold a declared name. Their rows refuse with a door to state the identifier first.
- **Composition rule.** A registry-declared composition on party-name export fields: the component order and separator, plus a kind discriminator for natural person versus entity. It is generated from the reviewed semantic map like other layout properties and validated against the cited design text, and the renderer applies it before width checking. Hypothesis: it reuses the semantic-map requirement pattern (`source_ref`, `statement` quoted from the design) rather than a new review channel.
- **Bindings that switch.** `modelo-347-contraparte-row-nombre`, `modelo-347-inmueble-row-arrendatario-nombre`, `iva-349-operador-row-apellidos`, `iva-349-rectificacion-row-apellidos`, `modelo-190-perceptor-row-name`, `modelo-193-perceptor-row-name`, `modelo-193-gasto-row-nombre`, `modelo-194-perceptor-row-nombre`, `modelo-180-perceptor-row-name`, `modelo-184-member-row-name`, `modelo-156-row-nombre`, `modelo-720.type_2.apellidos-y-nombre-razon-social-o-denominacion-del-declarado`, and the confirmed casilla and header fields. Each reads the declared filing name through the row's party identity instead of `party_legal_name` or `perceptor_legal_name`. The rows keep the free-text value as display and evidence.
- **Refusal and door.** A new registered error code family under the filing domain carries the fields named under Constraints. The door is an operator-remedy catalogue action that opens the party's filing-name declaration through CLI, TUI and MCP. The surfaces render backend-served wording only.
- **Migration.** Existing invoices, withholding observations and capture rows keep their free-text names unchanged as display only. Nothing is backfilled from them into a declaration. After the switch, an export of a period whose parties have no declared name refuses with the door, and the operator states each name once per party. The M193 placeholder name and the ledger-payment 256-character bound stop feeding exports.

## Rationale

The designs define this field's content as an ordered composition with no sanctioned shortening, so the only truthful sources are the party's own name parts as stated by someone who knows them, the operator, and the design's own composition rule. Holding components rather than one string is what lets the order be enforced without the application guessing where a surname ends. Holding the fact on the entity means it is stated once rather than per invoice. Reading the width from the hydrated layout keeps one authority for geometry. A typed refusal with a door turns today's silent blank or generic codec failure into an operator action.

## Consequences

- One party-name path serves 156, 180, 184, 190, 193, 194, 347, 349 and 720, and the declarant fields of designs with the same rule. CALC-PAGOS's 190/193 perceptor rows adopt it on acceptance.
- Exports that today emit spaces or a given-name-first name will refuse until the operator declares the names. This is a deliberate, visible cost.
- The single-surname composition stays advisory until grounded. Reconsider if AEAT guidance or a design states the rule, or if a design gains an abbreviation rule for party names, or splits the field into separate apellido and nombre positions (as 309's later edition does for the transmitente). In that last case the stored components bind to the split fields directly.
- The CALC-PAGOS report that 180 has no party record conflicts with the published layout. It must be verified before the 180 binding is switched.
