# `release-asset-transport` adr: `evidence and cohort transport moves from Actions artifacts to GitHub Release assets` | (**status:** `accepted`)

## Problem Statement

The Cadrumo release pipeline transports every inter-workflow payload — the sealed release cohort (`cadrumo-release-cohort`), the per-OS smoke cohorts (`cadrumo-python-cohort[-windows|-macos]`), and the per-row `DistributionEvidence` JSON records — through GitHub Actions artifact storage (`actions/upload-artifact`, `actions/download-artifact`, `gh run download`). The repository is private, on a GitHub Free plan for a User account, with the Actions spending limit deliberately pinned to zero dollars under the cost-policy mandate. Private Actions artifact storage is capped at roughly 500 MB included; the multi-hundred-MB cohort exhausts it on essentially every packaging leg, and the account now hits "Artifact storage quota has been hit" on every run, hard-failing uploads. Compute is free on the self-hosted runners, but the transport layer is structurally broken.

GitHub Release assets do not count against Actions storage: they are stored outside the shared Actions/Packages pool, carry a 2 GiB per-file cap and up to 1000 assets per release, and have no practical quota at these sizes. One channel already uses them: the operator's four `claude-*` rows are minted locally and uploaded to a draft release tag (the `claude_evidence_release` input), and `publish-release.yml` already consumes them via `gh release download`. The operator has ruled: generalize that proven pattern — all evidence and cohort transport moves to Release assets. The operator approved the overall design on 2026-07-20 in-session with four rulings folded into this decision: scrub runner metadata from any evidence published on the final release, defer build-provenance attestations, garbage-collect keeping the newest three draft sets per lane, and keep garbage collection dispatch-only with no schedule trigger.

## Considerations

- **The promotion contract is provenance-first.** Gate 2 of `publish-release.yml` verifies each source run's identity against the Actions API (workflow path, conclusion, event, branch, head_sha) before trusting a single byte, then binds every evidence row to the sealed cohort via `dev/release/readiness.py`. Any new transport must preserve run-identity verification and add byte-integrity verification, because release assets — unlike run-scoped artifacts — are not intrinsically bound to the run that produced them.
- **Industry grounding.** Mature release pipelines were examined for the same problem shape. GoReleaser's release flow natively stages every GitHub release as a draft while assets upload and publishes only at the end, supports reusing existing drafts, and retries asset upload on HTTP 422 by deleting and re-uploading the colliding asset — direct precedent for draft releases as an upload-in-progress container and for retry-on-upload semantics. cargo-dist (which drives the uv and several Rust-ecosystem release pipelines) deliberately uses Actions artifacts as scratch transport between its plan/build/host jobs and creates the real release transactionally at the very end, explicitly to avoid using a draft release as scratch storage; that choice is only available when Actions artifact storage is available, which the zero-spend Free-plan constraint removes here, so this design inverts the transport while adopting cargo-dist's underlying principle — the one user-visible release is created transactionally at the end from verified inputs, never incrementally. PyPI Trusted Publishing via `pypa/gh-action-pypi-publish` (already the publish path here) anchors trust in the workflow run identity, which supports keeping run ids as the promotion inputs. Sigstore-style attestation (`actions/attest-build-provenance`) was examined and deferred by operator ruling: it needs `id-token: write` plus `attestations: write` and its verification UX presumes a public repo or paid features; the manifest-plus-API cross-check below covers the threat model until then.
- **A documented draft-release pitfall shapes the topology.** GitHub permits multiple coexisting draft releases with the same `tag_name`, because a draft creates no tag ref and therefore reserves nothing: `gh release create` against a tag that exists only as a draft does not fail — it mints a second draft. This race is documented across the ecosystem (cli/cli issue 4270, actions/create-release issue 72, release-drafter issue 1146, GitHub community discussion 51299, softprops/action-gh-release issue 602). An idempotent-create-anywhere pattern (`gh release create ... || true` in every uploader job) is therefore unsafe under concurrency: parallel jobs mint duplicate drafts and scatter assets across them, and tag-addressed uploads resolve ambiguously. The decision below mandates a single-creator topology instead.
- **Same-run draft consumption is load-bearing and holds.** A `needs:`-downstream job in the same workflow run must reliably download assets from a draft created by an earlier job. Release asset upload is a synchronous API operation (the asset is durably stored when the upload call returns), and `gh release download <tag>` resolves drafts by tag for any authenticated token with push access — the workflow `GITHUB_TOKEN` qualifies, and this repo's existing claude-evidence flow already exercises draft download by tag in `publish-release.yml`. Residual flakiness (API hiccups, list-pagination lag) is handled with a short bounded retry in the verify helper, mirroring GoReleaser's upload-retry posture, not with an architectural change.
- **Release assets are flat files.** `gh release upload` flattens to basenames and the cohort is a directory tree; directory payloads must be archived, and the archive digest becomes part of the provenance manifest.
- **Draft vs prerelease.** A prerelease is publicly visible the moment the repo goes public, pollutes the release list, and creates a real tag ref. A draft is visible only to collaborators, creates no tag ref, still stores `target_commitish`, and is fully addressable by `gh release view/download/upload` for a token with push access. Drafts are the correct non-user-facing container.
- **Same-host vs cross-host handoffs.** Inside one `packaging-smoke.yml` run, `build-release-cohort` (self-hosted Linux) feeds `oracle-emit-linux` on the same physical host, but also `oracle-emit-windows` and `oracle-emit-macos` on different physical hosts. Only the Linux-to-Linux edge could ever be disk-local; the other two genuinely need cloud transport.
- **Local-first parity.** Local lanes mint the identical `DistributionEvidence` rows to a local directory and `readiness.py` reads them via `--evidence-dir`. The transport must stay invisible to the row contract.
- **Permissions.** Artifact upload needed no write permission; release upload needs `contents: write`. That token can also push commits and tags, so it is scoped job-level, only on jobs that upload, and checkouts stay `persist-credentials: false`.
- **Privacy of published evidence.** `DistributionEvidence` rows carry runtime identity fields and command transcripts in which runner hostnames, usernames (in absolute paths), and machine identifiers appear. Publishing them verbatim on the public `v<version>` release would leak operator machine metadata once the repo is public. The operator ruled runner metadata is scrubbed from anything published on the final release. During implementation this was reconciled into scrub-at-birth: the evidence builders redact at mint time, so identifiers never persist anywhere — which also keeps draft bytes and published bytes identical, preserving one evidence identity and letting the draft manifests' digests carry through to the final release unchanged.
- **Safety.** No change may create an auto-publish path. The `CADRUMO_PUBLISH_ENABLED` variable gate, the `release` protected environment with a human required reviewer, and the promote-never-rebuild invariant are untouched. Draft evidence releases must be structurally unconfusable with the one real `v<version>` release.
- **Hosted-blocked legs are out of scope.** `packaging-scoop.yml` (windows-2022) and two `packaging-homebrew.yml` matrix legs are GitHub-hosted and remain blocked by the zero spending limit regardless of transport. This ADR fixes storage, not hosted minutes.

## Considered options

1. **Retention-shrink (`retention-days: 1`) on Actions artifacts.** Rejected: the quota counts stored bytes until expiry; a single run's cohort set alone exceeds the roughly 500 MB private allowance, so even one-day retention hard-fails the upload on the very run that needs it, and artifacts cannot outlive the promotion window anyway.
2. **Runner-local disk handoff.** Rejected: two of the three oracle legs and all acquisition lanes are different physical hosts; workspace persistence between jobs is not a contract; the bytes are unverifiable; and promotion (possibly weeks later, any runner) still needs a durable store.
3. **External object storage (S3, R2, B2).** Rejected: violates the minimal-cloud-cost mandate, adds a credential and an availability dependency, and loses the free run-to-release-to-API provenance triangle GitHub gives natively.
4. **Git LFS or committing cohorts to git.** Rejected: LFS bandwidth and storage quotas on Free, repo bloat, and the build-output-in-git precedent this repo explicitly avoids.
5. **Prerelease (non-draft) evidence releases.** Rejected: publicly visible if the repo goes public, creates tag refs per run, appears in release listings — exactly the user-facing confusion the design must prevent.
6. **A single rolling draft (one fixed tag, clobbered per run).** Rejected: it destroys the run-to-assets binding (a promotion could race a newer smoke run overwriting assets mid-download) and erases the audit trail between runs.
7. **cargo-dist-style Actions-artifact scratch transport with a transactional final release.** The industry-preferred shape, but structurally unavailable: it presumes Actions artifact storage, which the zero-spend Free plan denies. Its transactional-final-release principle is adopted; its transport is not.
8. **Draft releases per producing run with a provenance manifest and layered verification.** Accepted, with the single-creator amendment below.

## Constraints

- Depends on the accepted distribution-installation-readiness and distribution-harness-identity ADRs (cohort sealing, evidence schema, readiness gate) remaining in force; this ADR changes transport only.
- Draft-release behavior on private Free repos is the least-documented corner of GitHub's storage terms; GitHub reserves the right to police excessive release storage. The bounded keep-window (newest three sets per lane) keeps standing usage to a few GiB.
- GitHub permits duplicate drafts per tag name; every design element that assumes tag-addressed uniqueness must either enforce a single creator or assert uniqueness before trusting.
- The two GitHub-hosted packaging legs stay blocked by the zero spending limit; this ADR does not unblock them.

## Implementation

**D1 — Transport container: one draft release per producing workflow run, created by exactly one job.** Every packaging workflow that today uploads artifacts instead ensures a single draft release per run and attaches all of its sealed outputs as assets. Draft tags embed the run id: `evidence-smoke-<run_id>` for `packaging-smoke.yml` (cohort archive, three per-OS python cohort archives, python evidence rows, smoke-evidence bundles, manifest), `evidence-scoop-<run_id>` and `evidence-homebrew-<run_id>` for the acquisition workflows, `evidence-claude-<run_id>` for the claude lane's curated bundle; the operator's locally-minted draft carrying the four required `claude-*` rows is unchanged. The draft's `target_commitish` records the commit SHA. Because GitHub does not reserve draft tag names, draft creation is topologically serialized: exactly one root job per workflow (for `packaging-smoke.yml` the `build-release-cohort` job; for a matrix workflow a dedicated setup job the matrix `needs:`) creates the draft; every other job is upload-only against the existing draft. Creation itself is create-if-absent via a `gh release view` existence probe before `gh release create --draft` — never an error-suppressed create-or-ignore, because a re-run attempt's create SUCCEEDS against a tag that exists only as a draft and mints the duplicate the suppression was meant to tolerate; the conformance gate refuses any error-suppressed create line. Each draft's `target_commitish` is the creating run's own head SHA — for the acquisition lanes their own dispatch run's commit, not the consumed smoke run's source commit (otherwise the D2 release-to-run binding check could never pass); the consumed smoke commit stays recorded in the run context and is enforced by the existing source-identity steps. The verify path (D2) additionally asserts exactly one draft exists for the tag before trusting any asset, so a residual race fails loudly instead of scattering assets. A re-run attempt of the same run re-uploads with `--clobber` and stamps `run_attempt` in the manifest; a re-run of the same SHA mints a new run id and therefore a new, non-colliding draft.

**D2 — Provenance attestation: a per-run `evidence-manifest.json` asset.** Because a release asset is not run-scoped, each producing workflow finishes with a terminal seal job (`needs:` every uploader) that emits and uploads a manifest recording the schema id `cadrumo.packaging.evidence-release-manifest.v1`, the workflow path, run id, run attempt, head SHA, head branch, event, and a per-asset sha256 and size table. Gate 2 verification becomes three layered checks, strictly stronger than today: first, run identity against the Actions API exactly as now; second, release-to-run binding — the derived draft exists, is unique for its tag, its `target_commitish` equals the run's head SHA, and the downloaded manifest's run id, run attempt, and head SHA match the API answer; third, byte integrity — every downloaded asset re-hashes to the manifest's sha256 before extraction or use. Only then does the existing readiness gate run its cohort-binding row checks, unchanged. A tampered or substituted asset fails at hash time; a manifest forged by a non-Actions actor cannot survive the second check because it must agree with the Actions API record for a real successful run of the named workflow. Cryptographic attestation via `actions/attest-build-provenance` is deferred by operator ruling, revisited when the repo is public.

**D3 — Promotion inputs stay run ids.** `publish-release.yml` keeps `packaging_run_id`, `scoop_run_id`, `homebrew_run_id`, and `claude_evidence_release` exactly as-is. The run is the identity anchor Gate 2 verifies, so the evidence tag is derived from the run id; one input serves both verification and asset location, and the operator workflow does not change. Only the download steps change: `gh run download` becomes `gh release download` of the derived tag plus manifest verification. The claude input remains a literal tag because it has no backing run.

**D4 — Intra-run handoff also rides the draft release, uniformly.** `build-release-cohort` creates the run's draft and uploads the cohort archive; all three `oracle-emit-*` legs download it from the draft. The Linux-to-Linux same-host edge is deliberately not special-cased with runner-local disk: two of the three legs are cross-host anyway so the upload happens regardless; a digest-verified download gives every leg identical, provable input bytes where a shared disk path is unverifiable and couples jobs to runner workspace-retention behavior; and one mechanism keeps the workflow auditable. Within the run, before the manifest is sealed, the cohort's own manifest and digests are the integrity check — the cohort loader already refuses a corrupt cohort. Draft download by tag with the workflow token is proven in-repo by the claude-evidence flow; the verify helper wraps download in a short bounded retry for API transients. The per-OS smoke cohorts consumed cross-workflow by the acquisition lanes move to the same draft with the full manifest hash check.

**D5 — Archive format.** Directory payloads ship as `tar.gz` created with deterministic ordering (`tar --sort=name --mtime=@0 --owner=0 --group=0 --numeric-owner`); Windows consumers extract with the OS-bundled bsdtar. Flat JSON rows ship as-is. The archive's sha256 lives in the manifest; content integrity below the archive remains governed by the cohort's own manifest and digests, so integrity is checked at both layers.

**D6 — Lifecycle and cleanup: bounded retention, promotion-preserving, dispatch-only.** Evidence drafts are retained under a keep-window policy: every draft referenced by the most recent successful promotion is kept, plus the newest three draft sets per producing workflow (operator-ruled K equals 3). Everything older is deleted by a new `evidence-gc.yml` that is `workflow_dispatch`-only — the operator ruled out a schedule trigger — running on the self-hosted Linux runner with `dry_run` defaulting to true. The GC deletes only drafts whose tag matches the reserved pattern `^evidence-(smoke|scoop|homebrew|claude)-[0-9]+$`, refuses anything else, and never touches non-draft releases, so the real `v*` releases are structurally out of its reach. The keep-set and namespace-refusal logic lives in a tested Python subcommand, not inline shell.

**D7 — One evidence-row contract for local lanes and CI.** The `DistributionEvidence` schema, filenames, and the readiness reader are unchanged. The canonical row location remains a flat directory of JSON rows passed to the readiness gate via `--evidence-dir`; local lanes keep writing `var/distribution-install-readiness/`, and CI's Gate 2 aggregation fills the same-shaped directory from release assets instead of artifacts. The cohort contract stays a directory the cohort loader accepts. Transport is invisible below the gate; nothing in `dev/` learns about releases except the new manifest emit/verify/leak-sweep/gc helper, proposed home `dev/packaging/evidence_release.py`, with tests.

**D8 — Self-evidencing final release.** Gate 3 continues to create the single `v<version>` release from the sealed cohort. Addition: it also attaches the twelve verified evidence rows and the per-lane evidence manifests to the final release — gated by the D9 publication leak sweep — so the published release is self-auditable and draft GC can never orphan the audit trail of a shipped version. Because rows are clean at birth, the bytes attached to the final release are byte-identical to the draft assets Gate 2 verified, and the draft manifests' digests remain valid for the published copies.

**D9 — Runner-metadata scrub at birth, plus a fail-closed publication leak sweep (new, operator-ruled).** The scrub happens where the evidence is minted, not at publication. The evidence builders redact runner hostnames, operating-system usernames (including usernames embedded in absolute filesystem paths inside command transcripts), and machine identifiers (runner names and labels, machine-scoped serial or hardware identifiers) from runtime identity fields and transcript text at mint time, replacing each with a stable structural placeholder so the row remains schema-valid and diffable; the evidence identity is computed over the scrubbed content, so there is exactly one identity per row and no draft-versus-published divergence. A field-agnostic leak detector runs inside the builders and refuses the mint outright on any residual identifier (including UNC-path and cohort-embedded forms) — fail-closed, never a warning. Full-fidelity diagnostics stay in the runner-local job logs, which never leave the machine; runner identity for incident forensics remains recoverable from the run id via the Actions job records, so nothing forensic is lost by scrubbing early. Gate 3 then runs the same detector as a publication leak sweep (verify-then-refuse, no rewriting) over every asset it is about to attach to the `v<version>` release — rows, evidence manifests, and any transcript or bundle assets — hard-failing the promotion and naming the leaking asset and pattern. The sweep is a tripwire for payloads the builders did not mint and a regression ratchet if a new metadata field ever slips past them. A unit test feeds rows containing known hostname, username-path, and machine-identifier patterns through the builders and asserts none survive the mint; a conformance check asserts Gate 3 attaches nothing that has not passed the sweep.

**Per-workflow changes** (mechanical fragments recorded in the implementation notes accompanying this feature): `packaging-smoke.yml` converts its cohort and evidence uploads to draft-release uploads with the single-creator topology and gains the terminal seal job; `packaging-scoop.yml`, `packaging-homebrew.yml`, and `packaging-claude.yml` swap their source-cohort downloads to verified draft downloads (gaining integrity checks the acquisition lanes never had) and publish their evidence to their own per-run drafts; `publish-release.yml` Gate 2 derives tags from the run-id inputs and verifies manifests before the unchanged readiness invocation, and Gate 3 re-downloads with the same verification, runs the publication leak sweep, and attaches; `evidence-gc.yml` is new. Conformance tests in the `dev/packaging/tests/test_ci_workflow.py` family pin: no packaging workflow uses Actions artifacts for cohort or evidence payloads; every packaging `gh release create` carries `--draft` and an `evidence-` tag with exactly one creator job per workflow; publish-release derives evidence tags from run ids; the GC pattern excludes `v*`; and the three oracle legs' asset names are pairwise disjoint. Migration lands the helper module first, converts `packaging-smoke.yml` for the immediate quota relief, then the acquisition workflows, then the publish gates validated by a full `dry_run` dispatch, then the GC and documentation updates.

## Rationale

Release assets are the only zero-cost durable store the platform offers this account, and the pattern is not novel: GoReleaser has used draft releases as the upload-in-progress container for years, and the repo's own claude-evidence lane already proves draft upload and download by tag with the workflow token. The design's departures from the draft proposal it started from are all grounding-driven. The idempotent-create-everywhere topology was replaced by single-creator-plus-uniqueness-assertion because the duplicate-draft race is a documented GitHub behavior, not a theoretical one. The cargo-dist counter-example — the most mature tool in this space deliberately avoids draft-as-scratch — was weighed honestly: its choice presumes artifact storage this account does not have, and its real principle (the user-visible release is created transactionally at the end from verified inputs) survives intact here because drafts are never published, only read, and the one `v<version>` release is still minted in a single terminal gate behind a human approval. Run ids stay the promotion inputs because the Actions run record is the only identity GitHub will attest for free, and every verification in Gate 2 anchors there; tags are derived, not chosen, so the operator cannot be phished into promoting from an unverifiable container. The scrub decision resolves the one open privacy question the draft carried, and its final shape came out of implementation reconciliation: an initial Gate-3-rewrite design kept full-fidelity drafts, but that fidelity proved not load-bearing (runner-local logs retain it, and runner identity is recoverable from the run id via the Actions job records) while the rewrite split every row into two identities with divergent digests. Scrubbing at birth is stronger on every axis — identifiers never leave the machine, one identity per row, draft and published bytes identical — and the Gate-3 stage survives as the fail-closed publication leak sweep rather than a rewriter.

## Consequences

- The storage quota ceases to constrain the pipeline: every packaging run and the promotion window ride release-asset storage, and the standing footprint is bounded by the keep-window at a few GiB.
- Integrity strictly improves: today the acquisition lanes trust downloaded bytes with no digest check; after this change every cross-boundary byte is hash-verified against a manifest that must agree with the Actions API run record, and the readiness gate's cohort-binding checks run unchanged on top.
- No auto-publish path is created. Only Gate 3, behind the untouched `CADRUMO_PUBLISH_ENABLED` variable and the `release` environment's human approval, ever creates a non-draft release or pushes to a public channel. Draft creation and upload are not publication.
- Confusability is bounded structurally: evidence containers are drafts (never publicly listed, no tag ref, never `latest`) in a reserved `evidence-*` namespace; the GC refuses non-matching tags; conformance tests pin both.
- Token escalation is bounded: `contents: write` is granted job-level only to uploader jobs, checkouts keep `persist-credentials: false`, and the promote-never-rebuild invariant means no uploader job also executes publication logic.
- Failure honesty: a missing draft, duplicate draft, missing manifest, hash mismatch, or manifest-to-API disagreement is a hard Gate 2 failure naming the mismatching values — never a warning.
- The published release becomes self-auditable at the cost of a redaction surface that must be maintained in the evidence builders; the builders' fail-closed leak detector plus the Gate-3 publication sweep are the double ratchet against a new metadata field leaking — a residual identifier refuses the mint at birth and, failing that, refuses the promotion at publication.
- Deferred: cryptographic attestations and the two GitHub-hosted packaging legs remain on the operator checklist; neither is worsened by this change.
