# `python-runtime-compatibility` adr: `one source tree with an open Python floor and rolling CPython evidence` | (**status:** `accepted`)

## Problem Statement

Cadrumo must support one source tree across CPython 3.13 and every later released minor, including 3.15 and future releases. The current declaration, classifiers, CI execution, lock metadata, dependency resolution, and release-cohort builder do not describe one coherent support contract.

A speculative upper bound prevents installation on a later interpreter before compatibility has even been tested. Removing that bound alone would permit installation but would not prove that the code, dependencies, native wheels, or shipped artifacts work. The project therefore needs one decision that separates the open installation floor, finite blocking evidence for released interpreters, readiness evidence for the next prerelease, exact release-cohort reproducibility, annotation semantics, and dependency and binary-wheel availability.

The decision is grounded in `2026-09-02-python-runtime-compatibility-research` and must compose with the artifact and CI authorities already accepted by `2026-07-15-distribution-installation-readiness-adr`, `2026-08-05-ci-lane-deconflation-adr`, and `2026-07-27-canonical-release-pipeline-adr`.

## Considerations

- The package must stop rejecting future interpreters through a project-level ceiling, while support claims remain bounded by executed evidence (`2026-09-02-python-runtime-compatibility-research`).
- Released artifacts require installed-runtime proof, not only source-tree tests; the Python row must remain bound to the tested artifact cohort (`2026-07-15-distribution-installation-readiness-adr`).
- Existing protected CI and release-cohort lanes have stable names, timing, and single-builder contracts; compatibility coverage needs an independently verdictable surface (`2026-08-05-ci-lane-deconflation-adr`).
- The exact interpreter recorded in `.python-version` defines reproducible cohort construction and must not be confused with the supported runtime range (`2026-09-02-python-runtime-compatibility-research`).
- `from __future__ import annotations` provides one annotation representation across the supported transition and remains supported; removing it would be a semantic migration, not compatibility cleanup (`2026-09-02-python-runtime-compatibility-research`).
- Native dependency wheel gaps and resolver failures are compatibility evidence and must remain visible rather than becoming successful skips (`2026-09-02-python-runtime-compatibility-research`).

## Considered options

- **Keep a moving upper bound**, such as `<3.15`, and raise it for each new interpreter. Rejected: it actively denies later runtimes, repeats the same annual maintenance failure, and turns package metadata into a speculative gate.
- **Remove the ceiling without adding a runtime matrix.** Rejected: installation permission would be mistaken for verified support, leaving untested interpreters and dependency failures invisible.
- **Expand the existing release-cohort and protected CI lanes for every interpreter.** Rejected: it multiplies cohort construction, weakens byte-identity guarantees, changes protected lane contracts, and makes release reproducibility depend on the test matrix.
- **Remove `from __future__ import annotations` and adopt each interpreter's native annotation behavior.** Rejected: it creates semantic drift between 3.13 and later versions and risks changing forward references and runtime annotation consumers.
- **Chosen - open the package floor and add a dedicated rolling compatibility surface.** The package declares `>=3.13`; every released CPython minor from 3.13 through the current release is an explicit blocking row; the next prerelease is an advisory canary until its RC/final promotion point; source and binary installation evidence are separate; the exact release-cohort builder remains unchanged; and future annotations remain the project-wide annotation model.

## Constraints

- This decision claims CPython minor releases only. PyPy, alternative implementations, and unsupported platform or architecture combinations require their own evidence and are not implied by the open floor.
- The root package declaration is `>=3.13` with no speculative upper bound. The lock must be regenerated by the owning package tool so its Python markers agree.
- The released-runtime inventory is explicit and complete: every released CPython minor at or above 3.13 through the current stable release has a named blocking row. A completeness gate fails when a released minor is absent; a wildcard or silently generated list is insufficient evidence.
- Each blocking row exercises the real package boundary: isolated dependency resolution, source or sdist installation as applicable, built-wheel installation, import/startup and CLI smoke, relevant focused tests, and attributable deprecations promoted to errors. Artifact proof inherits the cohort and acquisition requirements of `2026-07-15-distribution-installation-readiness-adr`.
- The next CPython prerelease begins as an advisory canary. At the release-candidate or final-release promotion point, it becomes blocking only with explicit source-install and binary-wheel evidence. Those modes remain separately recorded: source-build success does not imply binary-wheel support, and missing native wheels are an explicit blocker or unsupported mode, never a passing skip.
- Stable classifiers are metadata claims, not forecasts. A classifier is added only for a final stable interpreter whose applicable blocking evidence passes. A prerelease canary receives no stable classifier.
- `.python-version` remains the sole release-cohort builder identity. Compatibility jobs select their target interpreter independently and test the already-built cohort where artifact proof is required. No per-runtime rebuild, restamping, or replacement of the canonical cohort is permitted.
- `from __future__ import annotations` remains in the established source model. Runtime consumers use supported APIs such as `typing.get_type_hints`, `typing.get_origin`, and `typing.get_args`, rather than depending on the internal representation of `__annotations__`.
- Syntax and static-analysis targets remain at Python 3.13. Version-specific behavior is isolated behind capability checks or a small compatibility boundary and covered on both sides.
- Dependency upper bounds, missing wheels, build failures, and deprecation warnings remain attributable to the affected runtime and installation mode. They may be resolved or explicitly scoped, but cannot be hidden by `continue-on-error`, unconditional skips, or broad exemptions.
- Companion distributions and classifiers agree with the root compatibility contract. A root claim is incomplete when an exact-version companion cannot resolve or execute on that runtime.

## Implementation

Change the root metadata to the open floor `>=3.13` and regenerate the lock through the repository package-management authority. Remove stale comments and checks describing the former ceiling, while preserving exact release-cohort validation around `.python-version`.

Add a dedicated compatibility workflow with an explicit matrix sourced from one canonical runtime inventory. It contains blocking rows for each released CPython minor and a separately identified `next` prerelease row. It does not rename or expand protected quick, full, or release-cohort lanes. The matrix records interpreter, stability phase, operating system, architecture, installation mode, dependency result, and test verdict.

The workflow validates that the stable inventory covers every released minor from 3.13 through the current release. Each stable row performs frozen dependency resolution and real source/package checks. Artifact jobs install the same sealed wheel, sdist, companions, extras, `aeat`, and `cadrumo-mcp` surfaces under the selected interpreter, with checkout imports and ambient executables removed from acceptance.

Source and binary installation are separate verdict dimensions. Source-built native dependencies may prove source compatibility; they do not satisfy binary-wheel availability. An unavailable upstream wheel leaves evidence naming the dependency, interpreter, platform, and installation mode and leaves that mode red or explicitly unsupported according to release policy.

The prerelease row remains advisory before RC. At RC or final, its verdict policy changes through the canonical inventory and requires explicit source-versus-binary evidence before becoming blocking. At final release it moves into the stable inventory, gains a classifier only after blocking gates pass, and the next prerelease row takes its place.

Add focused contracts for annotation behavior and runtime introspection, including forward references and dynamically constructed annotations. Keep the future import and update consumers that inspect annotations to use public APIs. Do not perform tree-wide removal based on interpreter age.

Dependency and native-wheel results are retained with compatibility evidence and surfaced in release readiness. The release pipeline continues to build one exact cohort and promote only that cohort; runtime coverage consumes it rather than rebuilding it. Documentation and metadata describe only stable rows whose required evidence is complete.

## Rationale

The chosen policy separates permission from proof. `>=3.13` lets packaging tools consider current and future interpreters, while the explicit blocking matrix makes each released claim measurable and prevents an omitted runtime from disappearing behind an apparently successful build.

A dedicated matrix preserves the accepted immutable-cohort and protected-lane decisions. The same shipped bytes can be exercised across runtimes without turning the reproducibility builder into a test matrix or coupling release timing to every compatibility job.

The prerelease promotion rule gives early warning without claiming an unreleased interpreter as stable. Requiring separate source and binary evidence makes dependency reality visible: source-build success establishes one capability but cannot silently stand in for a missing native wheel.

Retaining future annotations keeps one annotation contract across 3.13, 3.14, 3.15, and later versions. Any eventual migration is an explicit future decision with runtime-introspection evidence rather than an incidental cleanup.

This is the smallest policy that supports one evolving codebase while keeping installation, artifact, dependency, and release claims honest (`2026-09-02-python-runtime-compatibility-research`; `2026-07-15-distribution-installation-readiness-adr`; `2026-08-05-ci-lane-deconflation-adr`; `2026-07-27-canonical-release-pipeline-adr`).

## Consequences

- Later Python releases are no longer rejected by a project-level ceiling; adding a stable row becomes an inventory update rather than a metadata workaround.
- Every released interpreter has an independently visible blocking verdict, making support regressions and omitted rows release-relevant.
- The next interpreter is tested before final release and becomes part of the blocking contract at the defined promotion point.
- Source and binary support can temporarily differ, but the difference is explicit. A dependency without a native wheel may delay binary support or release promotion instead of being silently skipped.
- CI consumes more runner time and may require source builds, platform-specific workers, or dependency-owner intervention.
- Stable classifiers may lag the open installation floor until final-release evidence is complete.
- The release-cohort builder remains reproducible, while compatibility jobs provision interpreters independently of `.python-version`.
- Future annotations remain a deliberate compatibility contract. A later Python semantic change may require a focused migration and ADR amendment.
- Alternative Python implementations and unexecuted platform rows remain outside the claim.
- When CPython publishes a final release, the current `next` row must be promoted, its evidence reviewed, and a new prerelease canary enrolled.
