# `agent-harness` adr: `AEAT CLI agent-harness framework` | (**status:** `superseded`)

## Problem Statement

The `aeat` CLI is a deterministic, machine-facing toolkit for Spanish tax
calculation, ledger management, and filing-handoff. Its target operator is an
LLM agent — an autonomous "agentic tax advisor" — not a human at a terminal. The
backbone is ~75% agent-ready (a versioned JSON envelope, a stable exit-code
table, a typed `Notice` channel, instructive self-correcting failures, permanent
live-submit prohibition), but the operating layer that would let an LLM agent
drive it reliably and safely does not exist. There is no operator-facing
capability manifest, no agent operating rules, no tax-advisor personas, no
executable workflow playbooks, and no agent-tool exposure.

The agent-harness research grounds this gap and recommends building the operating
layer in the project's existing artifact shapes plus a tool-exposure layer. This
ADR records the architecture and resolves the six open questions the research
left for decision: (Q1) tool-exposure mechanism and sequencing, (Q2) where the
harness artifacts live and how they distribute, (Q3) the human-in-the-loop
policy tiers, (Q4) faithfulness enforcement, (Q5) the eval substrate, and (Q6)
naming discipline. It is a new-feature ADR derived from the research; it
introduces no code, only the decided shape and its rationale.

The reframing this ADR preserves at every layer: the CLI is the **backbone** —
deterministic, it computes the tax; the harness is the **operating layer** — the
agent orchestrates, extracts, classifies, narrates, and hands off, but never
computes a tax value itself. External research confirms every surveyed production
financial-AI system converged on exactly this LLM-over-deterministic-engine
split, with never-auto-submit and provenance-on-every-output as hard standards.

## Considerations

**The backbone is the asset; the harness must consume it, not duplicate it.** The
two-root command tree (`aeat config`, `aeat app`), the `SchemaEnvelope` shared
spine (`schema_version`/`command`/`status`/`result`/`notices`), the
`SCHEMA_REGISTRY` command identifiers, the `ExitCode` table, and the typed
`Notice` channel are confirmed present at HEAD and are the agent's reading
surface. The harness adds knowledge and orchestration on top; it does not
recompute or restate what the deterministic layer owns.

**A capability manifest already exists but is not exposed.** The backend-owned
`OperatorSurfaceContract` (built by `build_operator_surface_contract()`)
enumerates the two roots and their required children, every mounted command
family with its domain, commands, one-line operator intent, service owner, and an
`OperatorMutability` annotation (`READ_ONLY` / `LOCAL_STATE_MUTATING`), the
`CALCULATE → VERIFY → FILE` modelo lifecycle, and source-kind aliases. It is
consumed only by the operator-surface conformance test; no CLI command emits
it. This is the single highest-leverage, lowest-cost enabling piece — it is the
agent's tool catalogue, and it is the natural input to a tool-list endpoint.

**Three hard architectural constraints bind the design.** First, the CLI root
surface is pinned by rule to exactly `config` and `app`; no third root command
family may be added, so any new operator-facing CLI affordance mounts under
`app`, and the tool-exposure server must be a sibling entry point, not a CLI
root. Second, the repository's `.claude/` directory is the vaultspec
**developer** harness's provider surface, regenerated by `vaultspec-core sync`
(its agents and most skills are the `vaultspec-*` set); the operator harness must
not collide with it, and must not be authored as hand-edited files inside a
sync-regenerated provider directory. Third, the accepted product-packaging model ships a
self-contained wheel: reviewed product data lives under `src/aeat/_data` and
resolves through `importlib.resources`, optional integrations are capability-
gated extras that lazily import and degrade with an install hint, and
credentials/model-weights/runtime caches never ship.

**The persona testimonial harness is the negative inverse, not a template.** The
existing `cli-persona-testimonials` lineage withholds knowledge to expose UX
friction; the operator harness must supply exactly the knowledge the persona is
forbidden. Its scenario-based golden methodology (the round-30 M200 silent-
under-declaration discovery) is reusable; its withholding brief is not.

**The field's settled patterns map onto the project's shapes.** Per-session
behavioural rules (CLAUDE.md/AGENTS.md), lazy-loaded per-workflow `SKILL.md`
(progressive disclosure), and deterministic-layer-enforced rules (our conformance
gates) are the three decomposition tiers. MCP is the de-facto CLI-to-agent
exposure, giving `inputSchema`/`outputSchema`, structured `isError` execution
errors, `tools/list` discovery, and `ToolAnnotations` (`readOnly`/`destructive`/
`idempotent`) that clients use to gate human confirmation. The Claude Agent SDK
supplies subagents with isolated context and scoped tools plus
`PreToolUse`/`PostToolUse`/`Stop` hooks for validation and audit.

## Considered options

**Q1 — Tool-exposure mechanism and sequencing.**
- *Raw `aeat --format json` only* (rules + skills over the bare CLI): fastest first
  cut, no new runtime dependency, but no schema-validated arguments, no
  annotation-driven confirmation, no `tools/list` discovery — the agent scrapes.
- *MCP server only:* the validated end-state (typed args, capability discovery,
  annotation-driven HITL), but a larger first increment that front-loads runtime
  surface before the operating rules are proven.
- **Chosen — both, sequenced behind a common manifest.** Land Layer 0 (expose the
  contract manifest) first; build and prove the rules + one-workflow skill slice
  over raw `--format json` against a golden eval; then invest in the MCP server
  as the end-state, reusing the same manifest as its `tools/list` source. Cheap,
  falsifiable first increment; committed validated end-state.

**Q2 — Artifact home and distribution.**
- *In the dev `.claude/`:* rejected — collides with the vaultspec-owned, sync-
  regenerated developer harness and targets the wrong audience.
- *A separate installable repository/bundle:* rejected for v1 — splits the harness
  from the CLI surface it couples to, re-opening the verb-drift orphaning the
  `aeat-cli-pull-and-file-standard` rule exists to prevent.
- **Chosen — reviewed package data under `src/aeat/_data/agent/` plus an
  `entrypoints/mcp/` server, distributed behind an `aeat[agent]` extra.** Authored
  operator rules, personas, and skills are reviewed markdown product data shipped
  in the wheel (read via `importlib.resources`), exactly analogous to corpus/
  registry/terminology data. The MCP server is a new entrypoint with a sibling
  `aeat-mcp` console script (not a third CLI root). An `app`-mounted command
  materialises an operator workspace for an end user from the shipped data,
  keeping it distinct from the dev `.claude/`.

**Q3 — HITL policy tiers and gate location.**
- *CLI only* (`--yes`/`--confirm`, write-policy guard, `LiveSubmitForbiddenError`):
  deterministic but coarse, and invisible to the agent before it calls.
- *MCP only* (`ToolAnnotations` + `PreToolUse`): operator-facing and granular, but
  bypassable if the harness misbehaves.
- **Chosen — both, defense in depth.** The contract's `OperatorMutability` projects
  to MCP `ToolAnnotations` that drive a `PreToolUse` confirmation policy (auto-
  approve read-only and `--dry-run`; confirm irreversible/destructive and the
  filing-handoff marker; never expose a live-write tool at all). The existing CLI
  guards remain the deterministic backstop that holds even when the harness is
  wrong.

**Q4 — Faithfulness enforcement.**
- *Advisory-only flag:* low friction, but a fabricated figure can still reach a
  filing-grade narration.
- *Hard block on every suspected hallucinated numeric:* maximally safe but brittle
  — false-positives on legitimately reformatted figures stall routine narration.
- **Chosen — advisory by default, hard block at the irreversible boundary.** A
  `PostToolUse` faithfulness check flags any numeric casilla value in agent
  narration absent from the preceding tool-result JSON, as a `warning`; in the
  export / record-marker handoff path it escalates to a hard block. This mirrors
  `no-silent-under-declaration` (advisory where legitimate cases exist, blocking
  where the consequence is irreversible).

**Q5 — Eval substrate.**
- *Reuse the persona-testimonial machinery wholesale:* rejected — its withholding
  brief is the inverse of the operator harness.
- **Chosen — a separate operator golden-task replay gate that reuses the
  methodology, not the brief.** Golden scenarios assert the trajectory (expected
  tool sequence, argument validity), the expected casilla values sourced from the
  same AEAT-authoritative oracles the calculation tests already use, and
  provenance presence. A determinism-replay mode captures golden tool
  call/response pairs and asserts identical replay. Bound by
  `no-tautological-calculation-tests` and `no-silent-under-declaration`.

**Q6 — Naming discipline.**
- **Chosen — `aeat-spanish-stem-naming` governs.** AEAT domain nouns keep their
  Spanish stem in artifact names, tool names, and prose (`casilla`, `modelo`,
  `declaracion`, `justificante`, `censo`, `borrador`, `retencion`); generic
  computing vocabulary stays English (`coordinator`, `verifier`, `classifier`,
  `server`, `harness`). MCP tools are namespaced and unambiguous (`aeat_calculate`,
  `aeat_verify`, full `filing_year` not `year`), per Anthropic tool-design
  guidance.

## Constraints

This ADR layers on four accepted decisions and treats them as stable parent
constraints. **Product packaging** (`2026-06-28-product-packaging-adr`, proposed)
fixes the wheel-and-extras model the `aeat[agent]` extra must follow; it is
proposed-status, so the harness extra rides its acceptance and must not bundle
weights or credentials. **The operator surface** (`2026-06-03-cli-workflow-redesign-adr`
lineage, with the accepted `2026-06-10-cli-operator-surface-adr` as its most
recent parent) owns `OperatorSurfaceContract` and its mutability annotations —
Layer 0 exposes that contract, it does not redefine it, and aligns with that
accepted decision rather than diverging from it. **The CLI envelope/notice standard**
(`cli-notices-are-the-only-diagnostic-channel`) is the only diagnostic channel
the agent reads. **The safety/legal gates** (`aeat-safety-legal-gates`,
`LiveSubmitForbiddenError`) make live submission permanently forbidden — the MCP
layer must never expose a live-write tool, and this is a permanent rail, not a
configurable policy.

Blocking precondition: Layer 0 (the manifest command) must land before the MCP
server, because the server consumes the manifest as its `tools/list` source and
its annotation table. The MCP runtime dependency is a frontier surface — its
exact pinned package is deferred to the implementation plan and gated behind the
`aeat[agent]` extra so a bare `pip install aeat` stays MCP-free. The Agent-SDK
hook contracts (`PreToolUse`/`PostToolUse`) are an external evolving surface;
the harness depends on their stable shape and degrades to the CLI backstop if a
hook is absent.

The shared dirty worktree forbids destructive git/workspace operations; all
harness work is additive and path-scoped, co-committing every rule/skill that
names a CLI verb or JSON field with the surface it couples to.

## Implementation

A layered harness authored in the project's existing artifact shapes plus a
tool-exposure layer. The layers are built in dependency order; each is
independently valuable.

**Layer 0 — Capability manifest (enabling).** A read-only `app`-mounted command
emits the `OperatorSurfaceContract` plus the `SCHEMA_REGISTRY` payload schemas as
a single machine-readable `SchemaEnvelope` (`--format json`): the two roots, every
command family with its operator intent, mutability, and service owner, the
`CALCULATE → VERIFY → FILE` lifecycle, source-kind aliases, and per-command
result-schema references. This is the agent's tool catalogue and the MCP
`tools/list` source. It mounts under `app` (never a third root) and is itself a
registered schema under the conformance gate.

**Layer 1 — Operator rules.** The agent's behavioural contract, authored as
reviewed markdown product data: never compute or invent a tax value; relay CLI
JSON verbatim with `legal_refs`/`source_refs` intact; never assert a local export
is official AEAT evidence; never submit live; act on `warning` notices rather than
proceed; treat `verified_complete` with zero findings on positive income as
suspect; resolve revision by law, not injection; read `status` not stdout/stderr;
treat exit `1` as an actionable verdict, not an abort. These are the operator
analogues of the existing engineer-facing safety rules, re-cast for the agent
that uses the tool.

**Layer 2 — Tax-advisor personas.** A coordinator plus task-scoped roles
(onboarding/profile, bookkeeper ledger-groomer, classifier, modelo-preparer,
verifier, filing-handoff reconciler), each given the manifest and the operator
rules, with tool access scoped to its mutability tier. The verifier persona runs
in isolated context from the preparer to avoid the rationalisation problem.

**Layer 3 — Workflow skills.** The canonical end-to-end flows as executable
playbooks (preconditions, command sequence, JSON success assertions, progressive-
disclosure per-modelo reference), beginning with a single vertical slice (one
modelo, e.g. 130 or 303) proven over raw `--format json`.

**MCP server.** A new `entrypoints/mcp/` server with the `aeat-mcp` console
script wraps CLI leaves as typed tools, sourcing schemas and mutability
annotations from the Layer 0 manifest. `PreToolUse` hooks enforce the HITL tiers
(auto-approve read-only/dry-run, confirm irreversible and the filing marker,
block any live-write); a `PostToolUse` hook enforces faithfulness (advisory flag,
hard block at handoff). Distributed behind the `aeat[agent]` extra.

**Eval gate.** A golden-task replay harness with AEAT-worked-example oracles
asserting tool trajectory, expected casilla values, and provenance presence,
run on every harness change — the operator-side counterpart of the persona
testimonial gate.

## Rationale

The layering follows the research recommendation and the settled external
patterns directly: Layer 0 first because it is the smallest change, unblocks both
the MCP server and the skills, and is independently valuable; then rules and a
single proven workflow slice over the bare CLI to keep the first increment cheap
and falsifiable; then the MCP server and full matrix as the validated end-state.
Building both the raw-CLI slice and the MCP server (Q1) lets the operating
contract be proven before the runtime surface is committed. Shipping the artifacts
as reviewed `_data` behind an `aeat[agent]` extra (Q2) keeps them inside the
accepted self-contained-wheel model, co-located with the CLI surface they couple
to, and clear of the vaultspec-owned dev `.claude/`. Defense-in-depth HITL (Q3)
and the advisory-then-blocking faithfulness posture (Q4) put the granular gate
where the agent can see it while keeping the deterministic CLI rail as the
backstop, matching the `no-silent-under-declaration` discipline of warning where
legitimate cases exist and blocking at the irreversible boundary. A separate
golden-replay gate (Q5) reuses the proven scenario methodology without inheriting
the persona harness's inverted withholding brief. Spanish-stem naming (Q6) keeps
the operator vocabulary aligned with the AEAT surfaces it integrates with. Every
decision is the project-specific application of a pattern the external landscape
has already settled, grounded in the four findings of the research.

## Consequences

The harness turns a ~75%-agent-ready backbone into a drivable system: an LLM tax
advisor gets its capability map, operating contract, executable workflows, and a
typed tool surface with built-in human-in-the-loop gating and faithfulness
checks. Layer 0 is immediately useful to any agent (and to documentation) even
before the rest lands.

Honest difficulties. The MCP runtime and Agent-SDK hook contracts are evolving
frontier surfaces; pinning them and tracking their drift is ongoing cost, and the
hooks must degrade gracefully to the CLI backstop. Co-commit discipline is now a
standing obligation: every harness rule or skill that names a CLI verb or JSON
field must move with that surface or it silently orphans — the same failure mode
that produced the pull/file-standard rule. The faithfulness hook will produce
false positives on legitimately reformatted figures; tuning the advisory
threshold without weakening the handoff block is delicate. Golden oracles must
come from AEAT-authoritative worked examples, never hand-computed from the
registry formula under test, or the eval becomes tautological. The `aeat[agent]`
extra depends on the proposed packaging ADR being accepted; until then the
distribution story is provisional.

Pathways opened. Once the manifest and MCP server exist, the same surface feeds
documentation generation, a future Agent-SDK bundle, and additional operator
personas without re-deriving the catalogue. The golden-replay gate becomes the
operator-side assurance counterpart to the persona testimonial gate, catching
both harness regressions and the non-determinism that is itself an assurance
failure in regulated tax work.
