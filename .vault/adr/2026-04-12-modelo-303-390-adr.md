# modelo-303-390 adr (#62)

Date: 2026-04-12
Branch: `feature/62-modelo-303-390`
Issue: wgergely/aeat#62

## Status

Accepted (self-review, 2026-04-12). Executed end-to-end per the
vaultspec-system mandate; code review documented in the matching
exec summary.

## Context

`FilingBuilder` (ABC), `FilingDraft`, `FilingValue`,
`FilingValidationFinding`, `FilingValueKind`, `FilingDraftStatus`,
`FilingValidator`, and `build_draft` dispatch are all on `main` via
#39. `Modelo130Builder` is the reference implementation. #25 has
landed the Manual práctico IVA ingest scaffolding (manifest on
disk, PDF fetched on demand). This ADR decides how the two new
builders plug in.

## Decision

### 1. Module layout

Two new private modules colocated with `modelo_130.py`:

- `src/aeat/application/filing/_builders/modelo_303.py` — `Modelo303Builder`
- `src/aeat/application/filing/_builders/modelo_390.py` — `Modelo390Builder`

Two new synthetic casilla schemas, re-using
`StaticCasillaSchema` / `StaticCasillaCollection` from
`_modelo_130_schema.py`:

- `src/aeat/application/filing/_builders/_modelo_303_schema.py`
- `src/aeat/application/filing/_builders/_modelo_390_schema.py`

Registration: both classes are added to the `_BUILDER_REGISTRY`
dict inside `src/aeat/application/filing/_builders/__init__.py`, exactly the
same pattern as `Modelo130Builder`. `Modelo303Builder` and
`Modelo390Builder` are re-exported at that package's `__all__` for
the existing `aeat.application.filing.__init__` import chain.

`aeat.application.filing` public API adds `Modelo303Builder` and
`Modelo390Builder` to `__all__` for symmetry with
`Modelo130Builder`. **No other public API change.** Callers
continue to use `build_draft(modelo="303", ...)`.

### 2. Casilla coverage (v1)

Per research doc, committed truth table:

**Modelo 303** — casillas `01`–`09` (IVA devengado general
regime), `28`–`45` (IVA deducible + resultado régimen general),
`64`–`71` (resultado de la liquidación). Everything else is
deferred.

Formula casillas (computed, provenance = `COMPUTED`):

- `03 = 01 × 0.04`
- `06 = 04 × 0.10`
- `09 = 07 × 0.21`
- `44 = 29 + 31 + 33 + 35 + 37 + 39 + 40 + 41 + 42 + 43`
- `45 = (03 + 06 + 09) − 44`
- `64 = 45`
- `66 = 64 × 65 / 100`
- `69 = 66 − 67`
- `71 = 69`

Literal casillas: `01`, `04`, `07`, `28`–`43`, `65` (default 100),
`67` (default 0). Constant-rate casillas `02`, `05`, `08` carry
the AEAT tipo as a `DEFAULT` (4 / 10 / 21), not as a user input.

**Modelo 390** — ejercicio (`01`), annual IVA devengado totals
(`100`, `101`, `104`, `105`, `108`, `109`), annual IVA deducible
totals (`190`, `191`, `192`, `193`), annual resultado
(`84`, `85`, `86`, `95`).

Formula casillas:

- `100 = Σ quarterly 01`
- `101 = Σ quarterly 03`
- `104 = Σ quarterly 04`
- `105 = Σ quarterly 06`
- `108 = Σ quarterly 07`
- `109 = Σ quarterly 09`
- `190 = Σ quarterly 28`
- `191 = Σ quarterly 29`
- `192 = Σ quarterly 30`
- `193 = Σ quarterly 31`
- `84 = 101 + 105 + 109`
- `85 = 191 + 193`
- `86 = 84 − 85`
- `95 = 86`

The quarterly-sum casillas carry a formula trace over synthetic
pseudo-ids of the form `Q1:01`, `Q2:01`, `Q3:01`, `Q4:01` — but
since the real `formula_inputs` live at the 303 casilla level and
the validator walks the collection's own `formula_inputs`, the
static 390 schema declares empty `formula_inputs` for
quarterly-sum casillas and records the trace in
`FilingValue.formula_trace` for provenance only. This keeps the
existing formula-divergence validator rule from firing on them.

The four intra-390 aggregates (`84`, `85`, `86`, `95`) are proper
same-draft formulas and DO declare `formula_inputs` on the
schema.

### 3. 390 → 303 reconciliation

The 390 builder consumes the four quarterly 303 drafts via a
reserved key on the `inputs` mapping:

```
inputs["_quarterly_303"] = (q1, q2, q3, q4)
```

Contract (build-time, hard failure via `FilingComputationError`):

- Exactly four drafts, all `modelo == "303"`.
- All four `period` strings start with the same 4-digit year that
  equals `inputs["01"]` (the ejercicio).
- The four drafts' periods form the set `{"Q1","Q2","Q3","Q4"}`
  when their `period` suffixes are parsed.

Contract (validation-time, soft findings via
`FilingValidationFinding`, severity ERROR, code
`filing-390-303-mismatch`): for each of the 10 quarterly-sum
casillas, the stored annual value must equal the recomputed sum
from the four 303 drafts; any divergence emits one finding.

Because the 390 validator needs the four 303 drafts to recompute
the sums, the validator resolves them from a registry keyed by
`draft_id`. In v1 the registry is a tiny
`Mapping[str, FilingDraft]` threaded through the validator via a
new optional constructor kwarg `draft_resolver`. This kwarg is
additive on `FilingValidator` — no signature changes for the 130
path. For unit tests the resolver is a plain strict pydantic
model that conforms to a new Protocol.

Rationale for the reserved-key approach: `FilingBuilder.build`
signature is fixed on `main`. Reading the 303 drafts out of the
inputs mapping keeps the ABC intact and does not fork the
registry dispatch. The `_` prefix marks the key as internal and
the builder docstring documents it explicitly. A cleaner typed
facade is a follow-up once the workflow engine #59 is merged.

### 4. Validator extension

`FilingValidator.__init__` gains one additive optional kwarg:

```
quarterly_303_drafts: tuple[FilingDraft, ...] | None = None
```

A new private rule `_validate_quarterly_reconciliation` runs only
when `draft.modelo == "390"` and that tuple is populated. For
each of the 10 quarterly-sum casillas, the rule recomputes
`Σ quarterly casilla_x` from the passed-in 303 drafts and emits a
`filing-390-303-mismatch` ERROR finding when the stored annual
value diverges by more than a `Decimal("0.005")` tolerance. The
130 validation path is unchanged (the tuple defaults to `None`).

The rule additionally runs a *self-consistency* cross-check on
each 303 draft: it recomputes `03 = 01 × 0.04`, `06 = 04 × 0.10`,
`09 = 07 × 0.21` and surfaces a `filing-303-internal-mismatch`
ERROR finding when the stored 303 value diverges. This covers
the "a 303 draft with mismatched totals against the 390 inputs →
ERROR" case from the issue, which can only arise if a caller
round-trips a 303 draft through `model_copy` to poison a value.

`build_draft` is extended to detect `modelo == "390"` and thread
`inputs["_quarterly_303"]` into the validator's constructor. The
130 call path is untouched.

Alternatives considered:

- **Rerun the 390 builder inside the validator.** Rejected —
  creates a circular dependency and duplicates formula logic.
- **Store the quarterly drafts inline on the 390 draft.** Rejected
  — would bloat the `draft_id` hash and make round-trip tests
  unstable.
- **`draft_resolver` Protocol.** Rejected as over-engineered —
  the four drafts are always available at `build_draft` call
  time, so threading them into the validator constructor is
  strictly simpler than a registry.
- **Skip reconciliation at validation time.** Rejected — the
  issue explicitly requires mismatch findings.

### 5. Pydantic v2 discipline

Every new record is a strict, frozen, `extra="forbid"` pydantic
v2 BaseModel. The new Protocol `FilingDraftResolver` is
runtime-checkable, same pattern as the existing `CasillaCollection`
/ `DeadlineChecker` Protocols. No dataclasses, no bare dicts.

### 6. Errors and logging

- Every failure path raises `FilingComputationError` (existing)
  which inherits from `AeatError` via `FilingDraftError`.
- Every module uses `aeat.core.logging.get_logger(__name__)`.
- User-facing strings on findings are `Translatable` with
  `es` / `en` / `hu` keys populated.

### 7. Testing

Pytest only, `@pytest.mark.unit`, colocated in
`src/aeat/application/filing/test_filing.py` (extended). Coverage:

- Modelo 303 happy path: hand-calculated 21%-only and 10%-only
  inputs; every formula casilla checked.
- Modelo 303 validation: missing required casilla, out-of-range,
  formula divergence (user-supplied literal on a computed
  casilla).
- Modelo 390 happy path: four synthetic 303 drafts built via
  the real 303 builder, fed into the 390 builder.
- Modelo 390 cross-validation: mutate one 303 draft's stored
  value by round-tripping through pydantic `model_copy` and
  confirm the 390 validator emits a
  `filing-390-303-mismatch` finding.
- 303 and 390 JSON round-trip via
  `FilingDraft.model_dump_json` / `model_validate_json`.
- 303 and 390 stable `draft_id` — equality of hash across two
  builds.

Zero mocks, patches, fakes, or stubs. Every test double is a
hand-written frozen pydantic model conforming to the relevant
Protocol.

### 8. Manual práctico citations

The casilla IDs, descriptions and formulas above are cited from
the *Manual práctico IVA 2025* (AEAT). The manual's PDF is
fetched on demand via the #25 manifest at
`corpus/manuals/iva/2025/manifest.json` (sha256
`e4f800972e06466ac39f893ed6a4118bf9594b0bad52301bc763eacb92db18a3`,
fetched 2026-04-12). The casilla numbering is also authoritative
in the BOE-published modelo orders (HAC/819/2024 for 303,
HAC/1/2024 for 390).

## Consequences

**Positive**

- Autónomos in the general regime can now produce quarterly 303 +
  annual 390 drafts alongside the existing 130, covering ~80% of
  annual filings.
- Zero public API churn: existing #39 consumers are not touched.
- Protocol-based draft resolution keeps the validator decoupled
  from persistent storage (#11).

**Negative / deferred**

- The reserved `_quarterly_303` inputs key is a short-term
  ergonomic blemish; a typed facade lands with #59.
- The hand-curated casilla schemas duplicate the Manual práctico
  table. Migration to #23 is a search/replace once the casilla DB
  subpackage ships.
- v1 ships no intracomunitarias / recargo / simplificado
  coverage.

## Non-goals

- Every IVA regime other than general.
- Casillas not listed in section 2.
- Live AEAT submission tests (the submission engine #42 already
  handles dispatch by modelo and is not re-tested here).
- Any modification to in-flight sibling branches
  (#14/#15/#20/#23/#59/#60/#61).
