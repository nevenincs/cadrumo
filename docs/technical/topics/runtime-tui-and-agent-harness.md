## Architecture and product capability

Cadrumo places a native installed runtime between CLI/TUI/MCP frontends and profile-owned operations. Its bootstrap starts an isolated interpreter with filtered Python/loader environment, checks the installed package cohort and storage endpoint, builds the production operation registry, then serves profile workers. A profile host pins one authority generation and binding; connections distinguish native peer, frontend, profile, session and login evidence. Operation submission, start, commit, observation, review response and result disclosure each recheck registered policy and current authority. Worker task-local guards do not grant child tasks authority by inheritance. Large payloads travel through bounded secret frames and worker-local staging, whose finished JSON becomes a canonical request only after validation. Runtime bootstrap (`src/cadrumo/entrypoints/runtime/bootstrap.py`), profile connections (`src/cadrumo/entrypoints/runtime/profile_connections.py`), authority guards (`src/cadrumo/entrypoints/runtime/operation_authority.py`), staging (`src/cadrumo/entrypoints/runtime/worker_submission_staging.py`), [analyses](../articles/174-installed-runtime-profile-host-and-worker-authority.md), [analysis](../articles/175-profile-worker-request-staging.md).

This is an enforced access boundary in the source, not merely command metadata. Password/receipt login is limited to CLI/TUI; API keys depend on a verified grant. A persisted human receipt requires password login. Session refresh, lock generation, profile replacement and disconnect retire stale access. Review response capability stays with the original local process, while one-shot secret submission requires the admitted submitter and expires. Enrollment binds a live connection, OS owner, login, profile, lock generation and deadline; automation approval requires a fresh human commit lease. Shutdown stops admission, drains workers and retains cleanup ownership until containment is settled, with a watchdog terminating an uncontained runtime. Platform-level process and IPC behavior remains untested by this static pass. Login/session (`src/cadrumo/entrypoints/runtime/profile_connections.py`), host submission (`src/cadrumo/entrypoints/runtime/operation_host.py`), enrollment (`src/cadrumo/entrypoints/runtime/enrollment_connections.py`), automation (`src/cadrumo/entrypoints/runtime/automation_execution.py`), shutdown (`src/cadrumo/entrypoints/runtime/shutdown.py`), [analysis](../articles/174-installed-runtime-profile-host-and-worker-authority.md).

The Textual TUI consumes the runtime's authenticated projections rather than holding a separate tax database. Installed-session orchestration offers first-profile registration, human login into the full workbench, and a restricted shell for API-grant sessions. Its root displays Home, searchable commands and admitted routes. AEAT Sync displays census, filing history, notifications, evidence comparison, reconciliation and overview, with concrete effect doors for selected capture/review tasks. The Declarations portfolio and calendar preserve semantic model/year/period identity through filtering and refresh, display local filing separately from observed AEAT status, and require a canonical action plus decline-by-default confirmation for recovery. Installed session (`src/cadrumo/entrypoints/tui/installed_session.py`), root navigation (`src/cadrumo/entrypoints/tui/app.py`), AEAT handoff (`src/cadrumo/entrypoints/tui/aeat_sync/runtime_handoff.py`), calendar recovery (`src/cadrumo/entrypoints/tui/declarations/calendar.py`), [analyses](../articles/176-textual-terminal-workbench-and-declarations-calendar.md), [analysis](../articles/177-home-declarations-portfolio-and-ledger-tui-flows.md).

Ledger TUI workflows provide entry browsing, classification, statement/invoice-book import preview and apply, invoice entry, evidence extraction and confirmation, activity-asset forecasts/claims, and local transaction-to-invoice reconciliation. The application writer owns financial validation and arithmetic. Import preview locks the form and applies the same typed path request, but the UI does not retain a byte digest; the worker must establish whether a changed file is detected between preview and apply. Evidence confirmation does retain the source and draft-review digests, is one-shot for the same session and document, and expects the operation to re-read before persisting an invoice. Two row-selection query routes are visibly pending: Ledger review and evidence-review selections currently produce “destination pending”; the related mutation doors remain present. Import flow (`src/cadrumo/entrypoints/tui/ledger/import_flow.py`), evidence confirmation (`src/cadrumo/entrypoints/tui/ledger/runtime_evidence.py`), pending routes (`src/cadrumo/entrypoints/tui/ledger/controller.py`), [analyses](../articles/177-home-declarations-portfolio-and-ledger-tui-flows.md), [analysis](../articles/178-ledger-operations-and-modelo-lifecycle-tui-doors.md).

The Modelo workbench renders a declaration as casillas, official grids, repeating records, result/deadline headers, issue lists, provenance/source maps and help cards. Search and attention views preserve field identity; unavailable or inapplicable pages are distinguished from unanswered ones. Edits are in-memory typed `SET`, `CLEAR` and `RESTORE` intents. The editor parses each lexeme through the application parser, preflight rebases against the admitted form, and a review explains source displacement and changed baselines before apply. Assumed values need explicit confirmation. The next-step UI sequences calculate, verify, export and local filing; its export statement always warns that an artifact is not official AEAT filing evidence. These presentation gates depend on the registered operations for final authorization and tax correctness. Workbench form (`src/cadrumo/entrypoints/tui/modelo/workbench/casilla_list.py`), edit session (`src/cadrumo/entrypoints/tui/modelo/workbench/session.py`), review gate (`src/cadrumo/entrypoints/tui/modelo/workbench/review.py`), lifecycle (`src/cadrumo/entrypoints/tui/modelo/lifecycle.py`), export warning (`src/cadrumo/entrypoints/tui/modelo/export_result.py`), [analyses](../articles/178-ledger-operations-and-modelo-lifecycle-tui-doors.md), [analysis](../articles/179-modelo-workbench-casilla-editing-and-lifecycle-screens.md), [analysis](../articles/180-modelo-workbench-issue-review-progress-and-navigation.md), [analysis](../articles/181-modelo-workbench-editing-source-map-and-operation-flow.md).

The generic operation modal displays only public paged events and registered review projections. It polls a submitted operation, preserves monotonically sequenced events up to a cap, binds apply/reject to exact interaction/revision/actor coordinates, and treats cancel/detach as requests rather than rollback. It supports safe `REVIEW` interactions; public `INPUT` and `CHOICE` interactions are explicitly unsupported in this TUI. Profile management likewise uses runtime projections, serialized revision/digest-bound writes, masked fields, and explicit setup completion. The runtime workbench composes a generation and profile overview under one session, but those two reads do not claim an atomic shared storage revision. Modal (`src/cadrumo/entrypoints/tui/operations/modal.py`), runtime controller (`src/cadrumo/entrypoints/tui/operations/runtime_controller.py`), profile writes (`src/cadrumo/entrypoints/tui/profile/overview_writes.py`), workbench capture (`src/cadrumo/entrypoints/tui/runtime_workbench.py`), [analyses](../articles/182-supervised-operation-modal-and-profile-manager.md), [analysis](../articles/183-runtime-tui-access-workbench-and-secret-entry-flows.md).

First-run registration and login deliberately handle credentials in distinct journeys. Registration offers optional recovery after profile creation, displays a one-time code and installs it only after re-entry. Login verifies profile/frontend/session before transferring the client to a screen owner. An uncertain recovery dispatch fences another attempt rather than inviting replay. Credential widgets are masked and mutable buffers wiped, but decoded Python strings and Textual widget disposal are outside a physical-erasure guarantee. The recovery offer's failure status may disappear when registration immediately dismisses; that is a UX question needing host-flow verification. Registration recovery (`src/cadrumo/entrypoints/tui/secret/registration.py`), login handoff (`src/cadrumo/entrypoints/tui/secret/runtime_login.py`), [analysis](../articles/184-profile-registration-recovery-and-runtime-login.md).

## Harness knowledge and limits

The bundled agent harness contains personas, operator rules and model/workflow skills. They instruct an LLM operator to discover current tools, use structured receipts, retain legal/source references, separate bookkeeper/classifier/preparer/verifier roles, avoid remembered arithmetic, obtain human filing, then reconcile official evidence. Casilla companion pages say they are orientation and point to the exact year/period registry as authority. These are instructions packaged as product data, not executable tax controls. A documented Modelo 202 casilla-33 manual check is a prompt-level mitigation, not a validator. The empty `py.typed` marker signals inline typing to tooling but proves neither type soundness nor runtime behavior. Harness rules (`src/cadrumo_harness/_data/agent/rules/cadrumo-operator-operating-rules.md`), verifier persona (`src/cadrumo_harness/_data/agent/personas/cadrumo-verifier.md`), M202 guidance (`src/cadrumo_harness/_data/agent/skills/cadrumo-preparar-modelo-202/reference/casillas.md`), typing marker (`src/cadrumo/py.typed`), [analyses](../articles/185-python-typing-package-marker.md), [analysis](../articles/186-agent-personas-operator-rules-and-workflow-skills.md).

The executable harness parses skill frontmatter, validates typed applicability hints against profile-model facts, materializes workspace/plugin assets, and exposes a 15-tool MCP catalogue. MCP request schemas reject extra or mistyped fields; authority queries pin one bundled registry generation. Its connection-owned runtime adapter admits only the exact profile/frontend/session and live grant, serializes calls, and returns unresolved request IDs after uncertain submission. It neither adds filing authority nor makes prompt guidance enforceable. The skill copier handles only direct files and one child level, which matches reviewed assets but could omit future deeper resources. The materializer's caller-selected destination is a filesystem trust boundary. Metadata (`src/cadrumo_harness/_skill_metadata.py`), MCP contracts (`src/cadrumo_harness/mcp/protocol_contract.py`), runtime admission (`src/cadrumo_harness/mcp/runtime_admission.py`), admitted operations (`src/cadrumo_harness/mcp/admitted_operations.py`), skill copier (`src/cadrumo_harness/_workspace.py`), [analysis](../articles/187-filing-skills-and-the-mcp-operator-harness.md).

The implementation is strongly explicit about profile/session binding, uncertain effects, local-versus-official evidence and user review. Its main unresolved checks are platform containment, cancellation races, TUI focus/layout and logging privacy, application production of trustworthy form/provenance projections, and congruence of skill recipes with the current registry and tool grants. No runtime or test execution supports a broader assurance claim here.
