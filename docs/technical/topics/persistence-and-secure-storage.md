Profile facts, transactions, calculations, filings and evidence live primarily in bucket-scoped encrypted SQL secure objects. Registered namespaces define sensitivity, schema and custody policy. Session acceleration splits an OS-keychain random key from an encrypted receipt. Automation credentials use native stores and durable denial intents. Attachments and archives retain encrypted bytes with digest checks. An operation journal validates ordered history and exact lease ownership; consent history appends before off-host evidence dispatch without retaining document bytes. ## Storage model and capability

Private product state is primarily stored as profile-bound encrypted secure objects in SQLite, with separate filesystem custody for profile key capsules, attachments, archives, native secret handles and durable operation journals. Namespace definitions declare owner, sensitivity, schema and custody/mirror policy. A `BucketSession` retains one profile DEK, deadlines and a bucket-routed database engine; closing it wipes its mutable key buffer and disposes the engine. SQL rows use HMAC-addressed object identities and AES-GCM associated data for namespace, key digest and schema version. The database also has a plaintext, rebuildable transaction date index containing routing dates and record IDs; missing or incomplete index rows trigger encrypted-scan fallback, so it is metadata with a different confidentiality posture from the transaction content. Namespace registry (`src/cadrumo/adapters/persistence/storage/secure_object_namespaces.py`), bucket session (`src/cadrumo/adapters/persistence/storage/master_key/bucket_session.py`), SQL row model (`src/cadrumo/adapters/persistence/storage/sql/orm.py`), date fallback (`src/cadrumo/adapters/persistence/profile/transactions.py`), [analyses](../articles/019-profile-persistence-for-transactions-review-exchange-and-workflows.md), [analysis](../articles/023-profile-custody-primitives-session-state-and-secure-envelopes.md), [analysis](../articles/024-profile-custody-adapter-storage-routing-and-secure-object-contracts.md), [analysis](../articles/025-encrypted-sql-repository-revision-writes-and-workflow-storage.md).

The secure-object write funnel validates registered namespace/classification, encrypts payloads with identity AAD, derives deterministic revision IDs, checks expected revisions and commits batch writes/deletions with read assertions in one SQL transaction. Profile repositories use those revisions for compare-and-swap mutations, parent validation and related event co-commits. Invoice creation joins catalogue and bucket event; calculation revisions are validated against pinned authority and work units; verification reports require their calculation parent; official and pending-local observations remain separate layers; withholding windows co-commit head, generation, idempotency and source-liability guards. The transaction catalogue encrypts individual rows plus membership index, and checks its plaintext date route against that encrypted membership before trusting it. These mechanisms reduce lost updates and misleading cross-record reads, though actual isolation and crash behavior were not exercised. SQL writes (`src/cadrumo/adapters/persistence/storage/sql/_secure_object_writes.py`), invoice co-commit (`src/cadrumo/adapters/persistence/profile/catalogue_creation.py`), verification parent (`src/cadrumo/adapters/persistence/profile/modelos_verification_reports.py`), withholding workflow (`src/cadrumo/adapters/persistence/profile/withholding_observation_workflow.py`), transaction catalogue (`src/cadrumo/adapters/persistence/profile/transactions.py`), [analyses](../articles/017-persistence-for-llm-records-durable-operations-and-profile-state.md), [analysis](../articles/018-profile-persistence-for-invoices-filings-and-calculation-evidence.md), [analysis](../articles/019-profile-persistence-for-transactions-review-exchange-and-workflows.md), [analysis](../articles/025-encrypted-sql-repository-revision-writes-and-workflow-storage.md).

An operation journal stores a credential-free current snapshot and ordered history with contiguous sequence, monotonic timestamps and terminal-state consistency. Leases share its lock and require exact ownership for commits. Sensitive operation operands are stored separately as content-addressed encrypted objects and re-hashed on resolution. LLM cache, usage and run records occupy encrypted diagnostic namespaces with age/count retention; the cache avoids persisting a redaction-altered response. Off-host evidence consent history is different: it records content address, provider/model, surface and time, appends before dispatch and has no pruning path, because later withdrawal analysis needs history. This is audit metadata, not a copy of transmitted bytes or prompts. Journal validation (`src/cadrumo/adapters/persistence/operations/_journal_validation.py`), leases (`src/cadrumo/adapters/persistence/operations/lease.py`), operand custody (`src/cadrumo/adapters/persistence/operations/secure_references.py`), LLM cache (`src/cadrumo/adapters/persistence/llm/cache.py`), consent ledger (`src/cadrumo/adapters/persistence/llm/consent_ledger.py`), [analysis](../articles/017-persistence-for-llm-records-durable-operations-and-profile-state.md).

## Key custody and recovery

Profile registration generates a DEK wrapped by a password-derived key and writes an encrypted sentinel proving that an unwrapped key belongs to the claimed profile and epoch. Recovery is optional and wraps the same DEK under an independently derived, high-entropy code. KDF work runs in a fresh supervised child with bounded frames, an Argon2id parameter grid, pre-secret readiness attestation and process/resource containment; malformed or timed-out work has no in-process fallback. Capsules are staged as complete sibling directories, write a commit marker last, then publish with a no-replace rename. Discovery accepts only canonical UUID directories and current markers; retired plaintext layouts are refused. Rotation requires a direct predecessor and same DEK epoch; deletion uses a transaction marker, tombstone and inventory witness. Registration/recovery (`src/cadrumo/adapters/persistence/storage/profile_custody.py`), sentinel (`src/cadrumo/adapters/persistence/storage/custody/sentinel_contract.py`), KDF worker (`src/cadrumo/adapters/persistence/storage/custody/_kdf_worker.py`), capsule publication (`src/cadrumo/adapters/persistence/storage/custody/capsule.py`), rotation (`src/cadrumo/adapters/persistence/storage/custody/capsule.py`), [analyses](../articles/020-encrypted-blobs-bucket-archives-and-custody-filesystem.md), [analysis](../articles/021-supervised-key-derivation-and-automation-custody.md), [analysis](../articles/022-profile-capsule-lifecycle-and-custody-proof.md), [analysis](../articles/023-profile-custody-primitives-session-state-and-secure-envelopes.md), [analysis](../articles/024-profile-custody-adapter-storage-routing-and-secure-object-contracts.md).

Human login acceleration splits a random key in the OS keychain from an encrypted receipt in the profile keystore, with authenticated profile/session/generation/epoch/deadline metadata. Exact-byte journals recover interrupted receipt swaps. Automation keys and grant wrapping material use explicitly selected native secret stores, anchored control-file publication and durable denial before optional native cleanup. The design accepts the OS account as a trust boundary; it does not claim defense against another equally privileged process. Memory wiping covers mutable buffers, not all Python or native copies. The login throttle intentionally fails open if its revocable local sidecar is missing or corrupt, favoring availability over resistance to a local actor who can disrupt it. Acceleration receipt (`src/cadrumo/adapters/persistence/storage/custody/acceleration_receipt.py`), automation store (`src/cadrumo/adapters/persistence/storage/custody/automation_store.py`), session close (`src/cadrumo/adapters/persistence/storage/master_key/bucket_session.py`), throttle (`src/cadrumo/adapters/persistence/storage/master_key/login_throttle.py`), [analyses](../articles/021-supervised-key-derivation-and-automation-custody.md), [analysis](../articles/023-profile-custody-primitives-session-state-and-secure-envelopes.md).

Attachments are encrypted content-addressed blobs with encrypted manifests. Reads recheck bucket ownership, digest, size and row identity; duplicate ingestion merges links. A separate filesystem blob store encrypts non-CORPUS classifications and checks ciphertext and plaintext digests. Portable archives have strict versioned members and staged publication; archive data remains encrypted. These are real confidentiality and integrity measures, with bounded exceptions: attachment manifest merge reads before its optional writer fence and passes no local revision witness, so caller serialization must prevent concurrent lost links; a blob/manifest pair spans two files and can become mismatched after sudden termination; the archive reader materializes all tar members before rejecting a noncanonical member count. Attachment store (`src/cadrumo/adapters/persistence/storage/attachment.py`), manifest merge (`src/cadrumo/adapters/persistence/storage/attachment.py`), blob store (`src/cadrumo/adapters/persistence/storage/blob_store/blob_store.py`), archive reader (`src/cadrumo/adapters/persistence/storage/bucket/sealed_archive_reader.py`), [analysis](../articles/020-encrypted-blobs-bucket-archives-and-custody-filesystem.md).

## Scoped quality and assurance limits

Several integrity boundaries deserve precise language. SQL revision IDs are unkeyed hashes over a declared subset of columns; they detect inconsistent rows but do not authenticate arbitrary database edits or cover all ancestry/provenance metadata. Review-package recipient AEAD locally binds the recipient key but not the outer expiry, replay nonce or review-only flags; a higher-level signature may cover the envelope, so impact requires tracing package verification. Financial-operand checkpoints use direct in-place `write_text`, unlike the atomic journal writer, and could be unreadable after interruption. Deletion inventory binds ordinary custody file bytes but only database presence by path, leaving concurrent database content changes outside its witness. The secret store checks expiry presence on write but `get` does not itself reject an expired value; consumer checks remain to be verified. Revision coverage (`src/cadrumo/adapters/persistence/storage/sql/secure_object_crypto.py`), recipient AEAD (`src/cadrumo/adapters/persistence/profile/review_package_recipient_encryption.py`), checkpoint write (`src/cadrumo/adapters/persistence/operations/financial_operand_custody.py`), inventory (`src/cadrumo/adapters/persistence/storage/custody/_inventory.py`), secret-store get (`src/cadrumo/adapters/persistence/storage/secret_store/store.py`), [analyses](../articles/017-persistence-for-llm-records-durable-operations-and-profile-state.md), [analysis](../articles/019-profile-persistence-for-transactions-review-exchange-and-workflows.md), [analysis](../articles/020-encrypted-blobs-bucket-archives-and-custody-filesystem.md), [analysis](../articles/024-profile-custody-adapter-storage-routing-and-secure-object-contracts.md), [analysis](../articles/025-encrypted-sql-repository-revision-writes-and-workflow-storage.md).

SQLite uses WAL and `synchronous=NORMAL`, explicitly allowing loss of the most recent transaction on OS/power failure while preserving database integrity. `create_all` establishes current tables, not a proven upgrade path for arbitrary older databases. Replay-nonce history is append-only without expiry and can grow, while classified namespace/custody rules govern which records can be mirrored or exported. Runtime tests, power-loss recovery, native keychain behavior, cryptographic deployment and current legal correctness were not established by this static review. Engine settings (`src/cadrumo/adapters/persistence/storage/sql/engine.py`), replay nonce (`src/cadrumo/adapters/persistence/profile/recipient_replay_guard.py`), namespace taxonomy (`src/cadrumo/adapters/persistence/storage/namespace_taxonomy.py`), [analyses](../articles/018-profile-persistence-for-invoices-filings-and-calculation-evidence.md), [analysis](../articles/025-encrypted-sql-repository-revision-writes-and-workflow-storage.md).
