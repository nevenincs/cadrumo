## Scope

This chunk covers eight local-runtime modules. The modules implement Windows desktop login evidence, Windows process containment, operation-scoped worker authorization, lease transfer, and a workbench-generation reader. Static-only review; no Windows APIs, workers, or application flows were run.

## Capabilities and flow

Windows login capture binds a retained peer process token to the runtime’s current interactive desktop. It reads owner SID, authentication LUID, session ID, logon SID, token IDs, and LSA logon kind; it separately checks the current process’s `WinSta0` association, repeats token and station observations, and accepts only the exact matching witness. Session observations use WTS metadata and resolve the account owner from the same snapshot, then recheck the WTS generation and LSA token facts. `WindowsLoginBinding.observe` repeats those checks rather than trusting a recycled session number. An observation is eligible only when the exact login/session remains valid; uncertain failures return inactive, locked, and unknown eligibility. Credential-facility availability is supplied separately, so a desktop observation does not prove that a key store is ready. The inventory bounds counts and its overall loop budget, considers only logons associated with the current desktop witness, and returns incomplete when rows cannot be resolved or verified. Native calls and account lookup are synchronous, however, so the two-second loop budget cannot cancel a single blocked OS/domain-controller call (windows_desktop_logon.py (`src/cadrumo_client/transport/windows_desktop_logon.py`), windows_login.py (`src/cadrumo_runtime/adapters/windows_login.py`), windows_login.py (`src/cadrumo_runtime/adapters/windows_login.py`), windows_login.py (`src/cadrumo_runtime/adapters/windows_login.py`)).

The Windows process scope uses a noninherited Job Object configured with kill-on-close and verifies that setting. It attaches each new process to the job in `CreateProcessW` through the kernel job-list process attribute, before child code can execute; it does not use a create-then-assign interval. Launch requires absolute executable and working-directory paths, an explicit environment, and no credential in arguments/environment. Termination fences later launches, terminates the job, waits for zero active members, and retains its job handle if it cannot prove that condition. The scope expressly excludes children created by external brokers; job membership alone does not cover those (windows_process.py (`src/cadrumo_runtime/adapters/windows_process.py`), windows_process.py (`src/cadrumo_runtime/adapters/windows_process.py`), windows_process.py (`src/cadrumo_runtime/adapters/windows_process.py`)).

The worker’s authorization channel is distinct from its operation/custody channels. `WorkerAuthorizationServer` accepts only a verified worker process with the expected owner, profile, and boot identity. It asks the runtime-owned `WorkerAuthorizationOwner` for a narrowly typed permit while a dedicated thread holds the profile guard, limits concurrent authority channels to eight, and bounds permit expiry. Inventory permits carry only a bounded inventory projection; response-scope permits cannot be confused with effect permits. A held operation permit allows at most one command: an automation approval publication or, under the held COMMIT permit of `local-reader.provision` only, an instruction that has the runtime process start the model runtime's server and that carries no program and no environment. Automation approval publication is tied to the exact commit action, approval/decline operation definition, request, session, connection, operation, enrollment reference, and review digest. A lost approval-phase reply triggers best-effort proof cleanup. The worker client opens a separate native connection to its exact runtime parent, validates boot and channel identities, requests authority, performs the body, and acknowledges release on that same connection. Async cancellation paths still settle acquisition/release before dropping the lease. Approval passwords use the ready-then-secret flow, and lease payloads are canonicalized, digest-checked, duplicate-key rejected, schema-validated, and reassembled before the worker applies them (worker_authorization.py (`src/cadrumo_runtime/adapters/worker_authorization.py`), worker_authorization_client.py (`src/cadrumo_runtime/adapters/worker_authorization_client.py`), worker_authorization_client.py (`src/cadrumo_runtime/adapters/worker_authorization_client.py`), worker_authorization_client.py (`src/cadrumo_runtime/adapters/worker_authorization_client.py`), worker_authorization_client.py (`src/cadrumo_runtime/adapters/worker_authorization_client.py`), worker_lease_transfer.py (`src/cadrumo_runtime/adapters/worker_lease_transfer.py`), worker_lease_transfer.py (`src/cadrumo_runtime/adapters/worker_lease_transfer.py`)).

## Knowledge, security, and implementation assessment

The main data are OS login/session identity, process incarnation, runtime-owned worker authority, and a typed workbench-generation projection. No broad reference corpus is present. The stronger security properties are enforced through native token/session checks, kernel-at-creation job membership, exact worker-parent checks, profile-guard-held permits, separate channels, finite lifetimes, and durable release acknowledgements. The Windows process helper retains native handles rather than reopening PIDs as authority. Approval and lease secrets are transferred only after typed protocol setup; worker lease bytes are cleared from the temporary payload buffer after parsing.

Windows desktop inventory is deliberately conservative and cannot be treated as a complete machine-wide login inventory: the code only establishes positive binding for the current desktop witness, and any unsupported or unreadable row makes completeness false. The stated two-second bound governs iteration but not individual synchronous WTS, LSA, token, or domain account calls. Process containment is strong for children created in the job but has an explicit broker boundary. The authorization code’s critical guarantee depends on the runtime-supplied `WorkerAuthorizationOwner` actually retaining and enforcing the canonical profile guard; this adapter provides the fenced channel and effect-command checks around it, but does not implement domain access policy itself.

One cleanup edge merits verification: the authorization server’s connection-finally block closes the channel and then releases its semaphore slot; if native channel close raises, the slot release is skipped. The accept loop submits connection work without retaining or inspecting its future, so that exception does not directly latch server failure. Normal OS closes may make this rare, but an injected/native close failure could reduce capacity without latching server failure. No tests are included in this chunk, and static review cannot validate WTS/LSA behavior, job-object semantics under brokered launches, or the concrete authority owner’s policy (worker_authorization.py (`src/cadrumo_runtime/adapters/worker_authorization.py`), worker_authorization.py (`src/cadrumo_runtime/adapters/worker_authorization.py`), worker_authorization.py (`src/cadrumo_runtime/adapters/worker_authorization.py`)).

## Dependencies and follow-up

Synthesis should connect login observations to the profile access policy and credential-store readiness provider; and inspect the concrete `WorkerAuthorizationOwner` composition and callbacks. It should also confirm whether executor callbacks must report close failures as worker health failures, and distinguish the limited current-desktop inventory from any other login enumeration claims.
