## Capabilities and mechanisms

Profile custody makes create, restore/delete, and recovery decisions through a single application service backed by a composed persistence port. The port contracts keep crypto, encrypted-object repositories, filesystem records, bucket paths, and locking behind an outward-bound capability. It provides anchored bounded local-record reads/writes and compare-and-replace operations; capsule archives and encrypted profile records pass opaque bytes across this boundary. Password records use the adapter’s Argon2id policy and authenticated encryption, while recovery enrollment mints a high-entropy code in a wipeable container, uses an independent salt, and binds its wrapper to the same DEK epoch. These are interface-level guarantees; the concrete KDF, AEAD, filesystem hardening, and key erasure are outside this chunk. Custody capability boundary (`src/cadrumo/application/user_profile/custody_ports.py`), recovery-code handoff (`src/cadrumo/application/user_profile/custody_ports.py`)

Capsule creation records a bounded canonical journal before building a transaction-owned stage. It verifies stage inventory and label provenance, publishes the capsule, then compare-and-swaps the active profile pointer and writes a receipt. Recovery recognizes prior durable states and refuses to overwrite an independently changed pointer. When selection displaces another profile, it retires that profile’s local session acceleration before swapping the pointer, preventing the old bucket key from remaining recoverable without a password. A global root lock currently serializes custody transactions across all profiles; the inner per-profile lock expresses a fixed lock order but does not yield per-profile parallelism. Create and recovery flow (`src/cadrumo/application/user_profile/custody_service.py`), root-before-profile lock (`src/cadrumo/application/user_profile/custody_repository.py`)

Deletion is a journaled, local-only operation. Preflight refreshes independently owned legal and filing evidence, captures the exact capsule inventory and active-pointer state, and creates a random confirmation challenge. A retention override must include a nonempty reason and can bypass only a filing hold; a legal hold remains absolute. Execution requires the exact transaction, profile, inventory digest, and challenge, then rechecks active-target restrictions, hold state, and inventory before proceeding. Ordered effects revoke process secrets, remove local session acceleration, clear the pointer, rename the marked capsule to a transaction tombstone, verify/remove that tombstone, and finally write idempotent owner and transaction receipts. Receipt fields disclose external registrations, backups, recovery artefacts, and certificate/token state as retained; the operation does not claim remote deletion. Hold evidence join (`src/cadrumo/application/user_profile/custody_hold.py`), override boundary (`src/cadrumo/application/user_profile/custody_hold_models.py`), delete preflight (`src/cadrumo/application/user_profile/custody_service.py`), ordered delete/recovery (`src/cadrumo/application/user_profile/custody_service.py`), digest-bound journal (`src/cadrumo/application/user_profile/custody_transactions.py`)

Profile facts have one shared mutation door for wizard, manager, capability, descendant, and language-preference changes. It replaces named paths against the authenticated current record, validates the full resulting fact set with the current profile schema, and records exactly one `PROFILE_VALUES_UPDATED` event with the writer identity. Effective-value equality suppresses no-op revisions; explicit clears remain real changes. Manager field edits can also compare an expected revision/digest and normalize blank input to a clear. Descendant replacement validates the whole row family against one pinned governed-fact authority and exact record baseline, refuses unsupported or noncanonical fields instead of silently dropping them, and clears stale indexed paths in the same write. Filing-baseline helpers separate identity omissions from conditional filing omissions for accurate refusal guidance. Shared fact writer (`src/cadrumo/application/user_profile/fact_write.py`), descendant replacement (`src/cadrumo/application/user_profile/descendant_rows.py`), filing baseline groups (`src/cadrumo/application/user_profile/filing_baseline.py`)

Five human-facing Google configuration operations cover folder view, login, logout, provider probe, and status. Requests bind an explicit profile and carry no secret input. Result projections expose the account email, scopes, the profile's Drive folder, reachability and status without token or client fields. Ordinary configuration leaves are recorded and CLI-only; login consent is resumable and requires an exact terminal review/response checkpoint bound to operation identity, revision, request digest, and profile. Request and result contracts (`src/cadrumo/application/user_profile/google_configuration_operation_contracts.py`), operation definitions (`src/cadrumo/application/user_profile/google_configuration_operation.py`), consent proposal digest (`src/cadrumo/application/user_profile/google_configuration_operation_contracts.py`)

The Google executor rechecks the profile at local commit and outbound handoff boundaries. Its effect tracker records `UNKNOWN` before a provider/local write can become ambiguous, then changes the effect only after canonical acknowledgements; an error after an acknowledged change becomes `PARTIAL`. Register input is consumed from the ephemeral secret scope. Provider refusals are narrowed to closed code/message/fact contracts and stored as encrypted operation detail; terminal result projection checks the exact invocation and terminal receipt before release. Effect tracking (`src/cadrumo/application/user_profile/google_configuration_executor.py`), operation execution (`src/cadrumo/application/user_profile/google_configuration_executor.py`), closed refusal contract (`src/cadrumo/application/user_profile/google_configuration_operation_refusal.py`), receipt-bound release (`src/cadrumo/application/user_profile/google_configuration_result_projection.py`)

History contracts accept an exact profile plus inclusive UTC time bounds and optional event-type, object, and actor filters. Returned projections require count/identity agreement, canonical event ordering, exact profile membership, and every supplied filter to match each event. History request and projection (`src/cadrumo/application/user_profile/history_contracts.py`)

## Security and implementation assessment

Strong local controls include self-digested canonical journals and receipts, bounded record sizes, exact stage and inventory witnesses, target-bound human confirmation, pointer compare-and-swap, idempotent per-owner receipts, and recoverable tombstone ordering. Hold evidence is derived from separate legal and filing owners, bound to profile and canonical source digests, and timestamped; its registry-backed retention projection is read under a pinned authority. The code explicitly avoids treating a retention override as a false “no hold” fact. Evidence model and digest (`src/cadrumo/application/user_profile/custody_hold_models.py`), journal repository (`src/cadrumo/application/user_profile/custody_repository.py`)

One documented freshness limitation deserves focused verification: immediately before deletion, the service compares current legal/filing hold dispositions rather than the evidence digests or source-record identities. With no retention override, a still-held filing assessment continues to block deletion, and a legal hold always blocks it. With an override, however, a changed filing source that remains `held` may pass the unchanged-disposition comparison while the journal’s recorded override still names the earlier retained-record count/date. The service comments identify the omitted source-record digest. Consider binding and rechecking the filing evidence relevant to the override, then test a changed-held-source race. This is a conditional concern around overridden filing holds, not evidence that every delete is unsafe. Disposition-only comparison (`src/cadrumo/application/user_profile/custody_service.py`), override fields (`src/cadrumo/application/user_profile/custody_hold_models.py`)

The global lock is a known scalability tradeoff: one long custody operation blocks publication or deletion for unrelated profiles. Google handoff callbacks synchronously bridge worker-thread work to the event loop; the design keeps authority checks adjacent to side effects, but integration tests should exercise callback ordering, cancellation, and worker settlement. The Google request/result layer itself does not establish which third-party API scopes are least-privileged or what data a concrete adapter logs. The custody port similarly cannot prove its provider actually honors its no-follow, atomic-write, KDF, AEAD, and wipe contracts. No tests are included in these assigned files, and none were executed. Global lock behavior (`src/cadrumo/application/user_profile/custody_repository.py`), handoff/effect boundary (`src/cadrumo/application/user_profile/google_configuration_executor.py`)

## Dependencies and follow-up

Trace `ProfileCapsuleLifecycle` into this transaction service, then inspect the concrete custody filesystem/crypto adapter, profile-pointer transaction, session revocation and acceleration owner, and legal/filing hold owners. Verify recovery at each journal state, concurrent pointer movement, rollback, tombstone tampering, and retention override behavior when hold source records change. For profile edits, follow `ProfileRecordRepository` and validation/schema authority; for Google operations, follow the canonical configuration service, OAuth and outbound-storage adapters, ephemeral-secret runtime, and terminal projection publisher. Exercise receipt mismatch, unacknowledged provider writes, partial local/remote success, exact consent replay, and result-release filtering. History read execution and its access policy are outside this contract-focused slice.
