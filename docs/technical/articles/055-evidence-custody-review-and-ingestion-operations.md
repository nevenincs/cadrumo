## Evidence capture and catalogue lifecycle

The evidence record is metadata around bytes kept by the attachment custodian. It carries a bucket, evidence ID, source hash, attachment ID, media kind, source-path breadcrumb, optional invoice fields, and timestamps; attachment identity is content-addressed and validated separately from the record's metadata. Add admits PDF/image/XML through media-kind checks, while later read admission is based on the actual bytes. Evidence metadata is a tier below a confirmed invoice: fiscal fields are optional here rather than an assertion that invoice confirmation has happened. Record and validation (`src/cadrumo/application/ledger/evidence.py`) Media and ID policy (`src/cadrumo/application/ledger/evidence.py`)

`PurchaseInvoiceEvidenceService.add` resolves the supplied path, requires a readable file, validates the complete candidate metadata before the first durable attachment write, then delegates bytes to the attachment ingestor with an optional expected digest. It preserves the operator-supplied path as provenance instead of storing an absolute host-resolved path. An optional idempotency key creates a stable keyed evidence ID; on retry, matching content and metadata return the earlier row without another catalogue event, whereas changed metadata under the same key is refused. Add uses a revisioned evidence snapshot and commits its new row with the bucket event through the repository's secure-object batch API. Add admission and custody sequence (`src/cadrumo/application/ledger/evidence.py`) Keyed replay and atomic catalogue/event write (`src/cadrumo/application/ledger/evidence.py`) Revision-guarded contracts (`src/cadrumo/application/ledger/evidence_ports.py`)

One important boundary remains: attachment custody is written before the evidence row and event. The registered add worker therefore marks effect UNKNOWN before entering the service and reports UPDATED only after the call returns. If the later catalogue write fails, the attachment-side write can already exist; whether that leaves a harmless reusable content-addressed object or a reviewable orphan depends on the concrete attachment adapter and its cleanup policy. A repeated keyed add also invokes ingestion before it discovers the prior row, so confirm that same-digest ingestion is idempotent at the storage layer. The source shows this sequencing, not a reachable authorization bypass. Worker effect and service call (`src/cadrumo/application/ledger/evidence_add_operation.py`) Separate custody write before catalogue loop (`src/cadrumo/application/ledger/evidence.py`)

Update and removal use revision snapshots, replay only after persistence conflicts, and append the corresponding event in the guarded batch. Mutable fields are limited to supplier, invoice number/date, tax base, rate, amount, and notes; immutable source identity, attachment reference, and evidence ID are not patchable. A no-field update is an explicit no-op with no event. Removal detaches catalogue metadata and emits an event; this module does not delete attachment bytes, which keeps evidence metadata lifecycle separate from shared attachment custody. Patchable fields and omission-mask validation (`src/cadrumo/application/ledger/evidence_mutation_operation.py`) Update executor and no-op (`src/cadrumo/application/ledger/evidence_mutation_operation.py`) Remove executor (`src/cadrumo/application/ledger/evidence_mutation_operation.py`) Service update/remove (`src/cadrumo/application/ledger/evidence.py`)

## Registered interfaces and human ingestion

The registered purchase-evidence add request uses bounded hidden-input fields, canonical dates and nonnegative decimal strings, an exact profile UUID, a source directory, and an optional idempotency key. It preflights the bounded result and exact evidence/event custody identity, then runs the add in an irreversible cancellation section. The registration restricts projection to the declared profile and successful UPDATED receipt and resolves whole-profile ledger read access plus COMMIT. Update and removal use analogous exact-profile, event-count, receipt, and access checks; update's empty patch may settle with effect NONE. List/view expose an allowlisted projection with bounded fields and result size; list verifies row count, duplicate IDs, and bucket correlation, while view refuses a mismatched returned record. Three CLI-only ingestion routes cover a local batch, one remotely acquired document attached to a resolved ledger transaction, and a Google Drive folder sweep that stores listed documents without linking each to a transaction. The batch reuses canonical per-document ordering/outcomes; the single pull resolves a transaction prefix against the current catalogue before fetch and uses the canonical manual-evidence mutation; folder pull preserves each fetched/refused row and derives counts from that ordered result. A concrete writer tracker distinguishes NONE, UPDATED, PARTIAL, and uncertain outcomes; uncertain writes are refused from successful projection. The ports bind acquisition, attachment storage, extraction, ledger actions, and evidence under one pinned profile/authority. ## Review, byte reading, and derived advisories

Five read-only follow-up operations expose pending attachment queue/view, consent history and derived-artifact survey, and filtered review queue/view. They check definition, subject, active profile, and bounded result size; attachment view discloses manifest review metadata without bytes. Review list derives blockers and advisories from every bounded stored draft under the retained authority, with filters for blocker reason, discrepancy, advisory, and blocking-only. Review view returns the full typed draft plus blockers and party/country advisories. Consent survey filters entries to the profile and explicitly preserves that transmitted bytes cannot be recalled. The operation definitions are typed, read-only and restricted to CLI/TUI projections. Review and consent result shapes (`src/cadrumo/application/ledger/evidence_followup_operation.py`) Attachment queue/view (`src/cadrumo/application/ledger/evidence_followup_operation.py`) Review list/view (`src/cadrumo/application/ledger/evidence_followup_operation.py`) Exact five registrations (`src/cadrumo/application/ledger/evidence_followup_operation.py`)

Decrypted evidence bytes are represented by `EvidenceInput`, whose digest must match the data and which must carry evidence or attachment provenance. Its serializer, `model_dump`, JSON dump, iteration, and pickle hooks raise to make accidental persistence fail; raw bytes are excluded from `repr`. The common resolver reads the attachment manifest and blob from an injected profile-bound store, probes content-derived shape, and refuses UNKNOWN rather than trusting stored MIME. Purchase-evidence reads delegate through the attachment ID and retain evidence ID as provenance; source paths are never fallback byte sources. These are in-process tripwires and a narrow resolver contract, not proof that every downstream reader or adapter avoids copying bytes elsewhere. Transient DTO and serialization tripwires (`src/cadrumo/application/ledger/evidence_input.py`) Byte-shape gate and shared resolver (`src/cadrumo/application/ledger/evidence_input.py`) Profile-bound probe port (`src/cadrumo/application/ledger/evidence_input_ports.py`)

Two advisories preserve human-readable document evidence without silently changing persisted facts. The printed-IVA check extracts the first matching whole amount token, lets the canonical European-decimal parser reject ambiguity, and returns a non-blocking warning only when it differs from registry-derived IVA beyond the tolerance. The direction-resolved draft projection selects customer for issued or supplier for received, with no fallback to the other party; the printed-total comparison reports a difference but never overwrites the derived invoice total. IVA advisory parser and comparison (`src/cadrumo/application/ledger/evidence_advisory.py`) Counterparty-side selection (`src/cadrumo/application/ledger/evidence_draft.py`) Printed-total discrepancy (`src/cadrumo/application/ledger/evidence_draft.py`)

## Assessment and cross-module follow-up

The strongest local design choices are bounded private/public schemas, exact profile and subject correlation, atomic evidence/event writes, conflict-aware mutations, no-effect read operations, a no-serialization in-memory byte wrapper, and a clear separation between printed-document checks and authoritative derived figures. The central uncertainty is composition: verify concrete port factories bind the active bucket consistently, attachment ingestion is safe on retries and partial failure, and downstream readers honor `EvidenceInput`'s in-memory boundary. For ingestion, trace the caller's admission and consent checks and confirm every acquisition port applies cancellation/authority checks before remote reads. For consent withdrawal, establish whether the injected ledger and stored-draft survey cover every relevant off-host dispatch and derived artifact. None of these local modules alone proves whole-product reachability or completeness.

Static inspection found explanatory comments and contracts but no tests in the assigned files; no tests were run. The chunk supports application-layer behavior and defensive validation, not runtime persistence, remote provider, UI projection, deployment, or current legal claims. Source comments identify intended security properties, but the report treats only the code paths and type-level contracts described above as implementation evidence.
