## Scope and capabilities

This chunk groups the Google Sheets calculation readback adapter with supporting Drive evidence acquisition, OAuth configuration/session handling, and one inert outbound LLM package initializer. The primary workflow reads operator-edited calculation workbooks, checks that they belong to the application and were compiled from the current registry/layout, then returns immutable typed edits for local calculation. Related adapters resolve Drive evidence links and enumerate folder documents under the granted `drive.file` scope. Google authentication supports both per-profile Desktop OAuth and an alternative short-lived service-account impersonation source.

## Main behavior and data flow

`pull_operator_edits` first validates the spreadsheet ID, confirms the Drive ownership marker, and reads developer metadata. It checks model, revision, filing year/period, engine version, and registry hash against the supplied snapshot before it derives cell addresses or reads worksheet values. Conflicting repeated identity metadata is rejected, while repeated export-time stamps are allowed. It then batch-reads manual/bound casillas, bindings, relations, and allocated detail-row blocks, preserving relation provenance metadata in typed `PullResult` records. `compute_from_pull` rechecks the snapshot binding, maps numeric and text inputs into separate channels, handles enum bindings as strings, and calls the registry Decimal runtime. The pull does not persist edits. It reports nonblank cell counts and returns strict, frozen records, including per-cell row-set coordinates and typed source/legal references. Empty numeric inputs and relations are deliberately converted to Decimal zero so the calculation runtime receives its complete input lattice; blank text inputs stay absent. This makes an empty numeric cell semantically equivalent to zero in the computed result, so callers should keep the workbook instructions and review flow clear about that behavior. Drive evidence acquisition converts supported Google Drive links to bytes, with admission hooks immediately before outbound requests. Folder listing is paginated and filtered to PDFs and common image formats; unrelated non-folder entries are counted as skipped. Gmail links and arbitrary URLs are refused because the configured scope bundle does not grant those read capabilities. A 403/404 on Drive content becomes a typed permission refusal describing the `drive.readonly` scope required to reach arbitrary files. The shared Drive-entry helper escapes query literals, enforces the application ownership marker, backfills an unmarked legacy entry, and refuses a marked-foreign entry. OAuth configuration validation pins the auth, token, and certificate endpoints to canonical HTTPS hostnames. ## Security and quality observations

The strongest safety control in spreadsheet readback is the sequence of ownership and registry/layout checks before cell coordinates are derived or values are read. It prevents unrelated Drive content and stale templates from silently feeding current calculations. Decimal coercion rejects ambiguous or non-finite amount strings rather than converting them into plausible figures; text-family casillas remain text, and edits against undeclared or computed casillas are refused. The calculation is local after the pull, and the adapter does not apply or persist operator changes.

One concrete credential edge deserves attention: the OAuth flow converts `credentials.refresh_token` with `str(...)` before constructing `OAuthToken`. If the provider object exposes `None`, that becomes the nonblank string `"None"`; the record validator only rejects whitespace, so this malformed session can be persisted and fail later during refresh rather than at login. Token extraction (`src/cadrumo/adapters/outbound/google/oauth_flow.py`) Refresh-token validation (`src/cadrumo/adapters/outbound/google/records.py`) Session save (`src/cadrumo/adapters/outbound/google/session_store.py`)

Drive owned-entry lookup requests at most ten matching rows and returns the first entry classified as owned or adoptable. It does not establish uniqueness across later matches/pages. Duplicate same-name entries can therefore make selection dependent on Drive response ordering or hide a later conflicting entry; this is primarily a consistency risk for repeated folder/spreadsheet creation. Owned-entry lookup (`src/cadrumo/adapters/outbound/google/drive_entries.py`)

The evidence resolver fetches each returned document fully into memory and folder enumeration has no total item/byte ceiling in this chunk. That is operationally simple, but very large operator-selected files or folders could amplify memory and request costs. `sniff_document_mime_type` uses magic bytes for PDF/PNG/JPEG and then a filename MIME fallback; it is a labeling helper, not a content-integrity or malware scan. The authentication boundary has useful typed failure distinctions for missing scopes, noninteractive use, loopback binding, endpoint/network failures, stale ADC, and IAM impersonation refusal. Client JSON decoding verifies the expected source digest before parsing, and configuration refusals are reconstructed only from the canonical refusal projection. The type validators still rely on the provider for final acceptance of actual service-account identities, delegated subjects, and scope combinations; the local checks are structural rather than proof of the corresponding Google grants. ## Assessment and limits

The chunk implements a coherent and fairly defensive integration boundary: strict immutable models, explicit scope refusals, ownership checks, registry-hash binding, typed provider errors, per-request admission seams, and secure-object persistence are visible in the source. The main product-level ambiguity is blank numeric spreadsheet cells becoming zero; the main concrete defect candidate is accepting a stringified missing refresh token. Duplicate Drive-name resolution and unbounded document acquisition also merit review. This is static analysis only: no Google API contract, interactive consent, credential persistence, workbook round-trip, calculation output, or remote Drive behavior was exercised here. The directory initializer for outbound LLM is intentionally inert and exposes no capability by itself.
