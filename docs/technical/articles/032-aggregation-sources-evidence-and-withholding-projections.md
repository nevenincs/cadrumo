## Operator previews and evidence policy

The M347/M349 counterpart aggregator is an operator-supplied preview surface, not the live calculation source mesh. It reads dated operation-kind and readiness declarations through a pinned registry operation, validates the selected model revision and registry token vocabulary, groups by source kind, counterparty NIF and operation kind, rejects conflicting countries within a cohort, and reports totals and readiness. M349 readiness is conditional on country: the configured GROI country requires GROI verification; non-GROI countries may require NIF-IVA verification. M347 returns unthresholded totals because the declaration floor is enforced in the binding consumer. The strict frozen input requires the country rather than assuming Spain, and typed country/date/period fields constrain the operator payload. Counterpart payload and aggregation (`src/cadrumo/application/aggregation/counterpart.py`) Model entry points and threshold boundary (`src/cadrumo/application/aggregation/counterpart.py`)

Currency helpers distinguish raw EUR from converted foreign currency. General ledger projections can use a preconverted amount and apply the same FX rate to native taxable base and IVA; an unconverted foreign row raises a typed configuration error rather than contaminating EUR totals. The transaction IVA admission path in the prior chunk has a stricter tax-substrate rule, so this helper’s availability should not be read as universal permission to convert every kind of tax fact. EUR amount and taxable-base helpers (`src/cadrumo/application/aggregation/currency_predicates.py`)

The IVA evidence advisory fires only for active business-bearing rows with positive quota in a quota-bearing category. It applies a stronger test to deductible input IVA (purchase-invoice evidence or a validated catalogue invoice) than to output IVA (any linked evidence), with the former marked blocking at verification and the latter visible but non-blocking. Evidence trigger and output evidence test (`src/cadrumo/application/aggregation/evidence_advisory.py`) Diagnostic construction (`src/cadrumo/application/aggregation/evidence_advisory.py`)

A narrow boundary question remains: the output-side helper counts purchase-invoice-evidence ID or attachment IDs, but not Transaction.invoice_id, even though the module describes any linked document as enough and its deductible-side helper explicitly counts invoice_id. If a valid issued invoice linked by invoice_id is an accepted output document in this flow, the current advisory can still report missing evidence. This is a non-blocking false-warning risk, conditional on that invoice-link shape being reachable; trace the output evidence contract before calling it a defect. Output evidence membership (`src/cadrumo/application/aggregation/evidence_advisory.py`) Deductible evidence membership (`src/cadrumo/application/aggregation/evidence_advisory.py`)

## Foreign assets and inventory

Modelo 720 foreign-asset observations accept four canonical source kinds, constrain currencies to a nonnegative EUR valuation, validate countries and real ISO date strings, and require ledger transaction IDs to meet the canonical identity format. Aggregation produces per-source/per-class rollups; a separate threshold step sums classes within each registry obligation block and marks all present classes declarable when the block exceeds its initial floor. This separation exposes raw totals and leaves filing applicability to the selected, dated threshold data. 720 observation boundary (`src/cadrumo/application/aggregation/foreign_assets.py`) Obligation-block thresholds (`src/cadrumo/application/aggregation/foreign_assets.py`)

The repository-free source resolver accepts typed observations or already-validated worksheet rows. For observations, it filters to threshold-selected classes and binds row values to the selected M720 revision, but intentionally emits no provenance because there is no authoritative persisted asset identity; ledger transaction IDs are carried separately. The worksheet path can instead build row identities and content fingerprints from validated detail records. Thus a valid aggregate preview does not by itself establish a grounded calculation source. Resolver and aggregate path (`src/cadrumo/application/aggregation/foreign_assets.py`) No-provenance aggregate result (`src/cadrumo/application/aggregation/foreign_assets.py`) Worksheet row identities (`src/cadrumo/application/aggregation/foreign_assets.py`)

The inventory resolver reads one injected encrypted ledger repository. Before storage access it checks the binding cohort uses the exact canonical row operations and selected filing coordinate, and checks year applicability. A profile that explicitly declares no economic activity makes the source inapplicable; otherwise absent repository, unreadable storage, missing activity ledgers, invalid row templates, or projection inconsistency return unresolved bindings with typed diagnostics. A valid projection generates the three values for each activity, a fingerprint, primary provenance, and a non-blocking physical-closing-conflict diagnostic where applicable. The resolver does not invent a manual fallback or aggregate across activities. Template, storage and projection flow (`src/cadrumo/application/aggregation/inventory.py`) Inventory row projection and provenance (`src/cadrumo/application/aggregation/inventory.py`) Source resolver (`src/cadrumo/application/aggregation/inventory.py`)

One privacy detail merits downstream tracing. Inventory provenance uses a content digest rather than actividad_id and says the taxpayer’s activity identifier is not disclosable, but RowSourceIdentity separately stores projection.actividad_id as source_row_identity. This module does not establish whether that identity is persisted or exposed in explanations; verify the downstream serialization and redaction before concluding it is private. Content-addressed provenance (`src/cadrumo/application/aggregation/inventory.py`) Plain source-row identity (`src/cadrumo/application/aggregation/inventory.py`)

## Income ledgers and invoice timing

The impatriado ledger loads only from a caller-supplied repository bound to the requested bucket and date-partitions annual reads. Active incoming rows are admitted against the revision-selected source-jurisdiction and income-category sets; unresolved/out-of-scope jurisdiction, unsupported currency, absent business attribution, and out-of-window rows become typed issues. Governed eligible categories admit the full value; other income uses business proportion. Gross and optional taxable base are converted to EUR consistently and scaled by the same proportion, then folded to the selected target casilla. Repository partition and bucket check (`src/cadrumo/application/aggregation/impatriado_income_ledger.py`) Transaction classification and EUR projection (`src/cadrumo/application/aggregation/impatriado_income_ledger.py`)

The M210 IRNR ledger similarly checks the injected revision against authority selection, reads income-code namespace and source-jurisdiction scope from that revision, validates the selected official code, and optionally date-partitions the repository. Active incoming rows outside the target scope or missing a declared classification yield traceable issues; only rows matching the selected two-character income code reach the output. The classification’s explicit gross income, applicable rate, payer mode, and optional payer/asset IDs are carried forward rather than reconstructed from signed cash. This makes operator-entered classification a critical input contract. IRNR repository flow (`src/cadrumo/application/aggregation/irnr_income_ledger.py`) Selected revision and projection (`src/cadrumo/application/aggregation/irnr_income_ledger.py`) Registry code namespace (`src/cadrumo/application/aggregation/irnr_income_ledger.py`)

Invoice devengo is represented as both a date and a rank: declared operation/advance date or issue-date proxy. One shared predicate uses that result for period membership, and a non-blocking diagnostic names proxy-attributed invoices so the operator can record operation dates. A staged series of partial advance payments is explicitly unrepresentable in this one-date model. The direction-only bank mapping has another explicit limitation: an incoming refund of a purchase maps to ISSUED/output IVA, because the two-member invoice-kind axis cannot express a signed correction; consolidating that decision avoids duplicated drift but does not solve the refund treatment. Devengo resolution and period membership (`src/cadrumo/application/aggregation/invoice_devengo.py`) Proxy advisory (`src/cadrumo/application/aggregation/invoice_devengo.py`) Direction mapping and refund limit (`src/cadrumo/application/aggregation/invoice_kind.py`)

Received-invoice withholding is a projection into the existing per-perceptor store, not another persistence path. The application reads liability/base and identity from a received invoice, requires declared scheme and recipient/payment or exigibility evidence from the request, rejects nonresident suppliers from this IRPF path, and submits one capture command to a shared producer with idempotency, mode, baseline, supersession, and annual-detail evidence. The projection accumulates all defects and either yields a typed observation or a defect-only refusal; it does not infer scheme from invoice kind. The request’s allocation values are caller supplied, while the invoice supplies the source liability snapshot; the downstream producer owns write/consistency enforcement. Invoice withholding capture builder (`src/cadrumo/application/aggregation/invoice_retencion.py`) Projection and liability defects (`src/cadrumo/application/aggregation/invoice_retencion.py`) Defect sweep (`src/cadrumo/application/aggregation/invoice_retencion.py`)

## Assessment and dependencies

Strong patterns include registry-selected applicability, explicit EUR conversion helpers, date-partitioned repository reads, strict source IDs, typed exclusions, and a visible distinction between blocking deductible evidence and advisory-only output evidence. Important limits are equally explicit: 347/349 is a preview, aggregate M720 observations lack primary provenance, partial advance schedules are unsupported, refunds are not modeled by invoice kind, and IRNR gross/rate classifications depend on input facts. No tests are included in these modules; runtime reachability, repository encryption, operator display of diagnostics, and final persistence behavior remain unverified. Follow up on the output evidence membership question and inventory activity-ID exposure through downstream persistence. Dependencies include the shared grouping helpers, transaction/invoice repository protocols, selected modelo and obligation registries, the sealed inventory projection, invoice catalogue, and shared withholding producer. Do not treat descriptions of tax law in docstrings as current legal verification.
