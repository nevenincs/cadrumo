## Capabilities and flow

The package lets a CLI or TUI speak to an already-verified runtime connection for one profile, authenticate that profile, and request typed runtime operations. `RuntimeFrontendClient` is bound at construction to the connection, profile, frontend kind, and storage identity. Its operation path checks the request’s profile and session against that binding; login establishes a session only after the returned status proves it is connected, authenticated, profile-bound, and for the expected profile. The client also provides explicit password/API-key login and refresh, session lock/revoke, recovery, enrollment preparation and reconciliation, automation denial, and public operation-contract lookup. Profile-view reads paginate validated operation results, checking profile, revision, page sizing, and digest while obtaining fresh consent for each page; if the collection fails, it discards partial output and clears its local mutable buffer. The runtime remains the authority that decides admission and performs operations (frontend_client.py (`src/cadrumo/adapters/local_runtime/frontend_client.py`), frontend_client.py (`src/cadrumo/adapters/local_runtime/frontend_client.py`), frontend_client.py (`src/cadrumo/adapters/local_runtime/frontend_client.py`), frontend_client.py (`src/cadrumo/adapters/local_runtime/frontend_client.py`)).

The protocol framing separates ordinary JSON documents from secrets using distinct frame kinds and exact length headers. Both frame classes are capped at 64 KiB; document decoding rejects duplicate JSON keys, non-finite values, and invalid schema data. Incomplete or malformed frames fail closed. A verified connection correlates requests and replies with request, boot, and connection identity, serializes I/O under a per-connection lock, and applies deadlines that include time waiting for that lock. A secret frame can be sent only after a matching `RuntimeSecretReady` reply; refusing before readiness leaves the secret unsent. Mutable secret and oversized-payload buffers are cleared after use. The handshake validates the negotiated version and storage identity before accepting a connection (framing.py (`src/cadrumo/adapters/local_runtime/framing.py`), framing.py (`src/cadrumo/adapters/local_runtime/framing.py`), framing.py (`src/cadrumo/adapters/local_runtime/framing.py`), framing.py (`src/cadrumo/adapters/local_runtime/framing.py`)). Automation has separate owner and requester journeys. Approval requires the precise `automation.password` secret channel; decline forbids a secret. A supplied mutable password is cleared in a `finally` path. ## Knowledge, security, and implementation assessment

This chunk is chiefly an authority and transport boundary. Its useful knowledge consists of typed contracts and observations tied to one profile, storage identity, connection, boot, OS owner, and native session/process identity. It does not provide broad legal or domain reference material. Credential handling is explicit: secrets travel on a separate ready-gated frame, mutable buffers are cleared, enrollment offers are callback-scoped, and automation results distinguish verified runtime evidence from mere completion metadata. Linux/macOS session uncertainty is preserved rather than converted into a positive unlocked claim. Filesystem publication uses private staging and no-clobber semantics; process ownership uses pidfds/cgroups where supported. Unsupported native facilities are refused rather than silently replaced with PID-only or heuristic checks.

The main quality strength is disciplined binding across layers: exact-profile checks, request and receipt correlation, terminal-effect validation, deadlines, and typed failure/uncertainty surfaces prevent callers from treating a timeout as success. The code also separates “installed/configured,” “running,” “authenticated,” and “operation settled” states. Important residual questions belong to adjacent chunks: the server-side handshake and secret-channel implementation must enforce the other half of these contracts; the transport launcher must establish peer identity before this client accepts it; the GNOME state query cannot make lock observations atomic with later user activity; and the native system manager/kernel remain trusted sources for unit and process state. No tests are assigned in this chunk, and static inspection cannot establish behavior against real D-Bus, systemd, macOS session APIs, or concurrent adversarial state changes. Parent-level syntax and import checks are not runtime validation.

## Dependencies and follow-up

Synthesis should connect `RuntimeFrontendClient` and `VerifiedRuntimeConnection` to the runtime’s canonical request dispatcher, secret receiver, handshake, and transport startup; trace the callback-scoped enrollment candidate into the native credential store; and verify how manager provisioning and worker cgroup termination are orchestrated by the runtime lifecycle. It should also compare the Linux and macOS login evidence with the policy that consumes `OsLoginContext`, preserving their different uncertainty guarantees.
