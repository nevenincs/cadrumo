## Capabilities and mechanisms

This chunk implements the application-level operation lifecycle from admission through execution, review, result projection, settlement and restart recovery. Submission validates the exact registered request type, resolves the definition contract, checks optional host authority and binds optional admission provenance to the same invocation. Requests either go to the secure reference store or are persisted as credential-free JSON with a content digest. An idempotency claim and conflict-scope lease prevent duplicate admissions; the operation snapshot is journaled as `CREATED` before `submit` returns. If journal creation fails, the exact acquired lease is released. Submission and authorization (`src/cadrumo/application/operations/_supervisor_submission.py`), request storage and durable admission (`src/cadrumo/application/operations/_supervisor_submission.py`), lease and idempotency behavior (`src/cadrumo/application/operations/_supervisor_lease.py`)

`start` accepts only a created snapshot whose definition-contract digest still matches the live registry. It checks execution and cleanup deadline configuration, enforces any exact live ephemeral-secret requirement, resolves the stored request, rechecks START authority, and durably moves the snapshot to RUNNING before scheduling the executor under supervision. Authority is checked again at actual coroutine entry. Executor results settle as success only when they are valid references; declared refusal evidence is validated against the public registration; a stopped executor returning no result fails unless another durable interaction/cancellation/terminal path will settle it. Start and task admission (`src/cadrumo/application/operations/_supervisor_execution.py`), authority at task entry (`src/cadrumo/application/operations/authorization.py`), result and failure settlement (`src/cadrumo/application/operations/_supervisor_execution.py`), returned-result classification (`src/cadrumo/application/operations/_supervisor_execution.py`)

While running, the supervisor renews an exact durable owner lease by compare-and-swap. A cancellation request is persisted with a cleanup deadline; the executor can acknowledge only after a request and outside an irreversible section. `irreversible_section()` serializes concurrent entry, checks cancellation before entry, takes the optional authority owner's commit guard, and records cancellation deferral until exit. Cleanup must finish before a terminal receipt and lease release are committed together. If cleanup reaches its deadline, the operation remains unsettled in `SETTLING`; cancellation is not falsely reported as complete. Irreversible-section controls (`src/cadrumo/application/operations/_execution_context.py`), durable cancellation and acknowledgement (`src/cadrumo/application/operations/_supervisor_settlement.py`), cleanup and terminal commit (`src/cadrumo/application/operations/_supervisor_settlement.py`), cleanup deadline and stop proof (`src/cadrumo/application/operations/_supervisor_settlement.py`)

On restart, reconciliation observes the conflict lease and either refuses an active owner, acquires/takes over absent or expired ownership, or classifies the operation as resumed, recovered, interrupted or orphaned. A checkpoint resumes only when the declared policy allows it, the pending/consumed interaction matches the snapshot and definition, and the executor structurally implements the resumable interface. Where the host authority is enabled, RESUME is checked before reentry. A path with no valid checkpoint is interrupted; if it might have produced effects, the receipt retains `UNKNOWN` effect. Reconciliation and resume (`src/cadrumo/application/operations/_supervisor_reconciliation.py`), checkpoint validity and execution (`src/cadrumo/application/operations/_supervisor_reconciliation.py`), interruption receipt (`src/cadrumo/application/operations/_supervisor_reconciliation.py`)

The projection readers separate safe public REVIEW data, workspace-refresh targets, and terminal results. Each checks request version, durable lifecycle/revision, current definition digest and exact registered schema identity. REVIEW additionally checks pending interaction identity, expiry, response schema and contract, resolves the private reviewed operand, requires the projector to return the registered model class, then validates a fresh model before return. Refresh requires an exact successful terminal receipt and its registered adapter. Result reads permit successful results or declared refusal detail, resolve private operands, and keep refusal explanation separate from business result semantics. Failures map to typed public refusals rather than leaking raw exceptions. Review projection (`src/cadrumo/application/operations/_projection_read.py`), refresh target checks (`src/cadrumo/application/operations/_projection_read.py`), terminal result projection (`src/cadrumo/application/operations/_projection_read.py`)

Response control uses a process-local broker to reserve an opaque actor-bound capability, attach the response token only after a digest-bound REVIEW checkpoint exists, inspect allowed APPLY/REJECT intents, and transfer a matching unexpired bearer to the secure response authority. Exact operation, interaction, revision, actor, pending checkpoint, proposal digest and expiry coordinates are compared. The mutable token buffer is zeroized on rejected issue, transfer cleanup and shutdown. Cancellation and detachment similarly verify supported version, current revision, live contract, cancellation policy and detach policy before invoking the supervisor. Response bearer binding and transfer (`src/cadrumo/application/operations/_projection_authority.py`), versioned response/cancel/detach gates (`src/cadrumo/application/operations/_projection_control.py`), cancellation authorization (`src/cadrumo/application/operations/_projection_control.py`)

## Knowledge, security, and implementation assessment

The public registry contract is a digest over definition identity, schema identities and declared policy axes. Registration must bind exactly the schemas named by the manifest, match request/result types, provide the required result/review/refresh projectors, and reproduce a live fixed point from the operation definition. Projector and adapter signatures must be synchronous with exact positional arity. A recursive model-graph checker rejects lax or mutable Pydantic model shapes, mutable annotations, custom schema hooks, schema serializers, coercive validators, private/computed fields and unvalidated defaults. Contract and registration checks (`src/cadrumo/application/operations/_registry_contracts.py`), live fixed point (`src/cadrumo/application/operations/_registry_contracts.py`), strict immutable model graph (`src/cadrumo/application/operations/_model_contract.py`)

The access resolver combines host-supplied profile, destination, frontend, action, contract and authority with a registered operation resolver. It requires the resolver to return those same coordinates and contract digest. A replayed operation must come from its original destination/frontend and satisfy its period scope; otherwise current held authority is required. OBSERVE/CANCEL/DETACH disclose operation metadata, RESULT discloses only the registered result schema and declared categories, and other actions disclose nothing. Named profiles encode permitted actions, disclosure categories, period scope, schema pinning and human requirement. The host rechecks authority on submit, start and resume, and may hold a commit guard across an irreversible effect. Admission replay and disclosure policy (`src/cadrumo/application/operations/access_resolution.py`), named access profiles (`src/cadrumo/application/operations/access_resolution.py`), live registration and host-coordinate match (`src/cadrumo/application/operations/access_resolution.py`), execution-authority contract (`src/cadrumo/application/operations/authorization.py`)

The operation host treats credentials and operands as separate custody concerns. Ephemeral secrets are accepted only for the exact durable requirement, never serialized or digested here, and the caller's mutable buffer is zeroized on every exception. Transient financial operand amounts are delivered to a running invocation without journal serialization. Executor exceptions are not persisted with their messages, arguments, traceback, URL or path; the receipt carries a registered code or safe correlation reference, and optional bounded public details are stored separately through the secure operand store. Secret submission (`src/cadrumo/application/operations/_supervisor_execution.py`), safe failure receipt (`src/cadrumo/application/operations/_supervisor_execution.py`), transient financial input (`src/cadrumo/application/operations/_supervisor_execution.py`)

Public mirrors convert canonical models and dataclasses to an explicit scalar/tuple form, check the field inventory and allowed omissions, and restore typed values with strict decimal canonicalization. Contract registration and response/result projection validate models again at the release boundary. Drain stops new admissions, closes ephemeral-secret custody, gives tracked settlement and cleanup tasks one finite monotonic window, cancels remaining local tasks, and reports unresolved operations and those needing recovery. Its own documentation correctly assigns process/descendant containment to the caller. Public projection and inventory (`src/cadrumo/application/operations/_public_mirror_projection.py`), restoration and decimal checks (`src/cadrumo/application/operations/_public_mirror_restoration.py`), bounded shutdown accounting (`src/cadrumo/application/operations/_supervisor_drain.py`)

The main strengths are explicit lifecycle durability, stale-revision refusal, contract pinning, exact lease CAS, encrypted-reference boundaries, typed public refusal, and cleanup-before-terminal ordering. One important operational limitation is local: the drain can report and cancel tracked tasks but cannot prove that subprocesses or external side effects stopped. Storage encryption, cross-process lease correctness, idempotency durability, authority implementation and real executor recovery depend on modules outside this chunk. The code catches broad `Exception` at public projection boundaries and turns it into a stable refusal, which contains detail but makes diagnosis dependent on the separate diagnostic/error-detail channels. No tests are included in the assigned files, so none of these behaviors are runtime-verified here.
