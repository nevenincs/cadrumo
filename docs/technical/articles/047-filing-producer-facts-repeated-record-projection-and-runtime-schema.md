## Scope

This chunk covers seven filing-application modules: producer snapshot models and validation, Modelo 200 row facts, M303 projection planning, fixed-width record rendering, record value types, filing-retention snapshots, and runtime registry-schema projection. The assigned files total 4,055 lines and 38,616 measured `o200k_base` proxy tokens. I read all seven bounded pages, including every assigned range. ## Filing producer facts and validation

`FilingProducerSnapshot` is a frozen, strict aggregate for a filing’s model, subject tax ID and identity, presenter, optional declaration contact, model-specific facts, elections, amendment evidence, selected account, and optional M303/M390 facts. Presenter identity is separately typed and requires its own identity; it does not fall back to the taxpayer’s name. Taxpayer legal-name facts keep legal-entity identity distinct from natural-person names, while contact details have a separate optional model. This separation gives downstream header projection typed roles rather than one undifferentiated “name” field. Identity and contact facts (`src/cadrumo/application/filing/producer_snapshot.py`) Snapshot aggregate (`src/cadrumo/application/filing/producer_snapshot.py`)

Snapshot validation requires the matching profile class for supported specialized models, restricts M303 and M390 evidence to their own models, and rejects embedded bank accounts in the IVA profile. Account selection is disposition-aware: direct debit requires a charge account; refund requires a refund account; an otherwise account-free disposition rejects a retained account except the explicitly modeled M303 Nota 3 case. The public builder first strips accounts embedded in the profile and retains only the selected account, and it refuses a refund without an IBAN. These are concrete local controls against carrying both account roles or leaking profile-held accounts into a producer snapshot. The same comments flag a real integration concern: detailed M296 rows may still be hand-populated even though withholding observations exist, so caller projection is needed to avoid divergence between filed rows and the underlying ledger. M303 facts join filing-period evidence to canonical calculation and register state. Validation constrains official periods, requires year-end exemption evidence on the final period, aligns arrival periods and calculation result, verifies the annual regularisation result against the supplied investment register and parameters, and checks prorrata coverage/evidence membership. ## Projection and byte rendering

The projection plan is specifically an M303 repeated-row producer. It binds to a selected registry snapshot and a layout owned by that snapshot, checks model and filing period, then dispatches only recognized typed projection-reference families. It projects prorrata, differentiated deductions, simplified-regime rows, and the Modelo 390-exemption-related activity/third-party values. Required projection records must have an emitted occurrence unless the evidence explicitly scopes simplified-regime rows out. Mixed prorrata and differentiated families are composed back into the one layout-authored occurrence; duplicate or missing typed values refuse. M303 projection request and dispatch (`src/cadrumo/application/filing/projection.py`) Record-family composition (`src/cadrumo/application/filing/projection.py`) Required-occurrence rule (`src/cadrumo/application/filing/projection.py`)

Before rendering, `preflight_projection_plan` proves an exact address bijection among admitted layout fields and produced `(record, occurrence, projection reference)` values, rejects duplicate addresses, and runs the declared field formatter on every value. The renderer then walks records in declared order, applies the shared DID-page suppression predicate, rejects required records with no applicable occurrence, and turns payload text into bytes using each record’s encoding and line ending. Binding-row rendering derives active row indexes from nonempty values, rejects missing required binding fields, and groups only mutually non-overlapping fields for a row. A non-repeating binding-backed page is suppressed only when both its binding values and casilla values are empty, so a literal record identifier alone does not keep an otherwise empty page alive. ## Retention and runtime registry knowledge

The retention owner projects minimal filing facts from actual `ModeloRecord` objects: filing ID, model, year, and timestamp. It sorts and validates unique filing IDs, seals canonical JSON with a self-digest, writes under a profile-custody owner root while holding a lock, and recomputes the digest, profile identity, and canonical bytes on read. The deletion projection delegates the retention decision to the domain floor authority; absent or unreadable snapshots raise instead of being treated as “no records.” The best-effort write helper logs and returns false rather than blocking profile creation or filing persistence, relying on absence to fail closed. Retention facts and snapshot (`src/cadrumo/application/filing/retention.py`) Record and read validation (`src/cadrumo/application/filing/retention.py`) Owner persistence and assessment (`src/cadrumo/application/filing/retention.py`) Best-effort writer (`src/cadrumo/application/filing/retention.py`)

The self-digest and canonical-byte check establish internal consistency, not authenticated origin against a party able to rewrite the file and recompute its digest. Also, the write helper explicitly permits an old snapshot to remain after a write failure, while reads show no freshness threshold. If a prior snapshot exists and an update fails, a later deletion assessment could use stale filing facts; caller ordering, store failure behavior, and whether another layer detects staleness need cross-module verification. The absent-snapshot fail-closed behavior does not by itself settle that stale-snapshot case.

The runtime schema provider builds immutable filing-facing views from validated registry snapshots. The default path uses the bundled indexed authority; an explicit validated-authority path shares the same projection. Both require a typed `Period` consistent with the requested year. An indexed operation requires explicit model IDs and resolves point snapshots under that pinned operation. An unfiltered authority sweep can skip models whose authority grade is below filing, but an explicitly requested below-grade model propagates its refusal. The accessor checks consistent model/revision/schema identities, freezes its mappings, exposes published source bytes through evidence, and returns casilla schemas sorted by canonical ID. It rejects duplicate casilla IDs and dangling formula inputs; subviews carry exported layout, source/legal references, completeness and record metadata, profile-export bindings, and rate-box partitions. ## Assessment and follow-up

This slice has clear trust boundaries in its strongest paths: strict immutable facts, evidence-backed M303 joins, snapshot-owned layout references, exact projection preflight, required-row checks, canonical rendering, and fail-closed retention reads. The main unresolved questions are caller-side rather than inferable here: whether M200/M210/M296 facts are populated from authoritative records and admitted only after appropriate operator review; which M210 scopes a given filing requires; whether a retention update failure can leave a stale but accepted snapshot; and what filesystem permissions/authentication protect persisted retention records. M202 is explicitly unsupported at snapshot admission. Tests and runtime behavior are not established by these implementation files.
