## Capabilities and mechanisms

Storage management derives its inventory, health check, initialization, and reclaim targets from the shared storage taxonomy. The inventory aggregates internal locations into stable public areas and reports occupancy, durable/reclaimable/mixed disposition, number of resolved paths, immediate entry count, and disk footprint. A bucket-scoped location is `UNRESOLVED` when no active profile is selected, distinct from a path that was checked and found absent. Tree inspection is read-only, considers only configured root-scoped locations, and distinguishes a missing directory from a normal absent file-valued leaf. Permission drift is reported only where root mode bits are enforceable; the report says explicitly when that check is not available. Taxonomy-backed inventory (`src/cadrumo/application/storage_management/service.py`), read-only tree inspection (`src/cadrumo/application/storage_management/service.py`), public report contracts (`src/cadrumo/application/storage_management/models.py`)

Initialization delegates to the same tree materializer used by runtime bootstrap and reports only directories created during that invocation. It does not clear or recreate existing storage. Reclaim derives eligible locations from the declared RETENTION, ROTATION, and TTL lifecycles, refusing durable state and exports. Before any deletion it selects minimal outermost paths, validates all candidate lifecycles and root scope, checks for protected declared descendants, rejects link-like or out-of-root targets, counts the current entries, and requires explicit `confirmed=True`. Removal keeps failures in the report and avoids following symlink or junction entries. Lifecycle policy and init (`src/cadrumo/application/storage_management/service.py`), reclaim preflight and confirmation (`src/cadrumo/application/storage_management/service.py`), all-target preflight (`src/cadrumo/application/storage_management/service.py`), live path containment and link handling (`src/cadrumo/application/storage_management/service.py`)

Area-level occupancy is derived from the strongest state among its selected paths: populated outranks empty, empty outranks absent, and unresolved is returned only when nothing could be resolved. Directory occupancy counts immediate children; file occupancy distinguishes zero-byte from non-empty files. Nested paths are reduced to unique outermost roots before calculating entry totals or size, so one cache tree is not counted repeatedly through its descendants. Occupancy precedence and area aggregation (`src/cadrumo/application/storage_management/service.py`), minimal-path and footprint handling (`src/cadrumo/application/storage_management/service.py`)

Ledger import preview emits strict, typed diagnostics for parser-empty input, duplicates or ID collisions, calendar gaps, and an optional original-file check. A single pure classifier is shared with the persistence path so preview and actual import use the same decision. A previously stored fingerprint is skipped; a repeated fingerprint within the current batch imports both rows and produces an advisory; a repeated transaction ID in the batch is skipped because it would overwrite the earlier catalogue key. The ordering gives stored duplicates precedence, then ID collisions, then intra-batch fingerprint repeats. Shared row verdict (`src/cadrumo/application/transactions/import_classification.py`), classification order (`src/cadrumo/application/transactions/import_classification.py`), diagnostic preview flow (`src/cadrumo/application/transactions/import_diagnostics.py`)

The preview requires exactly one caller-derived, direction-qualified import fingerprint per raw row, compares those against existing catalogue fingerprints, and reports imported/skipped counts with diagnostic records. It processes rows in input order, collects their dates, and warns when adjacent sorted dates are more than 35 days apart. A present original-source path gets an informational diagnostic; an unreadable path gets a warning. Diagnostic kinds and severities are closed enums, source locators are trimmed and bounded, and construction verifies the translation key has an authoritative Spanish rendering. Row processing and gap checks (`src/cadrumo/application/transactions/import_diagnostics.py`), original-file check (`src/cadrumo/application/transactions/import_diagnostics.py`), diagnostic validation (`src/cadrumo/application/transactions/diagnostics.py`)

## Knowledge, security, and implementation assessment

Storage decisions rely on the canonical taxonomy and current settings, plus live filesystem observations. Reclaim selects no arbitrary user-supplied path: area and lifecycle determine candidates. Durable namespaces and key material are explicitly outside the reclaimable set, while symlink/junction and containment checks guard the destructive boundary. The explicit confirmation check lives in the service, so a programmatic caller receives the same confirmation requirement as the CLI. Inventory aggregation avoids double-counting nested paths and reports unresolved bucket paths honestly. Reclaimable lifecycle set (`src/cadrumo/application/storage_management/service.py`), root-scoped aggregate calculation (`src/cadrumo/application/storage_management/service.py`), occupancy semantics (`src/cadrumo/application/storage_management/service.py`), service-level confirmation error (`src/cadrumo/application/storage_management/errors.py`)

The import preview’s evidence is limited to parser-provided rows, the current catalogue, their fingerprints, and source paths. It does not persist records or mutate the catalogue; persistence, FX normalization, and bucket-event emission are delegated to the ledger application layer. Reusing the classifier avoids a previous preview/import disagreement that could have skipped a genuine repeated movement and understated totals. One terminology limit remains: the “verified original file” path check is based on existence/readability, not comparison of original bytes against the parsed source. Diagnostic-only package boundary (`src/cadrumo/application/transactions/__init__.py`), original path existence behavior (`src/cadrumo/application/transactions/import_diagnostics.py`)

One destructive-boundary caveat is worth testing. Reclaim validates each target before counting and deleting; it also rechecks link types at removal of individual entries. Filesystem paths can still change between those checks and a later recursive removal, so the concrete threat model should confirm whether a concurrent replacement can redirect deletion after containment was established. This static pass does not establish race-free deletion. The inventory also degrades unreadable enumeration and sizing to zero after debug logging; the resulting empty/zero report is not a distinct permission-failure state, so operators could mistake incomplete measurement for genuinely empty storage. Preflight and later deletion (`src/cadrumo/application/storage_management/service.py`), best-effort size and entry counts (`src/cadrumo/application/storage_management/service.py`)
