## Operator capabilities and how they work

The largest unit is the local Modelo 145 payer-communication record service. It creates a content-addressed record from the profile bucket, communication year/period, pinned revision, and sorted field values; a repeated identical creation reuses the existing record. Validation re-resolves the registry contract and checks the active revision and legal/source references, declared casilla membership, required values, scalar shapes, constraints, and the dated family-situation catalogue. Export proceeds only after successful validation, resolves the registry export layout, and delegates fixed-width bodies to an injected renderer; record order, encoding, and line endings come from that layout. The returned receipt re-hashes and measures its own payload, and an export event records its digest, size, and record count. Delivery and local completion are explicit successive states with ordered timestamps and are saved with their history events in one secure-object write unit. The service describes this as a local communication workflow and has no payer or AEAT submission call in this module. Record validation (`src/cadrumo/application/modelo/m145_communication_records.py`), export (`src/cadrumo/application/modelo/m145_communication_records.py`), creation (`src/cadrumo/application/modelo/m145_communication_records.py`), delivery transition (`src/cadrumo/application/modelo/m145_communication_records.py`), atomic event write and receipt validation (`src/cadrumo/application/modelo/m145_communication_records.py`), bucket-scoped persistence port (`src/cadrumo/application/modelo/m145_communication_records_ports.py`)

There is a narrow fiscal safety gate for Modelo 193. It identifies persisted withholding-resolver contributor rows whose accrual year is earlier than the current filing year. Filing and export raise a typed no-action precondition when the payment-year amounts lack an official authority; verification instead returns a warning so the draft remains inspectable. A row without a stored accrual year is decided by a conservative period-materialization bound, which the module says can over-refuse. For that fallback it opens a bundled indexed-registry operation locally rather than receiving the caller's pinned operation. Whether that can observe a different generation from the operation that calculated the revision is a cross-layer question for the authority lifecycle review. Contributor selection and enforcement (`src/cadrumo/application/modelo/m193_settled_row_gate.py`), verification finding (`src/cadrumo/application/modelo/m193_settled_row_gate.py`)

The Modelo 303 evidence code builds and validates the ordinary filing envelope. Authoring requires a quarterly or monthly work coordinate whose selected registry layout declares the three ordinary header producers, a matching work-unit revision, a current complete taxpayer profile, an applicable filing schedule, and the supported “simplified regime not claimed” branch. It recalculates and checks the empty simplified-regime row set against the annual order snapshot. For the final filing period only, the envelope also requires a secure attestation that the taxpayer asserted Modelo 390 was not applicable. The filing boundary then checks period identity, the profile-derived regime scope and recomputed result, and (where applicable evidence is asserted) full endpoint coverage and agreement with both revision values and recorded observations. Simplified-regime claimants and “applicable” Modelo 390 assertions remain explicitly unsupported by this ordinary branch. Ordinary envelope authoring (`src/cadrumo/application/modelo/m303_ordinary_filing_evidence_authoring.py`), revision-bound validation (`src/cadrumo/application/modelo/m303_filing_evidence.py`), profile-to-scope mapping (`src/cadrumo/application/modelo/m303_regimen_simplificado_scope.py`)

Attestation admission stores canonical JSON through the encrypted attachment service. Resolution verifies the nominal attachment ID/digest pair, bucket, attachment kind/source/MIME, blob integrity, profile witness, filing coordinate, assertion, and observation timing. It additionally scans matching bucket manifests for contradictory assertions and accepts the evidence only when the target coordinate has exactly the non-applicable assertion. The registered profile-worker operation accepts either one existing Modelo 303 work unit or one explicit period, checks active-profile/work-unit ownership, and returns only the attachment/digest receipt. This ties the evidence to a taxpayer assertion and secure custody; it is not an independent external determination of the tax fact. Admission and resolution (`src/cadrumo/application/modelo/m303_exonerado_390_applicability_attestation.py`), conflict scan (`src/cadrumo/application/modelo/m303_exonerado_390_applicability_attestation.py`), profile-worker operation (`src/cadrumo/application/modelo/m303_attestation_operation.py`)

The maritime preview reads maritime-worker facts from the active workflow profile and delegates legal-pathway selection to the existing calculation service. If RETMAR registration makes the profile incomplete for mandatory filing, it keeps the original facts, reruns only the preview calculation with that flag cleared, and returns the warning separately so the renderer can still present observations. Its worker operation receives bounded canonical euro strings and day counts, uses an exact-profile retained registry operation, checks the active profile before and after calculation, and stores a closed observation projection with formula/legal/source references and a size cap. The result is a private preview, not a filing action. Absent or unreadable optional profile booleans become false here; the module says profile writes reject unreadable values, a dependency worth checking at that separate boundary. Profile service and RETMAR path (`src/cadrumo/application/modelo/maritime_preview.py`), worker request, projection, and checks (`src/cadrumo/application/modelo/maritime_preview_operation.py`)

The MCP query path offers typed binding previews and safe readiness summaries. A binding override must exist in the pinned revision, fit the declared channel and official scalar grammar, satisfy target casilla constraints, and—when typed—resolve through the applicable dated catalogue. Row sets, unsupported contracts, and malformed or out-of-range values are refused. Successful results merge validated values into the canonical binding preview and enforce count/identity consistency. The second MCP operation returns readiness axes, typed refusal causes, missing canonical fields, and closed ledger issue reasons while excluding the human prose and diagnostic strings held by the canonical reader. Both are registered for MCP only; their access resolver applies profile and disclosure rules. Channel validation (`src/cadrumo/application/modelo/mcp_binding_channel_validation.py`), pinned override resolution (`src/cadrumo/application/modelo/mcp_binding_validation.py`), closed result contracts (`src/cadrumo/application/modelo/mcp_query_contracts.py`), MCP operation projections (`src/cadrumo/application/modelo/mcp_query_operation.py`)

Metadata reads resolve a selector inside the addressed profile's persisted work-unit catalogue and grant the selected unit's period, rather than treating a caller-supplied work ID as its own authorization scope. The projection contains identity, dates, state, discard metadata, revision IDs, and CCAA, while excluding calculations and filing payloads. The separate metadata access composer also derives periods from persisted work units for lifecycle actions and verifies edit baseline coordinates. Metadata access scope (`src/cadrumo/application/modelo/metadata_operation_access.py`), snapshot schema (`src/cadrumo/application/modelo/metadata_projection.py`), registered read (`src/cadrumo/application/modelo/metadata_read_operation.py`)

Spreadsheet operations derive access from the pinned filing and, for relation-prefilled exports, add required source periods. The supervised executor binds ports to the exact profile and authority object, verifies the selected snapshot coordinates, and delegates pull, calculate, export, or verify through canonical ports. Local export checks writability twice, claims an unknown effect immediately before publication, and compares the sink receipt with the workbook digest and size. Remote verification requires the Google capability, validates an optional bounded/hash-matched local scenario file, marks the remote handoff before mutation, and requires explicit confirmation before reporting an update. Refusal results preserve whether an effect may already have occurred. Path behavior, provider implementations, and workbook generation live behind dependencies outside this chunk and need their own review. Spreadsheet access periods and provider requirement (`src/cadrumo/application/modelo/modelo_spreadsheet_access.py`), local publication (`src/cadrumo/application/modelo/modelo_spreadsheet_executor.py`), remote verification and effect accounting (`src/cadrumo/application/modelo/modelo_spreadsheet_executor.py`)

## Knowledge, safety, and implementation assessment

Across these features, legal/registry coordinates and provenance are resolved through pinned operations, while operator evidence and profile values remain distinct from authority. The strongest local controls are the exact-profile worker checks, frozen/closed result models, digest-checked attachments and export receipts, refusal before unsupported evidence can be treated as supported, and co-commit of M145 lifecycle state with event history. Spreadsheet effects are explicitly tracked across cancellation and partial external dispatch. The small shared descendant-message limit is three names, intended to bound interpolated operator diagnostics. Shared diagnostic bound (`src/cadrumo/application/modelo/minimo_descendientes_advisory.py`)

Two scaling or boundary questions are visible in this slice. Attestation conflict checking walks all bucket manifests and verifies each matching attestation blob before accepting one; correctness is clear, but runtime cost grows with retained evidence volume. M145 commands cap each field string at 512 characters, but this slice does not impose an explicit maximum number of field entries; whether upstream request or storage limits bound aggregate input is outside the inspected code. The 193 fallback's fresh bundled authority operation is another generation-coherence question noted above. These are conditional review points, not demonstrated production failures.

No tests are included among these 21 implementation files, so behavior, transactional guarantees, cancellation races, provider confirmations, and legal outcomes were not exercised here. No external legal source was independently checked; references in code are registry identifiers, not verification that bundled rules are current. Important follow-up boundaries are the operation/access registry, attachment and secure-object adapters, LocalFileExportSink, workbook/pull/verify ports, registry authority pin lifecycle, and tests that assert the refusal and partial-effect behavior.
