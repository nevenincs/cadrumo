## Discovery and capture behavior

`filed_data_capture.py` provides single and bulk listing/capture plus source capture and a composed onboarding sweep. Bulk listing/capture plans only model/year pairs for which the pinned registry has a covering revision that declares the authenticated filed-declarations read surface. Unsupported pairs become explicit failure rows instead of vanishing. Walks run newest year first; a per-walk timeout and the register's incomplete-grid refusal are captured as failures, while profile/custody/runtime refusals and async-cleanup failures propagate. Pair outcomes keep attempted/completed, row, reached and captured counts separate, so a failed walk with zero rows does not read as a genuine empty result. A cap is applied to reached declarations, including dry runs. Discovery combines two different signals. The profile signal derives candidate modelos from the declared taxpayer profile and a year span from activity start through the earlier of today or declared cessation; no activity-start declaration means “cannot say,” not a zero-year expectation. The AEAT register contributes the pairs its controls offered. The result is their tagged union: register options widen the walk and cannot erase profile expectations. Scoping is reported only as a hedge (`LIKELY_UNIVERSAL`, `LIKELY_NIF_SCOPED`, or inconclusive). Only an expected-by-profile pair that completed with zero rows triggers “expected but not found”; refused pairs and register-only empty pairs remain distinct. The report deliberately declines to calculate a completeness percentage when its denominator is only the unconfirmed register option list. Bulk dry-run is a real live read: it walks the discovered register, captures observations in memory, and computes what recapture would change, but does not persist observation manifests/artefacts, enroll justificantes, finalize calculation observations, record a sync run, or run the separate IVA-wallet and notifications stages. A normal sweep writes per declaration under a fresh effect guard, then finalizes calculation observations and records sync-run provenance under a further guard. The accumulator reads the prior observation before an unconditional upsert and compares only casillas present on both sides. This gives operators both the possibility of a complemented filing and the changed content signal without refusing a legitimate recapture. ## Evidence and local authority

The application ports keep Sede/browser work, parsing, encrypted artefact storage, calculation observation repositories, IVA history, filing records, and reconciliation behind structural contracts. Captured active observations are transformed into registry-grounded calculation envelopes stamped with the selected registry revision, presentation time, header facts, and normalized source metadata. Modelo 303 uses the dedicated IVA co-persistence port so the calculation envelope and IVA history move together; other modelos save the envelope directly. Latest observation selection prefers active `ALTA` over `BAJA`, then presentation time and expediente ID, and emits deterministic fiscal-period order. Persistence authority and M303 route (`src/cadrumo/application/live/filed_observation_persistence.py`) Selection and history ordering (`src/cadrumo/application/live/filed_observation_persistence.py`) Persistence ports (`src/cadrumo/application/live/filed_observation_ports.py`)

An AEAT justificante counts as filing-chain evidence only after a sequence of independent checks: the stored artefact loads, byte count and SHA-256 match its manifest, the PDF parses, the CSV recovered from the capture source URL matches the receipt's own CSV after normalization, and the receipt matches modelo, year, period, and authenticated taxpayer. Each refusal is surfaced as a typed warning reason. Once validated, the receipt is saved before a filing-chain entry can reference it, so interruption can leave an orphan receipt but not a record pointing to unloaded evidence. The chain's current in-force taxpayer identity is checked before reconciliation; a mismatch or unresolved identity leaves that chain untouched. Numeric filing baselines are supplied only for a complete all-numeric manifest, with Modelo 303 handled through its filing-instance evidence path. ## Assessment and follow-up

The strongest capability is the truthful capture funnel: registry support is checked before remote queries, pair failures stay separate from genuine emptiness, and evidence is promoted only after the receipt and taxpayer/file coordinates agree. The main follow-ups are preserving the exact discovered pair set through the sweep and tracing receipt binding at the registered-result boundary. In the bulk capture, single capture, register list/discover, and history result projectors, the `OperationTerminalReceipt` parameter is explicitly discarded before the private result is projected. Their executors/access resolvers do perform identity, effect, and access checks, but this slice does not prove whether the operation host calls projectors only with the matching successful receipt. Confirm that framework invariant rather than treating the local omission as a reachable bypass. Bulk/single projection hooks (`src/cadrumo/application/live/filed_bulk_capture_operation.py`) List/discover projection hooks (`src/cadrumo/application/live/filed_read_operation.py`) History projection hook (`src/cadrumo/application/live/filed_history_operation.py`)

The bulk accumulator comment still says its recapture advisory was never called by production code, although the same `absorb` method now invokes it before persistence. That stale explanation should be reconciled with the live path to prevent future edits from removing the pre-upsert check. No tests were reviewed or run, and AEAT behavior, extraction correctness, encrypted storage, host receipt dispatch, and user-facing result presentation were not exercised.
