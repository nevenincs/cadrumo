## Borrador snapshots and local PDF import

`Borrador100Snapshot` is an immutable, bucket-scoped Modelo 100 record containing the filing coordinate, pinned registry reference, capture time, source provenance, lifecycle state, and binding values. Validation makes the registry reference agree with model/year/period, applies shared active/superseded/discarded state invariants, and rejects blank binding keys. Snapshot IDs are content-addressed from the model coordinate, registry reference, capture time, source, and sorted binding values, with decimals normalized to fixed-point text. Reads re-confirm each stored registry coordinate against the pinned authority before returning it; `show`, `list`, and latest-by-year do not silently expose a snapshot whose calculation coordinate can no longer be carried. The storage interface is bucket-scoped and leaves encrypted persistence to composition. Snapshot invariants and coordinate re-confirmation (`src/cadrumo/application/live/borrador_100.py`) Content-addressed identity (`src/cadrumo/application/live/borrador_100.py`) Lifecycle service (`src/cadrumo/application/live/borrador_100.py`)

The local import path resolves exactly one `BORRADOR_PDF` extraction profile for the requested year/period, reads the PDF bytes once, computes SHA-256, and passes bytes plus the selected profile to a parser port. It rejects a different exercise, absent coverage, a mismatched profile or digest, non-finite/under-threshold coverage, duplicate or out-of-profile casillas, and non-finite decimal values. Explicitly blank observed casillas are retained separately; populated values become `casilla.<id>` bindings. The prepared result retains neither bytes nor local path, and its source spelling is the digest rather than a filesystem path. This verifies the parser's receipt and bounds its output to the pinned extraction profile; it does not prove the parser extracted every possible target, so the returned coverage and blank list remain meaningful review facts. Three separate operation purposes shape disclosure. The human read is limited to CLI/TUI and can include the source URL; the query is available across operation frontends and returns binding facts without provenance or document prose; import is CLI-only and accepts a secure-reference source path. Query and human read share canonical selection, profile-bound repository composition, and encrypted operation-result custody. Binding tuples must be sorted, unique, complete for their declared count, and contain only decimal or text scalars. The import parser warning list is returned only in the human import result. All three result paths validate an exact successful terminal receipt, expected subject, purpose, and allowed effect before releasing the registered projection. ## Authenticated live reads and expediente custody

The censo use case obtains a verified active session, takes the taxpayer identity from that session, and invokes an injected application-owned fetch port. It returns an observation only; the docstring explicitly leaves adoption and persistence to a separate user-profile review/commit workflow. Browser and Sede DTO/error translation stay outside the application port. Authenticated read-only censo use case (`src/cadrumo/application/live/censo.py`) Censo fetch contract (`src/cadrumo/application/live/censo_ports.py`)

Live-read refusals distinguish ordinary input errors from a closed set of observations for which retrying the same call is unsafe, such as a justificante that does not match its filing or a filed observation AEAT no longer reports active. These safety refusals carry machine facts and runtime-observation provenance with an explicit no-recovery outcome; adapter-specific IVA failures cross through an application protocol and unknown shapes classify as `UNKNOWN`. This avoids turning a dangerous mismatch into a generic retry suggestion. Live preconditions and no-recovery verdict (`src/cadrumo/application/live/errors.py`) Adapter failure classification (`src/cadrumo/application/live/errors.py`)

Expedientes acquisition uses a read-only declaration-register protocol under an active verified session, captures translated row facts, then places only the local snapshot write inside the effect guard. Single capture stores one model/year result. Bulk capture walks the chosen model/year range (or all authority-listed models), keeps per-query failures as bounded report rows, and persists one combined snapshot if at least one query succeeded. A fully failed sweep reports failures without creating a snapshot. The snapshot service derives identity and deduplicates through the shared stateless lifecycle; the stored bucket, capture and persistence times, authenticated identity, source descriptor, and declaration rows remain local evidence. Their result projectors check success, identity, result/refusal fields, and compatible effect before publishing bounded summaries; the bulk projector also validates its snapshot tally. Whole-profile access is extended with COMMIT because each sweep may cover any period. List/latest/detail results validate count and empty-state coherence and match a successful no-effect receipt. ## Filed capture reporting and follow-up

The filed-data selector is a read-only in-memory filter over already-fetched register rows; it can narrow by period, expediente, and caller limit before downloads. The shared finalizer selects the latest observation per period in persistence-defined history order, enrolls each through registry-grounded persistence, and separates non-numeric casilla skips from enrollment failures. Single/source flows can fail fast; bulk can retain typed failures and continue. The bulk public result carries aggregate effects, artefact/observation references, filing-record IDs, conflicts, failure coordinates, and skipped-casilla descriptions, while explicitly omitting casilla values. Filed register selection boundary (`src/cadrumo/application/live/filed_data.py`) Shared observation finalizer (`src/cadrumo/application/live/filed_capture_finalizer.py`) Bulk result projection (`src/cadrumo/application/live/filed_bulk_capture_operation.py`)

One integration invariant deserves a focused trace: the bulk filed result projector accepts a terminal receipt but discards it before validating and projecting the report. The executor itself enforces profile identity and records effects, and operation-host registration may already restrict when projection is called; confirm that the host guarantees the matching successful receipt before relying on that boundary. This is an unverified receipt-binding gap in this module, not evidence by itself of an externally reachable authorization bypass. Also confirm that consumers treat returned output paths, observation paths, artefact references, and filing identifiers as sensitive local data. Receipt currently unused by bulk projector (`src/cadrumo/application/live/filed_bulk_capture_operation.py`) Bulk executor and access resolver (`src/cadrumo/application/live/filed_bulk_capture_operation.py`)
