## Scope

This chunk covers 12 application files (3,111 lines): shared operation journals; local-reader readiness and its report; workstation preflight; producer capture coordinates; profile-deletion hold and profile-selection verdict contracts; the hardware capacity floor; location of the browser that the native component engine installed; and the judgement of the local AI program from the components role's status row. Static review only; I did not run the application, install packages or models, contact configured services, or execute provisioning. Installing the local AI program, pulling the models the person selected and removing them belong to the native component engine (`native/application/src/provisioning/`), which only the desktop host drives for the local AI; the runtime manager (`native/manager/src/supervision/local_ai.rs`) runs its server. Both are outside this chunk. Legal accuracy and runtime behavior outside these files remain unverified.

## Local reader readiness

Cadrumo defines no model. Each role (vision transcription, text extraction, table mapping and supply-nature proposal) reads with the lane and model the person selected in the desktop, which the agent service resolves from cadrumo-agent's catalogue; `read_role_lanes` asks the model-run port for every role at once. A role with no selection carries the agent's typed refusal and never falls back to another lane or a default. A lane whose catalogue entry sets `reads_off_host` needs nothing local and is reported as such. A lane that stays on this computer is judged in a fixed order: a model whose catalogue `size_bytes` this computer's installed memory cannot hold refuses first and offers no setup, because setup cannot change it; a local AI program whose status row is not ready or stale refuses with that row's own recovery; a model the lane reports as not installed refuses with the local AI setup verdict; and a model whose presence nobody stated refuses as unknown, never as missing. That setup is the desktop's, the only surface that installs the program or pulls a model. The program's presence and version come from the components role's read-only quick status, and a role that returns no row reads as unknown. A role's `installed` state is the agent service's reading of the `installed` flag of the catalogue the agent serves, carried on the lane. Python asks the local AI server nothing. Role lanes and readiness (`src/cadrumo/application/local_reader.py`)

Hardware admission reads its requirement from the selected catalogue entry's `size_bytes`, not from a Cadrumo table; an entry that states no size makes no claim and is not checked against an invented one. NVIDIA capacity is per device: reporting can sum total VRAM, but free VRAM is the largest single-device amount; two partially free cards are not treated as one larger card, and the capacity floor compares the requirement with the largest single card. System and accelerator readings preserve “unmeasured” separately from zero, and an unmeasured computer is never held back. Installed memory decides whether a selection can ever fit; whether a load fits the memory free is cadrumo-agent's answer when it loads the model, and Cadrumo does not judge free memory. Hardware capacity floor (`src/cadrumo/application/provisioning.py`)

The only registered local-reader operation is `local-reader.report`, a read that names no profile: it reports measured memory and accelerator figures and the lane each role resolves to: a lane that stays on this computer names its model and, when the catalogue states one, its size, and an off-host lane is selected and names no model. It reports nothing about the local AI server or about what is loaded. It downloads, installs, loads and removes nothing; the application layer has no load, pull or fitness action. Report contract and execution (`src/cadrumo/application/local_reader_report.py`) Machine-scoped access (`src/cadrumo/application/local_reader_operation.py`)

The application layer installs and starts nothing. The native component engine owns two setup items, the browser and the local AI. A setup plans the items it names, checks their hosts and the storage volume's free space, and asks for approval bound to the plan's digest; an approval given for a plan that has since changed is refused as a changed plan. Items then run one at a time under per-item writer locks and stop at the first that does not finish. The local AI item installs the program from its pinned portable archive, and the runtime manager runs the one server on a fixed loopback address while the program is set up, restarting it after a crash; the engine then pulls each model the person selected for a local role through that server, from role, model-name and catalogue `size_bytes` triples that only the desktop host hands its in-process engine. Integrity is Ollama's content-addressed manifest, and Cadrumo pins no model digest. The browser item extracts each pinned Chromium build into a private staging folder and moves it into the layout the Playwright driver reads only after its completion marker is written. Once an item verifies, the engine writes a record of where it is. Python locates the browser from that record alone: the browser probe requires the record to be for the browsers folder Playwright is given and for the installed driver's version, and the executables it names to exist, so an unrecorded or stale build never reads as installed. The local AI program is not located by Python: its presence and version come from the components role's quick status, read with a bounded timeout, and `local-reader.status` and the workstation check judge that row. The command line, terminal interface and MCP drive the engine through its `components` role over a line protocol: they report every component and run its full check, and they set up and remove the browser, but for the local AI they route setup and removal to the desktop. The desktop links the engine in process, so all four see the same rows. Component records (`src/cadrumo/core/component_records.py`) Role client (`src/cadrumo/adapters/outbound/components/client.py`) Engine (`native/application/src/provisioning/engine.rs`) Server supervision (`native/manager/src/supervision/local_ai.rs`) Program judgement (`src/cadrumo/application/local_reader.py`) Browser probe (`src/cadrumo/application/provisioning_browser.py`)

## Health and state contracts

Preflight projects typed rows for local auth-provider configuration, secure-storage reachability, bundled corpora, configuration/key posture, Windows path headroom, and assembled portal-registry health. Healthy rows carry no failed verdict; unhealthy rows carry a typed condition and either a canonical recovery action or an explicit no-recovery outcome. Provider results are partitioned into optional/unconfigured, warning, healthy, and error states; unknown enum values fail closed. The storage-root check is read-only and tests writability with `os.access` on the nearest existing ancestor. That is a useful preliminary signal, but it does not prove that creating or writing the configured root will succeed. Preflight health rows (`src/cadrumo/application/preflight.py`) Storage and corpus checks (`src/cadrumo/application/preflight.py`)

The portal health function's stated contract says import-time registry-integrity failures become an error row. Its `PORTAL_REGISTRY` import occurs before the `try` that catches `PortalRegistryError`, however, so an exception raised while assembling the registry can escape this supposedly non-raising probe and the aggregate. Verify whether the registry can fail during import and move the guarded boundary if needed. This is a control-flow finding, not a claim that a malformed registry is currently present. Portal-registry probe and aggregate (`src/cadrumo/application/preflight.py`)

`ProducerCaptureScope` mints a non-persisted digest over owner, namespace, storage root, producer coordinate, and a random process nonce. It assigns a monotonically increasing generation per distinct observation, retries a projection if the producer changes during its build, refuses after eight unstable attempts, and rejects comparisons from another owner scope or process incarnation. The mechanism provides currentness and scope separation, not cryptographic authentication of the projection. Its callers still need to supply a coordinate that corresponds to the observed producer state. Capture domain and stable-window retry (`src/cadrumo/application/producer_capture.py`)

The shared journal base validates 64-character lowercase hexadecimal IDs, keeps journals in a direct storage-root child outside bucket storage, refuses link-like roots/files, atomically replaces one JSON file under a write lock, and validates the decoded schema and filename identity. Writes request POSIX `0700`/`0600` modes; the code explicitly makes no equivalent Windows ACL claim. A multi-step operation is not atomic, and schema validation does not authenticate journal contents. The root validation also documents that it is not protection from malicious concurrent path replacement. Profile preconditions use stable condition/evidence identifiers and bind failures to actionable operator actions or an explicit safety refusal; profile-deletion hold projections keep legal and filing owners separate and validate canonical record identity, digest, and UTC assessment time. Journal validation and write boundary (`src/cadrumo/application/journal_repository.py`) Profile precondition contracts (`src/cadrumo/application/profile_preconditions.py`) Deletion hold projection (`src/cadrumo/application/profile_deletion_hold_contract.py`)
