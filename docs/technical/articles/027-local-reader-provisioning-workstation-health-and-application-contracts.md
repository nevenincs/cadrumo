## Local reader and model provisioning

`select_role_model` is the shared resolution used by per-role status and provisioning. Text extraction, vision transcription, table mapping, and supply-nature proposal can therefore report distinct configured models. `role_model_targets` coalesces roles that resolve to the same runtime model, carries selection refusals as explicit targets, and attaches the measured requirement used for load admission. A missing vision model need not hide an installed text model, and text-layer invoices remain readable without a model; status reserves “all documents” for a reachable runtime, installed models for both extraction roles, and a recorded fitness verdict for the current text-model digest. The local AI is located from the component engine's record and the server is asked only at the address that record names; an operator-configured endpoint is used as written. Role model resolution and targets (`src/cadrumo/application/local_reader.py`) Readiness projection (`src/cadrumo/application/local_reader.py`)

Selection chooses the lowest-memory catalogued candidate that clears configured context, deployment-licence posture, and (when measurable) headroom. Operator overrides take precedence but retain advisories for unknown catalogue membership, licence, context, and memory fit. Unknown hardware does not prevent naming a default model, while later load admission fails closed if the binding arena cannot be measured. NVIDIA capacity is per device: reporting can sum total VRAM, but a load can use only the largest single-device free amount; two partially free cards are not treated as one larger card. System and accelerator readings preserve “unmeasured” separately from zero. This keeps selection, which plans a model, distinct from admission, which decides whether it may load now. Hardware admission quantities (`src/cadrumo/application/provisioning.py`) Model selection and override advisories (`src/cadrumo/application/provisioning.py`)

The `local-reader.provision` operation exposes two actions, load and verify, as one definition that every frontend submits; neither downloads, installs, starts or removes anything. Request validation takes the action, an optional role, and an optional named model of at most 256 characters. Load asks the running server to hold each selected model, using the measured memory requirement for load admission. Verify checks each model for readiness and then runs the role's fitness probe, recording a settled verdict. A role whose selection refused yields an unsuccessful outcome carrying that refusal. The effect is none for verify and updated or partial for load, according to how many models changed and failed. The registered operation is recorded and replay-idempotent, but cancellation is unsupported, no operation deadline is declared, close may detach, and reconciliation interrupts an unsettled run. Those settings matter for slow loads: the journal can describe progress and outcome, but does not promise rollback. Request contract (`src/cadrumo/application/local_reader_contracts.py`) Action execution (`src/cadrumo/application/local_reader_provisioning.py`) Operation capabilities (`src/cadrumo/application/local_reader_operation.py`)

The application layer installs and starts nothing. The native component engine owns two setup items, the browser and the local AI. A setup plans the items it names, checks their hosts and the storage volume's free space, and asks for approval bound to the plan's digest; an approval given for a plan that has since changed is refused as a changed plan. Items then run one at a time under per-item writer locks and stop at the first that does not finish. The local AI item installs the program from its pinned portable archive, and the runtime manager runs the one server on a fixed loopback address while the program is set up, restarting it after a crash; the engine then pulls and checks each role's model through that server. The browser item extracts each pinned Chromium build into a private staging folder and moves it into the layout the Playwright driver reads only after its completion marker is written. Once an item verifies, the engine writes a record of where it is. Python consumers locate a component from that record alone: the browser probe requires the record to be for the browsers folder Playwright is given and for the installed driver's version, and the executables it names to exist, so an unrecorded or stale build never reads as installed. Runtime host detection locates the local AI from its record, asks only the recorded address, and reports the host's package manager as a fact without running it. The command line, terminal interface and MCP drive the engine through its `components` role over a line protocol, and the desktop links it in process, so all four see the same rows and plan digests. Component records (`src/cadrumo/core/component_records.py`) Role client (`src/cadrumo/adapters/outbound/components/client.py`) Engine (`native/application/src/provisioning/engine.rs`) Server supervision (`native/manager/src/supervision/local_ai.rs`) Runtime host probe (`src/cadrumo/application/provisioning_host.py`) Browser probe (`src/cadrumo/application/provisioning_browser.py`)

Fitness probes are reserved for the text-extraction role, because model presence alone does not establish that its answer is parseable and grounded. A settled result is recorded against endpoint, model, role, and runtime digest; status reads that exact key and treats absent or malformed records as not verified. A transport failure is not a model verdict. The fitness document uses atomic replacement, and a measurement lock held across reading the record, probing and writing keeps two first uses of the same weights from measuring twice or dropping each other's verdict. One integration point to trace is whether every caller that records a verdict holds that lock. Fitness record and measurement lock (`src/cadrumo/application/provisioning_fitness.py`) Fitness outcome and status rules (`src/cadrumo/application/local_reader.py`)

## Health and state contracts

Preflight projects typed rows for local auth-provider configuration, secure-storage reachability, bundled corpora, configuration/key posture, Windows path headroom, and assembled portal-registry health. Healthy rows carry no failed verdict; unhealthy rows carry a typed condition and either a canonical recovery action or an explicit no-recovery outcome. Provider results are partitioned into optional/unconfigured, warning, healthy, and error states; unknown enum values fail closed. The storage-root check is read-only and tests writability with `os.access` on the nearest existing ancestor. That is a useful preliminary signal, but it does not prove that creating or writing the configured root will succeed. Preflight health rows (`src/cadrumo/application/preflight.py`) Storage and corpus checks (`src/cadrumo/application/preflight.py`)

The portal health function's stated contract says import-time registry-integrity failures become an error row. Its `PORTAL_REGISTRY` import occurs before the `try` that catches `PortalRegistryError`, however, so an exception raised while assembling the registry can escape this supposedly non-raising probe and the aggregate. Verify whether the registry can fail during import and move the guarded boundary if needed. This is a control-flow finding, not a claim that a malformed registry is currently present. Portal-registry probe and aggregate (`src/cadrumo/application/preflight.py`)

`ProducerCaptureScope` mints a non-persisted digest over owner, namespace, storage root, producer coordinate, and a random process nonce. It assigns a monotonically increasing generation per distinct observation, retries a projection if the producer changes during its build, refuses after eight unstable attempts, and rejects comparisons from another owner scope or process incarnation. The mechanism provides currentness and scope separation, not cryptographic authentication of the projection. Its callers still need to supply a coordinate that corresponds to the observed producer state. Capture domain and stable-window retry (`src/cadrumo/application/producer_capture.py`)

The shared journal base validates 64-character lowercase hexadecimal IDs, keeps journals in a direct storage-root child outside bucket storage, refuses link-like roots/files, atomically replaces one JSON file under a write lock, and validates the decoded schema and filename identity. Writes request POSIX `0700`/`0600` modes; the code explicitly makes no equivalent Windows ACL claim. A multi-step operation is not atomic, and schema validation does not authenticate journal contents. The root validation also documents that it is not protection from malicious concurrent path replacement. Profile preconditions use stable condition/evidence identifiers and bind failures to actionable operator actions or an explicit safety refusal; profile-deletion hold projections keep legal and filing owners separate and validate canonical record identity, digest, and UTC assessment time. Journal validation and write boundary (`src/cadrumo/application/journal_repository.py`) Profile precondition contracts (`src/cadrumo/application/profile_preconditions.py`) Deletion hold projection (`src/cadrumo/application/profile_deletion_hold_contract.py`)
