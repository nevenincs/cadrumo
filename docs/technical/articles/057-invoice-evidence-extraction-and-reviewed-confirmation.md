## Reading stored evidence into a reviewable draft

The application resolves one stored evidence record or attachment ID into in-memory bytes, then routes by content-derived document shape. Structured Facturae, CII, and UBL records use an exact reader without a model; the draft preserves line and rate breakdowns, declared country token, invoice class and findings, then runs deterministic checks. Unrecognized XML is refused rather than sent through PDF or image fallbacks. A text-bearing PDF is transcribed by the PDF text layer, read by deterministic label rules first, and filled by a semantic reader only where the label result is incomplete. Model-unavailable or resource-admission failures preserve a partial label result with machine-readable fallback facts; a text-native document with no useful reader refuses rather than silently escalating to vision. Scan-only PDFs and images use a separate vision transcription stage and then the shared semantic reader. ## Confirmation and persistence

Confirmation is a prepare/build/persist flow. Prepare re-extracts the selected bytes, re-runs the direction and review checks, resolves counterparty establishment and dated authorities, and refuses when the current source digest or complete draft review digest differs from the operator's reviewed values. The registered confirm request requires both digests, exactly one source reference, explicit direction, bounded override fields and individual finding resolutions. The draft digest uses the public projection, which includes the structured invoice class that would otherwise be omitted by a bare model dump. Preparation and source/draft freshness (`src/cadrumo/application/ledger/invoice_confirmation.py`) Review digest (`src/cadrumo/application/ledger/invoice_confirmation.py`) Confirm request (`src/cadrumo/application/ledger/invoice_evidence_confirm_operation.py`)

Build layers supplied operator answers over recovered values, refuses missing required identity/number/date/base data, checks filer/counterparty identity constraints, retains structured lines when amounts were not restated, and delegates invoice construction to the canonical catalogue writer. Confirmation first checks whether the same attachment already minted another invoice, then compares the full set of invoice fields the confirm owns before returning an existing same-ID record. A differing re-confirm is refused with divergent field names to avoid duplicate records for one document or silently discarded corrections. It links the source attachment to the invoice, updates the evidence summary where a purchase-evidence record exists, and writes a durable confirmation record on both new and guarded no-op outcomes. The result carries the re-read draft, operator-stamped provenance, establishment summary, confirmation ID and printed-versus-recorded total discrepancy. The operation enters irreversible write custody and marks UNKNOWN before its persistence function; successful completion is UPDATED even when catalogue creation is a no-op, because attachment linking and confirmation audit still occur. However, the local service sequences catalogue creation, manifest link, evidence summary update, and confirmation-record write as distinct calls. Confirm concrete adapter transactions and recovery behavior: a crash after one write but before later writes can leave an incomplete provenance chain, and the attachment's list of already minted invoice IDs is central to the duplicate-document guard. The operation's UNKNOWN effect is conservative, but it does not itself make those stores atomic. ## Local reader readiness and implementation assessment

The readiness operation reports host platform/endpoint facts, runtime reachability, model-role installation/residency/fitness/admission, the last local pull, and whether extraction is ready. It does not load or install a model and it returns no document or tax values. Exact profile binding, metadata access, result bounds, no-effect receipt checks, and CLI/TUI projection are enforced in the operation. Readiness projection (`src/cadrumo/application/ledger/invoice_evidence_readiness_operation.py`) Read-only executor (`src/cadrumo/application/ledger/invoice_evidence_readiness_operation.py`) Metadata access policy (`src/cadrumo/application/ledger/invoice_evidence_readiness_operation.py`)

The strongest local controls are content-bound review freshness, re-extraction at confirmation, distinct structured/text/vision lanes, refusal to fabricate missing fields, per-finding answers, exact-profile operation checks, and cautious effect accounting. Cross-module verification should focus on concrete reader/consent adapters, token audit coverage across vision and semantic stages, and recovery/atomicity of multi-store confirmation writes. The projections are size-bounded, but the permitted tax-rich result and filesystem/adapter confidentiality remain dependent on the registered access and composition layers. No tests in these files were inspected or run; static inspection cannot verify actual provider routing, cancellation timing, durability, or legal accuracy.
