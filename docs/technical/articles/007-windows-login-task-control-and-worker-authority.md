## Capabilities and flow

Windows login capture binds a retained peer process token to the runtime’s current interactive desktop. It reads owner SID, authentication LUID, session ID, logon SID, token IDs, and LSA logon kind; it separately checks the current process’s `WinSta0` association, repeats token and station observations, and accepts only the exact matching witness. Session observations use WTS metadata and resolve the account owner from the same snapshot, then recheck the WTS generation and LSA token facts. `WindowsLoginBinding.observe` repeats those checks rather than trusting a recycled session number. An observation is eligible only when the exact login/session remains valid; uncertain failures return inactive, locked, and unknown eligibility. Credential-facility availability is supplied separately, so a desktop observation does not prove that a key store is ready. The inventory bounds counts and its overall loop budget, considers only logons associated with the current desktop witness, and returns incomplete when rows cannot be resolved or verified. ## Knowledge, security, and implementation assessment

The main data are OS login/session identity, exact scheduler configuration and process incarnation, runtime-owned worker authority, and a typed workbench-generation projection. No broad reference corpus is present. The stronger security properties are enforced through native token/session checks, hardened XML comparison, kernel-at-creation job membership, exact worker-parent checks, profile-guard-held permits, separate channels, finite lifetimes, and durable release acknowledgements. The Windows process helper retains native handles rather than reopening PIDs as authority. Approval and lease secrets are transferred only after typed protocol setup; worker lease bytes are cleared from the temporary payload buffer after parsing.

Windows desktop inventory is deliberately conservative and cannot be treated as a complete machine-wide login inventory: the code only establishes positive binding for the current desktop witness, and any unsupported or unreadable row makes completeness false. The stated two-second bound governs iteration but not individual synchronous WTS, LSA, token, or domain account calls. Scheduler task control is also a different authority from runtime admission: a matching task can be configured or started without proving that any profile is authenticated. Process containment is strong for children created in the job but has an explicit broker boundary. The authorization code’s critical guarantee depends on the runtime-supplied `WorkerAuthorizationOwner` actually retaining and enforcing the canonical profile guard; this adapter provides the fenced channel and effect-command checks around it, but does not implement domain access policy itself.

One cleanup edge merits verification: the authorization server’s connection-finally block closes the channel and then releases its semaphore slot; if native channel close raises, the slot release is skipped. The accept loop submits connection work without retaining or inspecting its future, so that exception does not directly latch server failure. Normal OS closes may make this rare, but an injected/native close failure could reduce capacity without latching server failure. No tests are included in this chunk, and static review cannot validate WTS/LSA behavior, COM scheduler normalization across Windows versions, job-object semantics under brokered launches, or the concrete authority owner’s policy (worker_authorization.py (`src/cadrumo/adapters/local_runtime/worker_authorization.py`), worker_authorization.py (`src/cadrumo/adapters/local_runtime/worker_authorization.py`), worker_authorization.py (`src/cadrumo/adapters/local_runtime/worker_authorization.py`)).

## Dependencies and follow-up

Synthesis should connect login observations to the profile access policy and credential-store readiness provider; connect Task Scheduler managed stop to the transport server’s drain/finalize sequence; and inspect the concrete `WorkerAuthorizationOwner` composition and callbacks. It should also confirm whether executor callbacks must report close failures as worker health failures, and distinguish the limited current-desktop inventory from any other login enumeration claims.
