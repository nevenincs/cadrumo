## Capabilities and operation

The chunk implements much of the profile-management application surface. An operator can inspect and edit schema-backed profile facts, maintain repeatable sections, check filing preconditions, register a profile, rotate its passphrase, enroll or use a recovery code, and select or resume a profile session. Supporting modules provide projections, inventory, record/session access, persistence-facing façades, and presentation hints.

The overview builder constructs sections from the pinned profile schema, includes declared fields even when no fact has been stored, and expands repeatable rows and object namespaces from record facts. For each field it supplies localized label/help and choices, type/value presentation, row identity, and a shared completeness status. Its masking decision prioritizes the schema's `SECRET` sensitivity class; only facts without a schema declaration reach the fallback keyword rules. Indexed row instances retain their base field declaration, so adding `[n]` does not discard secret classification. This is a meaningful data-minimization control at the projection boundary, although safe use still depends on every display path consuming the masked overview rather than raw record values. overview.py (`src/cadrumo/application/user_profile/overview.py`) overview.py (`src/cadrumo/application/user_profile/overview.py`) overview.py (`src/cadrumo/application/user_profile/overview.py`) overview.py (`src/cadrumo/application/user_profile/overview.py`)

Registration creates a committed profile with an initially incomplete but schema-validated record, establishes a DEK and password wrapper, and only then publishes session state. It also attempts to capture initial retention/legal-hold evidence. The registration code and related evidence contract acknowledge that a genuinely external legal hold arising after this initial snapshot cannot be known until later expediente capture or operator affirmation. Deletion safety therefore depends on freshness and completeness of the recorded evidence, not on this registration snapshot discovering external facts by itself. registration.py (`src/cadrumo/application/user_profile/registration.py`) registration.py (`src/cadrumo/application/user_profile/registration.py`) profile_legal_hold.py (`src/cadrumo/application/evidence/profile_legal_hold.py`)

Passphrase rotation first proves the current password under the custody lock and validates the replacement and confirmation. The shared rewrap operation preserves the DEK and epoch, retires automation, mints a new envelope generation, reheads the profile record under that envelope, and then replaces the stored envelope; it records whether the proof came from the current password or the recovery code. Preserving the epoch is intended to keep an enrolled recovery wrapper usable. The rehead-before-envelope-replacement sequence presents an interruption-sensitive boundary: if those writes are not atomic across the involved adapters, a crash between them could leave the committed record tied to a newly minted envelope that was not durably installed. Recovery is opt-in. Enrollment proves the existing passphrase, mints a recovery code, gives it to a caller-provided delivery callback, and requires a matching possession echo before installing a recovery wrapper; the result model does not return the secret. Revocation likewise requires the current passphrase. Reset proves the recovery code, validates the replacement password, and reuses the locked rewrap path. Wrong proof updates per-profile throttling state; successful recovery clears it. Status can be read without a credential and exposes enrollment state rather than the recovery secret. These boundaries are useful, but the delivery callback's actual handling and the user experience of securely recording the code lie outside this module. recovery_custody.py (`src/cadrumo/application/user_profile/recovery_custody.py`) recovery_custody.py (`src/cadrumo/application/user_profile/recovery_custody.py`) recovery_custody.py (`src/cadrumo/application/user_profile/recovery_custody.py`) recovery_custody.py (`src/cadrumo/application/user_profile/recovery_custody.py`)

## State, knowledge, and security boundaries

Profile pointer changes use a reentrant transaction associated with a canonical storage root and a root lock. Compare-and-swap checks the observed pointer before transition, and clear/restore operations advance revisions rather than silently overwriting concurrent changes. Corrupt pointer state is surfaced for manual recovery. The dedicated ports separate pointer policy from persistence. profile_pointer.py (`src/cadrumo/application/user_profile/profile_pointer.py`) profile_pointer.py (`src/cadrumo/application/user_profile/profile_pointer.py`) profile_pointer.py (`src/cadrumo/application/user_profile/profile_pointer.py`) profile_pointer.py (`src/cadrumo/application/user_profile/profile_pointer.py`)

`ProfileRecordRepository` is a session-bound current-record gateway, not an unrestricted repository. It distinguishes a session derived from active custody from an explicitly bound session, validates backing liveness and schema generation, and declines access when the session is gone. Its invocation-scoped handoff publishes a record for one CLI operation and consumes it once, reducing accidental plaintext carry-over between commands. The neighboring repository exposes validated committed-capsule summaries and requires a session for an unlocked record view. The summary inventory is deliberately non-authenticating: it reports recognized, degraded, or concurrently changed capsule summaries without opening keys, envelopes, recovery material, or a sentinel. It avoids partial inventories and permits per-command reuse only after a successful recognized scan. Projections provide canonical paths, typed fact rendering, schema selection, and taxpayer-scoped values. Their temporal rule is narrower: ordering uses `valid_from`, but `valid_to` is explicitly ignored because no `as_of` date is threaded through this projection API. A closed fact can consequently remain effective in this view. Validation code separately warns about such inert boundaries. ## Assessment and follow-up

The strongest local qualities are centralized schema-aware redaction, version/pinned-schema checks on session-bound record access, explicit one-shot handoff semantics, stable repeatable-row identities, and typed distinctions between failed admission and an operator declining credentials. The modules also expose meaningful result state instead of collapsing unknown or degraded storage into a normal profile summary.

Two review points merit cross-layer verification. First, prove that envelope replacement and record reheading are transactionally recoverable under process interruption, including the recovery-code reset route. Second, trace every user-facing readiness consumer to ensure the separate `per_operation_requirements_assessed` flag is shown or enforced. Separately verify that profile projections with `valid_to` facts are not used for as-of decisions, that refreshed legal-hold evidence reaches destructive preflight, and that callback implementations do not log or persist recovery codes insecurely. The chunk includes no tests or runtime evidence sufficient to settle those questions. Its shared fact mutation port, custody adapters, CLI admission callers, and deletion-evidence capture flow are the most important synthesis dependencies.
